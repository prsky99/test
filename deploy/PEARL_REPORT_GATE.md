## 1. 최종 진주 인정 조건 (모두)
1. 진주 판정 조건 1~6을 통과한다: A, 보안, 7일 헬스, 시험 호출, 실행 보고서, 일 도구.
2. **조건 7(도구 지문, 3절)**: 근거 도구의 정의가 근거 보고서 이후 바뀌지 않았다.
3. 그 역할의 **시험 보고서 v2**(역할 과제 시험)가 있다.
   - 실제 인자로 호출했다.
   - 결과 발췌와 내용 판정(기대 필드·낱말)이 있다.
   - 7일 안의 최신 판이다.
4. 그 보고서의 **품질 점수가 85점 이상**이다(증거 60 + 글 40).
5. 그 보고서의 **내용 판정이 통과**다. 점수가 85 이상이어도 내용 판정이 실패면 인정하지 않는다.
6. 같은 역할 안에서 품질 점수 1위다.
   - 동점이면 최근 7일 반복 성공 수가 많은 쪽, 그다음 p95 지연이 짧은 쪽이다.
   - 2·3위는 최종 진주가 아니고, 목걸이 자리의 외부 대체 후보가 된다.

## 2. 운영·SRE 검증 (점수 파일을 그대로 믿지 않음)
검증 대상: 매일 새로 최종 진주가 되는 것 전부와, 이미 최종 진주인 것 중 무작위 10%(최소 3개)

| 확인 | 방법 | 통과 기준 |
|---|---|---|
| 파일 무결성 | `exports/pearls/` 점수 파일 | 형식이 맞음. 보고서마다 보고서 id·판(version)·원자료(호출 인자, 응답 발췌, 판정 근거)가 있음. 파일 해시를 판정 기록에 남김 |
| 증거 점수 60 다시 계산 | 운영 DB 읽기 전용: 그 자원의 7일 실행 증거(`capability_evidence`), 지연, 보고서의 인자 유무와 판정 | 검색과 RAG 점수와 **차이 5점 이하** |
| 글 점수 40 표본 확인 | AQEF-30 항목. 특히 근거 없는 주장과 한계 누락 감점을 운영·SRE가 다시 본다 | 차이 5점 이하 |
| 내용 판정 재현 | 공개 경로(`X-Agentcon-QA: pearl_gate`, 새 연결)로 같은 역할 과제를 **1번** 다시 호출하고 같은 판정기로 확인 | 다시 통과. 429·Retry-After면 미루고, 실패로 세지 않음 |
| 실패도 기록되는가 | 그날 v2 보고서 중 실패 보고서 수 | 0이 아님. 0이 이어지면 검색과 RAG에 확인 요청 |

- 하나라도 어긋나면 그 진주는 "최종" 표시를 받지 않는다. 이유는 현황판 '넘기는 일'로 검색과 RAG에 넘긴다.
- 기록: `logs/ops/pearl-gate/<YYYYMMDD>.jsonl`. 진주마다 `{at, resource_id, role, report_id, report_version, score_claimed, evidence_recomputed, writing_checked, verdict_rerun, fingerprint_ok, result, reasons}` 한 줄이다.
- 제공자 부하: 재현 호출은 진주마다 하루 1번이고, 관문 상한(호스트당 하루 60회, 간격 2초)과 매일 재시험 몫 안에서 한다.
- 매일 판정에서 다음이면 최종 진주에서 내리고 다음 순위를 올린다(목걸이 사슬 규칙과 같음).
  - 점수가 85 아래로 내려감
  - 내용 판정이 이틀 연속 실패함
  - 조건 7 위반이 생김

## 3. 조건 7: 도구 정의 지문 (PM 결정)
- 지문 정의는 `fingerprint-v1`이다(설계안 1절). 도구마다 `sha256(canonical({name, description, inputSchema}))`.
- **규칙**
  - 진주의 **근거 도구**(근거 보고서가 실제로 호출한 도구)의 지문이 근거 보고서 이후 바뀌면, 재시험 보고서가 나올 때까지 진주에서 뺀다.
  - 근거 도구가 사라져도 뺀다.
  - **다른 도구가 추가된 것만으로는 빼지 않는다.** 다른 도구의 변경·삭제도 빼는 이유가 아니다. 다만 위험 신호(설계안 2절: 지시문 주입 패턴, 읽기 전용 뒤집힘, 쓰기·결제·자격 증명 도구 추가)면 근거 도구와 상관없이 뺀다.
- **기준값**
  - 11-14 04시 기준값을 `gateway-data/fingerprints/pearls.json`(git 제외)에 진주 25개 근거 도구 지문으로 남겼다.
  - 근거 보고서보다 앞선 지문 기록은 없다. 그래서 첫 기준값은 다음 두 조건을 만족할 때만 인정했다.
    - 마지막 도구 변경 시각(`usage_updated_at`)이 보고서보다 앞섬
    - 보고서 뒤에 새 스키마 버전(`connection_versions`)이 없음
- **이후 감시**: 도구 조사(하루 1번 안팎)와 진주 6시간 tools/list 때마다 비교한다(설계안 3절).
- 지금 진주 25개의 판정 결과는 `reports/pearl-gate-2026-11-14/README.md`에 있다.

## 4. 실패 보고서 공개 문구 검수
시험 보고서 v2는 실패도 공개한다. 실패 보고서는 공개 전에 아래 규칙을 지켜야 한다. 처음 20건은 운영·SRE가 모두 읽고, 그 뒤로는 자동 검사와 하루 10% 표본 읽기로 한다.

**반드시 들어갈 것(측정 사실)**
1. 무엇을 시험했는지: 역할 과제 이름, 입력의 종류(예: "a city name"). 자격 증명이나 개인정보 같은 입력 값은 넣지 않는다.
2. 언제: UTC 시각
3. 무슨 일이 있었는지: 관측한 사실만 쓴다.
   - HTTP 상태, 오류 종류(timeout, protocol, tool error), 또는 판정 불일치(예: "the expected field `doi` was missing")
4. 이 결과의 범위를 밝히는 문구(예시): "This reflects one test at <time>. Results can change; the agent may work for other inputs."
5. 제공자의 반론 경로(예시): "Providers can ask for a re-test at contact@agentconcierge.biz."

**쓰지 않을 것**
- 평가하는 말: broken, unreliable, bad, poor, fake, scam, dead, useless, fraud와 그 비슷한 말
- 의도·원인 추측: "the provider stopped maintaining", "abandoned"
- 이름을 든 다른 제공자와의 비교 문장. 순위 표의 숫자는 괜찮다.
- 제공자 원문 오류의 긴 인용(200자 넘게), 내부 주소, 토큰, 자격 증명, 스택 추적
- **우리 쪽 원인을 제공자 실패로 쓰는 것**. 아래 경우는 실패 보고서로 공개하지 않고 재시험으로 돌린다.
  - 우리 게이트웨이 5xx, 우리 쪽 시간 초과, 우리 횟수 제한
  - 제공자 429(Retry-After). "rate limited at test time"으로 미룬다.
  - 우리 판정기 오류

**자동 검사**(운영·SRE가 만든다: `scripts/report_wording_check.py`)
- 필수 문구 5개가 있는지
- 금지 낱말 목록, 인용 길이
- 오류 종류가 우리 쪽 원인 목록에 들면 공개를 막는다.
- 결과는 보고서마다 `wording_ok`·`reasons`로 남긴다. 실패하면 공개를 멈추고 검색과 RAG에 돌려보낸다.
