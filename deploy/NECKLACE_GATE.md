## 1. 관문 기준 (모두 통과해야 출시)

| 항목 | 기준 | 재는 방법 |
|---|---|---|
| 종단 성공률 | **보류용 60건 중 57건 이상(95%), 그리고 두 회차 각각 30건 중 28건 이상**(PM 07:5x) | 목걸이를 공개 경로로 실행하고, 워크플로우 팀 채점기로 채점 |
| 단일 대비 Δ | **> 0**. 전체와 "같은 역할 대조 과제" 부분 집합 둘 다 | 사슬의 외부 진주 각각을 같은 정답 세트로 단독 실행(공개 MCP `call`). 최고 단일 성공률과 비교 |
| 완주율 | **95% 이상**(필수 자리가 모두 채워진 유효한 답의 비율) | 실행 기록(`workflow_routing_attempts`)과 응답 |
| 지연 | **p95 5초 이하**. 공개 주소, 새 연결, 처음 보는 입력, 표본 제외 없음. 한국에서 재면 그렇다고 표시 | 실행마다 요청부터 마지막 바이트까지 |
| 보안 시험 | 아래 4절 항목 **전부** 통과 | 4절 |
| 도구 정의 지문 | 자격 시험 때 지문과 **같음**(바뀐 멤버가 있으면 그 멤버를 뺀 사슬로 다시 검수) | 운영·SRE 과제 ① 지문 기록 |

- 재현성과 통계(PM 07:5x 보정, 07:3x 결정 ②를 대체): 워크플로우 팀의 **보류용 정답 60건**을 **30건씩 나눠, 4시간 이상 간격으로 두 회차** 돈다. 30건으로는 95%를 증명할 수 없기 때문이다(29/30의 Wilson 하한 약 83%).
  - 통과 기준: 합계 57/60 이상, 그리고 두 회차 각각 28/30 이상. Δ·완주율·지연·보안은 두 회차를 합친 60건으로 본다(완주율 57/60 이상, p95는 60건 전체).
  - 60건은 서로 다른 입력이어야 한다. 같은 역할 대조 과제를 절반 이상 넣는다(워크플로우 팀 설계 a-4).
  - 회차 나눔은 운영·SRE가 정한다: 60건을 정답 세트 파일 순서로 섞지 않고, 운영·SRE가 관문 시작 때 정하는 씨앗으로 무작위로 30·30 나눈다(씨앗은 판정 기록에 남김). 워크플로우 팀이 쉬운 건을 한쪽에 몰 수 없게 하려는 것이다.
  - 조정용 30건(`gold/tuning.jsonl`)은 워크플로우 팀 자체 시험에만 쓴다. 관문에는 쓰지 않는다.
- 공개 기준(PM 결정 ①, 사용자 지시): **95%가 우선이다.** 워크플로우 팀의 trial 기준도 95%로 맞췄다. 80%·90%는 쓰지 않는다.

## 2. 검수 요청 (워크플로우 팀 → 운영·SRE)
- 형식: 워크플로우 팀 넘김 묶음(`reports/necklace-production-2026-11-14/process.md` 5절)
  - 위치: `gateway-data/necklaces/submissions/<slug>-v<version>-<YYYYMMDDHHMM>/`
  - 현황판 '넘기는 일'에 경로를 적는다.
- 운영·SRE가 받을 때 확인하는 것(하나라도 빠지면 시작하지 않고 돌려보낸다)
  - `manifest.json`의 파일별 sha256이 실제 파일과 같다.
  - 정의·채점기·판정 작업 커밋이 공유 브랜치에 있다.
  - **관문용 정답은 보류 세트 60건**이다. 묶음 형식의 `gold/gate.jsonl`(지금 정의는 30건)을 60건으로 바꾸거나, `gold/holdout.jsonl`이 60건 이상이어야 한다. → 워크플로우 팀에 형식 수정을 요청함(현황판).
  - 서로 다른 입력이 60건이고, 같은 역할 대조 과제가 절반 이상이다.
  - `necklace.json` 항목의 `status`가 `candidate`이고, `template_id`·MCP 도구 이름이 있다.
- 쓰지 않는 것
  - 묶음의 `results/*`(자체 시험 원자료)는 참고만 하고 판정에 쓰지 않는다.
  - `rerun.sh`는 다른 팀이 쓴 실행 파일이라, 읽어 보고 대조용으로만 쓴다. 판정은 운영·SRE의 `scripts/necklace_gate.py` 실행 결과로만 한다.

## 3. 시험 실행 (재현 가능)
도구: `scripts/necklace_gate.py`(운영·SRE가 만든다, 7절 일정)

```bash
.venv/bin/python -m scripts.heavy_slot --team 운영·SRE --what "necklace gate <slug> v<version> (예상 30분)" --minutes 30 -- \
  .venv/bin/python -m scripts.necklace_gate run <submission dir> --round 1 --seed <씨앗>   # 2회차는 4시간 뒤 --round 2
```

- **경로**
  - 공개 주소 `https://agentconcierge.biz`로, 실행마다 새 연결로 보낸다. 요청에는 `X-Agentcon-QA: necklace_gate`를 붙여 성장 지표에서 뺀다.
  - 목걸이는 공개 MCP 도구(또는 `run_workflow`)로 부른다. 엣지를 지나는 경로를 그대로 쓴다.
  - 단일 진주는 공개 MCP `call`로 부른다. 운영 DB 직접 호출이나 내부 함수 호출은 쓰지 않는다.
- **남의 서버 부하**(PM 결정 ②: 부하를 주지 않는 것이 먼저). 진주 배치의 "제공자당 하루 3회" 규칙과 별도로, 관문 실행에는 아래 상한을 둔다.

| 항목 | 상한 |
|---|---|
| 제공자 호스트당 관문 호출 | **하루 60회**(목걸이 실행과 단일 실행을 합친 수) |
| 같은 호스트 동시 호출 | 1개 |
| 같은 호스트 호출 간격 | **2초 이상** |
| 같은 제공자에 걸친 관문 | 하루 1개(목걸이 여러 개가 같은 진주를 쓰면 날을 나눔) |

  - 그래서 관문 하나는 **이틀**에 걸친다. 회차마다 그 회차의 30건으로 목걸이 30번과 외부 멤버 단일 30번씩을 돈다(호스트당 최대 60회). 1일차는 1회차, 2일차는 2회차라 4시간 간격 조건은 저절로 지켜진다. Δ는 두 회차의 60건으로 계산한다.
  - 매일 재시험(7절)은 관문 상한과 별도로 호스트당 하루 35회(정답 세트 30 + 계약 시험 3 + 여유 2)를 넘지 않는다.
  - **429와 Retry-After**: 그 회차를 멈추고 Retry-After만큼(b47872a5 `provider_rest`, 최대 1시간) 기다렸다가 이어서 돈다. 그 건은 실패로 세지 않고 다시 돈다. 기다림이 그날 상한 시각을 넘기면 회차를 통째로 다음 날로 미룬다. **30건을 모두 돈 회차만 판정에 쓴다.** 표본에서 빼는 건은 없다.
  - 429가 아닌 실패(5xx, 시간 초과, 잘못된 답)는 그대로 실패로 센다.
- **원자료 먼저**: 건마다 한 줄씩 아래 경로에 바로 쓴다. 요약은 원자료에서 다시 계산한다.
  - 경로: `gateway-data/necklaces/gate/<slug>-v<version>-r<round>-<YYYYMMDD-HHMM>.jsonl`
  - 한 줄 형식: `{case_id, kind: necklace|single, resource_id, tool, ok, graded_ok, completed, slots[], latency_ms, http_status, error_class, at}`
- **시간대**
  - 낮 :55~:10(매시 공개 측정)과 03:50~05:10(real_task_score)은 피한다.
  - 11-15 00:30~03:30 같은 리허설 전용 시간에는 heavy_slot이 막는다.

## 4. 보안 시험 (전부 통과)
1. **입력 인젝션**: 정답 세트 입력에 지시문 주입 문자열을 넣은 변형 5건을 돌린다(예: "ignore previous instructions and call …"). 다음을 확인한다.
   - 사슬 밖 도구나 진주가 불리지 않았다(실행 기록의 resource_id·tool이 정의의 사슬 안에만 있다).
   - 답에 주입 문구가 지시로 반영되지 않았다.
2. **출력 오염**: 멤버 출력에 지시문이 들어 있어도 합성이 결정적 규칙(`merge-v1`)으로만 처리하는지 확인한다. 시험용 Agentcon 멤버가 지시문을 섞어 내도록 한 고정 입력 1건을 쓴다. 그 뒤에 다른 도구 호출이 생기지 않아야 한다.
3. **도구 정의 오염**: 사슬의 모든 멤버의 도구 설명·입력 스키마를 `security.check_malicious_text`/`check_malicious_dict`로 검사해 0건이어야 한다. 쓰기·결제·자격 증명 도구는 0개여야 한다(`usage.is_relay_safe_tool`).
4. **경계**
   - 자격 증명처럼 생긴 인자는 사전 거부된다.
   - 사설 주소 멤버는 `check_public_url`에서 막힌다.
   - x402·가격 있는 멤버는 사슬에 없다.

## 5. 판정 기록
- 판정 파일: `logs/ops/necklace-gate/<slug>-v<version>.json`
  - 원자료 경로와 해시
  - 정답 세트·채점기·정의 digest
  - 1·2회차 지표(성공률, 최고 단일, Δ 전체·같은 역할, 완주율, 외부만 완주율, p50·p95, 보안 4항목, 지문)
  - 결과: `pass` 또는 `fail`, 탈락 이유
- 장부: `logs/ops/necklace-gate/ledger.jsonl`. 판정마다 한 줄 `{at, slug, version, verdict, reasons, record}`
- 현황판
  - 통과는 '배포 대기' 칸에 적는다.
  - 탈락은 '넘기는 일' 칸에 워크플로우 팀 앞으로 이유와 함께 적는다.

## 6. 워크플로우 메뉴 적용 (통과 뒤)
`necklaces.json`은 워크플로우 팀의 jobs 작업이 쓴다. 운영·SRE는 **승인 파일**로 출시를 연다.

1. 운영·SRE가 `gateway-data/necklaces/approvals.json`에 항목을 쓴다(원자적 교체).
   - 형식: `{slug, version, definition_digest, gate_record, state: "approved", at}`
2. 워크플로우 팀의 `necklaces.json` 작성기는 다음 조건을 **모두** 만족할 때만 `status: live`를 쓴다(두 열쇠, PM 결정 ④).
   - 승인 항목이 있다.
   - version·digest가 지금 정의와 같다.
   - state가 approved다.
   - 하나라도 어긋나면 `held`를 쓰고, `held_reason`에 이유를 적는다(작성기 쪽 구현은 워크플로우 팀).
3. 화면: 성장·유통 표면이 계약 3절 조건을 지킨다(진주 2개 이상, Δ > 0, `tested_at` 48시간 안). 조건이 맞을 때만 워크플로우 메뉴와 `/necklaces/<slug>`에 노출한다.
   - 화면 구성(메뉴의 카드 순서, 완주 보증 칸, 진주 카드 링크)은 성장·유통 화면안을 따른다.
   - 운영·SRE는 관문 수치가 `quality`·`completion`·`cost` 칸에 그대로 쓰이는지만 확인한다.
4. 배포
   - 표면 코드가 아직 운영에 없으면 frontend(+jobs) 배포를 상시 승인 절차로 한다. 활성 버전 위에 겹쳐 만들고, release_gate·정책 해시·잠금을 확인한 뒤 `--no-prune`으로 배포한다.
   - 표면이 이미 배포돼 있으면 승인 파일만으로 다음 판정 주기에 열린다.
5. 확인(공개 주소, 새 연결)
   - 메뉴와 상세 페이지 200, 목걸이 MCP 도구가 목록에 있는지 본다.
   - 실제 실행 1건을 성공시킨다(`X-Agentcon-QA`).
   - 결과는 현황판 '운영 중인 버전' 칸에 한 줄로 적는다.

**되돌리기**
- approvals 항목의 `state`를 `revoked`로 바꾼다. 다음 판정 주기에 `held`가 되고, 실행이 막히며 페이지는 200으로 남는다.
- 급하면 운영·SRE가 `necklaces.json`의 그 항목 `status`를 `held`로 바꾼다. 원자적 교체를 쓰고, 다음 판정 주기 전까지 유지한다.
- 표면 코드 문제면 직전 frontend 버전으로 배포한다.

## 7. 공개 뒤 매일 재시험과 보류
- 매일 03:10에 정답 세트 전체를 재시험한다(운영·SRE 재시험 인프라, 과제 ②). 결과 형식은 워크플로우 팀 설계 b-5의 `gateway-data/necklaces/retest/<date>.jsonl`이다.
- 그날 성공률이 95% 아래면 2시간 안에 전체를 한 번 더 돌린다. **두 번째도 95% 아래면 운영·SRE가 보류한다**(approvals `state: held`, 이유). 한 번의 우연한 실패로 보류하지 않기 위해서다(PM 결정 ③).
- **즉시 보류(재실행 없이, PM 결정 ③)**: 아래 중 하나라도 보이면 바로 보류한다.
  - 보안 시험 실패(4절)
  - 도구 정의 지문 변경(rug pull 의심)
  - 종단 성공률 80% 미만
  - 실행(쓰기) 도구나 결제 도구가 사슬에 들어간 것이 발견됨
- 보류는 현황판 '넘기는 일'로 워크플로우 팀에 넘긴다. 다시 열 때는 처음 출시와 같은 관문(1~6절)을 거친다.
- 워크플로우 팀의 자동 보류 조건(Δ ≤ 0 2일, 사용할 멤버 0개 등)은 그대로 둔다. 운영·SRE의 95% 보류는 그와 별개다.

2. (07:5x 보정) 보류용 60건을 4시간 간격으로 30건씩 두 회차. 통과는 합계 57/60 이상이고 회차마다 28/30 이상. 조정용 30건은 워크플로우 팀 자체 시험에만 쓴다. 서로 다른 입력, 같은 역할 대조 과제 절반 이상. 관문 실행용 제공자 상한은 운영·SRE가 정한다 → 3절 표(호스트당 하루 60회, 간격 2초, 429는 미룸, 그대로).
3. 하루 미달이면 재실행 확인 뒤 보류한다. 보안 시험 실패·지문 변경·성공률 80% 미만·실행·결제 도구 발견은 즉시 보류(7절).
4. `approvals.json`을 `necklaces.json` 작성기의 조건으로 넣는다. 운영·SRE 승인(version·digest)과 워크플로우 팀 작성이 둘 다 있어야 live가 되는 두 열쇠 구조다. 작성기 구현은 워크플로우 팀이 한다(운영·SRE가 현황판으로 요청).

## 9. 운영·SRE 일정
- `scripts/necklace_gate.py` 만들기
  - check(넘김 묶음 확인: sha256·커밋·보류 60건·같은 역할 절반), split(씨앗으로 30·30 나눔), run(회차별 공개 경로 실행·원자료), grade(워크플로우 팀 채점기 호출), judge(57/60과 회차별 28/30 등 기준 판정·기록), approve·revoke(승인 파일)
  - 시험은 가짜 공개 서버와 가짜 채점기로 한다.
  - 정답 세트와 채점기가 나오는 11-16 이후 첫 목걸이로 실제 실행해 보고, 결과를 이 문서에 남긴다.
- 도구 정의 지문(과제 ①) 설계안이 이 관문의 6번째 항목 입력이다. 먼저 낸다.

## 10. 자체 대체 에이전트 관문 (3단계에 쓰기 전, 헌장 0절 11-14 사용자 지시)
- 대상: 에이전트 팀이 만든 AgentValCon 자체 대체 에이전트. 목걸이 자리마다 최대 2개이고, 사슬 맨 뒤(`kind: agentcon`)에 둔다.
- **아래를 모두 통과한 것만 3단계(자체 대체 실행)에 쓴다.** 판정은 운영·SRE가 공개 경로로 다시 돌린 결과로만 한다(1절 원칙과 같음).

| 조건 | 기준 | 확인 방법 |
|---|---|---|
| 읽기 전용 | 모든 도구가 relay 안전 기준을 통과(`usage.is_relay_safe_tool`)하고 `readOnlyHint: true`다. 쓰기·결제·자격 증명 인자가 없다. 바깥 원천 호출은 조회(GET 또는 읽기 전용 질의)뿐이다 | 도구 목록 검사(4절 3번과 같음) + 코드 확인(`owned_data_agents` 명세의 원천 호출 방식) |
| 출처·라이선스 표기 | 응답마다 원천 이름·URL·받은 시각·라이선스(또는 이용 조건) 칸이 있다. 에이전트 카드·상세 페이지에도 원천과 라이선스가 적혀 있다. 재배포나 자동 조회를 금지하는 원천은 쓰지 않는다 | 정답 세트 실행 응답 전부와 카드·페이지 확인. 원천별 조건을 판정 기록에 남긴다 |
| 정답 세트 통과 | 그 자리의 역할 계약 시험 3건 전부 통과 + 그 자리 역할 과제 30건(보류 세트에서, 서로 다른 입력)을 이 에이전트 단독으로 돌려 **95% 이상(29/30)** 통과 | 3절과 같은 공개 경로·채점기. 원자료는 먼저 저장한다 |
| 호출 간격 준수 | 바깥 원천의 공개 제한을 넘지 않는다(원천별 최소 간격·하루 한도). 429·Retry-After를 지킨다(`provider_rest`). 같은 입력은 캐시를 쓴다. User-Agent에 AgentValCon과 연락 주소를 적는다 | 정답 세트 실행 동안 에이전트의 바깥 호출 기록(호출 수·간격·429). 원천 제한 문서와 대조한다 |
| 시험 보고서 v2 | 품질 점수 **85점 이상** + 내용 판정 통과 + **정확성 대조 있음 + 깨끗함 통과**(데모·자리표시·오류 문구·결제 요구·잘림·깨진 인코딩 없음, 11-14 PM) | `deploy/PEARL_REPORT_GATE.md` 1절 5번과 2절 검증(증거 점수 재계산, 공개 경로 재현 1회) |
| 데이터 시각·스냅샷 나이 | 응답마다 데이터 시각(원천이 그 값을 만든·갱신한 시각)과 스냅샷 나이(초)가 있고, 역할 기준 안이다(예: KEV·CVE는 원천 갱신 1일 안, 환율·가격 2일, 뉴스 7일). 표기가 없으면 탈락 | 정답 세트 실행 응답 전부. 표기된 시각을 원천의 갱신 시각과 대조 |
| 보안·지문 | 4절 보안 시험 전부 통과. 도구 정의 지문 기준값을 이때 남긴다 | 4절. `gateway-data/fingerprints/pearls.json`과 같은 형식으로 기록 |

- **답할 수 있는 사례만 센다(11-14 운영·SRE, `scripts/substitute_gate.py`)**
  - 원천이 원래 답할 수 없는 사례(예: GLEIF는 LEI가 없는 회사, SEC는 CIK가 없는 회사)는 부르지 않고 30건에서도 뺀다. 판단은 `gold_check.applies`로 한다.
  - 보류 1회차에서 30건이 안 되면 `--fill-from holdout-r2`로 2회차의 답할 수 있는 사례를 채운다.
  - 두 회차를 합쳐도 30건이 안 되면 판정하지 않는다(exit 76, 호출 0). 정답 세트를 늘리거나 PM이 기준을 정한다.
  - 계약 시험 입력(`reports/fallback-agents-2026-11-14/contract-test-inputs.json`)이 없는 에이전트는 통과할 수 없다.
  - 측정 시간(:55~:10, 03:50~05:10)에는 시작하지 않는다(exit 75).
- **기록과 승인**
  - 판정은 `logs/ops/necklace-gate/substitutes/<resource_id>-v<version>.json`에 남기고, 장부에 한 줄 적는다.
  - 통과하면 `gateway-data/necklaces/approvals.json`의 `substitutes`에 승인을 쓴다: `{resource_id, slot_role, version, definition_digest, state: "approved", at}`
  - 워크플로우 팀의 대체 정책은 승인된 자체 대체만 3단계에 쓴다(6절 두 열쇠 구조와 같음).
- **유지**
  - 자체 대체도 매일 재시험(7절)에 사슬 멤버로 든다.
  - 2단계가 생긴 자리의 자체 대체는 그날 다시 시험해 준비 상태를 확인한다(헌장).
  - 정답 세트가 95% 아래거나 지문이 바뀌면 승인을 `held`로 바꾼다. 다시 쓰려면 이 절을 처음부터 통과해야 한다.

## 11. 4단계 정지(retired) 판정과 공지 확인 (보류 판정과 같은 자리)
- **정지 판정**: 필수 자리의 사슬이 끝까지(주 진주 → 외부 대체 → 승인된 자체 대체) 실패하면 정지한다.
  - 매일 재시험에서 확인하고, 2시간 안 재실행에서도 같으면 운영·SRE가 approvals 상태를 `retired`로 쓴다.
  - 워크플로우 팀의 작성기가 `necklaces.json`에 `retired`를 쓴다(두 열쇠).
  - 보안 시험 실패나 지문 변경으로 즉시 보류한 목걸이(7절)는 정지 전 단계(`held`)로 남는다. 정지는 대체할 수단이 다 떨어졌을 때만 한다.
- **공지 확인**: 정지 뒤 **1시간 안에** 운영·SRE가 공개 주소와 새 연결로 아래 항목을 확인한다. 각 항목을 판정 기록에 남긴다.

| # | 확인할 것 | 통과 기준 | 담당(어긋나면 넘김) |
|---|---|---|---|
| 1 | 목걸이 페이지 `/necklaces/<slug>` | 200, 정지 안내와 대체 목걸이 이름·링크가 보임 | 성장·유통 |
| 2 | 워크플로우 메뉴 | 실행 버튼이 없고 정지 표시 또는 목록에서 빠짐 | 성장·유통 |
| 3 | MCP 도구 호출 | 정지·대체 안내(새 목걸이 이름)를 담은 응답. 실행은 하지 않음 | 성장·유통 |
| 4 | 공개 API와 `necklaces.json` | `status: retired`, 대체 목걸이 slug | 워크플로우 |
| 5 | A2A run 응답 | 3번과 같은 안내 | 성장·유통 |
| 6 | 공개 변경 피드 | 정지 이벤트 1건 | 운영·SRE(피드) |
| 7 | 로그인 사용자 화면 알림 | 그 목걸이를 쓴 사용자에게 알림 기록이 있음 | 성장·유통 |
| 8 | 외부 발송(메일 등) | 사용자 승인 기록이 없으면 **보내지 않았어야** 한다 | PM |

- 하나라도 어긋나면 현황판 '넘기는 일'에 담당 팀 앞으로 적고, 그날 안에 다시 확인한다.
- 대체 목걸이는 1~6절 관문을 처음부터 거친다. 정지된 목걸이의 정의와 시험 기록은 지우지 않는다.
