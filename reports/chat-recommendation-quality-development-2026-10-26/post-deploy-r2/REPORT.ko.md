# R2 운영 확인과 긴 검색 보완

2026-10-26. **R2 운영 반영 확인. 추가 수정 R3 준비 완료, 아직 미반영.**

## R2 운영 확인

- 활성 프론트엔드 a의 릴리스는 `frontend-chat-task-quality-20261026-r2`이고 비공개 준비 상태 검사가 통과했다. 공개 Chat 페이지 HTTP 200, CSP·no-store, JavaScript의 릴리스 해시 일치를 확인했다. 내부 준비 상태 URL은 공개 경로에서 404다.
- 실제 합성 API 8건 중 7건 HTTP 200, 긴 조건 요청 1건 HTTP 503. 순차 재확인에서도 같은 긴 요청의 503이 재현돼 정상 완료로 처리하지 않았다.
- 논문 검색은 계약이 있는 1개 후보를 반환했고, 후속 DOI 요청도 논문 목적·MCP 범위·DOI 조건을 보존했다. `operation=refine`도 확인됐다. 한국어 계약서 요청은 A2A 후보 1개를 반환했다.
- 점검한 날씨·기술 뉴스 MCP 요청은 강화된 조건을 통과하는 후보를 반환하지 않았다. 전체 카탈로그에 없다는 증명이나 검색 품질 목표 달성으로 해석하지 않는다.
- 공개 Chromium 3개 여정에서 논문 검색·상세 열기·DOI 후속 조건·모바일 배치·빈 결과 안내·버튼 및 로딩 복구를 확인했다. 스크립트 오류 0건. R2 결과가 한 개여서 공개 여정에는 대안 펼치기 항목이 없었고, 대안 제어는 기존 격리 브라우저 회귀로 검증했다.
- 첫 일본어 요청은 입력 안내로 돌아갔지만, 같은 공개 요청을 순차 재확인하자 영어 정규화 후 검색 경로로 진입했다. 실제 서비스 팩토리와 설정된 모델을 조합한 격리 ASGI 검사도 약 1.14초에 정규화됐다. 모델 연결 누락은 재현되지 않았다. 첫 대체 응답의 정확한 원인은 제한된 계측만으로 확정하지 않는다. 모델 정규화가 모든 요청에서 성공한다고 주장하지 않는다.

## 긴 요청 503의 실제 원인

읽기 전용 PostgreSQL 검색으로 `ApplicationStoreError: result_limit`을 재현했다. 긴 입력 자체의 길이 제한이 아니라, 최대 600개 후보의 전체 리소스·대형 도구 계약을 읽는 과정에서 누적 **64MB** 보호 한도를 초과했다. 발생 위치는 `application_store_resource_batches.resources`의 전체 읽기 한도 검사였다.

## 준비한 R3 수정

- 검색·벡터 검증에 한해 예산 내에서 **온전한 계약을 읽을 수 있는 후보만** 사용한다. 64MB 누적 한도와 8MB 개별 쿼리 한도는 유지한다. 도구 계약을 잘라 입력 조건이나 권한 의미를 바꾸지 않는다.
- 한도 초과 시 검색 전체를 실패시키는 대신 해당 후보를 제외한다. 기존의 엄격한 전체 읽기 API는 기본값으로 유지한다. 크기가 큰 후보 뒤의 작은 후보도 계속 검토한다.
- 제한된 예산에서 lexical·dense 후보가 모두 검토될 수 있도록 입력 ID를 교차 배치한다. 제외 개수는 개인정보 없는 집계 카운터로 남긴다. 후보가 생략될 수 있으므로 이를 전체 카탈로그 완전 검색이나 Recall 보장으로 표현하지 않는다.
- 결과가 없는 긴 요청도 관심 작업에 최대 2,000자를 보존해, 다음 질문에서 300자 이후의 인증 제외 조건 등이 사라지지 않게 한다.
- 프로토콜을 선택한 새 외국어 요청이 단순히 검색어가 없다는 이유로 이전 작업으로 대체되지 않게 한다. 프로토콜 이름만 입력한 변경 요청과 새 작업을 구분한다.

수정한 읽기 전용 실제 카탈로그 검색은 같은 긴 요청에서 약 **1,705ms**에 예외 없이 완료됐다. 581개 결합 후보 중 185개가 예산 등으로 제외되고 396개의 온전한 리소스가 검토됐다. 추천 결과는 0건이었다. 이 결과는 읽기 전용 검색 단계 검증이며, R3 운영 HTTP 반영 확인과 구분한다.

## 최종 검증

- API·보안·동시성 385건, Chromium 24건, PostgreSQL 18 네이티브 2건: 고유 **411건 통과**, 실패·건너뜀 0건.
- PostgreSQL 테스트에서 엄격한 전체 읽기의 한도 초과 거부를 유지하면서, 선택적 부분 후보 읽기는 순서를 보존한 완전한 계약만 반환함을 검증했다.
- 공개 콘텐츠 296개 파일 검사 위반 0건, 수정 핵심 모듈 정적 검사 통과, 명시 SQL 카탈로그 일치. 동적 WHERE는 기존의 저장소 소유 조각이며 ID·필터 값은 바인딩함을 검토했다.
- 준비 R3의 수정 파일 해시는 검증한 작업 소스와 일치한다. 새 라이브러리·DB 스키마·모델 설정 변경은 없다.

실제 공개 검색은 정상적인 합성 대화 기록을 생성한다. 별도 읽기 전용 카탈로그 검증은 DB 쓰기가 0건이다. 에이전트 제공자 업무 실행·워크스페이스 변경·결제·크레딧 사용·운영 프로세스 조작은 하지 않았다.
