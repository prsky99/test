# 프론트엔드 실제 운영 분석 — 2026-10-19

분석 구간은 **한국시간 2026-10-19 00:00:00 이상, 11:40:00 미만**, 총 11시간 40분이다. 분석 시작 시각을 마감으로 고정했다. UTC로는 10월 18일 15:00부터 10월 19일 02:40까지다. 이후 확인한 현재 상태와 공개 화면 표본은 별도로 표시한다. 이 보고서는 내부 운영 분석 자료이며 공개 서비스에 게시하는 페이지가 아니다.

## 판단

**오늘 실제 활동의 중심은 수집·상태 점검과 관리자 모니터링이었다. 고객의 채팅 추천·워크플로우 이용 실적은 집계 구간에서 확인되지 않았다.** 서비스가 전혀 이용되지 않았다는 뜻은 아니다. 홈 접속, 에이전트 게이트웨이 호출, A2A 전송 요청은 있었지만, 접속자 식별 정보만으로 사람·봇·점검 트래픽을 확정할 수 없다.

기록된 HTTP 5xx는 없었고 분석 후 공개 페이지도 정상 응답했다. 다만 현재 공개 지표를 운영 성공률로 신뢰하기 어려운 근거가 있다. 홈의 고정 성공률·고정 그래프, 정적 성공 보고서의 카탈로그 연결 불일치, 실행 관측 누락, 검색 인덱스 적체가 우선 개선 대상이다. 따라서 “장애가 없고 검증이 정상 완료되고 있다”는 종합 판정은 할 수 없다.

## 1. 접속과 실제 이용

중복 집계를 피하기 위해 HTTP 요청은 통합 콘솔 로그에서 한 번만 셌다. 소스별 일별 로그는 오류·자동 작업의 교차 검증에 사용했다.

- 전체 HTTP 요청 **2,645건**: 관리자 2,335건(88.3%), 공개 프론트엔드의 알려진 경로 232건, 기타 경로 78건. 공개·기타 합계 310건을 모두 고객 요청으로 볼 수 없다.
- 관리자 `/admin/api/overview` 1,108건, `/admin/api/timeseries` 1,093건. 두 조회 API 합계 **2,201건, 전체의 83.2%**다. 관리자 화면을 보고 있는 동안 반복 조회된 기록으로 해석할 수 있다. 이 비율이 서버 자원 점유율을 의미하지는 않는다.
- 홈 GET 69건: 비루프백 연결 55건(200 응답 54, 403 응답 1), 로컬 연결 14건. 이는 69명 방문자나 69회 사람의 페이지 열람을 뜻하지 않는다. 27개 새 익명 집계 버킷 역시 고유 고객 수가 아니다.
- 200 응답 2,498건, 400 10건, 401 24건, 402 13건, 403 64건, 404 17건, 405 17건, 415 2건. **기록된 5xx는 0건**이다. HTTP 200 비율은 고객 작업 성공률이 아니며, 로그가 없는 단절이나 엣지 차단은 평가하지 못한다.
- POST는 4건: 루트 경로 415 두 건, A2A 200 한 건, 로컬 관리자 로그인 200 한 건. A2A의 전송 성공만으로 추천이나 외부 에이전트 실행 성공을 뜻하지 않는다.
- **`/chat` POST 0건, 추천 관측 0건, 저장된 채팅 메시지 0건, 신규 대화 방문자 0건.** 워크플로우 실행·고객 로그인 세션·문의·성공/실패 피드백도 해당 구간 신규 기록이 없다. “채팅 전환율 0%”라고 계산할 신뢰할 만한 사람 방문자 분모는 없다.

콘솔의 HTTP access 행에는 자체 시각이 없어 앞뒤 KST 로그 시각으로 구간을 배정했다. 99.4%의 요청은 앞뒤 기록 간격이 5초 이내, 최대 23초였고 자정·마감 경계를 걸친 요청은 없었다. 서버 access 로그까지 도착하지 않은 요청은 포함되지 않는다.

## 3. 에이전트 호출과 관측 신뢰도

게이트웨이 GET은 MCP 21건, x402 17건, A2A 7건이었다. MCP GET의 대부분은 405 또는 400 응답이다. 호출 안내·허용 메서드를 더 명확하게 제시할 여지가 있으나, 탐색 봇이 잘못 호출한 것인지 실제 통합 오류인지는 식별할 수 없다.

## 4. 우선 개선 사항

### P1 — 공개 지표와 검증 보고서의 사실성

**확인:** 현재 서비스하는 메인 스크립트에 `99.4% Automated Success`가 상수로 들어 있다. 24시간 그래프의 점 좌표도 고정 배열이다. `tests completed`에 쓰는 분모는 검증 성공·실패뿐 아니라 최초 시험 대기 항목까지 포함한다. 이 문구와 그래프를 오늘의 실측 성공률·실행 추이로 받아들일 수 없다. 공개 페이지에서 해당 표시를 확인했고, 메인 스크립트가 현재 작업 트리와 일치함도 확인했다.

오늘 생성된 성공 보고서 126건 중 **84건은 현재 운영 카탈로그의 같은 ID 리소스와 프로토콜이 다르다.** 오늘 보고서 126건 모두 이전 gateway DB에서는 ID·프로토콜이 맞는다. 연결 이름도 현재 collector DB와는 0/126 일치한다. 이름 불일치만으로 다른 자원이라고 단정하지 않았고, 확정 근거는 프로토콜 불일치다. `agent_url`이 managed gateway URL인 것은 정상 설계이므로 upstream URL과 문자열이 다르다는 이유로 결함 판정을 하지 않았다.

오늘 보고서를 만든 배치 스크립트는 고정 리소스 ID·본문·성공 상태·지연을 두 DB에 넣는 구조다. 전체 보고서 1,172건에 실행 시각·증거 범위 필드가 비어 있다. 읽기 전용 재현에서 서로 다른 에이전트의 보고서가 추천 후보 조회와 공개 보고서 투영을 통과하는 사례도 확인했다. 이후 관련성·버전 검사까지 통과하여 실제 Chat에 추천됐다는 증거는 없으며 오늘 Chat 사용도 없었다.

**개선:** 고정 성공률·장식용 실시간 그래프를 실제 기간별 이벤트 집계로 교체한다. 실행 대기·도달 가능·도구 목록 조회·실행 성공을 구분하고, 보고서에는 안정적인 리소스 식별자와 연결 버전, endpoint hash, 프로토콜, 실행 시각, 증거 범위를 묶는다. 두 DB 간 정수 ID 재사용으로 다른 자원에 연결되지 않게 하고 기존 불일치 보고서는 추천 증거에서 보류한 뒤 재검증한다.

**완료 기준:** 교차 DB·다른 프로토콜·다른 연결 버전의 보고서는 현재 검증·추천 근거에서 제외되고, 적법한 과거 보고서는 이력으로 명확하게 구분된다. 성공률과 그래프는 지정한 기간의 실제 증거에서 재계산되며 대기 건수는 완료 분모에서 제외된다. 검증 증거가 없으면 그 사실을 정확하게 표시한다.

### P1 — 검색 인덱싱 대기열의 진행 보장

**확인:** 마감 시점에 열린 인덱싱 작업 **113,915개**, 오늘 생성된 작업 124,808개의 시도 횟수는 모두 0이다. 최신 provenance는 0건이며 기존 물리 벡터 행 수를 최신 검색 인덱스 완료 수로 볼 수 없다. 가장 오래된 pending 작업은 비활성 리소스를 가리킨다. 현재 코드가 그 작업을 매번 선택한 뒤 상태를 바꾸지 않고 건너뛰는 경로를 격리 메모리 DB에서 재현했다. 세 번 연속 처리해도 후속 유효 작업이 진행되지 않았다.

이는 운영 적체를 설명할 수 있는 코드상 메커니즘과 현재 DB 상태가 일치한다는 근거다. 운영 프로세스의 당시 consumer 설정·내부 실행 상태까지 확보한 것은 아니므로 적체의 유일한 원인이라고 단정하지 않는다. 어휘 기반 검색은 별도 경로여서 전체 검색 중단을 뜻하지도 않는다.

**개선:** 비활성·삭제·세대 불일치 작업을 적절한 종료 상태로 전환하거나 claim 조건에서 제외하고 후속 작업의 진행을 보장한다. oldest age, 처리율, 신규 유입률, 시도 0건 유지 시간을 감시한다. 기존 적체는 보류 사유를 분류한 뒤 제한된 배치로 처리한다.

**완료 기준:** 선두 비활성·삭제·오래된 세대 작업 뒤의 유효 작업이 진행되고, 동일 작업 반복 선택으로 큐가 멎지 않는다. 운영에서는 최신 provenance 증가와 큐의 처리율 회복을 별도로 확인한다.

### P1 — 프록시 뒤의 차단 대상 정확성

**확인:** 보안 DB에는 스캐너 탐지 32건과 그에 따른 자동 차단 32건이 있다. 31건은 WordPress 계열, 1건은 환경 파일 탐색이다. `auto_jail_ddos`라는 이벤트 이름만으로 DDoS 공격이 발생했다고 결론 내리지 않는다. 차단 28건이 하나의 Cloudflare 네트워크 peer에 집중되어 있어 실제 요청자와 공용 ingress의 구분을 점검해야 한다. 이는 28명의 공격자나 정상 고객 오차단 28건을 뜻하지 않는다.

**개선:** 실제 배포된 ingress→프록시→앱의 신뢰 경로를 확인하고 검증된 헤더만 사용해 클라이언트 주소를 복원한다. 임의 전달 헤더 신뢰나 Cloudflare 전체 무차별 허용으로 해결하지 않는다. edge 차단·앱 차단·실제 클라이언트 집계도 구분한다.

**완료 기준:** 같은 ingress를 쓰는 서로 다른 합성 클라이언트가 독립적인 제한·차단 상태를 갖고, 외부에서 위조한 헤더가 주소를 바꾸지 못한다. 실제 사용자 오차단 여부는 해당 검증 전까지 미확정으로 유지한다.

근거: [보안 집계](request-security.json), [요청 분석](request-findings.md), [주소 해석](../../agent_market/concierge/security.py#L264), [프록시 설정](../../deploy/Caddyfile), [Cloudflare 공식 주소 목록](https://www.cloudflare.com/ips-v6/).

### P1 — 실행 관측 누락과 미확정 상태 관리

**개선:** 업무 트랜잭션을 지연시키지 않는다는 현재 원칙을 유지하면서 관측 쓰기 실패를 지속적으로 계수한다. 누락 경고, 미확정 처리, 완료 기록을 같은 상관 참조로 연결하고 관리자 화면에 관측 커버리지를 표시한다. 늦은 결과 확인 없이 미확정 실행을 재실행하지 않는다.

**완료 기준:** 격리된 DB 잠금·관측 저장 실패·응답 지연 시험에서 누락 건수와 미확정 상태가 정확하고, 자동 재시도 때문에 외부 작업이 중복 실행되지 않는다. 완료 경고가 있는데 장시간 running으로 남는 상황을 탐지한다.

근거: [실행 교차 검증](execution-crosscheck.json), [관측 코드](../../agent_market/observability.py).

### P2 — 반복 조회·로그량·상태 점검의 효율과 신선도

오늘 콘솔 기록은 약 **2.14 GB**, 930만 행이고 DEBUG가 약 99.7%다. 로그 전체는 약 6.5 GiB, 운영 데이터 디렉터리는 약 7.3 GiB다. 관측 시점 사용 가능 디스크는 약 284 GiB여서 당장 용량 부족이라고 판정하지 않는다. 짧은 하루 표본의 증가량을 장기 추세로 곧바로 외삽하지도 않는다.

상태 점검이 43만 회 이상 수행됐어도 확인 시점에는 일부 호스트에 오래된 점검이 집중되어 있었다. x402의 1시간 이상 지연 항목 대부분과 A2A의 지연 항목이 각각 단일 호스트에 몰렸다. 건강/도달 가능 상태의 x402 36,049개 중 7,856개는 최근 24시간 성공 관측이 없었다. 게이트를 유지하면서 호스트별 공정성과 신선도 분포를 개선해야 한다.

**개선:** 운영 DEBUG를 제한하고 회전·보존·민감정보 필터를 점검한다. 관리자 통계 조회는 탭 비활성 시 중지하고 갱신 간격·백오프·공유 캐시를 적용한다. 상태 점검은 호스트별 제한과 공정 큐, 연속 실패 백오프를 함께 사용한다. DB/WAL 증가와 체크포인트 지연은 감시하되 이번 분석에서 운영 체크포인트·VACUUM은 수행하지 않는다.

**완료 기준:** 변경 전후 동일 구간의 요청 수·로그 bytes/분·DB 잠금 대기·홈 TTFB를 비교한다. 점검 횟수뿐 아니라 프로토콜별 최근 성공 시각, 오래된 항목의 수, 호스트별 지연 분포가 개선되어야 한다. 공공 화면에는 사적인 인프라·런타임 정보를 노출하지 않는다.

### P2 — 고객 여정과 검증 신선도의 관측

확인 시점 카탈로그는 약 11.8만 항목이다. 관련성·최종 연결 버전 검사 전의 상한 후보군 77,147개 중 최근 24시간 성공 검증 시각이 있는 항목은 **697개(약 0.90%)**다. A2A 62, MCP 608, x402 27이다. 이 수치는 모두가 실제 추천·실행 가능하다는 뜻이 아니며, 보고서 연결 불일치 때문에 검증의 질도 별도 확인해야 한다.

**개선:** 기본 A2A와 명시적 MCP/x402/Any 선택을 유지하면서 질문 유형별 유효 후보·증거 신선도를 평가한다. 방문→질문→추천→상세→실행→결과를 목적에 맞는 최소 이벤트로 구분하고, 관리자·합성 점검·봇 트래픽을 분리한다. 방문자 토큰과 개인 정보를 UI나 공개 지표에 표시하지 않고 필요한 분석 권한·동의 기준을 지킨다. 한국시간 당일 분석과 현재 Home의 New York 자정/최근 24시간 집계는 시간대와 구간을 명시해 비교한다.

**완료 기준:** 집계의 단위·기간·대상·누락 범위가 표시되고, 실제 사람이 확인되지 않은 요청 수를 고객 수로 발표하지 않는다. 성공 검증의 최신성에 따라 정렬하되 관련성·안전·프로토콜 제한이 유지된다.

## 5. 분석 후 공개 화면 확인

11:43경 일반 GET·초기 화면 로딩으로 현재 상태를 표본 확인했다. **분석 구간 이후의 확인이며 위 일중 이용 통계에 넣지 않았다.**

- 로컬 HTTP·공개 HTTPS 모두 200. 현재 공개 메인 인라인 스크립트가 작업 트리와 일치했다. 서버 전체의 모든 파일·설정·배포 이력을 일치 검증한 것은 아니다.
- CSP, nosniff, HSTS, frame DENY 확인. 브라우저 표본에서 페이지 오류·실패 HTTP 요청은 없었고 데스크톱/390px 화면의 가로 넘침도 없었다.
- 홈 응답은 단일 표본 기준 로컬 약 5.90초, 공개 약 1.70초였다. 별도 브라우저 표본의 TTFB는 약 5.19초, DOMContentLoaded 약 5.74초였다. 초기 응답 지연을 조사할 이유는 있으나, 표본 수·캐시·DB 경합·네트워크 차이가 있어 관리자 polling이나 자동 수집을 원인으로 확정하지 않았다.
- 브라우저에서 전송량 약 136 KB, 압축 해제 본문 약 598 KB였다. 초기 HTML·부트스트랩 크기와 생성 비용을 함께 점검할 수 있다. Chat·외부 에이전트 실행·등록·발송 동작은 수행하지 않았다.

근거: [현재 응답·브라우저 표본](live-probes.json), [데스크톱](public-desktop.png), [모바일](public-mobile.png).

## 6. 적용 순서와 분석의 한계

먼저 공개 지표·보고서 연결의 사실성과 안전한 차단 대상 식별을 바로잡고, 인덱싱 큐 진행 및 실행 관측을 안정화한다. 그다음 로그·polling·점검 큐의 효율을 개선하고 실제 고객 여정과 검증 품질을 측정한다. 각 개선은 격리된 API/브라우저/보안 회귀 검증을 거쳐야 하며, 이 분석 요청에서 제품 코드를 수정하거나 변경을 적용하지 않았다.

운영 서버를 시작·중지·재시작하지 않았고 설정·운영 DB를 직접 수정하지 않았다. SQLite는 `mode=ro`와 `query_only`로 짧게 읽었다. 일반 페이지 조회에 따른 정상적인 access/익명 집계 기록은 마감 이후에 생길 수 있다. 발송·프로바이더 실행·광고는 수행하지 않았다. 분석 산출물에 IP·방문 토큰·연락처·고객 질문·비공개 응답 본문을 저장하지 않았다.

전체 기간의 엣지 로그, RUM, 외부 업타임 관측, 전체 배포 이력과 프로세스 설정은 확보하지 않았다. 현재 DB 스냅샷은 수집 중 변경될 수 있어 일중 이벤트 합계와 구분했다. 원시 로그/DB 일부에서 누락이 확인되어 성공률·실사용 고객 수·SLA를 확정하지 않았다. 보안 신호와 기본 헤더 확인은 전체 보안 인증이나 취약점 부재 판정이 아니다. 제품 소스 변경이 없는 분석이므로 전체 회귀 테스트는 재실행하지 않았고, 발견 경로의 격리 재현과 집계·파일 검증만 수행했다.
