## 2. 비활성 x402 자원의 옛 A 등급 861개 정리안 (실행하지 않음)
- 실측(운영 DB 읽기 전용)

| x402 | 등급 | 수 | 마지막 평가 |
|---|---|---|---|
| 비활성 | A | **861** | 11-01까지 |
| 비활성 | B | 11,372 | 11-13 |
| 활성 | B | 124,949 | 11-14 |

- 원인
  - 품질 정책 v2(11-10, x402는 B 상한)를 적용하는 `quality_policy_batch`(`application_store_collector.py:262-303`)가 `active=1`만 고른다.
  - 그래서 v2 전에 A를 받고 비활성이 된 x402가 그대로 남았다.
- 미리 계산(같은 정책 함수 `apply_quality_policy`, 7일 헬스 기록 0건, 쓰기 없음): 861개 전부 **B**가 된다.

**제안 방법**(PM 승인 뒤, 등급 행을 바꾸는 일이라 실행 전 승인)
1. 직접 `UPDATE`는 쓰지 않는다. 평가 이력(`eval_info`)과 등급이 어긋나고, 등록 SQL 규칙에도 맞지 않는다.
2. `quality_policy_batch`에 "비활성 x402만" 한 번 도는 단계를 더한다.
   - 정책 함수와 저장 함수(`apply_quality_policy` → `record_evaluation`, `observation_guard`)는 지금 것을 그대로 쓴다.
   - 따로 커서(`quality_policy_inactive_x402`)를 두고, 500건씩 2바퀴면 끝난다.
   - 새 SQL 1개(`... WHERE id>%s AND active=0 AND kind='x402' AND eval_grade='A' ORDER BY id LIMIT %s`)를 등록해야 한다(구조 변경 아님). frontend와 jobs를 함께 배포한다(등록 SQL 목록은 두 역할이 같이 읽음).
3. 영향
   - 비활성이라 탐색·추천에는 보이지 않는다.
   - 등급별 집계(insights, 관리 화면 통계)에서 A가 861개 줄 수 있다. 진주 후보 수(활성 A)에는 영향이 없다.
   - 되돌리기: 평가 이력이 남아 있어 이전 평가로 다시 기록할 수 있다.
4. 확인: 실행 뒤 `kind='x402' AND eval_grade='A'`가 0인지 센다. 같은 함수로 미리 계산한 결과(전부 B)와 같은지 본다.
