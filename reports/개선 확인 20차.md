## 3. 워크스페이스: 전체 화면 게이트 제거, 영역별 로딩
**원인**
- 개요와 워크플로 화면은 `data-workspace-loading`으로 레이아웃 전체를 숨기고, 세션 확인, 데이터 읽기, 글꼴 로드가 모두 끝나야 보였다.
- 그 사이 화면 전체를 덮는 "Opening your workspace…" 화면이 떠 있었다.
- 클릭할 때 뜨는 진행 팝업도 화면 가운데에 고정돼 있었다.
- 세션 확인이 끝나야 데이터 읽기를 시작했다(직렬).

**고친 것**
- 게이트와 전체 화면 진행 표시를 없앴다. 메뉴와 제목은 첫 페인트에 보인다.
- 로딩은 `#status` 줄의 작은 스피너로만 보인다.
- 진행 팝업은 오른쪽 위 배지로 옮겼다(`pointer-events:none`).
- 세션 확인과 읽기 요청을 병렬로 보낸다(개요, 워크플로).

**측정**(시험 환경, 지연 없이 3회)
- 메뉴와 제목 표시
  - 개요: 0.07~0.10초

- 데이터 완료는 그보다 0.02~0.03초 뒤였다.
- 이전에는 화면이 데이터 완료와 글꼴 로드 뒤에야 보였다.
- 운영 실측은 로그인이 필요해 배포 뒤 확인한다(§8).

## 8-1. 워크스페이스 Support 화면이 안 나온 원인 (14:50)
**증상:** 사용자가 Support 메뉴를 열었을 때 안내 문구만 보이고 양식과 요청 목록이 나오지 않았다. 다시 열자 정상이었다.

**로그 추적**
1. frontend 로그
   - `14:50:09 GET /api/customer-support/options 500`
   - `Private route failed ... exception=ApplicationStoreError`
2. PostgreSQL `server.log`
   - `14:50:09.283 ERROR: canceling statement due to lock timeout`
   - 0.3초 뒤 같은 오류가 하나 더 있다. 같은 초에 execution의 `Due workflow round deferred after a storage error: statement_failed`도 있다.
3. 코드
   - 고객 세션 확인 `identity.actor()`와 Support 읽기 경로(options, cases, detail, sharing-options)가 `identity.tx()`, 즉 `BEGIN IMMEDIATE`를 쓴다.
   - 운영 PostgreSQL 저장소는 이것을 쓰기 트랜잭션으로 바꾼다. 쓰기 트랜잭션은 전역 쓰기 잠금 `pg_advisory_xact_lock`과 `LOCK TABLE resources,...`를 잡는다.
   - 그래서 읽기만 하는 세션 확인도 백그라운드 쓰기(문서 갱신, 실행기)를 기다렸다. 1초(`lock_timeout`)를 넘기면 실패했다.
4. 화면
   - 세 요청 가운데 하나만 실패해도 `#support-content`를 숨긴 채 끝났다. 그래서 "화면이 안 나옴"으로 보였다.
   - 잠금 경합이 없을 때 다시 열면 정상이었다.
5. 같은 원인의 다른 증상: 이 세션 확인은 모든 워크스페이스 요청이 거친다. 메뉴마다 "세션 체크가 오래 걸리던" 현상(운영 실측 세션 API 0.45~1.0초)의 원인이기도 하다.

**수정:** 릴리스 `support-lock-frontend-20261101-r1`(기준 `snapshot-progress-frontend-20261101-r2`, 4개 파일)
- `CustomerIdentity.read_tx()`를 새로 만들었다. PostgreSQL에서는 `store.tx(readonly=True)`를 쓰고, 쓰기 잠금이 없다.
- `actor()`는 세션을 읽기 전용으로 확인한다. 1분에 한 번 필요한 만료 연장 때만 쓰기 트랜잭션을 연다.

- 세션 확인 중 저장소 오류는 500이 아니라 503과 `Retry-After: 2`로 답한다.

  - 로그인 오류일 때만 내용을 숨긴다.
  - Refresh는 처음 불러오기가 실패했으면 전체를 다시 시도한다.

**시험**
- 새로 추가
  - 세션 확인이 쓰기 잠금 없이 읽기만 하는지(연장 때만 쓰기)
