# 과제 있는 외부 질의 45건이 게이트웨이 연결로 이어지지 않은 원인 (성장·유통, PM 11-18 08:2x)

- 측정: 11-18 08:2x~08:5x, 읽기 전용(`prod_ro_sql` 집계와 질의 행, 하루 트래픽 파일). 개인 식별 정보는 쓰지 않는다. 방문 토큰·지문 값은 이 보고서에 넣지 않았다.
- 대상: 11-17(UTC 하루 = KST 09:00~다음 날 09:00)의 `ask|*|external|task` 약 45건. 우리 시험·측정·홍보 발송은 뺐다.

## 결론
- 45건은 연결을 시도할 "과제 있는 사람"이 45명이라는 뜻이 아니다. 서로 다른 외부 클라이언트(IP+접속 도구 지문)는 하루 **11개 이하**(프로세스마다 지문 소금이 달라 상한이다)이고, 새 분류 규칙(원인 1)을 적용하면 과제 요청은 **약 23건**(Explore 20, A2A 2, REST 1)에 클라이언트 **약 8개**(브라우저 5, 에이전트 3)다. 에이전트가 보낸 진짜 과제는 하루 **3건 안팎**이다.
- 외부 클라이언트가 게이트웨이(`/api/gateway/*`)를 부른 일은 11-10 이후 기록 전체에서 **외부 실행 시도 1건**(11-15)뿐이고, 외부 연결 성공은 **0건**이다. 11-17의 "외부 실행 성공 2건"은 검색과 RAG가 예시 확인으로 22:01에 돌린 우리 쪽 호출이었다(운영·SRE 확인). 그래서 "끊긴 단계가 connect"라기보다 **connect를 할 사람이 분모에 거의 없고, 있는 사람은 한 번 묻고 떠난다**가 맞다.

## 원인 3개와 고칠 안
### 1. 분모가 부풀어 있고 클라이언트 수로 보지 않는다
- 근거: 위 표. Explore 30건은 5개 브라우저에서 온 것이고, 그중 빈 검색어 화면 열기 10건이 과제로 센다. A2A도 광고·정해진 문장 9건이 "과제"다. 11-16은 Explore 21건이 브라우저 1개였다.
- 안(내부, 영어 화면 문구 없음):
  1. 북극성 분모를 **서로 다른 클라이언트 수**(`recommend_task|external` 서로 다른 지문)로 바꾸고, 건수는 보조로 둔다.
  2. 빈 검색어(browse)는 과제에서 뺀다(`explore_topics`의 browse와 같은 기준).
  3. `traffic_classes.json`에 정해진 문장 2종(날씨 API 질의, 기술 뉴스 워크플로우 질의)을 `ask_fixture_exact`로, "Hello from HelioGrid"·"Kyreos Trustkeeper"류를 `ask_outreach_contains`로 더한다. 규칙 파일이라 배포는 낮 묶음에 가능하다.
- 측정: 같은 11-17 기록으로 고친 규칙을 다시 돌려 과제가 약 45건에서 몇 건·몇 클라이언트로 줄어드는지 보고한다. 이 숫자가 새 기준선이다.

### 2. 한 번 묻고 떠나는 클라이언트에게 "다음 행동"이 응답 안에서 끝나지 않는다
- 근거: 방문 1회·메시지 1건. 웹 검색 질의의 답은 실행 줄(`Run here`, `Endpoint`, 한 번에 부르는 `Call` POST, MCP 설정 조각)을 모두 줬지만 그 방문자는 호출하지 않았다. 국가 지표 **워크플로우 찾기 답에는 실행 줄이 없고** "Open: …/workflows.html, 실행을 승인하세요"로 끝난다(사람용 화면으로 보내는 막다른 길).
- 안:
  1. auto_run(c4d5ada8, 11-17 20:14 r12)이 이미 이 문제의 1안이다. 다만 무장하는 곳이 **A2A message/send 한 곳**(front.py)뿐이라 웹 Chat과 REST가 같이 쓰는 `/chat`, MCP chat·find_agents에서는 시도가 늘 0이다(검색과 RAG 코드 확인). `/chat`에 같은 조건을 그대로 붙이면 사람의 대화마다 남의 서버 호출이 생기므로, 후속 안은 호출자가 요청에서 명시적으로 고를 때만 무장하는 방식(예: body `data.auto_run=true`, 영어 문서에 공개)이다. auto_run 소유 팀 판단이 먼저다. 다만 r12 이후 과제가 있는 A2A 질의는 REST 한 줄뿐이고 auto_run 시도 0건이라 **아직 효과를 잴 수 없다**. REST chat 경로도 같은 무장이 되는지 확인이 필요하다(검색과 RAG).
  2. 워크플로우 찾기 답에 에이전트용 한 줄을 더한다: `Run here: run_workflow {"workflow_id": ..., "definition_hash": ...}`(MCP `run_workflow`와 A2A run 형식)를 첫 항목에 붙이고, 사람용 `Open:` 줄은 그 뒤로 둔다. 영어 고정 문구 예: `Next step: send the Run here object to the call tool as it is; no sign-in needed for a free read-only run.` 위치는 추천 답의 첫 항목 바로 아래다.
  3. 쓰기·결제가 필요한 과제는 실행하지 않는다(안전). 그때는 `Connect directly — we don't relay this agent (provider terms)` 같은 고정 문구로 끝내(9e5851b1이 이 방향의 직접 연결 안내), 응답이 막다른 길이 되지 않게 한다.
- 측정: (a) 같은 클라이언트가 질의 뒤 같은 날 게이트웨이를 부른 비율(`follow|a2a|connect|external` / 서로 다른 과제 클라이언트), (b) `auto_run|external|attempt·ok`, (c) 워크플로우 답 뒤 `run_workflow` 호출. 9e5851b1과 auto_run이 배포된 뒤 7일을 앞 7일(0건)과 비교한다.

### 3. 사람(Explore) 쪽은 검색 뒤를 볼 수 없고, 연결이 우리 화면 밖에서 일어난다
- 근거: Explore는 검색 글자를 저장하지 않고, 카드를 연 일·엔드포인트를 복사한 일을 세는 칸이 없다(사용자 측정 RUM은 속도 값만). 사람은 엔드포인트를 복사해 **자기 MCP 클라이언트**에서 부르므로 그 요청은 다른 지문·다른 클라이언트 분류로 오고, 같은 사람으로 이어 볼 수 없다. 지금까지 그런 외부 호출이 한 번도 안 나타났다.
- 안:
  1. 카드 상세에서 **웹에서 바로 실행**하는 버튼을 눈에 띄게 한다: 이미 있는 시험 화면의 실행(`tbRunBtn`)과 같은 경로로, 첫 줄을 "Try this tool now" 영어 문구 하나로 하고 결과를 그 자리에 보여 준다(읽기 전용 도구만, 인자는 `run_here_fill`이 채움). 사용자는 연결 설정 없이 결과를 본다.
  2. 개인을 담지 않는 계수 두 개를 더한다: 상세 열기 수, "Try this tool now"·엔드포인트 복사 수(하루 집계, 에이전트 id별 합계만, 방문 토큰 없음). 정책 해시와 무관한 클라이언트 beacon이다.
- 측정: 상세 열기 → 실행/복사 비율, 그리고 웹 실행의 `execute|browser` 건수. 지금은 두 값이 기록되지 않아 기준선이 없다(0이 아니라 "측정 안 함").
