## 2. 1단계 (구현됨, d76d6d88, DB 변경 없음)

- 게이트웨이의 tools/call과 message/send 결과를 답 자체로 분류합니다(`agent_market/concierge/task_outcomes.py`).
  - succeeded
  - failed: isError, `{"error":…}`, "… failed", 빈 답
  - needs_key: "Provide an API key", "requires … api key" 등
- 자원별·도구별로 7일 동안 Redis 공유 저장소에 셉니다. 호출자, 인자, 답 내용은 저장하지 않습니다.
- 순위(`gateway_exposure.order_key`, Chat 의미 정렬 뒤에도 적용):
  1. 무료이면서 최근 실패가 없는 것
  2. 그 안에서 최근 실제 성공한 것이 먼저
  3. 실패만 있거나 키를 요구한 것, 반대 방향인 것은 뒤로
- 위 1번에 해당하는 후보가 3개 이상이면 2·3번 후보는 빠집니다.
- 한계: Redis는 7일 TTL의 집계라 시간이 없고, 과제 종류와 출처를 나누지 않습니다. 화면에 근거로 보이기에는 부족합니다. 그래서 2단계가 필요합니다.

## 3. 2단계 (DB 표, 결정 요청)

### 3.1 표 (별도 스키마 `task_evidence`, public 트리거 5개 불변)

| 표 | 열 | 보관 |
|---|---|---|
| `task_evidence.calls` | resource_id, tool, task_kind, source(gateway·real_task·test_screen), outcome(succeeded·failed·needs_key), latency_ms, at | 35일, jobs가 매일 지움 |
| `task_evidence.rollup` | resource_id, tool, task_kind, source, attempts_30d, successes_30d, needs_key_30d, last_success_at, last_outcome, median_latency_ms, updated_at | jobs가 10분마다 다시 만듦 |

- 적용과 복구: `scripts.task_evidence_schema`(status, migrate, rollback, `--i-have-approval`).
  - migrate: `CREATE SCHEMA/TABLE IF NOT EXISTS`만 합니다.
  - rollback: `DROP SCHEMA task_evidence CASCADE`입니다.
  - public 트리거가 5개가 아니면 거부합니다.
- 시험: `tests/test_task_evidence_schema.py`(사설 PG). 적용 → 다시 적용 → 앱 붙이기 → 잘못된 source 거부 → 복구까지 통과했습니다.
- 리허설: 11-12 03:00 사본 리허설(D', 트리거 변경과 같은 창)에 포함했습니다. 적용 뒤 붙이기 확인을 다시 재현합니다.

### 3.2 무엇을 남기나

- **task_kind(과제 종류):** 호출된 도구의 이름과 설명을 14개 카테고리 분류(`gateway/classify.py`)로 나눈 값입니다. 채점 과제는 과제 자체의 카테고리를 씁니다.
- **source(출처):** 셋으로 나눕니다.
  - gateway: 방문자와 외부 에이전트가 게이트웨이로 부른 호출
  - real_task: 매일 도는 실제 과제 채점기입니다. 공개 게이트웨이를 쓰므로, 로컬 비밀값이 담긴 헤더로 구별합니다.
  - test_screen: 사이트 시험 화면의 호출(managed_gateway.execute의 source 값)
- **latency_ms:** 게이트웨이가 제공자 호출 앞뒤로 잽니다.
- **쓰기 방식:** 요청 경로는 한 행 INSERT 하나만 합니다(트랜잭션 짧게, writer 잠금 아님). 실패해도 응답에는 영향이 없습니다.

### 3.3 어디에 보이나

| 화면·응답 | 보이는 것(영어, 공개 문구) |
|---|---|
| 상세 페이지 `/api/agents/{rid}`와 화면 | 도구별·과제 종류별로 "Real calls, last 30 days: M of N succeeded · last success <time> · median <ms>", 출처별 행 |
| MCP `find_agents` 응답 | `task_evidence: {task_kind, attempts_30d, successes_30d, last_success_at, median_latency_ms, sources}`. 요청 과제의 종류와 추천 도구에 맞춘 값을 먼저 줍니다 |
| Chat 카드 | 증거 줄 1줄: "This task kind: M of N real calls succeeded (30 days)". 증거가 없으면 "No real calls recorded for this task kind yet" |

SealKeeper와의 차이:
- 그들은 에이전트 단위로 "검증 작업 수"를 보여 줍니다.
- 우리는 "이 과제 종류에서 이 도구가" 성공했는지를 보여 주고, 같은 화면에서 대안과 바로 연결까지 이어 줍니다.

### 3.4 순위

순서는 다음과 같습니다(안정 정렬, 의미 순서는 각 묶음 안에서 유지).
1. 무료이고, 이 과제 종류에서 최근 30일 성공이 있고, 마지막 결과가 실패가 아닌 것
2. 무료이고, 증거가 없는 것
3. 최근 실패만 있거나 키를 요구한 것, 반대 방향인 것, 유료인 것

- 출처 가중치는 real_task > test_screen > gateway로 둡니다. 채점 과제는 정답 패턴으로 확인한 성공이기 때문입니다.
- 2단계가 적용되기 전까지는 1단계의 Redis 집계가 같은 자리를 채웁니다.
