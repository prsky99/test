# Explore PostgreSQL A1 — 권장 1~3단계 구현 결과

2026-10-30 KST. 소스 구현·격리 검증·배포 후보 준비 범위다. **운영 스키마와 운영 프로세스는 변경하지 않았으며 OpenSearch도 설치하지 않았다.**

> 갱신 10:50 KST: 1~5절은 적용 전 기록이다. 이후 [OPERATIONS.ko.md](./OPERATIONS.ko.md) 절차로 운영에 적용했다(10:17~10:23). 적용 결과와 남은 위험은 6절에 있다. OpenSearch는 여전히 설치하지 않았다.

## 1. 기준선과 품질 검사

기존 어휘 검색·임베딩·ANN·후보 투영 계측에 `resource_read`, `contracts`, `admission`, `cards`, `search_document`를 추가했다. 별도 입력·응답·방문자 데이터는 기록하지 않는다. 단계 시간은 중첩과 프로토콜 병렬 실행을 포함하므로 합산해 전체 응답 시간으로 계산하면 안 된다.

운영 카탈로그에 읽기 전용 연결로 공개 작업어 3종을 각 두 번 조회했다. 첫 측정은 지역 날씨 6,311.73ms, 번역 2,129.28ms, GitHub 이슈 3,349.14ms였다. 동일 검색 재요청은 2,293.90ms, 1,166.08ms, 1,216.88ms였다. HTTP와 결과 캐시는 포함하지 않았고, OS 파일 캐시를 비운 시험도 아니다. `baseline.json`에 단계별 값을 남겼다.

`quality-cases.json`은 **독립 의도 10종의 표현 변형 200개**다. 날씨·번역·GitHub 이슈·기술 뉴스·논문·환율·주가·음성 전사·PDF 추출·Python 문서를 포함하며 각 요청의 적합 항목과 무관 항목 판단을 고정했다. 200개의 독립 사용자 과업이나 운영 질의 분포를 대표하는 표본으로 주장하지 않는다. 다국어·프로토콜·안전성은 기존 회귀와 별도 API 검사로 함께 확인했다.

## 2. 검색 문서·검증 사실 사전 생성

`agent_market/explore_documents.py`에 검색 전용 파생 문서를 구현했다.

- 원본 텍스트의 길이 구분 SHA-256과 실제 정책 구현 파일들의 hash를 결합한다. 제공자가 선언한 hash만 믿지 않는다.
- 도구 이름·설명·입력 속성 이름·지원 가능 여부와 검색 텍스트를 미리 생성한다. **완전한 실행 입력 스키마를 이 메타데이터로 대체하지 않는다.**
- 읽은 현재 행에 결합된 내부 객체만 사전 생성 사실로 인정한다. JSON에서 같은 이름의 필드를 주입해 사용할 수 없다. 도구 사본을 수정해도 다른 요청에 영향을 주지 않는다.
- 실행 경계의 `tools_for()`는 검색 전용 객체를 받으면 도구를 반환하지 않는다. 실제 카드와 실행은 완전한 현재 계약을 사용한다.
- 문서가 없거나, 원본/정책이 다르거나, 읽기 예산이 부족하면 기존 전체 계약 경로로 돌아간다. 0건이나 허위 성공으로 바꾸지 않는다.
- 새 보조 테이블은 `agentcon_search.explore_documents`, `explore_document_queue` 두 개이며 대기열 인덱스 한 개가 필요하다. 자동 생성하지 않고 명시적 관리 명령으로만 준비한다.

처음에는 리소스 변경 트리거를 추가하는 방식을 시험했지만, 기존 Store가 정확한 무결성 트리거 집합을 검증하는 것과 충돌했다. 이 검증을 완화하지 않았다. **기존 `resource_observation_generations`의 영속 변경 세대를 재사용**하여 갱신을 감지한다. 따라서 프론트엔드·어드민·execution의 기존 리소스 무결성 정의를 바꾸지 않는다.

문서 갱신은 jobs의 제한된 maintenance 슬롯에서 기본 25건씩 처리한다. 새로 읽은 원본이 작성 직전에 바뀌면 게시하지 않는다. 원본의 현재 hash를 확인하는 짧은 트랜잭션 안에서 게시하며, 실패는 제한된 재시도로 남긴다. 초기 적재가 끝나지 않은 항목은 정확한 기존 검색 경로를 계속 사용한다. 5초 주기 설정은 초기 적재 전체가 5초 안에 끝난다는 뜻이 아니다.

## 3. PostgreSQL 조회 최적화

후보 순서·RRF·작업 관련성·프로토콜·품질 기준은 유지했다. 검색 문서가 현재일 때는 후보마다 큰 전체 스키마를 전송·파싱하지 않고 검색 사실로 먼저 판정한다. 최종 카드에 필요한 항목의 전체 계약은 같은 읽기 스냅샷에서 묶어 읽는다. 검증된 항목만 요청하는 경로는 기존의 완전한 계약 검사를 유지한다.

대형 제공자 메타데이터가 배치 메모리 한도를 넘지 않도록 SQL의 누적 바이트 예산을 적용했다. 검색 문서 한 개는 최대 2MiB, 한 번의 가벼운 조회는 24MiB 이내다. 예산에서 빠진 항목은 기존 바이트 제한 전체 읽기로 처리한다. 허용량을 늘리거나 원본을 조용히 자르지 않았다.

쿼리별 사실 캐시에는 내부 객체 대신 안정된 원본/문서 식별을 사용한다. 건강 상태·인증·언어 등 현재 행 필드는 계속 키에 포함하며 권한 캐시로 사용하지 않는다. 기존 결과 캐시와 페이지의 현재 가용성 재검사도 유지했다.

## 4. 동일 후보 비교 결과

최종 구현의 비교는 실제 카탈로그에서 읽은 **1,834개 후보 리소스**와 연결 증거를 외부 TCP가 없는 폐기용 PostgreSQL 18에 직접 복제해 수행했다. 원본 데이터 파일은 만들지 않았고 운영 DB 쓰기도 하지 않았다. 과거 보고서는 복제하지 않았다. 보고서 생성 예약 검사를 우회하거나 새 실행 성공 기록을 만들지 않았다.

두 경로는 같은 후보 ID·순위·현재 리소스·연결 증거를 사용했다. 매 요청마다 계약 캐시를 비우고, A0/A1의 실행 순서를 교차해 총 18회를 비교했다. **임베딩·ANN·최초 후보 검색·HTTP는 제외한 후처리 비교**다. 전체 서비스 지연이나 p95 개선율로 표시하면 안 된다.

- 지역 날씨 중앙값: A0 **4,314.74ms → A1 2,920.82ms**, 약 **32.3% 감소**.
- 번역 중앙값: **1,687.31ms → 1,033.87ms**, 약 **38.7% 감소**.
- GitHub 이슈 중앙값: **2,542.74ms → 1,725.52ms**, 약 **32.1% 감소**.
- 18회 모두 동일 검색의 결과 ID와 순서가 일치했다. 표본별 반환 수는 날씨 19개, 번역 46개, GitHub 이슈 17개였다. 46은 API의 45개와 다음 페이지 존재 확인용 한 항목을 포함한 내부 창이다.

`snapshot-benchmark.json`이 최종 원자료이고 `snapshot-benchmark-initial.json`에 앞선 시도도 보존했다. 실시간 카탈로그는 그사이 변하므로 서로 다른 시각의 후보 수 변화는 이 최적화의 회귀로 계산하지 않았다. **300/800ms 성능 목표와 16동시·p95 합격은 아직 입증하지 않았다.** 이는 이후 OpenSearch 비교·부하 검증 단계의 과제로 남긴다.

## 5. 검증과 제한

- 기능·검색·보안·네이티브 DB 묶음 372건 통과. 이후 사실 캐시 보완 표적 290건, 최종 바이트 예산 표적 227건 통과. 검사 간 중복이 있으므로 합산하지 않는다.
- 실제 브라우저 검색·Chat·공개 메뉴·XSS/CSP 회귀 37건 통과. 운영 계정이나 외부 제공자의 쓰기 작업을 사용하지 않았다.
- 별도 보안 묶음 96건 통과 후 기존 테스트 하나가 이전 403 문구를 기대해 실패했다. 이미 운영 중인 `REQUEST_POLICY_DENIED`·`review_request` 계약을 검사하도록 테스트만 수정했고 재검사 통과했다. 차단·권한 로직을 느슨하게 바꾸지 않았다.
- PostgreSQL 18에서 UTF-8 원본 hash 일치, 원본 변경, 잘못된 정책, 문서 손상, 빌드/게시 사이 변경, 반복 처리, 실행 계약과의 분리를 검증했다.
- 실제 Explore API에 연결한 폐기용 DB에서 45건·다음 페이지·중복 없음·엄격 프로토콜·무의미 질의·일반 용어·비활성화·인증 필터·검증 필터·읽기 예산 부족 시 결과 일치를 확인했다.
- 신규 코드 Ruff 및 변경 런타임의 오류성 린트 통과. 공개 콘텐츠 320파일 위반 0. HTML·CSS·공개 문구는 이번에 변경하지 않았다.
- 역할별 불변 후보의 전체 파일 hash 및 네이티브 검사 결과는 `frozen-verification.json`에 기록한다. jobs는 검색 문서 작성 역할이므로 공개 웹 화면 검사를 대신 수행했다고 주장하지 않는다. 읽기·작성 정책 hash는 세 후보가 같아야 한다.

OpenSearch 설치, 벡터 DB 이전, 운영 스키마 추가, 운영 서비스 교체, 실제 결제, 제공자 계정 연결, 운영 사용자 대화 삭제는 하지 않았다. 운영 속도 개선 반영은 [OPERATIONS.ko.md](./OPERATIONS.ko.md)의 별도 적용 후 확인해야 한다.

최종 후보 확인: frontend/admin 각 1,338개, jobs 1,330개 파일 hash가 모두 일치했다. 두 웹의 네이티브 문서·API 검사와 jobs의 네이티브 문서 검사를 통과했고, 세 후보의 정책 hash도 동일하다. 준비 전후 활성 서비스/PID/프록시 상태는 동일했다. `completion.json`, `frozen-verification.json`, `final-operating-status.json` 참조.

## 6. 운영 적용 결과 (2026-10-30 10:17~10:25 KST)

- 적용: 보조 테이블 2개와 인덱스 1개(install 1회), 초기 refresh(최대 500건), jobs r2(10:18), frontend/admin r2 슬롯 b(10:22). 이후 준비 상태를 확인했다. execution·프록시는 그대로다. 직전 상태는 `deployment-before-*.json`, 직후 상태는 `deployment-after-status.json`과 `deployment-readiness.json`에 있다. 바뀐 릴리스는 frontend/admin `qa11-remediation-*-20261030-r1`(슬롯 a에 남아 있음)과 jobs `experience-jobs-20261029-r4`다.
- 공개 API 확인 25개 항목 중 24개 통과(`post-deploy-api-checks.json`). 실패 1건은 `data` 다음 페이지 중복 ID 232426이다. 직전 QA11 슬롯에서도 같은 ID로 재현되어 A1 이전부터 있던 문제다(`live-pagination-comparison.json`). 첫 시도 기록은 `first-attempt-*.json`에 보존했다.
- 공개 검색 시간(`post-deploy-search-timings.json`, 조건별 1회): 첫 요청은 날씨 8,286ms, 번역 2,817ms, GitHub 이슈 6,523ms, 재요청은 466/426/329ms였다. **측정 당시 검색 문서는 x402 2,117건뿐이고 A2A/MCP는 0건이었다**(`document-progress.json`). 작업어 검색은 모두 기존 전체 계약 경로로 처리됐다. 재시작 직후라 캐시가 비어 있었고 초기 적재가 동시에 돌았다. 따라서 이 수치는 A1의 운영 효과나 회귀를 판정하는 근거로 쓰지 않는다.
- 대기열 219,183건(시도 0회)이 남아 있다. 첫 6분의 속도가 유지되면 완료까지 약 14시간이 걸린다(추정).
- **정체 위험(코드 검토):** `Refresher.run()`이 `resources()`로부터 돌려받지 못한 대기 항목(계약이 `MAX_BYTES`를 넘거나 활성 조건에 맞지 않는 항목)을 지우지도 미루지도 않는다. 이런 항목은 대기열 맨 앞에 남아 배치 자리를 계속 차지하며, 25건이 쌓이면 적재가 오류 없이 멈춘다. 실제로 그런 항목이 있는지는 확인하지 못했다. 검색 정확성에는 영향이 없다(문서가 없으면 기존 경로 사용). 수정안과 확인 명령은 [설계 문서 8.4~8.5절](../../docs/qa/explore-opensearch-design-2026-10-30.ko.md)에 있다.
- 남은 확인: 적재 진행 여부(`status`를 두 번 실행해 비교), A2A/MCP 문서 적재 후 캐시 미스/적중을 나눈 재측정, 6절 기준 부하 측정. 300/800ms 목표와 p95 달성은 아직 주장하지 않는다.
