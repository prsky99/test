# 에이전트 증가 대비 추천 정확도 99% 개선 방안 (2026-11-04)

에이전트 데이터가 늘면 검색·Chat(RAG) 답변·추천이 무거워지고 정확도가 떨어질 수 있다. 이 문서는 최신 논문과 SNS를 조사해 그 해결책을 정리하고, 우리 시스템에 맞춘 단계별 개선안을 제안한다.

## 1. 지금 상태 (11-04 운영 DB, 읽기 전용 집계)

| 항목 | 값 |
|---|---|
| 전체 목록 | 255,339 |
| 활성 | 236,976 (x402 128,432 · A2A 71,133 · MCP 37,411) |
| 검색 대상(건강·보안 통과) | 232,163 |
| 하루 신규 | 2천~1.8만 건, 최근 10일 평균 약 9천 건 |
| 같은 이름이 2개 이상인 그룹 | 8,249개 그룹, 17,870건 |
| Chat 정확도(159건 평가) | 151/159 (95.0%), 11-02 |
| 워크플로 생성 정확도(73건) | 73/73, 11-02 |

- 이 속도면 석 달 뒤 활성 목록은 약 100만 건이 된다(지금의 4배).
- 지금 정확도는 규칙(`selection.capability_terms`, `fast_chat` 결과 0건 복구)을 사례마다 덧붙여 올린 값이다.
  - 11-01~02에만 핵심어 규칙을 10개 넘게 더했다.
  - 이 방식은 목록이 늘수록 새 실패가 더 빨리 생긴다. 실패 사례를 사람이 하나씩 찾아야 하기 때문이다.
- 정책 파일을 하나 바꾸면 검색 문서 전체를 다시 만든다(약 100분). 목록이 4배가 되면 6시간 넘게 걸린다.

## 2. 조사 결과: 무엇이 정확도를 떨어뜨리나

### 2.1 후보가 많아지면 고르기가 틀린다
- Anthropic 자체 측정: 도구가 30~50개를 넘으면 선택 정확도가 크게 떨어진다. Tool Search(필요할 때만 도구 설명을 불러오기)를 켜자 Opus 4.5가 79.5%에서 88.1%로 올랐다. ([Anthropic Engineering](https://anthropic.com/engineering/advanced-tool-use), [Tool search 문서](https://platform.claude.com/docs/agents-and-tools/tool-use/tool-search-tool))
- RAG-MCP: 전체 도구 설명을 넣는 대신 검색으로 후보만 넣자 선택 정확도가 13.62%에서 43.13%로 올랐다. 다만 도구가 수천 개를 넘으면 검색 정밀도가 떨어진다고 정리돼 있다. ([arXiv 2505.03275](https://arxiv.org/abs/2505.03275))
- HN·X 개발자 토론에서 나온 관찰은 이렇다. ([HN 벤치마크 토론](https://news.ycombinator.com/item?id=47495475), [HN 스키마 설계](https://news.ycombinator.com/item?id=46941684), [X: Claude Code Tool Search 공개](https://x.com/trq212/status/2011523628773622234))
  - Tool Search는 앞에 쓰는 토큰은 줄이지만, 검색이 틀리는 새 실패 유형이 생긴다.
  - 비슷한 도구가 많으면 엉뚱한 것을 고른다.
- **우리에게 뜻하는 것:** 우리는 23만 건에서 1위를 고른다. 공개 벤치마크(수백~5천 개)보다 훨씬 크다. 그래서 "검색이 후보를 잘 좁히는가"(재현율)와 "좁힌 후보에서 1위를 맞히는가"(정밀도)를 따로 재야 한다.

### 2.2 문서가 부실하면 검색이 못 찾는다
- Tool-DE: LLM으로 도구 문서에 기능 설명·태그·언제 쓰는지·한계를 덧붙였다. 그러자 BM25의 Recall@10이 8.69포인트 올랐고, dense 검색과 reranker도 함께 좋아졌다. 사용 예시는 효과가 없거나 오히려 나빠서 뺐다. ([arXiv 2510.22670](https://arxiv.org/abs/2510.22670))
- 실제 A2A 에이전트 카드 466개를 분석한 글도 카드 내용이 부실하고 제각각이라고 보고한다. ([API Evangelist, 10-26](https://apievangelist.com/2026/10/26/what-466-conformant-a2a-agent-cards-are-actually-offering/))
- **우리에게 뜻하는 것:** 이번 Chat 실패(text to speech, Wikipedia, illustration)는 모두 요청 쪽 핵심어를 규칙으로 고쳤다. 같은 문제를 목록 쪽 문서에서 풀면 규칙 없이 일반화된다.

### 2.3 한 번의 검색으로는 복합 요청을 못 푼다
- TOOLQP (MIT, 2026-01): 요청을 하위 작업으로 나누고, 작업마다 검색어를 만들어 여러 번 검색한다. 고정 길이 임베딩 하나로는 도구 조합을 표현하지 못한다는 것이 출발점이다. ([arXiv 2601.07782](https://arxiv.org/abs/2601.07782))
- ToolSearcher (NeurIPS 2026 포스터): 대규모 도구 선택을 여러 번 검색하는 강화학습 문제로 본다. 기능이 비슷한 도구를 구별하는 학습을 따로 둔다. ([NeurIPS 포스터](https://neurips.cc/virtual/2026/poster/154349), arXiv 번호는 2차 출처라 확인하지 못함)
- **우리에게 뜻하는 것:** `fast_chat._cover_parts`(요청 일부씩 다시 찾기)와 워크플로 단계 분리는 이미 같은 방향이다. 그런데 둘 다 규칙 기반이다.

### 2.4 "의미상 맞는 것"과 "지금 작동하는 것"은 다르다
- RATED (CIKM 2026): 의미 검색기 뒤에 문맥 밴딧(contextual bandit) 재순위를 붙여, 실제 실행 결과로 순위를 고친다. API 30%가 실패하는 상황에서 고장 난 도구를 고르는 비율이 86.2%에서 2.9%로 줄었다. 추가 지연은 1ms 미만이다. 벤치마크는 실제 도구 5,172개, 질의-도구 쌍 21만 개다. ([arXiv 2610.13889](https://arxiv.org/abs/2610.13889))
- 위험도 반영 재순위(도구 6,108개에 위험 등급 부여)도 같은 학회에 나왔다. ([arXiv 2608.22751](https://arxiv.org/html/2608.22751))
- **우리에게 뜻하는 것:** 헬스체크·평가 점수·`record_outcome`·`global_failing_resources`는 이미 있다. 다만 지금은 이 신호를 제외 조건으로만 쓰고, 순위 학습에는 쓰지 않는다.

### 2.5 99%는 "모든 질문에 답해서 99%"가 아니다
- Knowing Before Answering (2026-08): 가장 확신 있는 50%에만 답하자 평균 정확도가 0.943이 되고, 틀린 답 비율은 0.013으로 줄었다. ([arXiv 2608.27661](https://arxiv.org/pdf/2608.27661))
- FinAbstain (2026-07): 보정된 불확실성으로 답하지 않을 때를 정한다. 보정 단계를 빼면 정확도가 나빠진다. ([arXiv 2607.24875](https://arxiv.org/abs/2607.24875))
- 프롬프트로 "모르면 모른다고 해"라고 하는 방식은, 검색 결과가 오해를 부르면 무너진다. ([arXiv 2608.22228](https://arxiv.org/pdf/2608.22228))
- LLM reranker가 스스로 순위 품질을 예측할 수 있다는 연구도 있다(도메인 안에서 Spearman 0.75 이상). ([arXiv 2606.03535](https://arxiv.org/html/2606.03535))
- **우리에게 뜻하는 것:** 99%는 "답한 것 중 맞은 비율"(정밀도)로 정의하고, "답한 비율"(커버리지)을 함께 보고해야 현실적이다. 확신이 낮으면 틀린 1위를 내는 대신, 되묻거나 후보 몇 개를 비교해 보여 준다.

### 2.6 검색 구조의 표준
- 업계에서 굳어진 기본형은 이렇다. BM25와 dense 검색을 RRF로 합치고, cross-encoder reranker로 상위 50~100개를 다시 매긴다. late interaction(ColBERT)은 두 번째 단계의 정밀 재채점으로 쓰고, 대신 저장 공간이 많이 든다. 다만 근거 대부분이 업체 블로그라 수치는 그대로 믿기 어렵다. ([Tensoria](https://tensoria.fr/en/blog/hybrid-search-reranking), [Denser](https://denser.ai/blog/hybrid-search-for-rag/), [Atlan](https://atlan.com/know/hybrid-rag/))
- **우리 상태:** OpenSearch(어휘 검색)와 pgvector HNSW(벡터 검색)의 하이브리드까지는 있다. 학습된 reranker는 없고, 그 자리를 규칙 관문(`_search_protocol`의 핵심어 75% 일치)이 맡고 있다.

## 3. 개선 방안 (우선순위 순)

### 단계 0. 측정부터 바꾼다 (1~2주, 다른 모든 단계의 전제)
1. **지표 정의**
   - 정밀도: 답한 것 중 1위가 맞은 비율. 목표 99%.
   - 커버리지: 전체 질문 중 답한 비율. 목표 90% 이상.
   - 재현율@50: 정답 후보가 상위 50개 안에 드는 비율. 검색 단계 지표다.
   - 응답 시간: 지금 정책 그대로(5초, 복잡한 질문 10·15초).
2. **평가셋 확대: 159건 → 1,000건 이상**
   - 운영 Chat 기록에서 표본을 뽑고, LLM이 먼저 판정한 뒤 사람이 검수한다.
   - 지금처럼 tuning과 holdout을 나눈다.
3. **결정적 평가**
   - 같은 코드로 두 번 재도 1~2건이 오가는 흔들림을 없앤다(검색 시간 예산, 동점 처리).
   - 1%를 다투려면 잡음이 0이어야 한다.
4. **규모 시험**
   - 운영 사본에 비슷한 목록(템플릿 복제, 다른 이름의 같은 기능)을 2배·4배로 넣는다.
   - 그 상태에서 정확도 곡선을 미리 본다.
   - 실제로 100만 건이 되기 전에 무너지는 지점을 찾는 것이 목적이다.

### 단계 1. 목록 쪽 품질 (2~4주)
5. **기능 문서 확장 (Tool-DE 방식)**
   - jobs가 오프라인으로 목록마다 짧은 구조화 필드를 만든다.
     - 무엇을 하는가(한 문장)
     - 기능 태그
     - 언제 쓰나 / 언제 쓰지 않나
     - 입력·출력 종류
   - 저장은 `capability_text` 옆이고, 이 필드는 어휘 검색과 벡터 검색에 모두 넣는다.
   - 로컬 모델로 하루 신규 9천 건을 처리할 수 있는지 먼저 잰다.
   - 생성 결과는 원문에 없는 기능을 지어내지 않았는지 검증한다.
6. **중복·템플릿 묶기**
   - 같은 이름이나 같은 템플릿인 목록(지금 17,870건)을 대표 1건으로 묶고, 나머지는 그 아래 변형으로 둔다.
   - 후보가 줄면 고르는 문제가 쉬워진다(2.1절).
   - 탐색에서는 이미 묶어 보여 주고 있다(4b519b01). 이를 추천에도 적용한다.
7. **증분 갱신**
   - 정책 파일이 바뀌면 지금은 전체를 다시 만든다(100분).
   - 문서마다 "어떤 규칙 버전으로 만들었는지"를 기록해, 바뀐 규칙이 영향을 주는 문서만 다시 만든다.
   - 목록이 4배가 되면 꼭 필요하다.

### 단계 2. 검색·순위를 규칙에서 학습으로 (4~8주)
8. **3단 검색 구조**
   - ① 카테고리·기능 라우팅: 기존 14개 카테고리 + 기능 태그로 후보 범위를 먼저 좁힌다.
   - ② 하이브리드 검색: BM25 + 벡터를 RRF로 합쳐 상위 100개를 뽑는다. 단계 1에서 확장한 문서를 쓴다.
   - ③ 재순위: 로컬 cross-encoder로 상위 100개 중 20개를 고른다. 그 20개에서 LLM listwise로 1~3위를 정한다(위치 편향을 고려한 방식).
   - 지금의 핵심어 규칙(`capability_terms`)은 ③이 자리 잡을 때까지 안전망으로 두고, 평가에서 차이가 없어지면 줄인다.
9. **복합 요청은 질의 계획으로 (TOOLQP 방식)**
   - "A 하고 B 해줘"는 모델이 하위 작업으로 나누고, 작업마다 ②~③을 돌린다.
   - `_cover_parts`와 워크플로 단계 분리를 이것으로 합친다.
   - 시간 예산은 복잡한 질문 10초, 매우 복잡한 질문 15초 안이다.
10. **학습 데이터**
    - 평가셋, 운영 Chat에서 사용자가 실제로 고른 것, Test 실행 성공을 (질의, 정답 목록) 쌍으로 모은다.
    - 그 쌍으로 임베딩과 reranker를 대조 학습한다.

### 단계 3. 작동하는 것을 위로 (단계 2와 병행 가능)
11. **실행 결과로 순위 보정 (RATED 방식)**
    - ③의 점수에 문맥 밴딧 항목을 더한다. 사용하는 신호는 헬스체크, Test 실행 결과, `record_outcome`, 응답 시간이다.
    - 새 목록도 기회를 얻도록 탐색 비율을 조금 둔다.
    - 지금은 실패한 목록을 제외만 한다. 이를 확률로 바꾸면 "의미는 맞지만 자주 죽는" 목록이 자연스럽게 내려간다.
12. **위험도 반영**
    - `eval_security`와 x402 결제 위험을 감점 항목으로 넣는다.
    - 지금처럼 격리(quarantine)는 그대로 제외한다.

### 단계 4. 모르면 묻는다 (단계 2 뒤)
13. **확신도 판정**
    - ③의 점수 차이(1위와 2위 간격), reranker의 자기 예측, 핵심어 일치를 합쳐 "확신"을 계산한다.
    - holdout 평가셋으로 보정해, 정밀도 99%를 지키는 문턱을 정한다.
14. **확신이 낮을 때**
    - 1위 하나 대신 다음 중 하나를 한다.
      - 후보 2~3개를 차이점과 함께 보여 준다.
      - 한 가지를 되묻는다("음성 합성인가요, 음성 인식인가요?").
    - 이 응답은 커버리지에서 "답하지 않음"으로 센다. 2.5절의 연구들이 99% 근처 정밀도를 이렇게 얻었다.

### 단계 5. 규모에 맞는 속도 (상시)
15. **3초·5초 정책 유지**
    - 탐색은 지금처럼 스냅샷·캐시로 답한다.
    - Chat은 ① 라우팅으로 검색 범위를 줄인다.
    - 벡터는 양자화(예: int8)와 종류별 분할로 HNSW 크기를 줄인다.
    - reranker는 상위 100개만 보므로 목록 수와 상관없이 시간이 일정하다.
16. **비싼 계산은 미리**
    - 문서 확장, 임베딩, 중복 묶기, 밴딧 통계는 jobs가 미리 계산한다.
    - 요청 경로에는 새 실시간 DB 확인을 넣지 않는다(응답 시간 정책).

## 4. 기대 효과와 위험

| 방안 | 기대 | 위험·비용 |
|---|---|---|
| 5 문서 확장 | 재현율 상승(논문: BM25 R@10 +8.7) | 로컬 모델 처리량, 지어낸 기능 → 원문 대조 검증 필요 |
| 6 중복 묶기 | 후보 수 감소, 1위 정밀도 상승 | 다른 서비스를 잘못 묶을 위험 → 묶기 기준 평가 |
| 8 재순위 | 규칙 의존 감소, 새 실패 유형 감소 | reranker 지연 → 상위 100개로 제한 |
| 11 실행 결과 보정 | 고장 난 목록 추천 감소(논문: 86%→3%) | 피드백이 적은 새 목록 → 탐색 비율 |
| 13~14 확신도 | 정밀도 99% 도달의 현실적 경로 | 커버리지 하락 → 둘 다 보고 |

- 99%를 "모든 질문의 1위 정확도"로 잡으면, 목록 증가 속도를 규칙 추가가 따라가지 못한다. 단계 4까지 가야 지속할 수 있다.
- 논문 수치는 각자의 벤치마크 값이다. 우리 데이터에서 같은 폭을 기대하면 안 되며, 단계 0의 평가로 직접 재야 한다.
- 확인하지 못한 것:
  - ToolSearcher의 arXiv 번호와 규모
  - Anthropic 수치의 독립 재현
  - 블로그의 하이브리드 검색 수치

## 5. 바로 시작할 것 (제안)
1. 단계 0의 지표·평가셋·결정적 평가를 만든다. 코드 변경이 작고 배포가 필요 없다.
2. 단계 1의 문서 확장을 표본 1,000건으로 시험한다. 확장 전후의 재현율@50과 Chat 평가를 비교한다.
3. 단계 3의 실행 결과 보정은 이미 모으는 신호로 할 수 있다. 오프라인 재생(과거 기록으로 순위를 다시 매겨 비교)부터 한다.

### 6.3 카탈로그 크기와 정확도
`EVAL_SUBSET`은 후보 600개 안에서 목록 id 해시로 일정 비율만 남긴다. 실제로 작은 카탈로그를 다시 색인한 것이 아니라 근사다. 정답 판정은 전체 카탈로그 기준이다.

| 카탈로그 | tuning 정밀도 | holdout 정밀도 | tuning 응답률 | p50 |
|---|---|---|---|---|
| 25% | 86.6% | 82.5% | 55.9% | 0.99초 |
| 50% | 86.6% | 84.9% | 66.4% | 1.17초 |
| 100% | 83.3% | 84.8% | 77.6% | 1.43초 |

- 25%에서 100%까지 정밀도는 2~3%p 안에서 오르내렸다. 카탈로그가 커져서 무너지는 모습은 아직 없다.
- 응답률은 카탈로그와 함께 오른다. 응답 시간도 함께 오른다(p50 1.0초 → 1.4초).
- 지금 정밀도를 막는 것은 규모보다 요청 이해(질문형, 긴 맥락, 낯선 표현)다.
- 2배·4배 규모는 아직 재지 않았다. 템플릿 복제 목록을 넣은 사본이 있어야 한다.

변형별 정밀도(tuning)는 다음과 같다.

| 변형 | 수정 전 | 수정 뒤 |
|---|---|---|
| 질문형 | 26.2% | 77.9% |
| 손으로 쓴 것 | 97.8% | 100% |
| 오타 | 88.1% | 90.3% |
| 한국어 | 84.7% | 87.1% |
| 긴 맥락 | 91.3% | 87.3% |

holdout 질문형은 응답률 9.1% → 81.8%, 정밀도 66.7% → 77.8%다.

- **고친 것과 깨진 것**: 고친 것은 96건(tuning 73, holdout 23), 깨진 것은 18건이다.
  - 깨진 18건 중 9건은 수정 전후 핵심어가 똑같다(QR 코드, 기사 요약 등). 두 실행 사이 약 2시간 동안 운영 DB의 헬스 상태가 바뀐 탓으로 본다. 평가가 실시간 DB를 읽는 한 이 정도 잡음은 남는다.
  - 나머지 9건은 핵심어가 틀린 것에서 맞는 것으로 바뀌었다. 예: "travel startup tooling keeps failing" → "validate site tls configuration", "there" → "render site mobile screenshot".
  - 이 9건이 수정 전에 맞았던 것은 우연이었다. 지금 남은 실패는 순위 문제(단계 2)다.
  - 긴 맥락 정밀도가 줄어든 것도 같은 이유다. 응답률은 71% → 73%로 올랐다.
- **응답 시간**
  - 같은 요청끼리 비교한 중앙값이 7~9% 늘었다. 5초 초과는 40 → 54건이다.
  - 측정 중 load average가 약 6이었다(다른 세션 작업 동시 실행). 수정 탓인지는 가려내지 못했다.
  - 원래 5초를 넘던 긴 요청(8~14초)은 Chat 정책(RAG 5초) 위반이다. 단계 5에서 따로 다룬다.
- **남은 흔들림 2건**(flight_status-typo, text_diff-ko0): 캐시는 같은 프로세스 안에서만 듣는다. 첫 호출이 실패하면 다음 호출이 성공 결과를 다시 만든다.
- **결론**: 정밀도 99%까지는 아직 멀다(tuning 87%, holdout 85%). 남은 실패 대부분은 "핵심어는 맞는데 1위가 틀림"이다. 단계 1(재현율 54% 개선)과 단계 2(재순위)가 필요하다.

### 6.6 다음에 할 것
- **평가 자동화**(전문가 재평가 A-3)
  - 정책 해시 파일이 바뀐 릴리스는 `release_gate`에서 이 1k 세트의 holdout을 돌린다.
  - 정밀도가 기준선보다 1%p 넘게 떨어지면 배포를 막는다.
  - 1회 약 20분이라 frontend 게이트에 넣으려면 holdout 표본 100건 정도로 줄여야 한다.
- **조건 줄 표시**(4.1-3)
  - 조건이 없는 일반 과업도 "대상: flight status"처럼 무엇이 과업 핵심과 맞았는지 적는다.
  - fast_chat의 merged_fit(조건 확인 결과)을 그대로 쓰면 된다. 화면 문구는 frontend 세션과 맞춘다.
- **단계 1**: 문서 확장 시험. 재현율@50이 54%라서, 검색 단계에서 놓치는 것이 가장 큰 손실이다.
- fast_chat의 `merged_fit`·`subject_first`(ecfc00dc)는 단계 2의 재순위가 대체할 때까지 둔다.
