# 테스트 결과 보고서 검증 및 품질 개선안

판정: **최신 30건의 저장·연결 정합성은 정상이나, 실제 업무 수행 품질을 보증하는 보고서는 아니다. 생성기의 검증·성공 판정·재평가 정책을 보완해야 한다.**

검증 기준 시각: **2026-10-26 18:44:34 KST**. 운영 DB는 PostgreSQL 읽기 전용·repeatable-read 스냅샷으로 조회했다. 보고서 전체 3,804건, 최근 24시간 2,546건, 최신 배치 30건을 구분했다. 이후 데몬이 만든 보고서는 이 고정된 집계에 포함하지 않는다.

운영 보고서·에이전트·스케줄·프로세스는 수정하지 않았다. 실제 제공자 재호출·도구 실행·과금도 하지 않았다. 이번 요청의 결과물은 검증과 개선 설계이며 운영 수정을 적용한 결과가 아니다.

## 1. 실제 확인한 현재 동작

- 데몬은 배치를 실행한 뒤 **종료 후 1,800초를 쉰다**. 따라서 고정된 30분 시작 간격이 아니다.
- 한 배치 목표는 **A2A 15개 + MCP 15개**, x402 제외다. A/B 등급·활성·healthy인 미보고 후보에서 무작위로 선택한다.
- A2A는 GET으로 카드 정보만 확인한다. 실제 메시지/작업은 실행하지 않는다.
- MCP는 initialize → initialized notification → tools/list까지만 확인한다. 실제 tools/call은 하지 않는다.
- 통과한 후보만 초안을 만들고, 관리자 API로 등록한 뒤 다시 읽어 lint를 실행한다.
- 보고서 범위는 `transport`, 품질 점수·등급은 null이다. 문서에도 실제 작업/도구 실행을 하지 않았다고 명시한다. 이 제한을 밝히는 점은 올바르다.

서버의 카탈로그 평가 등급과 이 보고서의 품질 점수는 별개다. 후보를 A/B로 골랐다는 사실이 이번 보고서에서 업무 정확성을 평가했다는 의미는 아니다.

## 2. 저장 데이터와 공개 조회 검증

### 최신 30건: #4093–#4122

작성 시각은 18:31:47–18:33:27 KST이며 A2A 15건·MCP 15건이다.

- 에이전트 이름·종류·주소 연결 30/30 일치.
- 생성·시작·종료 시각의 역전/미래값 이상 0건.
- JSON 필드 파싱, 지연 시간 숫자, Pros/Cons 구성 이상 0건.
- 전체 동일 공급자 주소 기준 중복 그룹 0건. 최신 30건 동일 출력 중복도 0건.
- 30건 모두 transport이며 새 품질 등급을 임의로 부여하지 않았다.
- 실제 실행 증거로 오인하지 않도록 공개 projection은 `historical_record`, `execution_verified=false`다.

따라서 **보고서가 잘못된 에이전트에 붙었거나, 이 배치에서 실행 성공 증거를 위조한 문제는 확인되지 않았다.** 다만 프로브가 수집한 응답의 진실성·업무 정확성은 이번 저장 정합성 검사로 증명되지 않는다.

### 전체 이력: 3,804건

- transport 2,950건, legacy 854건. 현재 버전에 결합된 `execution`/`contract` 보고서는 **0건**이다. 플랫폼 전체 capability evidence가 없다는 뜻은 아니며, 보고서 레코드의 분류에 관한 집계다.
- 현재 카탈로그와 연결이 달라진 이력 4건: **#25, #38, #2404, #3011**. 현재 공개 projection에서 모두 제외된다. 최근 24시간에 생성된 2건은 이름 변경으로 현재 카탈로그와 다르다. 잘못된 연결 노출을 막는 보호는 작동하며, 원본을 임의로 새 에이전트에 재결합하면 안 된다.
- 현재 healthy/reachable이 아닌 자원 관련 보고서 83건, 현재 비활성 5건. 생성 당시의 성공을 부정하는 자료는 아니며 **과거 보고서를 현재 상태 보증으로 해석하면 안 되는 이유**다. 두 집합은 중복될 수 있다.
- legacy 854건은 실행 시작/종료 시각이 없다. legacy 98건은 output_wire가 비어 있고, 20건은 Pros/Cons가 JSON 배열 형식이 아니다. 호환 렌더링이 있더라도 재현 가능한 실측 품질 근거로 승격하지 않는다.
- 공개 projection 데이터에 한글이 포함된 보고서 7건: **#265, #1542, #2826, #2881, #3334, #3722, #3780**. 대부분 외부 도구 설명·다국어 예시이며 일부 과거 장단점 문구다. 공식 공개 API에서 #2826·#3334가 한글을 포함한 상태로 전달됨을 확인했다. 영어 설명과 원본 증거를 분리하는 보완이 필요하다.
- 내부 문자열 정규식은 공개 데이터 5건을 표시했지만, 개별 대조 결과 localhost 예시 명령·입력 검증 설명이었다. **이 서비스의 실제 내부 주소·자격증명 유출로 확인된 것은 아니다.** 원본 증거와 사람용 설명을 나눠 표시하는 편이 낫다. 정규식 경고를 곧바로 보안 사고로 집계하지 않았다.
- 서로 다른 주소의 동일한 비어 있지 않은 output_wire 그룹은 24개다. 동일한 도구 제품/복제 서비스도 원인이 될 수 있어 이 사실만으로 조작으로 판정하지 않았다.

## 3. 생성기의 실제 문제와 위험

### P1 — 성공 판정과 실제 검증 수준이 약함

**업무 품질 측정 부재.** 연결·도구 목록만 확인하므로, 원하는 요청을 처리하는지·출력이 정확한지·다음 에이전트가 사용할 수 있는지는 검증하지 않는다. 최신 30건이 모두 통과했다는 사실을 품질 성공률 100%로 사용할 수 없다.

**프로토콜 오탐/누락.** 합성 응답으로 다음을 실제 재현했다.

1. MCP의 JSON-RPC 버전/응답 ID가 잘못되고 protocolVersion·inputSchema가 잘못돼도 성공으로 처리한다.
2. A2A에서 name+url만 있는 불완전한 카드도 통과한다. 지원 버전에 맞는 카드 스키마 검증이 없다.
3. SSE에서 응답 앞에 notification이 오면, 첫 JSON data를 읽어 실제 요청 응답 대신 사용한다. 정상 서버도 잘못 실패할 수 있다.

**실패해도 프로세스 성공.** API 저장 실패는 failed 카운터만 올리고 종료 코드는 0이다. 적합 후보가 없어 초안 0건이어도 정상 종료한다. read-back lint 경고도 저장 성공 카운터를 올린다. 상위 데몬은 반환 코드만 보고 성공으로 기록하므로, 장애/미달 배치를 성공으로 오인할 수 있다. [오프라인 재현 5건](offline-reproductions.json).

### P1 — 별도 수집기의 네트워크·권한 경계

초기 URL만 DNS 검사하고 urllib 기본 redirect를 따라간다. 리디렉션 후 주소 재검증·연결 IP 고정이 없어 재바인딩/내부망 이동에 대한 방어가 충분하지 않다. 실제 내부망 요청으로 공격 재현하지 않았다. 기존 관리형 게이트웨이의 SSRF·응답 크기·시간 제한 경계를 재사용해야 한다.

예약 작업이 DB에 관리자 세션을 직접 만들고 삭제한다. 토큰 자체를 출력하는 코드는 아니지만 사람 계정 역할을 재사용하고 권한·세션 수명 관리를 우회하는 구조다. 실패/강제 종료 시 정리도 보장되지 않는다. 전용 작업 주체, 보고서 작성 한정 권한, 짧은 서버 발급 권한과 감사 이력으로 대체하는 것이 적절하다.

### P2 — 실패 표본과 시간·출처 추적 부족

- 실패·타임아웃 후보는 저장하지 않으며, 이미 보고된 동일 공급자는 이후 배치에서 제외된다. **성공 편향 + 기존 보고서 재평가 부재**가 생긴다. 신규 보고서가 늘어도 기존 보고서의 신뢰도가 갱신되는 것은 아니다.
- MCP 지연 시간은 initialize+tools/list 두 응답 시간의 합으로, 중간 initialized 요청을 포함한 전체 경과 시간과 다르다. 최근 24시간 MCP 1,273건의 누락 경과 시간 중앙값은 **510ms**다. 최신 15건의 보고 지연 중앙값은 1,286.8ms, 전체 경과 중앙값은 1,965.9ms다. 두 중앙값의 차이를 개별 누락 시간 중앙값과 혼동하지 않는다. `wall_ms`와 단계별 지연을 별도로 기록해야 한다.
- 원본 응답은 일부 필드·도구 10개, 설명 200자로 축약된다. 전체 응답/스키마 해시·파서 버전·평가 케이스·validator 버전·배치 ID가 없어 같은 결론을 독립 재현하기 어렵다.
- 후보는 A/B·현재 정상만 대상으로 고르므로 서비스 전체 분포를 대표하지 않는다. 보고서 모두 성공이라는 사실로 전체 카탈로그 안정성을 추정할 수 없다.

### 배치 운영 대조

최근 24시간 데몬 로그에는 시작/완료 **44회**, 생성 **1,318건**, failed=0이다. 42회는 30건, **2회는 29건**인데 성공으로 기록됐다. 시작 간격은 **최소 31.0분 / 중앙값 32.87분 / 최대 34.72분**이다.

같은 DB 기간에는 verification_probe 2,546건이 있어 해당 데몬 로그 생성 수보다 **1,228건 많다**. 수동/다른 실행이 포함됐을 수 있으며 이 자료만으로 중복 데몬이나 오류라고 단정할 수 없다. 현재 확인한 standalone daemon은 1개다. batch_id·runner_id·attempt_id가 보고서에 없어 생성 경로를 정확히 회계할 수 없다는 점이 문제다. [운영 로그 집계](schedule.json).

## 4. 논문·SNS 기반 개선 설계

### 근거

- [τ-bench, 2024](https://arxiv.org/abs/2406.12045): 대화 후 실제 목표 상태와 비교하며 여러 번 모두 성공하는 `pass^k`로 일관성을 측정한다. 한 번의 접속 성공과 반복 가능한 업무 성공을 구분해야 한다는 근거다.
- [Towards a Science of AI Agent Reliability, ICML 2026](https://arxiv.org/abs/2602.16666): 단일 성공 수치가 놓치는 일관성·강건성·예측 가능성·안전성을 분리한다. 본 서비스도 grade 하나보다 수행 정확성·스키마 준수·지연·실패 방식의 근거를 함께 기록하는 편이 적절하다.
- [Anthropic: Demystifying evals for AI agents](https://www.anthropic.com/research/demystifying-evals-for-ai-agents): 코드·모델·사람 평가를 조합하고, 모델 채점은 사람 기준으로 보정한다. 작업별 목표 상태와 결과를 검증하고, 능력 측정과 회귀 방지를 분리한다.
- [Hamel Husain의 LinkedIn 게시물](https://www.linkedin.com/posts/hamelhusain_06-why-is-error-analysis-so-important-activity-7480727440705613825-EcLg): 실제 오류 분석이 무엇을 측정할지 결정한다는 실무 의견이다. [원저자의 상세 가이드](https://hamel.dev/blog/posts/field-guide/)와 교차 확인했다.
- [Reddit 운영 평가 경험](https://www.reddit.com/r/LLMDevs/comments/1rweggk/what_broke_when_i_evaluated_an_ai_agent_in/): URL·네트워크·인증 오류와 모델 결과 오류가 섞이는 문제, 지연 변동·출력 형식 변동을 논의한다. 개인 경험이므로 일반화된 수치 근거로 쓰지 않고 실패 분류 설계 참고로만 사용했다. X도 검색했으나 직접 확인되지 않은 재게시물은 핵심 근거로 채택하지 않았다.
- [MCP 2025-03-26 lifecycle](https://modelcontextprotocol.io/specification/2025-03-26/basic/lifecycle), [tools 명세](https://modelcontextprotocol.io/specification/2025-03-26/server/tools): 현재 생성기가 요청하는 버전을 기준으로 응답 ID·버전 협상·초기화·도구 스키마·페이지네이션 검증을 설계한다. 추후 버전은 별도 프로필로 추가하고 단순 문자열 치환하지 않는다.

위 자료의 연구 결과를 이 서비스의 성능 수치로 전용하지 않았다. 다음 설계는 현재 소스·관측 결과에 적용한 제안이다.

### 권장 작업 순서 — 한 번의 평가 파이프라인 보완으로 묶기

1. **배치 진실성·보안부터 고정.** 전용 작업 주체와 게이트웨이 경계를 사용한다. batch/attempt/job ID, 목표/실제 생성/실패/미실행/기존 보고서 수, 종료 상태를 저장한다. 0건·미달·저장/읽기 검증 실패는 partial/failed로 남긴다. 단일 실행 lease와 고정 시작 시간, 지난 슬롯 건너뛰기로 중첩 실행을 막는다. HTTP 실패·인증 필요·정책 차단·계약 실패·timeout/unknown을 구분한다.
2. **프로토콜 검증기와 증거 레코드 통합.** 기존 capability registry/evidence와 연결 버전 핀을 재사용한다. RPC ID/버전/오류·SSE·페이지네이션·전체 스키마를 검증한다. 응답 원본은 비공개·크기/보존 제한·민감 정보 제거 후 해시로 보존하고, validator/dataset/case ID와 시작/종료/단계별 지연을 결합한다. 공개 문서는 이 증거에서 생성한다.
3. **보고서 1개 정책은 유지하고 재평가 이력을 추가.** 공급자별 공개 보고서 header는 유지하며 그 아래 immutable evaluation attempts를 추가한다. 기존 unique subject guard를 없애거나 과거 기록을 덮어쓰지 않는다. 신규·재평가·실패·버전 변경을 한 경로로 기록하고 현재 성공/실패를 함께 반영한다. 4개 과거 불일치는 사유를 표시하고 안전하게 이력으로 보존한다.
4. **승인된 실제 읽기 작업 + 의미 계약 평가.** 안전한 도구/작업 allowlist와 명시적 권한이 있는 대상만 실제 실행한다. 기존 news/docs/products 계약과 검증기를 재사용한다. 정상·경계·잘못된 입력을 구성하고 입력 반영, 출력 스키마, task relevance, 근거 URL/출처 시각, 후속 노드 수용 가능 여부를 검사한다. 미실행은 N/A이며 실패나 성공으로 속이지 않는다. 쓰기·광고·결제·민감 입력은 자동 평가에서 제외한다.
5. **업무 품질·반복 신뢰도 보강.** 결정적 schema/known-answer/출처 검증을 먼저 적용하고, 개방형 답변에만 항목별 rubric과 제한된 LLM judge를 사용한다. 사람 판정 표본으로 채점기를 보정하고 원문에서 발견한 지시를 명령으로 따르지 않게 격리한다. 고정 holdout·표현 변경·결과 없음·연쇄 입력 사례, 동일 조건 반복, pass@1과 실제 관측한 all-trials success, 표본 수·Wilson 구간, p50/p95를 보고한다. 독립성 검증 없이 평균 성공률을 거듭제곱해 신뢰도로 공시하지 않는다.
6. **게시 품질과 운영 정착.** 사람용 영어 설명과 원본 wire 증거를 분리한다. 인간에게 보이는 provider 설명·Pros/Cons까지 언어/민감 정보/Markdown 점검을 확장한다. 번역은 원본과 별도 필드에 보존해 사실·단위·도구명을 변조하지 않는다. 공개 배지는 `Connection checked` / `Task tested` / `Contract verified` / `Quality reviewed`처럼 범위를 분명히 한다. legacy를 자동 승격하지 않고 증거 재검증부터 한다. 관리자에서 배치 미달·unknown·드리프트·의미 실패를 추적하고 격리 회귀와 shadow 비교 후 운영 전환한다.

슬롯 예시: 현재 A2A 15/MCP 15를 유지하면서 **프로토콜별 신규 5 + 기존 재평가 8 + 경계/실패 재검토 2**로 시작할 수 있다. 이는 30개 평가 대상의 예시이며 실제 네트워크 요청은 다회 테스트 때문에 더 많아질 수 있다. 시간·호출·제공자별 한도를 먼저 정하고, 한도를 넘으면 미실행으로 이월한다. 고정된 30건 신규 문서 수보다 검증 범위와 증거의 질을 우선한다.
