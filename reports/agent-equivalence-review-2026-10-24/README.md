# 에이전트 기능 동등 그룹과 대체 실행 사전 검토

2026-10-24 · 운영 PostgreSQL 읽기 전용 조사 · 외부 에이전트 호출/운영 변경 없음

## 결론

**가능하다. 다만 ‘스키마가 같은 후보 그룹’과 ‘대체 실행이 승인된 동등 그룹’을 구분해야 한다.** 이름·카테고리·입출력 JSON 모양만으로 서로 대체하면 다른 자산/영역의 결과를 반환하거나 중복 실행을 일으킬 수 있다. 에이전트 전체가 아닌 **특정 도구 또는 A2A skill의 버전**을 그룹 단위로 삼고, 기능 의미·입력 허용 범위·출력 계약·대상 문맥까지 검증하는 방식을 권장한다.

현재 폴백 전역 제어는 **꺼짐(enabled=0, revision=0)**이며 설정된 워크플로 정책도 없다. 조사 중 활성화하지 않았고 그룹을 운영 DB에 등록하거나 원본 에이전트/계약을 수정하지 않았다. 아래 후보는 메타데이터 분석 결과이며 실행 권한이 아니다.

## 동일 주소·동일 장애 영역 제외 조건 반영 (추가 요청)

**같은 주소가 다른 에이전트 이름으로 등록된 경우는 독립된 대체 에이전트로 인정하지 않는다.** 후보 분석 코드에 다음 기준을 반영해 다시 집계했다. 현재 런타임/운영 DB의 그룹·정책에 적용했다는 뜻은 아니다.

- URL 호스트 대소문자/IDNA·끝 점, 기본 포트, 보수적인 끝 슬래시 정규화로 동일 주소 별칭을 하나로 합친다. 이름/등록 ID가 달라도 같은 주소면 대체 멤버를 늘리지 않는다.
- 최초 파일럿은 **같은 호스트의 다른 경로·쿼리·포트·HTTP/HTTPS**도 대체 대상으로 서로 남기지 않는다. 주소별 대표를 고른 다음 호스트별 대표를 하나만 남긴다. 서로 다른 호스트가 2개 미만이면 그룹 후보에서 제외한다. 이 규칙은 독립된 서비스가 같은 호스트에 있어도 제외하는 보수적 초기 정책이다.
- 다른 호스트도 같은 원본 서버/CNAME·운영 서비스·상위 API/데이터 공급자·공유 인증/요청 한도에 의존하면 장애가 함께 날 수 있다. 검증된 공통 장애 영역은 같은 것으로 묶어 주/대체에 함께 넣지 않는다. 공유 CDN IP 하나만으로 동일 서버라고 확정하지 않으며, DNS/IP/인프라 독립성은 이번 조사에서 검증하지 않았다.
- 따라서 남은 모든 후보의 **independence_status는 unverified, routing_approved는 false**다. 주소만 다르다는 이유로 자동 승인하지 않는다. 독립성이 확인되지 않으면 첫 파일럿의 실행 대상에서 제외한다.
- 실제 선택 시에는 최근 실패·dead/down·열린 circuit·격리된 원천을 제외하고, 실행 직전에 주소/버전/계약/권한/가용성을 다시 확인해야 한다. 주 에이전트 장애를 관측하면 같은 주소·확인된 장애 영역의 모든 별칭도 후보에서 제외한다. 독립 제공자까지 동시에 장애가 나지 않음을 절대 보장할 수는 없으며, 적격 대체가 없으면 무의미한 순환 대신 안전하게 중단·안내해야 한다.

**같은 스냅샷의 주소 필터 전후:** 원시 스키마 후보 **1,865개 → 서로 다른 호스트를 가진 후보 526개**로 줄었다. **1,339개 그룹 제외 = 같은 주소만 남은 164개 + 다른 주소지만 같은 호스트뿐인 1,175개**다. 서로 다른 호스트에서 활성·healthy/reachable 대표가 2개 이상인 후보는 505개지만 최신 실호출·기능 동등성·장애 독립성 승인은 아니다.

도구별 멤버십에서 동일 주소 별칭 179개와 같은 호스트의 다른 주소 32,579개를 중복 대체 멤버에서 제외했다. 이 수는 여러 도구 그룹에 중복되는 멤버십 수이며 고유 에이전트 삭제 수가 아니다. 원본 카탈로그는 삭제·수정하지 않았다.

정규화·이름 변경 별칭·같은 호스트의 다른 경로/포트/스킴·무효 주소·대표 선택 등 **오프라인 검사 8건을 통과**했다. 현재 전역 폴백은 계속 꺼져 있다. DNS/실호출/실제 장애 유도나 런타임 차단 기능의 동적 검증은 수행하지 않았다. 근거: [재집계](inventory.json), [8건 검사](address-checks.json), [실행 기록](inventory-address-run.txt).

**구현 시 필수 조건:** 현재 R-06 configure는 서로 다른 resource_id를 요구하지만 같은 URL/호스트의 별칭까지 배제하는 규칙은 없다. 그룹 작성 단계와 실제 dispatch 직전 **두 곳 모두** 위 배제 규칙을 공통 판정기로 적용해야 한다. 기존 reliability_routing의 host_key/상관 장애 분류는 재사용할 수 있으나 이는 zero-dispatch 기능이며 실제 실행기의 적용을 대신하지 않는다. 이번에는 조사/후보 분류만 보완했다.

## 최초 주소 필터 전 조사 결과 (과거 스냅샷)

`inventory-before-address-exclusion.json`에 보존한 최초 반복 읽기 스냅샷에서 총 자원 152,740개(A2A 51,188 / MCP 37,425 / x402 64,127)를 확인했다. 수집기가 계속 동작하므로 다른 시각의 조회 건수와 조금 달라질 수 있다.

MCP 중 저장된 전체 도구 메타데이터가 있는 **20,446개 자원 / 272,173개 도구**를 전수 순회했다. 이는 모든 자원에 완전한 입출력 계약이 있다는 의미는 아니다.

- JSON 객체로 표현된 inputSchema·outputSchema가 모두 있는 도구: **76,705개**.
- 이 조건을 충족하지 않는 도구: **195,468개**. 필드 누락/비객체 스키마를 함께 포함한다. 모든 경우를 잘못된 프로토콜로 판정하지 않는다.
- 프로토콜 MCP + 정확히 같은 도구 이름 + 동일 입력 스키마 + 동일 출력 스키마로 묶고 서로 다른 자원이 2개 이상인 **후보 그룹 1,865개**를 발견했다. 동일 자원이 여러 도구 그룹에 속할 수 있어 에이전트 1,865종이라는 뜻은 아니다.
- 활성 자원이 2개 이상인 그룹: **1,834개**. 이는 현재 호출·계약 검증 통과 수가 아니다.
- 명시적 readOnlyHint=true/destructiveHint=false/idempotentHint=true 자원이 2개 이상인 그룹: **1,023개**. 이 값도 제공자 선언의 집계이며 안전성 승인 수가 아니다.
- 좁은 형식의 출력 구조를 가진 것으로 보수적으로 분류된 후보: 1,474개. ‘generic_schema’는 기술적 필터 휴리스틱이며 JSON Schema 의미 동등성 판정이 아니다.
- 엄격한 읽기 선언과 기존 안전 도구 정책을 통과하고 **현재 폴백의 news.search.v1/docs.search.v1 원본 스키마에 정확히 일치하는 저장 도구 후보는 0개**였다. 이를 다른 계약·어댑터까지 포함한 전체 가능성 0으로 해석하지 않는다.

조사 기준은 JSON 키 정렬 후 해시이며 스키마 내부 배열 순서/설명은 보존한다. 따라서 실제로 호환 가능한 도구를 놓칠 수 있다. 반대로 같은 스키마/도구 이름은 의미 동등성을 증명하지 못한다. 결과에는 상위 30개 그룹의 제한된 예시만 저장했으며 1,865개 그룹을 운영에 게시하지 않았다. 프로토콜 버전·인증·상태·동일 제공자·실제 검증은 별도 관문이다.

### 직접 확인한 잘못된 그룹화 예

`SPCXx`(65262)와 `MEITx`(65268)의 `holders`는 입력 필드가 둘 다 limit/offset이며 원본 입출력 스키마가 동일하다. 하지만 도구 설명은 각각 다른 자산의 보유자 정보를 반환한다고 명시한다. `price_history`도 tf/limit을 받아 서로 다른 자산의 시세를 반환한다. 즉, 동일 입력을 다른 연결에 보내면 **다른 자산 결과**가 나오는 구조다.

이 계열은 도구별로 3,321개 자원이 같은 스키마 후보에 묶이지만 원천 호스트는 1개다. 자산 식별자를 포함한 의미 문맥으로 분리해야 하며 동일 호스트 장애의 독립 대안이라고 표시하면 안 된다. 참고: `context-collision.json`(공개 자산 계약 주소는 생략).

## 기존 구현을 활용할 수 있는 범위와 부족한 부분

`agent_market/workflow_fallback.py`는 이미 명시적 주/대체 쌍, 버전·승인 고정, 최신 실행·계약 증거, shadow 선행, 실행별 입력 공유 동의, 제한된 canary, 실행당 최대 1회 대체 및 kill switch를 제공한다. 최초 구성에서 양쪽 성공 증거를 요구하며 승인된 canary에서는 주 에이전트의 확정 장애 때문에 후속 대체가 막히지 않도록 구현돼 있다. 그룹을 고르는 UI와 이 실행 권한을 분리해서 재사용하는 것이 효율적이다.

다만 현재 지원 대상은 **news.search.v1/docs.search.v1의 stateless MCP**이며 카탈로그 전체에서 자동으로 동등 그룹을 찾아 실행하는 기능은 없다. 공개 테스트·일반 게이트웨이·워크스페이스 typed/private 실행으로 자동 확장되지 않는다. compiled/composition 초안은 명시적으로 제한돼 있다. 별도 `reliability_routing.py`는 offline/decision_shadow의 **zero-dispatch** 판단 기능으로, 실제 대체 실행기가 아니다. Cloudflare→Origin 전달 경로 폴백도 에이전트 교체와 별개다.

### 승인된 문서 검색 연결 2개

현재 승인 이력은 `docs.search.v1`의 Paper Finder(34807, search_papers)와 자체 Research Papers(133019, search_research_papers) 두 연결이다. 읽기 전용 facade로 현재 `FallbackRouter.pin()`을 그대로 호출한 결과 **둘 다 현재 폴백 적격이 아니다.**

- 두 연결 모두 현재 버전은 승인된 버전과 같고 고정된 검토 어댑터가 있다.
- 두 연결 모두 원본 도구 입출력은 docs.search.v1과 다르다. 기존 R-06 pin/execute는 이 원본의 정확한 스키마 일치를 요구하므로 현재 어댑터가 있다는 사실만으로 통과하지 않는다.
- 계약 성공 증거는 둘 다 유효 기간이 만료됐다. Paper Finder의 최신 실행은 unknown이고 만료됐으며, 자체 Research Papers는 조회 당시 최신 성공 실행은 유효하지만 계약 증거는 만료 상태다.
- 현재 실제 pin 적격 연결 수는 0개이며 승인된 주/대체 쌍을 바로 켤 수 없다. 근거: `approved-check.json`.

최초 파일럿으로는 이 두 **공개 논문 검색 도구**의 어댑터 정규화 경로를 검증하는 것이 효율적이다. 하지만 기능 범위·출처 신뢰성·원천 독립성과 실호출 결과가 먼저 통과해야 하며 현재 품질이 같다고 승인하지 않는다. 자체 구현은 Crossref를 조회한다. 상대 연결의 데이터 범위/원천은 별도 확인이 필요하다.

입력 범위도 다르다. 현재 Paper Finder는 query 최대 200자, limit 최대 10이고 자체 Research Papers는 query 최대 500자, limit 최대 5다. **공통 계약은 최소한 query≤200, limit≤5** 범위부터 검증해야 한다. 추가 연도/open-access 필터는 양쪽에서 같은 의미를 보장하기 전에는 포함하지 않는다. ‘docs.search.v1’라는 이름만 같다고 허용 입력 전체가 같아지는 것은 아니다. 논문 검색처럼 좁은 의미 프로필/계약을 두어 일반 문서·웹 검색과 혼합하지 않는 것이 좋다.

## 권장 그룹 설계

1. **그룹 정의:** 업무 의미(예: 공개 학술 논문 검색), 버전, 지원 프로토콜/실행 프로필, 정규화 입력·출력 스키마, 언어/시간대/단위, 데이터 범위, 부작용 분류, 최신성 기준을 가진다. 뉴스/논문/제품/종목별 시세 등을 분리한다. 외부 출력 문자열이 완전히 같아야 한다는 조건 대신 필드·의미·품질 불변 조건을 정의한다. 같은 시점/출처를 쓰지 않는 검색 결과의 문장·순서까지 동일함을 보장할 수는 없다.
2. **멤버십:** resource_id + 불변 connection version + tool/skill + 검토 어댑터/구현 해시 + 의미 문맥 해시를 고정한다. 자산·국가·테넌트·계정·데이터셋에 종속된 연결은 문맥이 다른 그룹으로 나눈다. 스키마/바인딩/어댑터/승인이 변하면 자동 격리·재검증한다.
3. **후보와 승인 분리:** 이름/설명/카테고리/벡터 유사도는 후보 검색에만 사용한다. 형식 일치 → 업무 범위 검토 → 고정 공통 입력의 독립 실검증 → 관리자 승인 → shadow 준비 순으로 승격한다. 현재의 제공자 readOnly 선언만 믿고 안전 그룹으로 등록하지 않는다.
4. **방향과 입력 범위:** 완전한 계약 멤버는 같은 계약을 제공해야 한다. 단순한 A→B 부분 호환 관계를 무조건 대칭/전이 그룹으로 합치지 않는다. 입력 범위가 겹치는 경우 공통 하위 계약 또는 요청별 허용 조건을 명시한다. 통화/단위/결측값·날짜를 임의로 만들거나 손실되게 변환하지 않는다.
5. **실행 정책 분리:** 그룹에 속했다는 사실은 실행·입력 공유·과금·개인정보 전송 승인과 다르다. 선택한 버전의 명시적 주/대체 쌍과 원래 동의·권한·grant를 고정한다. 현재 워크플로의 전역 제어/정책/실행별 opt-in을 유지한다. 모든 고객에게 자동으로 전송하지 않는다.
6. **선택과 장애 독립성:** 같은 의미/범위의 적격 멤버 안에서 최신 성공 계약 검증, 현재 가용성, 품질, p95/오류율을 비교한다. 원천 호스트가 같거나 같은 데이터 제공자·인증·장애 영역에 의존하면 독립 대안으로 과대평가하지 않는다. 회원/크레딧 등급으로 의미 호환을 우회하지 않는다.
7. **빠른 조회:** 도구 수십만 개를 매 실행/질문마다 LLM으로 재분류하지 않는다. 수집/스키마 변경 시 증분 후보 해시·그룹 인덱스를 갱신하고 실행에서는 버전 고정된 작은 적격 집합만 조회한다. 현재 pgvector는 의미 후보 발견에 활용할 수 있지만 실행 승인 근거로 대체하지 않는다.

## 권장 구현 순서와 완료 조건

**1. 주소·장애 영역 배제 규칙과 좁은 그룹 계약을 확정한다.** 최초는 MCP 공개 논문 검색 또는 명확한 읽기 전용 분야 1개, 독립성이 확인된 주 1개·대체 1개부터 한다. 동일 주소·호스트·확인된 공통 장애 영역의 별칭은 제외한다. 프로토콜 혼합·A2A 세션·x402 지출·쓰기 작업은 첫 묶음에서 제외한다. Chat의 기본 A2A 추천 정책은 바꾸지 않는다.

**2. 후보 그룹 인덱스와 관리자 검토 화면을 구현한다.** 후보/검증 대기/승인/만료/차단을 구분하고, 공통 입력·출력, 의미 범위·자산 문맥·어댑터·원천 상관관계·검증 시각/제외 이유를 보여준다. 전역 폴백은 계속 꺼 둔다. 전체 후보를 일괄 승인하지 않는다.

**3. 고정 어댑터와 실제 호출 경로를 맞춘다.** 공유 어댑터 레지스트리를 사용해 R-06 pin·dispatch 입력 변환·결과 정규화·계약 검증·체크포인트/복구·관측까지 같은 버전을 사용한다. 단순히 exact-schema 체크만 없애거나 클라이언트가 보내는 매핑/URL을 실행하지 않는다. 워크스페이스 적용은 해당 runtime/동의 경로까지 연결하는 별도 수용 조건으로 명시한다. 기존 typed 연결/정규화 로직을 복제하지 않는다.

**4. 양쪽을 동일 공개 테스트 입력으로 실검증한다.** 정상/빈 결과, 공통 최대값과 경계 초과, 관련 없는 결과, 언어/단위/날짜/출처, 잘못된 스키마, 개인정보·인증·SSRF, 429/확정 오류·전송 후 타임아웃, 버전 변경·권한 철회·중복/프로세스 중단을 검증한다. 실제 성공 증거·계약 증거를 새로 발급하고 품질/지연·제공자 독립성도 확인한다. 이번 조사에서는 제공자 호출을 하지 않았다.

**5. 기존 shadow → 제한 canary를 재사용한다.** shadow는 대체를 호출하지 않고 준비 상태만 확인한다. 기존 상한인 10%/100회/24시간보다 작은 시작값(예: 5%/10회/1시간)을 적용하려면 별도 운영 승인을 받는다. 실제 정책·입력 공유 동의·관측이 갖춰져야 하며 이번 보고서가 활성화 승인은 아니다.

**6. 첫 파일럿 수용 후 범위를 넓힌다.** 잘못된 자산/범위 대체 0건, 계약/권한 위반 0건, 중복 전송 방지, 실제 품질·지연과 롤백을 확인한 뒤 다른 계약 및 A2A에 확장한다. 현재 runtime은 전송 후 결과가 불확실하면 자동 대체하지 않는다. A2A의 messageId 중복 처리가 다른 제공자에게까지 보장되는 것도 아니다. x402/쓰기·지출은 별도 멱등·예산·정산 설계 전 자동 확대하지 않는다.

### 이번 조사로 수행하지 않은 것

운영 그룹 등록/계약 승인, 폴백 활성화/정책 변경, 서버 재시작, 고객 입력 전송, 외부 에이전트 호출, 새 실행·품질 증거 발급은 하지 않았다. 런타임 소스를 변경하지 않았으므로 새 전체 회귀·보안 검증을 수행한 것으로 표시하지 않는다. 실제 구현 단계에서 위 영향 범위의 격리 기능·보안·복구 회귀와 승인된 실검증을 수행한다.

## 공식 근거와 로컬 증빙

MCP 공식 문서는 inputSchema/outputSchema와 structuredContent 검증을 규정하지만 도구 annotation은 신뢰할 수 있는 서버가 아니면 믿지 말라고 명시한다. 따라서 동일 스키마나 readOnlyHint만으로 안전한 의미 동등성을 인정할 수 없다. [MCP tools 사양](https://modelcontextprotocol.io/specification/2026-07-28/server/tools)

A2A의 inputModes/outputModes는 미디어 형식 지원 정보이며 업무 JSON 의미 동등성의 증명이 아니다. Send Message의 멱등 처리는 MAY이며 모든 에이전트의 보편 보장이 아니다. 따라서 상태·문맥·중복 실행 경계를 별도로 검증해야 한다. [A2A 공식 사양](https://a2a-protocol.org/latest/specification/)

## 후속 구현·실행 검증 업데이트

사용자 후속 요청의 [장애 독립성 조사·대체 실행 검증](../agent-fallback-validation-2026-10-24/README.md)을 최신 결과로 사용한다. 후보 526개 전부를 대조했고 381개는 적격 독립 쌍 없음, 145개는 원천/상위 API 독립성이 미확인이다. 운영 승인 가능한 독립 조합은 아직 없다. 기본 주소·호스트/선언된 공통 게시자·원격/검토된 Crossref 의존성 차단은 정책 구성과 실행 경계의 소스에 구현했고 관련 134건 범위 회귀를 검증했다. 임시 실제 TCP 서버의 주 리스너 종료 후 대체 1회 성공도 확인했지만 운영 활성화/외부 독립 제공자 간 대체 성공은 미완료다. 앞선 ‘실행 차단은 후속 구현’은 이 보완분 이전 시점의 기록이며 모든 원천 독립성 검증이 구현됐다는 뜻으로 대체하지 않는다.
