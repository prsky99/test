## 확인한 품질 결함과 원인 범위

- 워크플로우: 문서 검색만 하라고 명시하고 뉴스를 금지해도 뉴스 계약이 포함됐습니다. 문서와 뉴스의 요청 순서를 바꾸는 오류도 관찰했습니다. 허용 에이전트·유효한 연결 구조 검사만으로 요청의 의미를 보장하지 못합니다. 그래프 연결 자체는 서버 컴파일러가 만들므로 모델의 추론 성공으로 간주하지 않았습니다.
- 초기 문서 시나리오는 “문서만” 표현이 덜 명확했습니다. 추가 16동시 시험에서는 이를 명시했습니다. 그중 공격 지시 포함 2건은 HTTP 422, 나머지 정상 요청 14건도 전체 품질 기준을 통과하지 못했습니다. 422의 원문은 해당 부하에서 보관되지 않았고, 단독 재확인은 HTTP 200이어서 원인 확정·보안 차단 성공으로 해석하지 않았습니다.
- 도움말: 저장/동의 질문에 필수 changes 필드를 빠뜨리거나 documents를 중복 작성했습니다. 실행 결과가 불확실할 때의 안내는 관련 문서가 있는데도 정보가 없다고 답했습니다. 목적지 검증 질문에 저장 설명을 반복하기도 했습니다. 실제 어댑터는 형식 위반을 거절하지만, 형식이 맞는 내용 오류는 남았습니다.
- 형식·후보 순서 비교 6건: 동일 문서 전용 목표에서도 후보 순서 또는 json_schema/json_object 변경에 따라 성공·실패가 달라졌습니다. 무제약 응답은 Markdown 코드 블록을 사용해 현재 JSON 파서에서 거절됐습니다. 조건당 1회이므로 특정 형식이 우월하다고 확정할 수 없습니다.
- 현재 공개 Chat은 DB·규칙 기반이며 intent/lead/RAG 모델 어댑터를 사용하지 않습니다. 해당 3개 항목은 기존 어댑터 호환성·용량 시험 결과입니다. RAG 기본 기준 통과는 모든 사실성·제품 문구 정책 통과를 뜻하지 않습니다. 재사용 시 프롬프트가 제공하는 가격/무료 정보 등이 Chat 표시 정책에 맞는지 별도 검사가 필요합니다.

- 워크플로우 비중이 높은 혼합 작업: 동시성 1/4/8/16의 p95 = 15.361 / 17.301 / 21.634 / 24.091초. 16동시 측정 요청 32건, 0.559요청/초, 출력 64.219토큰/초.

서버 지표에서 실제 실행 중 요청 최대 16개, 대기 최대 4개를 관찰했습니다. Metal active 최대 10.01GiB, 서버가 보고한 peak 최대 10.55GiB입니다. 프로세스가 보고하는 메모리 지표이며 전체 시스템 RAM이나 장기 안정성 한계가 아닙니다.

단문은 응답당 약 8토큰, JSON 식별자는 약 23~25토큰이며 프롬프트·형식도 다릅니다. 두 결과 차이를 JSON 형식만의 비용이라고 단정하지 않았습니다. 혼합 작업은 모든 기능이 균등하게 섞이지 않았으므로 기능별 별도 16동시 결과를 우선 참고해야 합니다.

## 실제 앱의 동시 요청 처리

격리 AppFactory에 16개를 동시에 요청했습니다. 현재 프로세스별 생성 제한 2개에 따라 2개가 완료됐고 14개는 WorkspaceConflict로 거절됐습니다. 실제 모델 전송 최대도 2개였습니다. 이는 모델 서버의 16슬롯과 별도 제한이며, 운영 전체 처리량을 단일 프로세스 시험으로 추정해서는 안 됩니다. 외부 에이전트를 실행하거나 저장된 고객 작업을 변경하지 않았습니다.

## 개선 우선순위

1. P0 — 워크플로우 목표에 맞춰 계약 후보를 사전 제한하고, 출력의 계약 종류·순서·단계 수를 의미 검증해야 합니다. 잘못된 결과를 실행·저장하기 전에 차단하고 불완전한 요청은 사용자에게 확인하도록 해야 합니다.
2. P0 — 도움말에 필수 출력 스키마를 강제하고 질문과 근거 문서 일치 검사를 추가해야 합니다. 명확한 정책 질문은 검증된 문서 응답을 우선하고, 생성 실패를 정상 답변으로 표시하지 않아야 합니다.
3. P1 — 복잡한 생성과 짧은 응답의 동시성·대기열을 분리해야 합니다. 현재 2개를 무조건 16개로 높이지 말고, 취소·대기 상태·공정성·기능별 시간 예산을 적용한 뒤 다시 측정해야 합니다. 도움말은 직접 16동시에서 모두 현재 10초 예산을 넘었습니다.
4. P1 — 개선 후 동일 기준으로 회귀하고, 혼합 비율 고정·긴 입력·긴 출력·다중 사용자·스트리밍·장시간 시험을 추가해야 합니다. 후보 순서 변화에도 의도 유지 여부를 포함해야 합니다.

## 검증과 한계

- 계산/모델/워크플로우/공유 보안 회귀 88개 통과, 실제 모델 격리 앱 동시성 검사 1개 통과. 시험 통과는 측정 코드와 보호 동작의 검증이며 제품의 내용 품질 통과를 뜻하지 않습니다.
- 시험 종료 후 모델 healthy, 실행/대기 요청 0개, 공개 홈 HTTP 200, 비로그인 워크스페이스 HTTP 303을 확인했습니다. 운영 서비스 상태 원문은 service-status-after.json에 보관했습니다.
- 시험한 7개 모델 관련 모듈은 현재 활성 프론트엔드 릴리스와 바이트 단위로 일치함을 확인했습니다(source-provenance.json).
- 운영 코드·구성·서버·고객 데이터는 이 시험에서 변경하지 않았습니다. 재시작하지 않았습니다. 합성/공개 입력과 일회성 테스트 DB만 사용했습니다.
- p95는 작은 표본의 선형 보간값입니다. 비스트리밍 전체 응답 시간이며 첫 토큰 지연이 아닙니다. 반복 프롬프트·prefix cache 영향을 포함하고, 이전 모델 동일 기준 실측값이 없어 속도 향상률은 계산하지 않았습니다.
- 초기 직접 부하의 출력 판정은 원문을 실제 어댑터 정규화 규칙에 맞춰 재평가했습니다. 원본 concurrency.json과 재평가 concurrency-regraded.json을 함께 보존했으며 시간 측정값은 수정하지 않았습니다.
