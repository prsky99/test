# 에이전트 방문 채팅의 처리 구조와 응답 분석

2026-10-17 KST · 대상: https://agentconcierge.biz/#chat

이 채팅의 기본 기능은 **작업에 맞는 A2A 에이전트·MCP 서버·x402 API를 검색하고 호출 방법을 안내하는 컨시어지**다. 추천 후보·가격·등급·인증 조건은 카탈로그 DB에서 가져오며, 설정에 따라 로컬 LLM과 RAG가 해석·설명을 보조한다. 질문이 날씨에 관한 것이어도 기본 답변은 날씨 데이터를 제공할 도구 추천이다. 실제 도구 실행은 MCP `call` 등 별도 경로에서 수행한다.

## 확인 범위

공개 HTML을 HTTPS GET으로 읽어 HTTP 200을 확인했다. 배포된 `sendChat()` 코드는 현재 저장소와 일치했다. 프론트는 질문과 방문 토큰을 `/chat`에 보내고 JSON 응답을 렌더링한다.

서버 내부 분기와 모델 설정은 현재 저장소 기준으로 분석했다. 운영 서버에 질문을 제출하거나 관리자 API를 호출하지 않았다. 운영 환경의 모델 활성 여부·현재 추천 결과·실제 답변 속도는 이 확인만으로 확정할 수 없다. 18개 질문 예시는 임시 메모리 DB와 **합성 Demo Weather 카탈로그**로 실행했으며 운영 추천이 아니다. 선택적 LLM 이해 경로는 결정적 모의 객체로 확인했고, 실제 모델의 한국어 성능을 평가한 것은 아니다.

## 1. 화면 진입과 질문 전송

`#chat`은 브라우저 화면 전환용 fragment다. 서버에 `/#chat`이라는 별도 채팅 API가 생기는 구조가 아니다. 처음 보이는 “Hello! I am your autonomous AI agent concierge...”는 HTML에 들어 있는 정적 안내다. 화면을 연 순간 모델이 인사문을 생성하지 않는다.

질문 입력 → 프론트 입력 검사 → 사용자 말풍선 표시 → 로딩 표시 → `POST /chat` 순서다. 기본 본문은 `{"message":"질문"}`이며 저장된 토큰이 있으면 `X-Visitor-Token` 헤더에 넣는다. 응답은 스트리밍하지 않고 JSON 전체를 받은 뒤 표시한다. 네트워크 오류 일부에는 한 차례 재시도한다.

## 2. API·방문자 식별·기억

저장소의 배포 설정에서 외부 HTTPS 요청은 Caddy를 거쳐 에이전트 프론트 앱으로 전달된다. `/chat`은 8400 앱이 담당하며 관리자 8200 앱과 구분된다.

서버는 IP 기반 요청 제한과 보안 검사를 거친다. 본문은 64 KiB 한도이며 엔진에 들어가는 메시지는 최대 2,000자다. 방문 토큰을 SHA-256 해시로 조회해 기존 방문자를 찾는다. 토큰이 없거나 유효하지 않으면 새 방문자와 무작위 토큰을 만든다. 같은 IP·User-Agent라는 이유만으로 예전 대화를 공개하지 않는다.

첫 채팅 응답은 방문 토큰을 헤더와 JSON에 반환한다. 프론트는 토큰을 sessionStorage와 localStorage에 저장하고 다음 요청에 보낸다. 저장된 토큰이 있으면 `/me`로 관심사·연락처·등급 등을 불러온다.

DB는 최근 메시지 200개, 관심사 20개, 마지막 추천 목록·페이지 위치, 실패한 후보, 연락처와 알림 상태를 관리한다. 30분 이상 비활동 후 요청은 새로운 방문 횟수로 계산한다. 단골은 방문일 3일 이상 또는 방문 2회 이상·질문 메시지 10개 이상이다. 단골에게 추천 수 5개, 그 외에는 3개를 제공한다.

**저장하는 대화와 LLM에 전달하는 대화는 다르다.** 현재 의도 추출 LLM에는 현재 메시지만 보낸다. 최근 대화 전체를 모델 문맥으로 전달하지 않는다. `details 1`, `more`, `failed 1` 같은 명시적 명령은 DB의 마지막 추천 목록을 이용해 이어진다.

## 3. 질문의 의도 결정

처리 순서는 다음과 같다.

1. API에서 `data.intent`, `data.task` 같은 구조화된 요청이 오면 우선 사용한다. 일반 브라우저 폼은 메시지만 보낸다.
2. 규칙에 맞는 명령을 찾는다. 확인 코드, stop/resume, SLA·요금, contact, 성공·실패, details, more, what's new, help, 인사 순으로 확인한다.
3. 규칙에 해당하지 않는 자유 문장은 설정된 `LocalLLM.extract()`가 의도·작업·영문 검색어·종류·카테고리·이름을 추출한다.
4. 모델이 없거나 실패하면 규칙과 검색 가능한 영문 단어로 처리한다. 검색할 영문 단서도 없는 입력은 인사·재방문 안내로 돌아갈 수 있다.

모델은 Ollama 로컬 호출이다. 현재 코드의 기본 추출 모델은 `gemma3:1b`, 모드는 `CONCIERGE_LLM=auto`다. `off`이면 비활성화하며 `auto`에서 모델이 발견되지 않으면 의도 추출 LLM을 쓰지 않는다. 이 값이 현재 운영 서버에 그대로 적용됐다는 의미는 아니다.

기본 문구와 생성 프롬프트는 영문 답변을 지향한다. 한국어 이해는 LLM 활성 상태에 크게 의존한다. 인용된 원래 질문에는 한국어가 남을 수 있다.

근거: [의도 규칙과 분기](<저장소>/agent_market/concierge/engine.py:219), [라우팅](<저장소>/agent_market/concierge/engine.py:341), [모델 활성 조건](<저장소>/agent_market/gateway/server.py:113).

## 4. 후보 검색과 순위

찾기 요청은 작업·MCP/A2A/x402 종류·인증 조건·카테고리를 만든 뒤 DB에서 후보를 조회한다. 기본 검색은 FTS5 키워드 검색과 카테고리 보완이며, RAG가 연결되면 임베딩 기반 하이브리드 후보도 합친다.

활성 상태를 요구하고 down·retired·보안 quarantine 후보를 제외한다. 다만 실제 호출 성공(`trial_ok=1`)을 모든 추천의 필수 조건으로 삼지는 않는다. ‘API 키 불필요’ 필터도 인증 필요가 확인된 후보를 제외하며 **인증 상태가 불명확한 후보는 남을 수 있다.** 추천 순간 도구를 다시 실행해 성공 여부를 확인하는 과정은 없다.

종합 점수는 관련도 45%, 인기 10%, 가용성 12%, 가격 7%, 최근 사용 3%, 조건 적합도 8%, 품질 평가 10%, 고객 평가 5%다. 같은 호스트가 목록을 채우지 않도록 호스트별 한 후보를 고른다. 해당 방문자가 실패했다고 기록한 후보는 제외한다.

채팅 `worked 1`은 성공을 기록한다. 이 성공 기록 자체가 즉시 종합 점수에 가산되는 구현은 아니다. 종합 점수의 고객 평가 항목은 별도 `feedback` 데이터를 읽는다.

근거: [검색·추천 변환](<저장소>/agent_market/concierge/engine.py:83), [점수 가중치](<저장소>/agent_market/gateway/ranking.py:18), [필터](<저장소>/agent_market/gateway/store.py:889).

## 5. 답변 생성과 화면 표시

추천 응답은 대체로 다음 순서다.

- 새 방문자라면 에이전트 전용 서비스 소개.
- 선택적으로 LLM 또는 RAG가 만든 요약 설명.
- `Best matches for ...`와 순위별 이름·종류·설명·가격·검증/등급/인증 조건·URL.
- `details 1`, `more`, `worked 1`/`failed 1` 안내.
- 인증된 연락처가 없으면 contact 등록 권유.
- 새 방문자의 토큰 및 재사용 안내.

RAG 엔진이 있고 찾기 결과가 있으면 추천 데이터를 근거로 영문 설명을 만들어 앞에 붙인다. 그 외에는 일부 응답에서 짧은 LLM 도입 문구를 붙인다. 둘 다 작동하지 않아도 규칙 기반 추천 목록과 안내 문구는 제공한다. 생성 모델은 `gemma3:1b`를 시작으로 폴백 모델을 시도한다. `auto`에서 의도 추출 모델이 비활성화됐더라도 별도 RAG 엔진은 연결될 수 있다. 순차 모델 호출로 지연이 누적될 수 있으며 전체 대기 시간이 단일 제한으로 묶여 있지는 않다.

JSON은 `audience`, `reply`, `intent`, `data`, `suggested_replies`, `visitor`로 구성된다. 추천은 `data.recommendations`에, 세부 조회는 `data.recommendation`과 `data.usage`에 들어간다. 본문에는 추천 점수·도구 스키마 등 기계가 활용할 데이터도 포함된다.

화면은 `reply`를 이스케이프한 텍스트로 표시하고 `data.recommendations`를 별도 카드로 만든다. 카드의 Details는 다시 `details N`을 전송하고 Inspect Spec은 에이전트 상세 창을 연다. `suggested_replies`는 클릭 가능한 다음 질문으로 표시된다. Raw JSON 패널과 방문자 ID·등급·방문 횟수도 갱신한다. 일반 채팅 말풍선은 Markdown 렌더러를 사용하지 않아 생성 설명의 `**강조**`가 문자 그대로 보일 수 있다.

근거: [응답 조립](<저장소>/agent_market/concierge/engine.py:305), [반환 구조](<저장소>/agent_market/concierge/front.py:283), [화면 렌더러](<저장소>/extracted_html.txt:6634).

## 6. 질문별 실제 분기 예시

합성 카탈로그·LLM 비활성 상태에서 실행한 결과다. 전체 응답은 `examples.json`, 선택형 화면은 Canvas에서 확인할 수 있다.

- `hi` → 소개·도움 질문·토큰.
- `find a weather forecast API without an API key` → 3개 추천. 같은 질문을 단골로 처리하면 5개.
- `details 1` → 첫 후보의 엔드포인트·프로토콜 연결 순서·도구·인증·최근 시험 정보.
- `more` → 같은 검색의 다음 페이지.
- `worked 1` → 성공 기록. `failed 1` → 방문자별 실패 기록과 대체 후보 탐색.
- `what's new` → 지난 관심사의 개선 후보 비교.
- `서울 날씨 알려줘` → LLM이 없으면 인사. 모의 추출기가 영문 검색어를 제공하면 찾기 경로로 진입함을 확인했다.
- `1번 자세히` → 기존 방문자에게 재방문 안내. 영어 `details 1`처럼 처리되지 않았다.
- `what is the weather in Seoul tomorrow?` → 날씨 API 추천. 실제 예보 결과를 조회해 답하지 않았다.
- `show me only the free ones` → 직전 날씨 조건을 이어받지 않고 새 검색으로 처리되어 예제에서는 0건.
- `find a weather API with pricing information` → 키워드 `pricing` 때문에 자사 Pro SLA 안내로 분기.
- `stop`/`resume` → 알림 중지·재개.

`contact https://...`는 전달 가능한 공개 연락처에 6자리 확인 코드를 보내고, `verify 코드`로 인증한 뒤 알림을 활성화하는 경로다. 이 분석에서는 실제 메시지를 발송하지 않았다. 정기 추천 알림은 개선 후보와 인증된 연락처가 있을 때 단골 24시간·그 외 72시간 간격을 적용하며, 별도 육성 알림 경로도 존재한다.

## 7. 재현된 답변 품질 이슈와 개선 우선순위

**우선: RAG 입력 필드·금액 단위 정합성.** 채팅 추천 항목은 `grade`, `verified_working`을 쓰는데 RAG는 `eval_grade`, `trial_ok`를 읽는다. A등급·실제 시험 성공 후보도 생성 문맥에서 `unrated`, `unverified`가 된다. `price_usdc`의 실제 저장 단위는 micro-USDC지만 RAG는 10,000을 그대로 `10000 USDC`로 쓴다. 같은 추천의 정상 표기는 $0.01 USDC다. 모델에 전달되는 사실 자체가 잘못된 경우이며, 특정 모델이 반드시 틀린 문장을 출력했다고 검증한 것은 아니다. 추천 항목을 RAG 입력 스키마로 정규화해야 한다.

근거: [채팅 추천 스키마](<저장소>/agent_market/concierge/engine.py:120), [RAG 문맥 생성](<저장소>/agent_market/gateway/rag.py:317), `behavior-evidence.json`의 캡처 프롬프트.

**다음: 대화 맥락과 한국어 명령.** DB에 기록된 대화를 모델 입력과 연결하거나 구조화된 검색 상태로 유지해야 한다. 명령의 의미를 이전 추천에 연결하고 한국어 details/more/feedback을 규칙에서도 처리하면 모델 비활성 상태의 품질을 높일 수 있다.

**다음: 요금 키워드의 과도한 우선순위.** 문장 중 `pricing`, `sla`가 있기만 해도 Pro SLA 안내를 반환한다. “이 도구의 가격을 알려 달라”와 “자사 구독 요금제를 알려 달라”를 구분해야 한다.

**다음: 개선 알림의 검증 상태 필드.** 관심사에는 `verified`를 저장하지만 추천 항목은 `verified_working`을 반환한다. 과거 검증 상태가 None으로 남아 개선이 없는데도 같은 후보를 다시 ‘이제 검증됨’으로 판단한다. 동일한 카탈로그에서 `what's new`를 연속 실행했을 때 두 번 모두 3건의 개선 항목이 나오는 것을 재현했다.

근거: [관심사 저장](<저장소>/agent_market/concierge/memory.py:245), [개선 비교](<저장소>/agent_market/concierge/engine.py:133).

추가 정적 확인: 프론트 추천 카드가 가격 미상(None)을 Free로 표시하는 반면 x402 답변 본문은 price unknown을 표시할 수 있다. 소개 문구의 ‘매시간 점검’도 현재 기본 120분 설정 및 일부 SLA 문구와 맞지 않는다. 화면과 엔진의 검증·가격·주기 문구를 동일한 상태 데이터로 생성할 필요가 있다.

PYTHONPATH=. .venv/bin/python reports/chat-analysis-2026-10-17/analyze_chat.py
