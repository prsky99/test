# 탐색·채팅 RAG 성능 및 품질 개선 결과

검증 기간: 2026-10-24~25 KST. 준비 릴리스: `frontend-rag-quality-20261025-r1`.
현재 단계: 사용자 적용 후 운영 릴리스와 실제 공개 HTTPS·브라우저 검증 완료.

## 결론

pgvector 적재만으로 공개 탐색과 채팅에 RAG가 연결되는 구조가 아니었습니다. 공개 탐색의 기존 전문 검색은 넓은 질의에서 대량의 문서에 순위 계산을 반복했고, 채팅은 검색 결과를 요청마다 임시 FTS로 재구성했습니다. 생성 모델을 끄면 임베딩 검색까지 전달하지 않는 연결 조건도 확인했습니다. 이러한 경로를 실제 pgvector와 제한된 전문 검색을 결합하도록 수정했습니다.

사전 운영 API 측정에서 탐색은 12건 중 2건이 HTTP 500이었고, 성공 요청도 11.942~28.949초가 걸렸습니다. 채팅은 12건 중 8건이 HTTP 503이었으며 성공한 일부 추천도 요청과 달랐습니다. DB 최대 연결 24개 중 애플리케이션 연결 21개가 점유되어 있던 문제도 함께 확인했습니다.

사용자가 승인한 이전 대기 프론트엔드·어드민 프로세스 2개만 정리했습니다. 프록시 비연결·처리 중 요청 0건을 확인한 후 종료했고, 운영 경로와 롤백 파일을 유지했습니다. 애플리케이션 연결은 11개로 줄었고 최종 진단에서도 유지됐습니다. DB 재시작이나 최대 연결 설정 변경은 하지 않았습니다.

## 준비 릴리스 검증

동일한 12개 질문을 동시성 3으로 실행했습니다. 준비 릴리스의 격리 HTTP 앱은 실제 운영 카탈로그와 실제 임베딩 서버를 사용하며, 별도 서비스 포트를 열지 않았습니다.

- 탐색: 12/12 HTTP 200, 0.644~1.686초, 중앙값 1.151초.
- 채팅: 12/12 HTTP 200, 0.736~2.255초, 중앙값 1.478초.
- 최종 릴리스 16개 동시 채팅: 16/16 HTTP 200, 1.110~5.160초.
- 영향 범위 API·보안·저장소 회귀 177개, Chromium 브라우저 회귀 37개 통과. 두 집합 합계 214개.
- 공개 프론트엔드 콘텐츠 262개 파일 검사: 위반 0건. 변경 파일 AST·오류 중심 정적 검사 통과. 내장 HTML과 `extracted_html.txt` 일치 확인.

사전 측정은 운영 프록시를 통과했고 개선 후 측정은 준비 릴리스의 격리 HTTP 앱입니다. 질문과 동시성은 맞췄지만 카탈로그가 계속 갱신되고 연결 압박도 정리했으므로, 이를 동일 스냅샷의 엄밀한 모델 성능 비교나 특정 배수 개선으로 해석하면 안 됩니다. 운영 반영 후 공개 경로 확인 결과는 아래 추가 검증 항목에 기록했습니다.

## 수정 내용

1. 탐색·채팅에 동일한 제한형 검색 후보 경로를 연결했습니다. PostgreSQL GIN으로 전문 검색 후보를 먼저 제한하고, pgvector ANN 후보와 RRF로 합칩니다. 전체 카탈로그의 반복 순위 계산과 요청마다 대량 임시 FTS를 만드는 비용을 줄였습니다.
2. 임베딩 쿼리는 1.5초 예산, 동시 처리 제한, 동일 질의 중복 실행 방지, 모델·엔드포인트에 묶인 최대 128개 메모리 캐시를 사용합니다. 임베딩이 응답하지 않아도 전문 검색 경로가 남습니다. 생성 모델 설정과 임베딩 활성화는 분리했습니다.
3. 벡터는 현재 원본·세대·작업·모델·해시가 일치할 때만 사용합니다. 기존 판정과 같은 100개 ID를 읽기 전용 스냅샷에서 비교해 결과가 일치했습니다. 검증을 일괄 조회하도록 바꾸어 해당 표본에서 74.937ms→22.394ms였습니다.
4. 추천 전 기능 일치 조건을 보강했습니다. 한 도구가 실제 작업을 설명하는지, 다른 에이전트의 안내만 반환하는 A2A인지, 날씨 지역 제한·기술 문서 대상·음성 시간표시·번역 언어·지갑 대상 체인·보안 검토 기능 등을 확인합니다. 정확한 이름 검색은 기능 추론과 구분합니다.
5. 채팅은 기존의 최근 성공 검증→최근 활동→품질 순서를 유지합니다. 요금·티어 우선순위를 추가하지 않았으며, 본문에는 안전하게 정리한 기능 설명을 더했습니다.
6. 채팅 DB 동시 연결은 4개로 제한하고 대기를 8초까지 허용합니다. 대기 요청이 있으면 연결을 재사용하고 유휴 시 1개만 유지합니다. DB 연결 상한을 무작정 높이지 않았습니다.
7. 탐색 카드 조회는 읽기 전용이며 연결 버전을 자동 생성하지 않습니다. 테스트 보고서 필터의 기존 정규 보고서 조건을 유지했습니다. 검색 결과 총수는 제한된 후보에서 계산한 경우 추정치로 전달합니다.
8. 추가 조회는 45→90→300개를 확인했고 ID 중복과 앞 페이지 순서 변화가 없었습니다. 빈 탐색에서 특정 제공자가 후보 창을 소진하는 문제는 URL만 먼저 읽어 제공자 다양성을 적용한 뒤 계약 본문을 읽도록 수정했습니다. 프로토콜 필터도 모두 일치했습니다.

## 추천 품질 검토

응답 성공과 추천 정확도를 구분했습니다. 아래는 준비 릴리스 HTTP 응답의 실제 예이며, 외부 제공자를 호출해 작업 결과를 받아본 증거는 아닙니다.

- **docs** — Microsoft Learn MCP: 문서 검색 제공자. Python 라이브러리 범위와 실제 조회 가능한 문서는 제공자 연결 후 확인해야 하며, Python 공식 사이트 전체를 보장하지 않습니다.
- **news** — market.datapackvibe.com/x402/news-technology-product: 기술 뉴스 수집 기능과 일치. 실제 기사 내용 생성·출처 도달 검증은 이번에 실행하지 않았습니다.
- **weather** — io.github.cyanheads/open-meteo-mcp-server: 전 세계 예보 제공자 범위와 일치. 미국·일본 전용 예보가 서울 요청에 추천되는 사례를 배제했습니다.
- **papers** — com.nobleblocks/nobleblocks-mcp: 학술 논문 검색·서지 및 인용 제공 범위와 일치.
- **invoice** — 402.com.tr/api/x402/receipt-parse: 문서·영수증 파싱 계열. 실제 스캔 파일을 업로드한 검증은 수행하지 않았습니다.
- **translation** — com.auto-reader/ocr: 텍스트 번역 도구를 가진 제공자. OCR 서비스 이름만으로 배제하거나 모든 언어 품질을 보장하지 않습니다.
- **transcript** — Brainiall Pronunciation: 음성 전사 기능을 광고하는 제공자. 실행 가능한 스키마가 없으면 도구를 임의로 만들어 표시하지 않습니다.
- **code** — AiScale Agent Services: 코드·diff의 보안 및 품질 검토 도구를 가진 제공자. 단순 에이전트 카탈로그 추천은 배제했습니다.
- **wallet** — agentstoolshub.com/api/v1/crypto/wallet-snapshot: Ethereum/Base 주소의 잔액·거래 수·활동·토큰 보유 현황 조회 제공자. 지속 감시·알림 전달까지 실행되었다는 뜻은 아닙니다.
- **travel** — 추천 없음: 항공·호텔 동시 요청에 현행 안전·신선도 조건을 충족한 단일 추천 없음. 탐색에 후보가 있는 것과 채팅의 단일 추천 자격은 다릅니다.
- **semantic** — Brainiall Pronunciation: spoken interviews→audio transcription 의미를 연결해 후보를 찾았습니다. 실제 음성 업로드는 하지 않았습니다.
- **unsupported** — 추천 없음: 가상의 기능 요청에 관련 없는 여행·메모리 서비스를 반환하지 않고 추천 없음으로 응답했습니다.

현재 Chat 제품은 일반 지식의 장문 답변을 생성하는 챗봇이 아니라, 자연어 요청에 맞는 에이전트 1개와 연결 근거를 안내하는 기능입니다. 이번 16개 동시성 결과는 HTTP 검색·추천 처리량이며 Gemma 생성 모델의 16개 동시 추론 벤치마크가 아닙니다.

일부 MCP 목록은 수집된 도구 스키마가 불완전하거나 로컬 실행 정책이 지원하지 않는 계약을 포함합니다. 해당 도구를 실행 가능하다고 확대 해석하지 않고 빈 도구 목록과 실제 연결 준비 상태를 유지합니다. 검색으로 찾았다는 사실과 외부 실행 성공을 구분해야 합니다.

## 논문·SNS 적용 근거

- [RRF 원 논문](https://cormack.uwaterloo.ca/cormack/cormacksigir09-rrf.pdf)의 서로 다른 검색 순위를 결합하는 방식을 적용했습니다. 결합 점수는 정렬 신호이며 응답 신뢰도 확률로 표시하지 않습니다.
- [BEIR 논문](https://arxiv.org/abs/2104.08663)은 다양한 도메인에서 단일 검색 방식의 성능을 일반화하기 어렵다는 근거입니다. 벡터만으로 바꾸지 않고 전문 검색을 유지하면서 자체 질문·보안 회귀로 검증했습니다.
- [Reddit의 직접 구축 경험](https://www.reddit.com/r/Rag/comments/1vn09ig/what_we_learned_building_hybrid_retrieval_for/)은 키워드·벡터 경로 분리와 순위 결합, 원문 근거 보존이라는 운영 관점에 참고했습니다. 해당 글의 경험을 우리 서비스의 검증된 성능 수치로 사용하지 않았습니다.

## 검증 범위 및 남은 단계

외부 유료 호출·결제·사용자 워크플로우 실행·알림 및 메시지 발송은 하지 않았습니다. 정상 API 요청으로 익명 테스트 대화가 생성됐지만 토큰은 보고서에 저장하지 않았습니다. 임베딩 요청 외에 제공자 실행 요청은 없었습니다.

초기 연속 스트레스 측정 중에는 정상 호출 제한으로 HTTP 429가 발생했습니다. 이를 성능 성공으로 집계하지 않았고 제한을 해제하지 않았습니다. 최종 16개 요청은 별도 격리 앱에서 제한량 이내로 실행했습니다. 초기 2초 DB 대기로 발생한 503도 원시 로그에 남겼으며, 대기·재사용 정책 보완 후 최종 릴리스에서 다시 통과했습니다.

사용자가 준비 릴리스를 프론트엔드에 적용했습니다. 이번 확인 과정에서는 서비스를 중지·교체하거나 이전 대기 프로세스를 추가 종료하지 않았습니다. 롤백 릴리스와 대기 슬롯을 유지한 상태에서 운영 검증을 완료했습니다.
