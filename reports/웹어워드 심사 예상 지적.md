# 웹어워드 심사 예상 지적 (agentconcierge.biz 프론트엔드)

- 작성: 2026-11-01
- 방법
  - 운영 사이트를 앱 내장 브라우저로 직접 점검했다(데스크톱 1240px, 모바일 375px, 다크 테마).
  - 페이지별로 접근성과 구조를 자동 측정했다.
  - API와 페이지 응답 시간은 curl로 쟀다.
- 대상: 홈, Agent Status, Learn, Explore, Test, Workflows, Chat, List Your Agent, 404
- 심사 기준은 웹어워드에서 흔히 쓰는 항목으로 나눴다: 기획·콘텐츠, UX, 디자인, 기술·성능, 접근성, 반응형.

## 먼저 좋게 볼 점 (감점 요인 아님)

- 진주 목걸이 콘셉트(에이전트를 이어 워크플로를 만든다)가 메뉴, 일러스트, 404 문구("Find your next connection")까지 일관되게 이어진다.
- 세리프 제목과 차분한 색 조합이 다른 AI 서비스와 구별된다.
- 다크 테마가 제대로 동작한다.
- 기본 구조가 갖춰져 있다.
  - 모든 페이지에 `lang="en"`, 고유한 제목, 설명 메타, OG 이미지가 있다.
  - h1이 하나씩이고, 본문 바로가기 링크와 header·nav·main·footer 랜드마크가 있다.
  - `:focus-visible`, `prefers-reduced-motion`을 지원하고, 대체 텍스트가 빠진 이미지가 없다.
- 375px 화면에서 가로 넘침이 없다.
- 보안 헤더가 단단하다(CSP nonce, HSTS, frame-ancestors none).
- 숫자 옆에 "About these numbers", 기록 시각, "AI can make mistakes"를 함께 보여 줘서 근거를 투명하게 드러낸다.

## 심사위원이 지적할 문제

### A. 기획·콘텐츠

1. **첫 화면에서 누구를 위한 서비스인지가 엇갈린다.**
   - 같은 주소 `/`가 요청 방식에 따라 다르게 답한다.
     - 브라우저에는 사람용 화면을 보여 준다.
     - 일반 요청에는 "FOR AI AGENTS ONLY. ... not for humans"라는 JSON을 돌려준다.
   - 사람용 화면도 A2A, MCP, x402, "execution check" 같은 용어를 설명 없이 바로 쓴다. 심사위원은 이 사이트의 사용자가 개발자인지 일반인인지부터 물을 것이다.
   - 개선
     - 첫 화면 한 줄에 대상을 밝힌다(예: "AI 에이전트를 만들고 쓰는 개발자를 위한").
     - 용어에는 처음 나올 때 짧은 설명이나 툴팁을 붙인다.
2. **Explore를 처음 열면 품질 낮은 목록이 먼저 보인다.**
   - 기본 정렬이 '최신순'이다.
   - 그래서 맨 위 카드들(Frestis41, Gadani, Klunor, Fruson 등)이 모두 같은 문장을 쓰고 카테고리도 "Other"다: "is an AI agent on Central City, where people and AI agents work together…"
   - 심사위원에게는 "스팸 디렉터리"라는 첫인상을 준다.
   - 개선: 기본 정렬을 품질·검증순으로 바꾸고, 템플릿 문장이 반복되는 목록은 묶거나 낮춘다.
3. ~~같은 질문인데 Chat과 Explore가 다르게 답한다.~~ 결함이 아니라 의도된 설계라 지적에서 뺐다.
   - 11-01 사용자 결정: Chat은 AI가 추천하는 것이고, Explore는 검색엔진 인덱스로 결과를 보여 주는 것이다. 그래서 결과가 다른 것이 맞다.
   - 출품 설명에서 대응할 점
     - 심사위원이 같은 질문을 두 곳에 넣어 보고 차이를 물을 수 있다.
     - 기획서와 화면 문구에 "Chat = AI 추천(검증된 것만 최대 3개), Explore = 전체 색인 검색"이라는 역할 차이를 한 줄로 밝혀 두면 된다.
4. **같은 통계가 여러 곳에 반복된다.**
   - 홈과 Agent Status가 같은 숫자 카드 4개를 보여 준다.
   - 시각에 따라 값이 조금씩 다르다(예: 도달 가능 178,505와 178,494).
   - 전체 수(217,904), Explore 결과 수(96,274), 프로토콜별 수가 서로 어떤 관계인지 한눈에 알 수 없다.
5. **메뉴 이름과 실제 내용이 다르다.**
   - Workflows 페이지 제목에 "Web App Downloads"가 섞여 있다.
   - 메뉴 9개(Agent Status, Learn, Explore, Test, Workflows, Chat, List Your Agent, About, Workspace)가 같은 무게로 나열돼 있다. 핵심 흐름(찾기 → 시험 → 연결)이 드러나지 않는다.

### B. UX

6. ~~검색 중 화면 가운데에 "Finding agents…" 표시가 뜬다.~~ 지적에서 뺐다.
   - 11-01 사용자 결정: 진행 표시는 화면 가운데의 작은 표시가 맞다.
   - 정책 문서도 이에 맞게 고쳤다.
   - 다만 표시가 검색창이나 필터 위에 겹치지 않는지는 화면 크기별로 확인한다.
7. **검색했을 때 결과가 바뀌었다는 것을 알아채기 어렵다.**
   - 검색하면 목록 제목은 바뀐다("Latest Discovered Agents" → "… Search Results").
   - 하지만 결과 목록이 화면 아래에 있어서, 위쪽 검색창을 보고 있는 사용자는 결과가 바뀐 것을 놓친다.
   - 개선: 검색 뒤 결과 영역으로 초점을 옮기거나 스크롤하고, 바뀐 결과 수를 알린다(`aria-live`).
8. **Chat 입력창을 프로그램으로 다루기 어렵다.**
   - 접근성 트리에 나오는 입력창이 화면 밖(0,0)에 있다. 눈에 보이는 입력창과 다른 요소로 보인다.
   - 화면 낭독기와 자동화 도구가 엉뚱한 요소를 잡을 수 있다.
9. **결과가 없을 때 다음 행동을 안내하지 않는다.**
   - Chat은 "No currently verified match…"와 함께 Explore 링크 하나만 준다.
   - 비슷한 결과, 조건을 완화한 결과, 검색어 제안을 함께 보여 주면 나아진다.
10. **404 페이지에 메뉴가 없다.** 상단 메뉴, 검색창, 바닥글이 없고 버튼 두 개만 있다.

### C. 디자인

11. **글자가 작다.**
    - Explore 카드의 보조 정보(카테고리, 등급, 프로토콜 배지)가 11px이다. 12px 미만 텍스트가 한 화면에 137개다.
    - 홈에는 10px 텍스트가 있다.
    - 세리프 제목과 크기 차이가 커서 정보 위계가 '제목과 아주 작은 글자' 두 단계로만 보인다.
12. **카드 정보가 단조롭다.** 카드마다 '설명 2줄과 View details'만 반복된다. 무엇을 할 수 있는지, 바로 써 볼 수 있는지, 무료인지 같은 판단 정보가 카드 앞면에 부족하다.
13. **여백 배분이 고르지 않다.**
    - Workflows와 Test 첫 화면은 위가 비어 있다.
    - 핵심 실행 버튼(Run Workflow)은 첫 화면 아래쪽에 있다.
    - 홈 오른쪽의 진주 일러스트가 모바일에서 화면을 많이 차지한다.
14. **누를 영역이 작은 요소가 있다.** 24px 미만인 요소가 Explore 5개, List Your Agent 7개, Chat 3개다(WCAG 2.2 대상 크기 기준).

### D. 기술·성능

15. **모든 페이지가 무겁다.**
    - 모든 페이지가 같은 거대한 HTML(약 198KB, DOM 2,500~3,000개)을 받는다.
    - 화면에 보이지 않는 다른 메뉴의 입력 요소도 페이지마다 42~48개씩 들어 있다(등록 폼, JSON 편집기, 지갑 주소 입력 등).
    - 첫 응답까지 0.6~2초가 걸려 고르지 않다. Lighthouse의 "DOM 크기 과다"와 "사용하지 않는 코드" 항목에서 감점된다.
16. **같은 요청이 여러 번 나간다.**
    - Explore를 처음 열면 같은 목록 요청이 2번 나간다.
    - Chat 페이지는 `/api/task-updates`를 4번 요청한다.
    - 홈의 숫자 카드는 처음에 "—"로 보였다가 나중에 채워진다. 정책상 허용되지만, 숫자가 늦게 채워지는 동안 레이아웃이 흔들리는지는 따로 확인해야 한다.
17. **화면에서 검색 결과가 늦게 보인다.**
    - API 자체는 처음 보는 검색어에도 0.9~2.2초 안에 답한다.
    - 하지만 화면에서는 3초쯤 지나도 아직 로딩 중이었고, 약 8초 뒤 확인했을 때는 결과가 보였다. 화면에 결과가 나타나는 시간은 따로 정확히 재지 못했다.
    - 3초 목표를 화면 기준으로 다시 재야 한다.

### E. 접근성 (영어권 어워드도 WCAG 기준으로 봄)

18. **Explore 체크박스가 "on"으로 읽힌다.**
    - 대상: Execution checked, No account required, Recorded reports
    - 접근성 트리에 이름이 "on"으로 나온다. 라벨 텍스트가 체크박스 이름으로 연결되어 있지 않다.
19. **색 대비 검증이 필요하다.**
    - 자동 측정에서 Agent Status의 링크 2개("Explore new arrivals", "Explore the catalog")가 대비 1.0대로 나왔다. 배경이 그라데이션이라 오탐일 수 있어 직접 확인해야 한다.
    - 11px 회색 보조 텍스트는 4.5:1 기준에 가깝다.
20. ~~한국어를 지원하지 않는다.~~ 지적 대상이 아니라서 뺐다.
    - 11-01 사용자 결정: 영어 전용 사이트를 영어 웹사이트 어워드에 출품한다.
    - 다국어 지원은 영어 사이트를 완성하고, 사용자가 늘어 서비스가 안정된 뒤에 진행한다.
    - 대신 영어권 심사위원은 영어 문구의 자연스러움을 본다.
      - "Recorded as reachable", "Execution checks", "Connected Intelligence, with Evidence"처럼 내부 용어에 가까운 표현이 있다.
      - 원어민 감수로 다듬을 가치가 있다.

### F. 반응형

21. 375px에서 레이아웃은 깨지지 않는다.
    - 다만 Explore 모바일 첫 화면이 검색 폼과 필터로 꽉 차서, 결과 카드는 스크롤을 한참 내려야 보인다.
    - 필터를 접어 두면 나아진다.

## 권장 작업 순서 (11-01)

순서는 다음 원칙으로 정했다.
- 작고 확실한 것부터 처리한다.
- 측정은 고치기 전에 한 번, 마지막에 다시 한 번 한다.
- 화면 구조를 바꾸는 큰 작업(페이지 분리)은 디자인이 정해진 뒤에 한다.
- 문구 감수는 문구가 더 바뀌지 않을 때 맨 마지막에 한다.
