# 에이전트 품질 평가 업그레이드 (2026-11-03, 품질 정책 v1)

수집 단계의 품질 평가(MCP 규칙 v5, A2A v4, x402 v1)를 최신 연구·커뮤니티 동향과 품질 공학의 원칙으로 다시 점검하고, 증거 기반 등급 정책을 덧씌웠다. 기존 평가 데이터도 네트워크 조사 없이 저장된 정보로 다시 매긴다.

## 1. 기존 평가의 문제 (운영 DB 실측, 11-03)

| 종류 | 평가 수 | A 비율 | 평균 | 비고 |
|---|---:|---:|---:|---|
| MCP | 24,235 | 63% | 86.8 | |
| A2A | 66,574 | 97.5% | 89.7 | 6.4만 개가 시험 메시지 없이 정의만 평가됐는데 점수가 같음 |
| x402 | 128,056 | 88.6% | 90.0 | |

- **등급이 변별력을 잃었다.** A가 대부분이라 A가 무엇을 보증하는지 말할 수 없다.
- **측정하지 않은 것을 인증했다.** 실제 호출을 한 번도 하지 않은 대상도 A를 받았다.
- **점검 1~2번으로 가용성을 판단했다.** A2A 6.2만 개, x402 8.9만 개는 24시간 점검이 1~2회였다. 7일 기록을 보면 중앙값이 A2A 6회, MCP 28회, x402 4회다.
- **경고가 없으면 보안 만점이었다.** 보안·프로토콜·컨텍스트 축 평균이 0.99~1.00이다. 이 세 축(가중치 합 45%)은 대상을 가르지 못하고 점수만 올렸다.
- **판정할 수 없는 측정을 실패로 쳤다.** MCP 시험 실패 6,155건 중 서버 장애(시간 초과·5xx)는 수십 건뿐이었다. 나머지는 아래와 같았다.
  - 응답 형식 불일치 2,699건(우리 쪽 엄격 검사)
  - 우리 시험 인자에 대한 도구 오류
  - 인증·결제 요구

## 2. 조사한 근거

- **도구 설명 결함:**
  - 103개 서버의 856개 도구 중 97.1%에 결함이 하나 이상 있다. 루브릭은 목적·사용 시점·제약·파라미터·완결성·예시다.
  - 설명을 보강하면 성공률이 중앙값 5.85%p 오른다. ([MCP Tool Descriptions Are Smelly, arXiv 2602.14878](https://arxiv.org/html/2602.14878v3))
  - 설명 결함은 LLM의 도구 선택에 8.8~11.6% 영향을 준다. 10,831개 서버의 73%가 설명에서 도구 이름만 되풀이한다. ([Smell-Aware Evaluation, arXiv 2602.18914](https://arxiv.org/abs/2602.18914))
- **신뢰성은 한 번의 성공이 아니라 반복 성공(pass^k)으로 본다.**
  - pass@10 78%가 10회 연속 성공으로는 36%였다. ([On the Reliability of Computer Use Agents, arXiv 2604.17849](https://arxiv.org/pdf/2604.17849))
  - 반복 성공에 섭동과 장애 상황을 더해 보는 틀이 제안됐다. ([ReliabilityBench, arXiv 2601.06112](https://arxiv.org/pdf/2601.06112))
  - [Princeton HAL 신뢰성 결과](https://hal.cs.princeton.edu/reliability/findings)
- **A2A 카드는 자기 신고다.**
  - 서명된 카드도 작성자를 증명할 뿐, 기능의 정확성은 증명하지 않는다.
  - 신뢰는 실행 측정이 필요하다는 데 커뮤니티 의견이 모인다. ([A2A 평판 확장 제안](https://github.com/a2aproject/A2A/discussions/1631), [Runtime attestation 논의](https://github.com/a2aproject/A2A/discussions/1677), [카드 18개 감사](https://dev.to/piiiico/i-audited-18-a2a-agent-cards-17-graded-f-mine-was-the-18th-540n))
- **보안 스캐너 오탐:**
  - 정규식 스캐너 경보의 진양성은 50% 미만이고, 스캐너끼리 결과도 엇갈린다. ([arXiv 2607.11086](https://arxiv.org/abs/2607.11086), [MCP 서버 보안 감사 2026](https://appsecsanta.com/research/mcp-server-security-audit-2026))
  - 기존의 "검토 필요" 신호 계수 0.2를 유지한다.
- **x402 관측 신뢰 점수:** 결제하지 않는 GET 탐침으로 증거를 모으고 "점수는 살 수 없다"는 원칙을 쓴다. ([x402 trust mcp](https://mcp.so/servers/x402-trust-mcp))

## 3. 품질 전문가 관점의 원칙

ISO/IEC 25010의 신뢰성·보안 특성, 측정 시스템 분석, SRE의 SLO 관행을 적용했다.

1. **측정하지 않은 품질은 인증하지 않는다.** 등급은 품질과 그 증거의 충분성을 함께 나타낸다.
2. **표본이 적으면 보수적으로 추정한다.** 점 추정 대신 신뢰구간 하한(Wilson)을 쓴다.
3. **결론이 안 나는 측정은 실패가 아니다.** 측정 시스템의 오류를 대상의 결함으로 돌리지 않는다.
4. **경고가 없다고 안전한 것이 아니다.** 실제 통제 수단을 확인해 반영한다.
5. **변별력 없는 지표의 비중을 줄인다.**
6. **순서를 지킨다.** 등급 상한은 점수를 자르지 않고 눌러 담아, 같은 등급 안의 순위를 남긴다.

## 4. 바뀐 규칙 (`collector/evaluation.py` `apply_quality_policy`, `POLICY_VERSION = "v1"`)

| 항목 | 이전 | 이후 |
|---|---|---|
| 가용성 근거 | 24시간 성공률(점검 3회 미만이면 라플라스 보정) | 7일 헬스체크의 Wilson 하한(z=1). 2/2는 0.67, 6/6은 0.86, 28/28은 0.97 |
| 시험 판정 | 성공/실패(인증은 제외) | 통과 / 조건부(인증·결제) / 실패(시간 초과·연결 오류·5xx) / 판정 불가(형식 불일치·도구 오류 문구) |
| 보안 축 | 100 − 경고 감점 | 경고 감점 85% + 통제 수단 15%(아래) |
| 가중치 | 가용성 25, 정의 20, 보안 20, 컨텍스트 15, 프로토콜 10, 출처 10 | 가용성 25, **정의 25**, 보안 15, 컨텍스트 10, 프로토콜 10, **출처 15** |
| 등급 상한 | 격리 40점만 | 증거 수준별 상한(아래) + 격리 40점 |

보안 통제 수단은 종류마다 다르다.
- **MCP:** HTTPS 엔드포인트, 안전 주석(`readOnlyHint`/`destructiveHint`)
- **A2A:** HTTPS 엔드포인트, 서명된 카드
- **x402:** HTTPS 엔드포인트

증거 수준과 등급 상한:

| 수준 | 조건 | 상한 |
|---|---|---|
| verified | 실제 호출 시험 통과(x402는 402 결제 안내 확인)이고, 7일 점검 3회 이상, 성공률 95% 이상 | 없음 |
| observed | 7일 점검 3회 이상이지만 시험 미통과(시험 없음·조건부·판정 불가) 또는 성공률 95% 미만 | B (84.9) |
| limited | 7일 점검 3회 미만 | B (84.9) |
| failed | 시험이 서버 장애로 실패, 또는 A2A 카드는 뜨는데 엔드포인트가 응답하지 않음 | C (69.9) |

- **상한 적용 방식:** 상한이 있으면 [상한−10, 100] 구간을 [상한−10, 상한]으로 눌러 담는다. 같은 B 안에서도 원래 점수 순서가 남는다.
- **평가에 남기는 정보:**
  - `evidence.level`, `evidence.trial`
  - `raw_score`, `raw_grade`, `raw_at`
  - `stats.uptime_window`, `stats.security_base`
  - 상한이 걸린 이유(발견 사항): `unverified_function`, `insufficient_monitoring`, `unstable_week`
- **적용 경로:**
  - MCP·A2A 조사와 x402 일일 평가는 기록할 때 정책을 바로 입힌다.
  - 기존 평가는 jobs의 `quality_policy_batch`가 id 순서로 한 바퀴 돌며 다시 매긴다(배치 500건, 네트워크 요청 없음). 한 바퀴를 마치면 `quality_policy_done`에 버전을 기록하고 멈춘다.
- **바꾸지 않은 것:** 도구별 정의 루브릭(원 평가)은 그대로 둔다. 규칙 버전(`VERSION`)을 올리면 9만 개를 모두 다시 조사해야 하기 때문이다.

## 6. 남은 과제

- **A2A 시험 메시지 범위 넓히기:** A를 받을 수 있는 A2A가 1.3천 개뿐이다. 시험 메시지를 보낸 에이전트가 적기 때문이다.
- **MCP 응답 형식 불일치 2,699건 원인 조사:** `capabilities._trial`의 엄격 검사가 정상 서버를 걸렀을 수 있다. 원본 상태 코드를 기록하도록 고칠지 검토한다.
- **pass^k 측정:** 지금은 마지막 시험 한 번만 저장한다. 시험 이력을 남겨 연속 성공률을 증거 수준에 넣는 것이 다음 단계다.
- **도구 설명 루브릭 보강:** 논문의 6개 루브릭 중 제약 사항과 예시를 넣는다. 원 평가 버전을 올려야 해서, 재조사 부담을 따로 계획해야 한다.
