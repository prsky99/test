# 운영 분석 후 개선 작업 — 2026-10-19

오늘 운영 분석에서 제시한 다섯 우선순위의 소스 수정을 완료했다. **운영 서버·프록시를 재시작하거나 설정을 적용하지 않았고, 운영 DB의 기존 보고서·인덱스·로그를 직접 정리하지 않았다.** 변경은 사용자가 기존 방식으로 서버를 재시작하고 해당 배포 설정을 반영한 뒤 활성화된다.

## 공개 지표와 검증 의미

홈의 고정 `99.4%`와 고정 그래프를 제거했다. 현재 카탈로그 도달 가능성과 최근 24시간의 실제 실행 증거를 따로 보여준다. 실행 성공·실패·미확정, 반복 실행 건수와 성공 관측 대상 수를 구분하며, 프로토콜 탐색·HTTP 도달 가능·정적 보고서·대기 항목은 실행 완료 건수에서 제외한다. 시간 범위와 UTC 시간대를 표시하고 데이터가 없을 때 성공률을 만들어내지 않는다.

프로토콜별 도달 가능 비율은 미점검 항목도 분모에 포함한다. 비활성 리소스는 공개 활성 집계에서 제외하고, 대상이 없는 프로토콜에는 성공률을 표시하지 않는다. 카탈로그 수는 현재 상태의 짧은 캐시를 사용하며 과거 New York 자정 상태를 재구성한 것처럼 표시하지 않는다. 공개 문서와 연결 안내도 도달 가능성과 실행 검증을 구분하도록 수정했다.

Explore의 `Execution checked` 필터와 검증 목록·배지는 현재 연결 버전·스키마·만료되지 않은 실제 실행 증거를 사용한다. 건강 상태나 시각 없는 `trial_ok`만으로 검증됐다고 표시하지 않는다. 기존 기계용 사실 필드는 보존했다. 브라우저 캐시 버전을 올려 이전의 잘못된 보고서·검증 카드가 재등장하지 않도록 했다. embedded HTML과 `extracted_html.txt`는 동기화했다.

## 보고서 연결과 이력 보호

리소스 ID에 더해 프로토콜·이름·완전한 endpoint·연결 버전과 실제 Registry 실행 증거를 확인한다. 보고서 발행 시각은 실행 시각으로 사용하지 않는다. managed URL의 정수 ID만으로 다른 DB의 에이전트 보고서를 연결할 수 없다. 카드·추천·필터·캐시·상세 조회에서 잘못 연결된 보고서를 제외하며, 현재 검증과 이력 보고서를 구분해 표시한다. 기본 A등급 같은 임의 표시도 제거했다.

SQLite에는 직접 INSERT/UPDATE에 대한 subject 보호를 추가했다. 기존 이력은 삭제하지 않는다. 관리 중인 일곱 정적 seed 진입점은 DB를 열기 전에 중단하고, 새 importer는 명시적으로 고른 DB의 canonical key로 리소스를 다시 찾는다. 기본 동작은 읽기 전용 사전 확인이며 가져온 문서를 실제 실행 증거로 승격하지 않는다. 이번 작업에서 importer를 운영 DB에 적용하지 않았다.

근거: [보고서 연결 구현](report-binding.md).

## 검색 대기열과 실행 관측

비활성·삭제·격리·retired·다른 세대·다른 원문 해시 작업이 앞에 있어도 유효한 인덱싱 작업을 선택하도록 수정했다. 정리·선택 범위는 제한하고 세대·lease·fence·provenance 검사를 유지한다. 대기열 전체를 무제한으로 훑는 대신 관련 인덱스와 제한된 후보 탐색을 사용한다. 운영 인덱스 재구축이나 강제 배치 실행은 하지 않았다.

저장에 성공한 업무의 dispatch·완료 메타데이터는 일시적 저장 경합 시 제한된 FIFO에서 재처리한다. 업무 자체나 외부 호출을 재시도하는 큐가 아니다. 기존 스케줄러 tick·관리자 조회·정상 종료에서 메타데이터를 배출하며 새 작업 스레드를 만들지 않는다. 관리자 화면에는 대기·유실·쓰기 오류·복구 건수와 불완전 여부를 표시한다.

큐는 최대 256건·60초의 프로세스 내부 완충이다. 용량 초과·만료·프로세스 비정상 종료의 손실을 없앴다고 주장하지 않으며, 전체 트래픽 관측 커버리지도 여전히 불완전할 수 있다. 미확정 실행을 성공으로 바꾸거나 중복 실행하지 않는다.

근거: [대기열·관측 구현](queue-observability.md).

## 프록시, 차단과 관리자 조회

신뢰할 ingress에서 받은 제한된 전달 체인을 한 번만 해석하도록 통합했다. Uvicorn과 앱이 주소를 중복 해석하지 않으며, 임의 vendor 헤더·위조 전달 헤더·과도한 체인·허용되지 않은 주소 형식은 신뢰하지 않는다. 명시적인 IPv4/IPv6 주소·CIDR을 지원하고 trust-all은 거부한다. Caddy도 검증된 client IP를 전달하도록 정리했다. Cloudflare 전체를 임의로 허용하거나 기존 차단 목록을 삭제하지 않았다.

차단 요청은 프로세스 전체 계수와 제한된 영속 표본을 분리해 기록한다. 저장 경합이 있어도 고객 요청이나 호출자의 DB 트랜잭션을 장시간 붙잡지 않도록 했다. 실제 배포의 신뢰 프록시 목록은 운영자가 확인해야 하며, 이 작업은 현재 서비스에서 실제 사용자 오차단이 해소됐다는 관측이 아니다.

관리자 자동 조회는 기본 30초, 오류 시 최대 5분 백오프를 사용한다. 숨겨진 화면·자동 조회가 필요 없는 탭·미로그인 상태에서 중지하고, 하위 조회까지 대기해 중첩을 방지한다. 이전 계정의 늦은 응답·401·대기 작업이 새 세션을 침범하지 않도록 요청과 갱신에 세션 검사를 추가했다.

근거: [프록시 검증](proxy-security.md), [관리자 세션 리뷰](admin-session-review.md).

## 로그량과 민감정보

콘솔과 일별 파일 모두 큐 진입 전에 소스별 로그 수준을 적용한다. HTTP wire DEBUG/INFO를 정상 출력에서 제외하고, 쿼리 값·URL userinfo·쿠키·인증 헤더·토큰과 예외 메시지를 마스킹한다. 관리자 오류 버퍼도 독립적으로 마스킹한다.

`agentcon`의 다음 백그라운드 시작부터 애플리케이션 콘솔 파일은 20 MiB 단위, 백업 5개로 회전하며 `logs`는 회전 후 파일을 따라간다. 직접 터미널 실행은 콘솔 출력을 유지한다. 기존 큰 로그는 회전 시 그대로 백업될 수 있어 디스크 사용량이 즉시 120 MiB로 줄지는 않는다. 초기 시작 stdout/stderr의 별도 `.startup` 파일은 이 회전 대상이 아니며, 기존 증거 파일도 자동 삭제하지 않았다.

## 검증과 적용 범위

**통합 검증: 33개 관련 파일에서 536개 통과.** 실제 native PostgreSQL 실행 환경이 필요한 1건은 명시적으로 제외했다. [통합 JUnit](final-regressions.xml), [실행 로그](final-regressions.log), [파일 목록](final-test-files.json)을 남겼다. 마지막 검색 합계 표시 변경은 [추가 회귀 69개](final-listing-accuracy.xml), [최종 표시 검증 5개](final-summary-assertions.xml), [SQL 등록·준비 상태 검증 13개](final-catalog.xml)에서 통과했다. 이들은 통합 실행과 중복되므로 합산하지 않는다.

테스트는 임시 DB·메모리 DB·가로챈 Playwright 요청과 격리된 임시 포트를 사용했다. 실제 발송·외부 에이전트 실행·운영 서버 동작 변경은 하지 않았다. 최종 테스트 결과는 아래 JUnit 파일과 최종 통합 결과를 기준으로 읽는다. 중복 실행한 여러 배치의 통과 수를 합산하지 않는다.

- [핵심 실행·보고서·인덱싱](core-regressions.xml), [브라우저 회귀](browser-regressions.xml), [프론트엔드·보안](frontend-security.xml), [최종 홈·복사·캐시](final-home-copy.xml).
- 공개 콘텐츠 검사: 81개 파일, 위반 0건. CSP·출력 escaping·Chat의 토큰/금액 비노출·프로토콜 선택·작업 업데이트 권한 경계를 유지했다.
- [Caddy 설정 검증](caddy-validation.json): 공식 임시 v2.11.7 실행 파일로 기본 설정과 명시적 IPv4/IPv6 신뢰 체인 모두 통과했다. 서버 시작·reload는 수행하지 않았다. 실제 배포 Caddy 버전·네트워크 경로와 일치하는지의 확인은 남아 있다.
- [Bandit 정적 검사](bandit-final.json): 전체 선택 파일 검사에서 15개 선택 Python 파일에서 High 0, Medium 83, Low 47. 기존 코드까지 포함한 경고이며 보안 무결점 판정이 아니다. [집중 수동 검토](secure-coding-review.md)에서 새 대기열·보고서 guard의 동적 SQL은 고정 상수·허용 목록·별도 바인딩을 사용하는지 확인했다.
- PostgreSQL의 유한한 승인 SQL 목록을 재생성하고 임의 SQL 거부 경계를 유지했다. 실제 PostgreSQL 실행·전환 검증은 하지 않았다. 기존 native 스키마에 새 측정 필드가 없으면 profile 검증이 실패하도록 유지하며 자동 마이그레이션하지 않는다. 직접 raw SQL 보고서 guard는 SQLite에 한정된다.

보고서·실행 검증 필터의 페이지 합계는 제한된 후보 조회와 최종 카드 검증의 차이 때문에 상한이 될 수 있다. 이를 `total_is_estimate`로 표시하고 화면에도 `up to`로 알린다. 실제 반환 카드에는 전체 subject·현재 실행 검증을 적용하며 오래된 보고서를 검증 근거로 승격하지 않는다. 전체 카탈로그에 대한 무제한 스캔으로 이 차이를 숨기지 않았다.

운영 적용 후에는 새 공개 지표·검증 필터·보고서 제외 동작, 인덱싱 처리율과 최신 provenance 증가, 관측 유실/복구 계수, 실제 프록시별 독립 차단, 로그 증가량을 확인해야 한다. 이번 격리 테스트 통과를 운영 환경에서 개선 효과가 확인된 것으로 바꾸어 표현하지 않는다.
