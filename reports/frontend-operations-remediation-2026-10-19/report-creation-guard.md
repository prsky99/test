# Existing-report creation boundary

The requested policy is one report per canonical agent. A new slug, new title, changed document, or later execution does not authorize another report for that same agent. Existing historical report rows are preserved. Actual execution history continues in its existing evidence ledger.

`Store.find_existing_test_report(resource_id=None, kind=None, agent_url=None)` returns an existing report ID or `None` and performs no provider request or write. Invalid or incomplete subjects raise `ValueError`. An explicit resource ID must exist in the current catalog. It resolves the full provider endpoint; the ID and name are not themselves identity. An unlinked historical document requires an explicit supported protocol and complete provider endpoint. An unbound numeric gateway URL is refused.

Canonical identity combines protocol with the complete canonical endpoint: scheme, IDNA host, effective port, path, and query. Different paths, queries, schemes, and protocols stay separate. Matching names, a shared origin, local resource IDs, or matching slugs cannot establish this identity. Existing direct endpoints are compared canonically. Existing gateway references require their original name/current-version subject proof before they can establish a provider endpoint.

`Store.create_test_report` validates the subject and evidence, then reserves its canonical subject as the first transaction write. The new `test_report_subject_claims` table has a primary subject key and nullable report foreign key. Independent Store connections/processes serialize through this reservation. The writer checks existing legacy reports before inserting, so preexisting reports also block new creation without backfilling or rewriting their contents. `ReportAlreadyExists(ValueError)` exposes only `report_id`; no duplicate row is inserted.

New rows carry `creation_subject_key`. A nullable unique index prevents two new rows for one subject. A SQLite `BEFORE INSERT` trigger additionally requires a nonnull key and the matching pending claim. Retired raw `INSERT` and `INSERT OR REPLACE` scripts omit that key and are refused before changing existing rows. The explicit native PostgreSQL bootstrap installs an equivalent fixed trigger/function; normal attachment verifies the exact enabled trigger and function body. Its claim lookup explicitly references the public schema. No arbitrary SQL fallback was added.

Existing report rows receive only an additive nullable schema column, with no subject-key backfill, deletion, merge, or document rewrite. The pending claim is finished only after insertion and the final binding/evidence recheck. A failed insert or slug conflict rolls its reservation back. Default slugs use UUIDs, avoiding unrelated submissions colliding within the same second. A conflicting explicit slug raises the separate safe `ReportSlugConflict` error.

Administrative list/detail accessors include execution timestamps/scope and `execution_measured`, computed using the existing strict current/latest `measured_report` gate. A false flag is not a statement that a historical execution never happened. Original evidence fields and the actual execution ledger remain intact.

Historical regression fixtures explicitly insert preserved pre-guard history into isolated SQLite stores. They temporarily remove and restore only the creation trigger and set the creation key to null. Subject identity triggers remain active. This test-only path is not available as a production bypass.

Validation includes canonical aliases, differing paths/query/protocols, missing resource IDs, unbound numeric gateway URLs, old numeric-ID drift, managed version proof, existing legacy reports, changed slugs/payloads, reservation rollback, raw INSERT/REPLACE refusal, unchanged historical rows, and a real two-process writer race. A later execution can add evidence without creating another report. Native guard tests accept the exact definition and reject missing, disabled, and changed definitions. All 64 fixed administrative report-list filter combinations and creation queries have exact native registrations.

The latest creation/native/catalog/inventory run passed 149 tests, with two tests requiring an actual PostgreSQL driver/server deselected. A broader overlapping creation/API-security/history/recommendation run passed 136 tests. These totals must not be added. The catalog check is unchanged with 3,373 statements and 206 tables. Bandit found no issue or scan error in the new `report_creation.py` module. Native PostgreSQL enforcement was inspected and tested through its finite registry/attachment boundary; it was not executed against a PostgreSQL server in this environment.

This implementation changed source and isolated fixtures only. It did not start/restart a project server or alter the operating database. SQLite startup installs the new additive boundary on the next authorized activation.
