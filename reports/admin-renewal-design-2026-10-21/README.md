# Agent Concierge 어드민 통합 리뉴얼 설계서

- 작성: 2026-10-21 · 버전 1.0 (초안, 결정 필요 사항 포함)
- 범위: 운영 관리자 화면(`/admin/ui`, 8200), 관리자 API(`/admin/api/*`), 워크스페이스 관리(WAC), 관리자 인증·권한, 운영 데이터·성능
- 원칙: 어드민 화면은 **한국어 유지**(공개 프론트·워크스페이스 고객 화면은 영어 전용, 변경 없음)
- 근거: 현재 코드, 운영 PostgreSQL 읽기 전용 조회, 기존 보고서(`admin-current-alignment-2026-10-21`, `admin-performance-2026-10-20`, `workspace-admin-control-2026-10-21`)

## 0. 요약

**왜 리뉴얼하는가.** 필요할 때마다 기능을 덧붙이면서 어드민이 **세 겹**으로 쌓였습니다.

1. 단일 대시보드 파일(912KB)과 메뉴 21개
2. 그 위에 붙은 워크스페이스 전문 패널 22개(JS 약 330KB)
3. 오늘 추가된 워크스페이스 통합관리(WAC)

여기에 인증 방식이 두 가지로 갈라져 있습니다. 데이터 규모(DB 4.5GB, 테이블 245개, 하루 약 75만 건 증가), PostgreSQL 전환, 전면 게이트웨이화를 반영한 운영 관측도 빠져 있습니다. 그래서 "무엇을 써야 하는지", "이대로 관리가 되는지"를 판단하기 어려운 상태입니다.

**핵심 결정 (제안)**

| # | 결정 | 이유 |
|---|---|---|
| D1 | 메뉴를 업무 기준 **7개 영역**으로 재편 | 기능 위치를 "누가, 무엇을 위해" 기준으로 찾게 함 |
| D2 | 관리자 인증을 **개인 직원 세션 하나로 통일**, 역할 4단계 | 공용 토큰과 localhost 접속이 화면에서 최고관리자로 통과하는 구조 제거 |
| D3 | 단일 HTML을 **화면 셸 + 영역별 모듈(지연 로딩)**로 분리, 빌드 도구 없이 정적 파일 유지 | 912KB 일괄 로딩과 수정 충돌 해소. 현재 배포·CSP 방식 유지 |
| D4 | API를 **`/admin/api/v2/{영역}`** 규칙으로 정리, 기존 API는 호환 어댑터로 유지 후 단계 폐기 | 240여 개 경로의 규칙 불일치(페이지 처리, 오류, 필터) 해소 |
| D5 | 무거운 통계는 **요약(프로젝션) 테이블 + 갱신 시각 표시**. 원본 집계는 화면 요청에서 하지 않음 | 개요 cold 3.6초, 통계 시간 초과, 쓰기 잠금 경합 이력 |
| D6 | **데이터 보존 정책**과 일별 요약을 명문화 | `health_checks` 하루 약 75만 건, 옛 SQLite 3.5GB 잔존 |
| D7 | **게이트웨이·실행 관측** 영역 신설 | 전면 게이트웨이화 이후 호출 제한·실패 원인을 볼 화면이 없음 |
| D8 | 5단계로 **점진 전환**(구 화면과 병행, 영역별 전환·폐기) | 운영 중단 없이, 언제든 되돌릴 수 있게 |
| D10 | 공개 프론트의 **진주(Pearl) 디자인 시스템**을 어드민에 적용: 같은 토큰·글꼴·Lucide 아이콘, 에이전트 = 진주·연결 = 목걸이 표현, 관리 화면에 맞춘 밀도(12장) | 서비스 정체성 통일. 파란색·이모지 위주 화면에서 정돈된 운영 화면으로 |
| D9 | 프론트의 캐시 방식(즉시 표시 후 조용한 갱신, 첫 화면 일괄 로딩)을 어드민 전체로 확장. **데이터 등급별 정책과 변경 범위별 무효화** 도입(11장) | 메뉴 이동·재방문 대기 제거. 민감 정보는 캐시하지 않음 |

| 관리자용 웹앱 내보내기 | v1·v12·v13 세 버전 공존(`admin_workflow_webapp*.py`) |

### 1.2 인증·권한

| 관찰 | 위험 |
|---|---|
| 공용 `ADMIN_TOKEN`을 쓰면 화면·API 모두 **최고관리자**로 통과 | 토큰 공유 시 개인 식별·감사 불가 |
| 토큰 미설정 시 **localhost 접속은 로그인 없이 최고관리자** | 같은 장비의 다른 프로세스·터널 설정 실수에 취약 |
| 기본 계정 `sadmin` 생성 로직 존재. 현재 관리자 계정은 최고관리자 1개뿐 | 역할 분리(운영자·조회자)가 실제로 쓰이지 않음 |
| 역할: 코드상 `superadmin/admin/operator` 3종, 스키마 주석은 2종 | 문서와 구현 불일치 |
| WAC는 **개인 직원 세션만 허용**(기계 토큰 거부), 운영자는 읽기 상한 | 같은 어드민 안에서 인증 모델이 두 가지 |

### 1.4 기능 중복·혼재

| 영역 | 중복·혼재 |
|---|---|

| 워크스페이스 | "워크스페이스 통합관리"와 "조직 작업공간" 메뉴 2개 + 전문 패널 22개 |

| 금전성 데이터 | 결제 관리(테스트 정산), 고객 크레딧, 샌드박스 결제, 제공자 정산이 서로 다른 메뉴 |
| 공개 서비스 화면 복제 | 어드민 안의 "알아보기/탐색/테스트"는 공개 화면과 같은 기능의 사본 |

### 1.5 관측 공백

- 게이트웨이(`/api/gateway/...`)를 통한 호출량·성공률·실패 코드·지연 시간, 에이전트별 호출 제한과 간격 대기를 볼 화면이 없습니다.
- 워크스페이스 실행이 게이트웨이 계층 대신 실행기를 직접 호출해, 정책(동시 실행 슬롯)과 지표가 둘로 나뉩니다.
- 에이전트 "호출 가능" 상태 변화(일시 오류 허용, 연속 실패 제외)의 이력이 화면에 없습니다.
- 수집기 반복 경고, 벡터 작업 적체, 쓰기 잠금 대기 같은 운영 신호가 로그에만 있습니다.

## 2. 리뉴얼 목표와 원칙

| 목표 | 측정 기준 |
|---|---|
| 찾기 쉬움 | 모든 기능이 7개 영역 중 하나에 속하고, 전역 검색(에이전트·고객·조직·워크플로·실행 ID)으로 2번 클릭 안에 도달 |
| 빠름 | 화면 셸 1초 이내, 목록 p95 1초, 상세 p95 0.5초, 무거운 통계는 비동기와 갱신 시각 표시 |
| 안전 | 모든 변경 작업에 확인과 사유 입력, 감사 기록. 위험 작업은 2인 승인. 개인 세션만 허용 |
| 정직한 수치 | 모든 숫자에 정의와 기준 시각 표시. 사용할 수 없는 값은 "확인 불가"로 표시(0으로 위장 금지) |
| 운영 가능 | 데이터 보존·정리 작업과 백업 상태를 화면에서 확인 |
| 점진 전환 | 구 화면과 병행. 영역 단위로 전환·되돌리기 가능 |

설계 원칙:
1. **업무 흐름 우선:** 화면을 "수집 → 검증 → 평가 → 연결 → 고객 결과" 서비스 흐름 순서로 배치합니다. 서비스 컨셉인 진주(에이전트)와 목걸이(연결)를 그대로 따릅니다.
2. **읽기와 쓰기 분리:** 조회 화면은 요약 테이블과 읽기 전용 세션을 씁니다. 변경은 명령(확인·사유·감사·필요 시 승인)으로 처리합니다.
3. **원본 SQL 카탈로그 유지:** 새 API도 기존 SQL 카탈로그 방식(등록된 문장만 실행)을 따릅니다.
4. **개인정보 최소 노출:** 고객 본문·비공개 출력은 기본으로 숨기고, 열람하면 사유와 감사를 남깁니다(WAC의 공유·열람 규칙 확장).

| 어드민 안의 "알아보기·탐색" | 폐기. 공개 화면 링크와 관리자 전용 정보(비공개 상태)는 ② 에이전트 상세로 이동 |

| 고객 요청 + 지원 케이스 | ④ 지원 케이스로 통합. 문의·알림·취소·개인정보 요청은 케이스 유형으로 연결 |
| 관리자 웹앱 내보내기 v1·v12 | 사용 기록 확인 후 v13만 유지(폐기 전 30일 읽기 전용) |
| `logs/clear`, `visitors/simulate` 등 운영 위험·데모 기능 | 개발 모드에서만 노출, 운영은 승인 명령으로 대체 |
| 결제 관리(테스트 정산) | ⑦ 시스템 > 테스트 정산으로 이동, "실제 결제 아님" 표시 고정 |

## 4. 권한 모델

### 4.1 인증

| 구분 | 변경 |
|---|---|
| 화면 로그인 | **개인 직원 세션만** 허용(아이디·비밀번호 + 세션 만료). 2단계 인증(TOTP)은 2단계 작업에서 추가 |
| `ADMIN_TOKEN` | **기계용 API 전용**(명시한 읽기·작업 API 목록만). 화면 로그인과 고객 데이터 열람에는 사용할 수 없음 |
| localhost 자동 최고관리자 | 운영에서 제거. `AGENTCON_ADMIN_DEV=1`일 때만 허용하고, 화면 상단에 "개발 모드" 표시 |
| 기본 계정 `sadmin` | 최초 설치 시 비밀번호 변경 강제, 이후 비활성화 가능 |

### 4.2 역할 (4단계)

| 역할 | 권한 |
|---|---|
| 최고관리자(superadmin) | 전체 + 관리자 계정·역할, 위험 작업 승인, 비공개 열람 승인 |
| 관리자(admin) | 변경 작업 요청·수행(위험 작업은 승인 필요), 지원 케이스 응대 |
| 운영자(operator) | 조회 + 운영 작업(수집 일시정지·재개, 재검사, 케이스 배정). 고객 본문 열람 불가 |
| 조회자(viewer, 신규) | 조회만, 개인정보 마스킹 |

### 4.3 위험 작업 (2인 승인 대상)

크레딧 조정, 에이전트 일괄 비활성화, 실행 킬스위치 해제, 보존 정책 변경·데이터 삭제, 관리자 역할 변경, 보안 규칙 일괄 해제, 고객 비공개 내용 열람.

요청자와 승인자는 다른 사람이어야 합니다. 15분 안에 승인하지 않으면 만료됩니다. WAC의 "reviewed command"를 공통 명령 체계로 확장해 적용합니다.

## 5. 기술 아키텍처

### 5.1 화면 구조

```
/admin/ui            화면 셸(로그인, 상단 바, 7개 영역 내비, 전역 검색, 알림) ≤ 60KB
/admin/assets/core/  공통 모듈: api.js, table.js, filters.js, drawer.js, confirm.js, format.js, charts.js
/admin/assets/areas/ 영역 모듈: home.js, catalog.js, gateway.js, customers.js, public.js, security.js, system.js
```

- **빌드 도구 없음:** ES 모듈 정적 파일을 그대로 쓰고, 영역에 처음 들어갈 때 지연 로딩합니다. CSP는 `script-src 'self'`(+ 기존 nonce)를 유지합니다.
- **주소 체계:** `#/catalog/agents/12345?tab=evidence`처럼 해시 라우팅을 써서 새로고침과 주소 공유가 됩니다.
- **공통 컴포넌트:**
  - 표: 서버 페이지 처리, 정렬, 열 선택, CSV 내보내기(권한 확인)
  - 필터 바
  - 상세 드로어
  - 확인 창: 사유 입력, 차감·영향 요약
  - 빈 상태, 오류, "확인 불가" 표시
  - 갱신 시각 배지
- **디자인:** 공개 서비스의 Pearl 디자인 토큰(색, 타이포, Lucide 아이콘, 라이트·다크, 동작 줄이기)을 같이 씁니다. 텍스트는 한국어입니다. 에이전트 연결을 보여 주는 곳(워크플로·실행 기록)은 워크스페이스와 같은 진주 목걸이 표현을 씁니다.

### 5.2 API 규칙 (`/admin/api/v2`)

| 규칙 | 내용 |
|---|---|
| 경로 | `/admin/api/v2/{area}/{resource}[/{id}[/{action}]]` (area: home, catalog, gateway, customers, public, security, system) |
| 목록 | `?cursor=&limit=(≤200)&sort=&filter[...]=`, 응답 `{items, next_cursor, total?, captured_at}` |
| 상세 | `{item, related:{...}, captured_at}` |
| 변경 | `POST .../{action}` + `{reason, expected_revision}`. 응답 `{result, audit_id}` 또는 `{command_id, status:'awaiting_approval'}` |
| 오류 | `{error_code, message_ko, retryable}`. 코드 체계는 실행 오류 분류와 정렬 |
| 캐시 | 인증 후 캐시. 응답에 `captured_at`, `stale` 포함 |
| 호환 | 기존 `/admin/api/*`는 v2 핸들러를 호출하는 어댑터로 남기고, 사용량이 0인 경로를 순차 폐기(접속 로그 30일 확인) |

### 5.3 읽기 모델 (요약 테이블)

화면 요청에서 원본 대형 테이블을 집계하지 않습니다. 작업자가 갱신하는 요약 테이블을 읽습니다.

| 요약 | 원본 | 갱신 |
|---|---|---|
| `admin_catalog_daily`(상태별·프로토콜별 에이전트 수) | resources | 5분 |
| `admin_health_daily`(에이전트별 일별 성공·실패·지연 p50/p95) | health_checks | 10분(증분) |
| `admin_gateway_minutely`(경로·에이전트·결과 코드별 호출 수·지연) | 실행·관측 이벤트 | 1분 |
| `admin_workspace_daily`(조직·워크플로·실행·크레딧) | 워크스페이스 테이블, WAC 이벤트 | 5분 |
| `admin_storage_snapshot`(테이블 크기·행 수·증가율) | pg_stat | 1시간 |

갱신은 기존 프로젝션 작업자(`workspace_admin_worker`) 구조를 확장해 공통 작업자로 둡니다. 쓰기는 짧은 트랜잭션으로 나눕니다(전역 쓰기 잠금 1초 이내 보유 원칙. Chat 503 사고의 교훈).

| 대상 | 목표(p95) | 수단 |
|---|---|---|
| 화면 셸 | 1초 | 셸 60KB 이하, 영역 모듈 지연 로딩 |
| 운영 홈 | 1초(cold 포함) | 요약 테이블만 조회. 현재 cold 3.6초 |
| 목록 | 1초 | 키셋 페이지 처리, 필터 열 인덱스 |

- 운영 홈에 **"쓰기 잠금 대기"와 "느린 쿼리 Top 5"**를 표시합니다(pg_stat_activity·pg_locks 읽기 전용).

## 7. 게이트웨이·실행 관측 (신규 ③)

| 지표 | 단위 | 경보 기준(초안) |
|---|---|---|
| 호출 수, 성공률 | 경로(Chat·Test·Workspace·SDK 앱)·프로토콜·에이전트 | 5분 성공률 < 90% |
| 실패 코드 분포 | UPSTREAM_TOOL_ERROR, TIMEOUT, NETWORK, PROTOCOL, SCHEMA_CHANGED, CAPACITY_EXCEEDED | 특정 코드가 10분 내 3배 증가 |
| 지연 시간 p50/p95 | 에이전트·경로 | p95 > 8초 |
| 간격 대기(페이싱) | 에이전트별 대기 횟수·시간 | 대기 비율 > 30% |
| 호출 가능 상태 변화 | 일시 오류 허용, 연속 실패 제외, 재검증 | 워크스페이스 후보 에이전트 제외 즉시 |
| 실행 제어 | 킬스위치·대체 실행·한도 상태 | 변경 시 감사 |

화면:
- 개요 그래프(시간대별)
- 에이전트별 표(호출·성공률·p95·최근 실패 코드·현재 상태)
- 에이전트 상세의 "호출 타임라인"

이를 위해 워크스페이스 실행도 게이트웨이 계층(`ManagedGateway`)의 정책·지표를 함께 쓰도록 실행 경로를 정리합니다(동작 변경은 별도 검증 후).

## 8. 주요 화면 설계 (요지)

### 8.1 운영 홈
- **상단 경보:** 심각도순 최대 5개. 예: 게이트웨이 성공률 하락, 수집 지연, 명령 승인 대기, 보존 작업 실패, 쓰기 잠금 대기.
- **핵심 지표 카드 6개:** 활성 에이전트, 호출 가능 검증 에이전트, 24시간 실행 성공률, 게이트웨이 p95, 고객 조직 수, 미처리 지원 케이스. 카드마다 정의와 기준 시각을 표시합니다.
- **대기 작업:** 승인 요청, 등록 심사, 지원 케이스, 사고.
- **최근 변경:** 감사 기록 10건.

### 8.2 에이전트 상세 (②)
- **헤더:** 이름, 프로토콜, 상태, 등급, 호출 가능 여부와 사유
- **탭:**
  - 개요
  - 연결 버전·계약
  - 검증(테스트·보고서)
  - 호출 타임라인(③ 연동)
  - 수집 기록
  - 관리자 메모·감사
- **작업:** 재검사, 활성·비활성(사유), 계약 승인, 테스트벤치 열기

### 8.3 조직·워크플로 상세 (④)
- 워크플로를 진주 목걸이로 표시합니다. 단계별 에이전트 상태와 최근 실행 결과를 진주 테두리 색으로 보여 줍니다.
- 탭(기존 전문 패널 흡수):
  - 실행 기록
  - 증거·보고
  - 릴리스·배포
  - 원격 A2A
  - 신뢰성 제어
  - 연구 제어
  - 성장 지표
  - 합의서
  - 크레딧
  - 지원
- 고객 비공개 출력은 기본으로 가립니다. 열람하려면 사유를 입력하고 승인을 받습니다.

### 8.4 시스템 > 저장소 (⑦)
- 테이블별 크기·행 수·7일 증가율, 보존 작업 마지막 실행·결과, 백업 상태, 옛 SQLite 파일 상태
- 보존 정책 변경은 2인 승인

| 단계 | 기간(예상) | 산출물 | 완료 기준 | 되돌리기 |

| **P3 카탈로그 + 고객·워크스페이스** | 3주 | ② ④(전문 패널 22개 흡수, 고객 요청·지원 통합) | 기존 기능 대응표 100% 이관 확인 | 영역 단위 전환 플래그 |

검증 원칙(각 단계 공통):
- 격리된 PostgreSQL에서 v2 API 전체를 대상으로 성공·권한 거부·입력 오류를 시험합니다.
- 브라우저 여정 시험을 합니다(로그인 → 영역 이동 → 확인 창 → 감사 확인).
- 보안 점검: CSRF, 권한 우회, 응답의 개인정보, CSP.
- 성능 측정(p95)을 남기고, 운영 반영은 사용자가 재시작한 뒤 읽기 전용 점검으로 확인합니다.

## 10. 결정이 필요한 사항

1. **localhost 자동 최고관리자 제거 시점:** 운영 서버에서 즉시 제거할지, P1 완료 시 제거할지
2. **조회자(viewer) 역할 신설 여부**와 2단계 인증 도입 시점
3. **`health_checks` 원본 보존 기간:** 7일 유지 또는 3일 단축(요약 400일)
4. **옛 SQLite 3.5GB 파일:** 보관 위치(외부 디스크·별도 폴더)와 운영 폴더에서 제거할 시점
5. **관리자 웹앱 v1·v12 폐기:** 사용 고객·배포가 있는지 확인한 뒤 폐기할지
6. **어드민 안의 "알아보기·탐색" 폐기:** 공개 화면 링크로 대체해도 되는지
7. **워크스페이스 실행의 게이트웨이 계층 통합:** 동작 변경이 따르므로 P2에서 함께 할지, 별도 과제로 둘지
8. **캐시 범위:** 비민감 참고·집계 데이터에 한해 탭 단위 저장(sessionStorage)을 허용할지(새로고침 후 즉시 표시), 다른 관리자의 변경을 반영하는 확인 주기(제안 15초)
9. **디자인 기본값:** 어드민 기본 테마(라이트/다크/시스템 설정 따름)와 한국어 제목 글꼴(세리프 명조 계열 또는 고딕 계열) 선택
10. **동시 작업 규칙:** 어드민 리뉴얼 기간에 다른 작업자(Codex 등)가 구 어드민을 수정할 때 따를 규칙(구 화면 수정 동결 또는 대응표 갱신 의무)

## 11. 캐시 설계: 프론트 캐시 방식의 어드민 적용

목표는 관리자가 메뉴를 옮기거나 돌아올 때 **기다리지 않게** 하는 것입니다. 단, 오래된 값으로 잘못 조작하거나 민감 정보가 남는 일은 없어야 합니다.

### 11.1 프론트엔드에 적용된 캐시 (기준)

| 장치 | 동작 |
|---|---|
| 첫 화면 일괄 데이터(bootstrap) | 개요·탐색 미리보기·가이드·템플릿·테스트 예제를 HTML에 넣어 보내 첫 화면이 대기 없이 그려짐 |
| 브라우저 SWR 캐시 | 메모리 + localStorage 2단. 키는 화면·필터별로 나누고, 버전 접두어(`concierge_swr_gateway_v5_`)를 바꾸면 옛 캐시를 자동 삭제 |
| 즉시 표시 후 조용한 갱신 | 캐시 값으로 먼저 그리고 뒤에서 새 값을 받아 교체. 같은 요청은 동시에 1개만(`ovRevalidating` 등) |
| 메뉴 재방문 | 이미 읽은 메뉴는 재요청과 로딩 표시 없이 즉시 표시. 입력값 유지 |
| 자동 갱신 | 홈 화면이 보이고 온라인일 때만 60초마다. 숨겨진 탭은 중지, 다시 보이면 1회 갱신 |
| 부분 데이터 표시 | 미리보기(일부 결과)를 완료된 페이지로 오인하지 않게 표시(`_complete_page`, `_request_limit`) |
| 서버 스냅샷 캐시 | 개요 스냅샷, 탐색 결과 캐시(잠금으로 동시 계산 방지), 실시간 지표 300초 |
| 작은 상세 재확인 | 캐시된 에이전트 상세도 실행 성공 표시는 다시 확인(오래된 성공 배지 재사용 금지) |
| 워크스페이스 요청 캐시 | 같은 GET은 동시에 1개로 합치고 10초 보관. 변경 요청 후 즉시 비움, 페이지를 떠나거나 숨기면 비움(메모리 전용) |

### 11.2 어드민 현황과 차이

| 항목 | 어드민 현재 | 차이 |
|---|---|---|
| 브라우저 캐시 | 메모리 전용. GET 7종(overview·timeseries·agents·insights·test-reports·workflows·templates)만 대상. 10초 신선, 60초까지 즉시 표시 + 갱신(`onFresh` 사용 화면만). 48개·8MB 한도. 변경 시 전체 삭제, 세션 변경 시 전체 삭제 | 대상이 좁음. 대부분 메뉴는 매번 로딩. 변경 한 번에 모든 캐시 삭제 |
| 서버 캐시 | `AdminReadCache`(5초 신선, 30초까지 즉시 표시, 갱신 1개만 동시 실행)를 개요와 벡터 통계(60초/300초)에만 적용 | 목록·상세에 없음. 재시작 직후 개요 3.6초 |
| 첫 화면 | 로그인 후 여러 API를 각각 호출 | 일괄 로딩 없음 |
| 메뉴 재방문 | 메뉴마다 다시 읽음(일부 메뉴 캐시 변수만 존재) | 즉시 표시·입력 유지 규칙 없음 |
| 기준 시각 표시 | 개요 일부만 | 오래된 값인지 알기 어려움 |
| 조건부 요청 | 없음(ETag 0건) | 변경이 없어도 매번 전체 전송 |
| 다른 관리자의 변경 반영 | 자동 갱신 주기에만 의존 | 변경 감지 없음 |

### 11.3 4계층 캐시 구조

```
[화면] ─▶ L1 브라우저 메모리 SWR ─▶ L2 탭 세션 저장(비민감만) ─▶ 서버
                                                          │
                              L3 서버 공유 캐시(권한별, 단일 갱신) ─▶ L4 요약 테이블 ─▶ 원본 테이블
```

| 계층 | 위치 | 내용 | 수명 |
|---|---|---|---|
| L1 | 브라우저 메모리(공통 `api.js`) | 모든 v2 GET. 키 = 경로 + 정렬된 쿼리 + 역할 | 등급별(11.4). 로그아웃·세션 변경·권한 변경 시 전체 삭제 |
| L2 | 브라우저 탭 세션 저장(sessionStorage) | **비민감 참고·집계 데이터만**(카테고리, 계약 정의, 카탈로그 통계, 메뉴 배지 수). 버전 접두어 사용 | 탭을 닫으면 삭제. 로그아웃 시 삭제. localStorage는 사용하지 않음 |
| L3 | 서버 프로세스 | `AdminReadCache`를 키별 캐시로 일반화(목록·상세·집계). 갱신은 키당 1개만 동시 실행. 키에 역할 범위 포함 | 등급별. 변경 태그로 즉시 무효화 |
| L4 | PostgreSQL 요약 테이블 | 5.3절의 프로젝션 | 작업자 주기 |

추가 장치:
- **로그인 직후 일괄 로딩:** `GET /admin/api/v2/home/bootstrap` 한 번으로 내 정보·권한, 메뉴 배지 수, 운영 홈 지표·경보, 참고 데이터를 받습니다. 프론트의 bootstrap과 같은 역할이지만, 인증 이후에 실행합니다.
- **조건부 요청:** 목록·상세 응답에 `ETag`(데이터 버전 또는 `captured_at` 기반)를 붙이고, 브라우저는 `If-None-Match`로 확인합니다. 변경이 없으면 304라 전송량과 서버 부담이 줄어듭니다.
- **변경 감지:** `GET /admin/api/v2/home/changes?since={version}`을 화면이 보일 때 15초마다 호출해 바뀐 태그 목록을 받고, 해당 캐시만 갱신합니다. 다른 관리자가 바꾼 내용이 여기로 반영됩니다. 이후 SSE로 바꿀 수 있습니다.

### 11.4 데이터 등급별 정책

| 등급 | 예 | L1 신선/즉시표시 한도 | L2 | L3 | 자동 갱신 |
|---|---|---|---|---|---|
| 실시간 운영 | 경보, 게이트웨이 지표, 승인 대기, 쓰기 잠금 대기 | 5초 / 30초 | 금지 | 5초 / 30초 | 화면이 보일 때 15~30초 |
| 운영 목록 | 에이전트 목록, 수집 진행, 보안 이벤트, 실행 기록 | 10초 / 60초 | 금지 | 10초 / 60초 | 변경 감지 시 |
| 상세 | 에이전트·조직·워크플로 상세 | 30초 / 5분 | 금지 | 30초 / 5분 | 변경 감지 시, 해당 키만 |
| 참고 데이터 | 카테고리, 계약 정의, 역할, 메뉴 구성 | 10분 / 1시간 | 허용 | 10분 / 1시간 | 버전 변경 시 |
| 금전성 | 크레딧 잔액·정산·조정 | 표시용 10초 / 30초(기준 시각 필수) | 금지 | 금지 | 변경 화면은 항상 새로 읽고 `expected_revision` 확인 |
| 민감 | 고객 메시지·지원 본문, 비공개 실행 출력, 자격증명, 열람 감사 상세 | **캐시 금지**(`Cache-Control: no-store`) | 금지 | 금지 | 화면을 떠나면 DOM에서 제거 |

### 11.5 무효화 규칙

- **태그 기반:** 변경 API 응답에 `invalidate: ["catalog:agent:12345", "catalog:agents"]`처럼 영향 범위를 담습니다. 브라우저(L1·L2)와 서버(L3)는 그 태그의 키만 지웁니다. 지금처럼 변경 한 번에 전체를 지우는 방식은 쓰지 않습니다.
- **세션·권한 변경:** 로그아웃, 세션 교체, 역할 변경이 있으면 L1·L2를 전부 지웁니다(현행 epoch 방식 유지).
- **변경 화면 진입:** 수정·승인·조정 화면을 열 때는 해당 대상을 항상 새로 읽습니다. 저장할 때는 `expected_revision`으로 그사이 바뀌었는지 확인하고, 바뀌었으면 차이를 보여 준 뒤 다시 확인을 받습니다.

### 11.6 사용성 패턴 (프론트에서 가져옴)

1. **즉시 표시 후 조용한 갱신:** 전체 로딩 화면 대신 기존 값을 보여 주고, 제목 옆에 작은 "갱신 중" 표시만 띄웁니다.
2. **메뉴 재방문 즉시 표시:** 필터, 정렬, 검색어, 페이지, 스크롤 위치, 펼친 행을 영역별로 기억합니다(메모리).
3. **기준 시각 배지:** 카드와 표마다 "기준 14:27:05 · 12초 전"을 표시합니다. 즉시 표시 한도를 넘으면 "오래됨" 색으로 바꾸고 새로고침 버튼을 강조합니다.
4. **미리 읽기:** 목록 행에 마우스를 올리거나 키보드로 포커스하고 300ms가 지나면 상세를 미리 읽습니다(상세 등급, 동시 2개 제한).
5. **보이는 화면만 갱신:** 숨겨진 탭이나 오프라인일 때는 멈추고, 다시 보이면 1회 갱신합니다. 실패하면 지수적으로 간격을 늘립니다(현행 유지).
6. **장애 시 마지막 값 유지:** 서버 오류나 오프라인이면 마지막 값을 그대로 두고 상단에 경고 띠를 표시합니다. 0이나 빈 값으로 덮어쓰지 않습니다.
7. **부분 데이터 표시:** 미리보기나 일부 페이지는 "일부" 표시를 붙여 완료된 목록으로 오인하지 않게 합니다(프론트 규칙 계승).

### 11.7 보안 원칙

- 캐시 조회는 항상 인증과 권한 확인 **뒤에** 합니다(현행 `AdminReadCache` 원칙 유지).
- 캐시 키에 역할 범위를 넣어, 조회자와 관리자의 응답이 섞이지 않게 합니다.
- localStorage는 쓰지 않습니다. L2는 비민감 등급만, 탭 단위로만 둡니다.
- 민감 등급 응답은 `no-store`입니다. 서버 공유 캐시(L3)에는 개인 식별 정보가 담긴 응답을 넣지 않습니다.
- 브라우저 캐시 한도는 현행(48개·8MB)을 기준으로 등급별 상한을 둡니다.

### 11.8 측정과 검증

| 지표 | 목표 |
|---|---|
| 메뉴 재방문 표시 시간 | 100ms 이내(캐시 적중) |
| 로그인 후 운영 홈 첫 표시 | 1초 이내(일괄 로딩) |
| L1 적중률 | 70% 이상 |
| 304 비율(조건부 요청) | 목록·상세 50% 이상 |
| 오래된 값 노출 | 즉시 표시 한도 초과 0건(배지로 확인) |

브라우저 시험 항목:
- 세션 전환 뒤 이전 관리자의 데이터가 남지 않는지(L1·L2 0건)
- 민감 화면을 떠난 뒤 DOM에 남지 않는지
- 변경 후 해당 태그만 갱신되는지
- 다른 관리자의 변경이 15초 안에 반영되는지
- 금전성 변경 화면이 항상 새 값으로 열리는지

## 12. 진주(Pearl) 디자인 시스템 적용

서비스 컨셉은 **에이전트를 진주로, 에이전트를 연결하는 일을 진주 목걸이로** 표현하는 것입니다. 어드민은 그 진주를 모으고(수집), 고르고(검증·평가), 꿰어(게이트웨이·워크플로) 고객에게 전하는 곳입니다. 공개 화면과 워크스페이스에 적용한 진주 디자인을 같은 토큰으로 어드민에 적용하되, 데이터를 많이 다루는 관리 화면에 맞게 밀도를 조정합니다.

### 12.1 기준: 공개 프론트의 진주 디자인 (`new/en/assets/styles.css`)

| 요소 | 값 |
|---|---|
| 색(라이트) | 바탕 `--bg #f8f7f3`, 면 `--surface #fffefc`, 글자 `--ink #103540`, 보조 `--muted #536d80`, 선 `--line #e3ded4`, 금 `--gold #a48154`, 부드러운 면 `--soft #ede5d8`, 청록 `--teal #005864`, 옅은 청록 `--aqua #e6f4f4` |
| 색(다크) | `--bg #101f25`, `--surface #172a31`, `--ink #eef3ef`, `--muted #b1c5ca`, `--line #395057`, `--gold #d2b48a`, `--teal #9cdbdc`, `--aqua #24474a` |
| 글꼴 | 본문 Arial/Helvetica, 제목 Georgia 세리프(자간 -0.045em, 굵기 500), 작은 머리말 `eyebrow`(11px, 대문자, 자간 0.24em, 금색) |
| 모양 | 카드 둥글기 16px, 버튼 10px, 은은한 그림자 `0 12px 32px #3b302006`, 카드 면에 옅은 흰 그라데이션 |

| 진주 | 다층 radial-gradient 진주(하이라이트·진주층·그림자), 브랜드 표식 = 금색 원 3개(진주 3알), 홈의 목걸이 도식, 워크스페이스의 실로 꿴 진주(`flow-thread`) |
| 아이콘 | Lucide 로컬 SVG, 아이콘 원판(`icon-disc`) |
| 원칙 | 라이트·다크, 동작 줄이기, 키보드 초점 표시, 접근 가능한 이름 |

### 12.2 현재 어드민과의 차이

| 항목 | 현재 어드민 | 적용 후 |
|---|---|---|
| 색 | 회색 바탕 `#f6f7f9`, 파란 포인트 `#2f6fde`, 별도 상태색 | 진주 토큰 + 진주 팔레트의 상태색(12.3) |
| 글꼴 | 브라우저 기본, 제목 구분 약함 | 진주 글꼴 체계 + 한국어 대체 글꼴(12.4) |

### 13.2 중단 작업 재개 · P1/P2 안정화 및 P3 조회 연결 (2026-10-21)

이번 재개분은 기존 `/admin/next` 구현을 보존해 미완성 조회 연결과 안전 경계를 보강했다. **리뉴얼 전체(P0~P4)가 완료된 것은 아니다.** `/admin/ui`가 계속 기존 운영 화면이며, 기본 화면 전환·구 API 폐기는 하지 않았다.

반영 내용:

- 공개 서비스 영역을 설명/바로가기에서 실제 방문·작업 알림·고객 요청 집계와 공개 템플릿 목록으로 교체했다. 새 `/admin/api/v2/public/summary`는 개인 직원 세션을 확인한 뒤 허용된 집계·템플릿 메타데이터만 반환한다. 연락처·방문자 행·LLM 설정·워크플로 비공개 구성은 반환하지 않으며 광고 발송도 켜지 않는다. 빈 집계의 SQL NULL은 정상 조회에 한해 0건으로 표시하고, 조회 실패는 확인 불가/503으로 구분한다.
- 고객·조직·AI/실행 이력·크레딧·사고/감사 조회를 현재 WAC 응답 계약에 맞췄다. 조직에서 초안·워크플로·실행·릴리스·배포 메타데이터를 열 수 있다. 고객/조직/실행 ID는 전역 검색으로 해당 화면에 연결한다. 이벤트 커서는 시각+ID를 함께 전달한다.
- 크레딧 대사는 `matched`만 일치로 표시한다. `incomplete`, `integrity_review_required`, 미지의 상태를 정상으로 표시하던 경로를 제거했다. 원본에 없는 원장 합계도 만들어 표시하지 않는다.
- 캐시는 비민감 v2 조회 허용 목록으로 제한했다. 고객·지원·크레딧·권한·레거시 응답은 메모리 SWR에 넣지 않는다. 같은 태그의 쓰기와 겹친 이전 응답이 캐시를 되살리지 않도록 방어하고, 관련 없는 태그의 캐시는 유지한다.
- 로그아웃 즉시 화면·드로어·확인 창·검색·세션별 필터·캐시를 비운다. 세션 교체 이후의 늦은 응답과 권한 만료 응답은 화면을 복구할 수 없다. 서버 로그아웃 확인 실패는 성공으로 숨기지 않는다. BFCache 복원 시 다시 로드한다.
- 서버 `TimedCache`의 cold 요청/갱신은 키당 하나로 합쳤다. 동시에 갱신 중인 stale 값은 추가 집계를 시작하지 않고, 무효화 이전 갱신이 새 캐시를 덮어쓰지 못한다. 128키 상한을 둔다.
- 변경 감지의 최초 감사 ID/100건 초과 누락 시 보수적으로 재조회한다. 중지한 감시 루프가 다시 예약되지 않게 했고 오류 시 백오프를 적용했다.
- 중복 JSON 필드·비유한 수치 상수는 변경 API에서 거부한다. 보존 미리보기의 개별 테이블 조회 실패는 행을 숨기지 않고 확인 불가로 남긴다. 게이트웨이 p50/p95에는 최근 최대 5,000개 시도 표본이라는 범위를 응답에 명시했다.

검증:

- 공개 콘텐츠 238개 파일 위반 0건. 어드민 한국어와 공개 영어 전용 경계는 유지했다. 기존 공개/워크스페이스 고객 코드의 동작은 수정하지 않았다.

운영 반영:

### 13.4 P1 인증 경계·조회자·초기 비밀번호 (2026-10-21)

구현한 범위:

- 조회자 응답은 서버에서 투영한다. 관리자용 원본 집계 캐시에서 수집 로그·모델/설정·실행 에이전트 상세를 그대로 전달하지 않는다. 화면도 허용된 네 영역만 표시하며, 접근 불가능한 ID 검색과 기존 어드민 링크를 숨긴다. 기존 화면에서 조회자로 로그인하면 새 화면으로 이동한다.
- `/admin/api/*`에서 `ADMIN_TOKEN`은 **GET `/admin/api/overview`와 GET `/admin/api/timeseries`만** 허용한다. 개요는 비식별 집계로 축소한다. `/auth/me`, 고객 데이터, 계정 관리 및 모든 변경 요청에는 개인 직원 로그인이 필요하다. 따라서 종전 토큰으로 다른 콘솔 API를 사용하던 스크립트는 그대로 호환되지 않는다. 콘솔 밖의 기존 수집기 전용 API는 이번 변경 범위가 아니다.

- 새 초기 계정의 비밀번호 해시에 초기 상태 표시를 보존하며, 과거 표시 없는 `sadmin` 기본 비밀번호도 인식한다. 초기 계정 세션은 본인 정보·로그아웃·비밀번호 변경 외 업무 API에서 428로 차단한다. 자체 인증을 쓰는 WAC 등에서도 초기 세션을 거부한다. 이미 바꾼 개인 비밀번호는 재설정하지 않는다. 과거의 임의로 지정된 강한 초기 비밀번호가 실제 변경됐는지는 이력 없이 추측하지 않는다.

### 13.6 P2 1차 — 영속 스냅샷과 DB 활동 (2026-10-21 밤)

**홈·게이트웨이 영속 스냅샷 (재시작 직후 cold 대응)**

- `TimedCache(persist=...)`: 메모리에 값이 없으면 마지막으로 저장한 스냅샷을 즉시 응답(`cache: stale`)하고, 원본 집계는 백그라운드에서 다시 한다. 홈 개요와 게이트웨이 1/6/24/168시간 요약에 적용했다.
- `SnapshotStore`:
  - 이미 운영에 마이그레이션된 `workspace_admin_state`에 `admin_next.snapshot:*` 키로 집계만 저장한다. 새 테이블이 없으므로 시작 검증이나 마이그레이션 위험이 없다.

### 13.12 P3 4차 — 고객 요청(공개 푸터) 처리 이전 (2026-10-22)

- ④ 고객·워크스페이스에 "고객 요청" 탭을 추가했다 (설계 13.3의 4번 "고객 요청 유형별 연결").

  - 종류(문의/개인정보 요청/수신 해지), 상태, 검색, 더 보기
  - 상세 서랍
- 새 API는 최고관리자와 관리자만 쓸 수 있다. 운영자와 조회자는 고객 본문을 열람할 수 없다(설계 4.2).

- 처리 규칙:
  - 변경 사유는 필수이며 감사 기록(`INQUIRY_UPDATE`, `PRIVACY_UPDATE`)에 남는다. 처리자는 개인 계정 이름으로 기록한다.

  - 처리자가 항상 "admin"으로 기록됐다. 이제 개인 계정 이름으로 기록한다.
  - 문의 상태값을 검증하지 않았다. 이제 422로 거절한다.

- 검증:
  - API 4건 (목록 비식별·역할 경계, 사유·처리자·감사, 개인정보 완료 근거와 되돌림 차단, 기존 경로 수정)

### 13.13 P4 선행 — 관리자 계정 변경 승인 경계 연결 (2026-10-22, Codex 인계 재개)

**이번 완료 범위:** 기존 관리자 계정 API의 즉시 변경 경로를 공통 위험 명령에 연결했다. 전문 패널 22개 이전이나 보존 기간 변경으로 범위를 확대하지 않았다.

- `POST /admin/api/users`, `PUT /admin/api/users/{id}`, `DELETE /admin/api/users/{id}`는 사유를 받아 **202 승인 대기**를 반환한다. 생성·역할·활성 상태·표시 이름·다른 계정 비밀번호 초기화·삭제는 승인 전 적용하지 않는다. 본인이 현재 비밀번호를 확인하는 개인 비밀번호 변경은 기존 경로를 유지한다.
- `admin_account_change` 명령은 기존 서명 저장소·15분 만료·CAS·감사 기록을 사용한다. 활성 최고관리자가 둘 이상이면 다른 최고관리자의 승인이 필요하다. 한 명이면 10분 이내 로그인과 단독 검토 확인이 필요하다. 승인 저장소가 없으면 변경을 차단하며 요청 중 스키마를 만들지 않는다.
- 승인 적용 시 요청자·승인자의 현재 최고관리자 권한, 대상 계정의 이름·역할·활성 상태·자격증명 상태를 다시 확인한다. 로그인 시각 갱신은 충돌로 보지 않는다. 대상이 바뀌었으면 새 요청이 필요하다. 마지막 활성 최고관리자와 기본 계정 삭제 보호, 권한·비밀번호 변경 시 기존 세션 폐기를 유지한다.
- 비밀번호는 writer transaction 밖에서 해시 처리한다. 평문을 승인 저장소에 넣지 않으며 해시·salt·내부 상태 서명은 API 목록/상세와 감사 내용에서 제외한다. SQL은 고정된 매개변수 쿼리를 사용한다.
- 기존 계정 화면에 역할 선택·변경 요청 및 승인 대기 바로가기를 연결했다. 성공 문구를 즉시 적용에서 요청 등록으로 바꿨다. 새 어드민의 **게이트웨이 → 승인 대기**에서 계정명·변경 전후 역할·활성 상태·비밀번호 설정 여부를 확인하고 승인/철회한다.
- 운영 계정·권한·비밀번호는 변경하지 않았다. 보존 기간, Provider connections 병행 개발 파일, 서버 프로세스를 변경하지 않았다. 추가 운영 스키마 마이그레이션 없이 기존 승인 테이블을 사용한다. SQL 카탈로그는 **229개 테이블 / 3,668개 구문**이다.

**검증:** 중복을 제외한 영향 범위 **152개 테스트를 최종 확인**했다. 첫 통합 실행의 실패 2건은 추가 최고관리자가 있는 기존 테스트 fixture에서 본인 승인을 기대한 문제였다. 단독 관리자 시나리오 fixture를 수정하고 해당 테스트를 포함한 76건을 재검증해 모두 통과했다. 별도 두 사람 승인·요청자 권한 소멸·대상 비밀번호 변경 충돌·세션 폐기·악성 입력·재사용 차단을 확인했다. Chromium 10건 및 조회 전용 역할 브라우저 1건, 임시 PostgreSQL의 생성→역할/비밀번호 변경→삭제 승인, 신규 모듈 정적 검사, Python 구문 검사, 카탈로그 검사를 통과했다. 검증 결과는 [accounts/validation.json](accounts/validation.json), [임시 PostgreSQL](accounts/postgres.json), [통합 검사](accounts/integration.txt), [브라우저 검사](accounts/browser.txt)에 있다.

### 13.14 전문 패널 이전 1차 — 구성·실행 / 계보 / 보관 근거 / 품질 검토 (2026-10-22)

**완료 범위:** 기존 순서의 첫 네 패널을 새 어드민 **고객·워크스페이스 → 전문 관리**로 이전했다. `workspace-flow`, `workspace-typed-evidence`, `workspace-evidence`, `workflow-quality`의 조회·변경 기능을 Pearl 화면에서 사용한다. 전체 22개 이전 완료를 의미하지 않는다.

- 기존 네 컨트롤러를 공통 원본으로 유지하고 `scripts/build_admin_specialist_panels.py`에서 새 셸용 모듈을 생성한다. `--write`는 재생성, 옵션 없는 실행은 동기화 검사다. 새 화면과 기존 화면의 실행 프로토콜이 따로 발전하지 않도록 했다. 주요 안내·버튼은 한국어이며 계약명·기술 상태값은 유지한다.

### 13.16 전문 패널 이전 3차 — 원격 A2A·규격 적합성 (2026-10-23)

- 원격 A2A: 승인된 기록 연결 선택, 새 작업 1회 제출, 보관 이력/작업 조회, 명시적 상태 확인 1회, 취소 1회, 동일 스트림 재연결, 동일 작업·세션의 추가 입력을 새 화면에 연결했다. 각 원격 명령마다 별도 동의와 변경 사유가 필요하다. 입력 변경 시 동의를 초기화하며 보관 이력 조회는 원격 호출을 발생시키지 않는다. 전송 후 결과 미확인은 이력 확인으로 복구하고 자동 재제출/상태 확인/취소는 하지 않는다.

### 13.17 전문 패널 이전 4차 — 신뢰성·연구 제어 (2026-10-23)

**구현 범위:** `workspace-reliability`, `workspace-reliability-controls`, `workspace-reliability-research`, `workspace-research-controls`를 **고객·워크스페이스 → 전문 관리**로 이전했다. 평가·연구·원본·실행 권한의 기존 도메인 계약을 유지하고, 새 화면의 변경 사유·감사·세션 경계를 연결했다.

- 평가 근거: 불변 계획/평가 항목/코호트, 목적별 보관 동의, 암호화 원본 보관·열람·삭제·철회, 실제 보관 실행 연결과 비공개 평가 보고서를 이전했다. 원본 삭제는 현재 목적별 동의와 영구 tombstone을 유지한다. 보존 기간을 변경하거나 자동 정리를 새로 켜지 않았다.
- 평가·라우팅 제어: 코퍼스 승인, 계획·예약·취소, 설정된 평가 워커의 활성/비활성, 신뢰 근거 조회, 업무 호출 없는 라우팅 미리보기/결정/재현을 이전했다. 미설정·실행 중이 아닌 워커는 활성화 버튼을 비활성화한다. 계획 저장이나 예약을 실제 평가 실행 또는 독립 품질 검증으로 표시하지 않는다.
- 짝지은 연구: 검토한 SHA-256 기반 연구 명세, 평가 계획, 짝지은 분석, 철회와 목적별 메타데이터 섀도를 이전했다. 분석에는 일치하는 현재 계획과 활성 평가 예약 제어가 필요하므로, 전제가 없을 때 버튼을 비활성화하고 별도 승인 절차를 안내한다. 워커 활성화와는 구분한다. 이 안내는 기존 원본 컨트롤러에도 반영해 두 화면을 동기화했다.
- 검토된 계획·단일 제공자: 정확한 그래프/입력/대상을 검토한 새 초안 저장, 공개 목적만 공유하는 선택적 모델 제안, 제한된 단일 제공자 파일럿, 운영 근거·회로 정책·별도 탐색 확인을 새 화면에 연결했다. 실행/탐색/모델 호출에는 기존 서버 설정과 각 목적별 동의가 계속 필요하며, 미설정 기능을 임의로 활성화하지 않았다.
- 위 계획 작성에 필요한 앱 생성 API는 `options`, `plan-reviews`, `intent-reviews`, `model-proposals`, `commits`만 별칭에 추가했다. 다른 앱 생성 리뷰, SDK 수명주기, 지원 성과는 이번 별칭 범위에 넣지 않았다. 따라서 `workspace-growth` 전체 이전 완료로 계산하지 않는다.
- 새 네 패널은 입력을 바꾸면 선택해 둔 목적별 동의를 초기화한다. 변경 사유 자체의 편집은 이 초기화 대상에서 제외한다. 사유 누락은 명령 처리 전에 안내하며, 실제 작업 전에 감사 intent를 저장하지 못하면 차단한다. 원본 내용·모델 목적·토큰을 공통 감사 내용에 복제하지 않는다.
- 병렬 조회의 마지막 응답까지 로딩 표시를 유지하도록 요청 수를 추적한다. 조회 완료가 진행 중인 변경 요청의 중복 방지 상태를 해제하지 않도록 했다. 선택적 모델 제안의 화면 대기 시간은 서버 60초 예산보다 긴 90초로 맞췄다. 기존 원격 A2A/실행 대기 예산과 세션 변경 뒤 응답 폐기는 유지한다.

**검증 범위·운영 제한:** 운영 계정·고객 데이터·평가 워커·모델·외부 제공자를 사용하지 않고 격리 API·브라우저·합성 전송과 임시 PostgreSQL로 검증한다. 실제 독립 평가 품질, 운영 워커 활성화, 외부 모델 수락·성능을 검증한 것으로 표시하지 않는다. 결과와 증빙은 아래 완료 기록에 이어 적는다.

**기능·시큐어코딩 검증:** 고유 **23건** 근거를 확인했다. 신규 도구 최종 12건과 기존 배포 11건이며 중복 실행은 합산하지 않는다. 처음 20건 통과/2건 실패 중 2건은 격리 native launchd 등록·임시 포트 바인딩의 샌드박스 제한이었다. 임시 경로/합성 서비스만 사용해 두 건을 다시 실행했고 모두 통과했다. 실제 운영 서버를 띄우거나 재시작하지 않았다. 경로 탈출·자격증명 경로·심볼릭 링크·변조 패키지·단일 패키지·배포 중 상태·없는 증빙·원본 유지·기존 보고서 덮어쓰기 거부와 Caddy 비공개 경로/프록시 경계를 검증했다. 신규 파일 Ruff 통과. 공개 프론트엔드/서버 API 코드는 바꾸지 않아 기존 전체 브라우저 회귀를 반복하지 않았다. 운영 전체 보안/부하 검사나 실제 고객 배포 철회로 표시하지 않는다.

증빙: [최종 인벤토리](retirement/final-inventory.json), [판정 요약](retirement/final-summary.txt), [검증 범위](retirement/validation.json), [최종 도구 검사](retirement/final-tests.txt), [격리 native 재검사](retirement/native-isolated.txt), [최초 실패 보존](retirement/tests.txt), [소스 지문](retirement/source-sha256.json).

### 13.24 전체 설계 대비 완료 여부·부분 누락 재점검 (2026-10-23)

**최종 판정: 어드민 리뉴얼 전체 설계가 개발 완료된 상태는 아니다.** 전문 패널 기능 이전 22/22와 앞선 고정 작업 묶음의 완료는 확인되지만, 이를 설계 2~12장의 모든 요구사항과 운영 수용 기준 충족으로 확대할 수 없다. 특히 앞선 ‘남은 것은 조건부 폐기’라는 정리는 전체 설계의 아래 부분 구현을 충분히 드러내지 못했다. 이번에는 새로운 기능을 제안한 것이 아니라 기존 설계 문구와 소스의 차이를 재분류했다. 런타임 코드는 수정하지 않았다.

**확인한 완료 범위:** 7개 영역의 모듈 셸, 개인 세션·4개 역할·기계 토큰 제한·초기 비밀번호 변경, 공통 위험 명령, 카탈로그/고객/공개 서비스 관리와 전문 패널 이전, 영속 상태/일별 헬스 요약, 제한된 관측과 권한을 유지하는 Pearl 그래프, 메모리 캐시·ETag·변경 감지가 구현되어 있다. 전문 패널 22개 자산과 기존 링크 6개는 모두 존재하고 끊어진 목적지가 없다. 전문 생성 패널 18개와 직원 컨트롤러 생성물의 동기화 검사는 변경 없음으로 통과했다. 정적 대응 도구의 `migrated` 값은 관리된 분류이며 그 자체가 모든 기능의 동적 합격 증명은 아니다.

**새로 명확히 확인한 부분 누락은 6개 묶음이다.**

1. **G01 · 우선 수정 — 기존 운영 위험/데모 경로 경계 미적용 (설계 2·3.2·4.3).** `/admin/api/logs/clear`와 `/admin/api/visitors/simulate`에 운영 모드의 개발 기능 차단/대체 승인, 변경 사유와 감사 경계가 빠져 있다. `DEPLOYMENT_MODE=production`, 개발 모드 해제, 개인 최고관리자 세션인 격리 fixture에서 사유·승인 없이 둘 다 HTTP 200이었다. 로그 **메모리 버퍼**가 비워졌고, 모의 simulator가 1회 호출됐으며 `admin_audit_logs`는 추가되지 않았다. 영속 감사가 삭제됐다는 의미는 아니다. 개인 인증·교차 출처 방어는 존재하며 비인증 우회로 판정하지 않는다. 운영에서는 두 POST를 실행하지 않았다. 근거: `gateway/dashboard.py`의 `visitor_simulate`/`clear_logs`, `completion-audit/probe-result.json`.
2. **G02 · API 규칙 일부 미통일 (5.2).** 카탈로그 목록은 cursor를 쓰지만 고객 요청 목록 등에는 offset 방식이 남고, 새 에이전트 상세·인증·전문 화면 일부가 기존 API를 직접 쓴다. 현재 v2 입력 오류는 `{"detail": ...}`인 경로가 있어 설계의 `{error_code, message_ko, retryable}`와 다르다. 격리 API에서 잘못된 카탈로그 limit의 400 응답이 detail 필드만 반환하는 것도 확인했다. 기존 API 호환 유지 자체를 취약점으로 분류하지 않으며 전체 v2 계약 통일과 혼동하지 않는다.
3. **G03 · 운영 홈의 업무 요약 일부 누락 (8.1).** 현재 여섯 카드는 헬스체크 주기·등록 수·상태 확인 대기·p95·고객 요청·수집기다. 설계의 호출 가능 검증 수·고객 조직 수·미처리 지원 케이스 등과 전부 일치하지 않고, 승인/등록 심사/지원/사고를 모은 대기 작업 및 최근 감사 10건이 홈에 통합되어 있지 않다. 해당 기능이 다른 영역에 있다는 사실과 홈 통합 완료는 구분한다. 근거: `areas/home.js`, bootstrap 응답.
4. **G04 · 저장소 운영 정보 일부 누락 (8.4·5.3).** 현재 크기/추정 행 수·최근 24시간 기록 증가·잠금·느린 쿼리·보존 정책은 있다. 하지만 새 시스템 화면의 테이블별 **7일 크기 증가율**, 실제 백업 성공/신선도·복원 확인, 옛 SQLite 보관 상태는 연결되어 있지 않다. `backup_confirmed` 체크는 관리자의 확인이지 실제 백업 상태 계측이 아니다. 백업 실패를 정상으로 만들어 표시하면 안 된다. 근거: `admin_next.storage_data`, `areas/system.js`.
5. **G05 · 공통 표/검색/이동 편의 일부 미구현 (2·5.1·11.6).** 공통 표의 열 선택·권한을 확인한 CSV 내보내기·일반 정렬이 없다. 전역 검색에는 고객/조직/실행 ID와 카탈로그 검색이 있지만 워크플로 검색 분기는 없다. 설계 예시인 `#/catalog/agents/{id}?tab=evidence`의 단계/탭 복원이 없고, 현재 지원하는 상세 링크는 `#/catalog?agent=ID`다. 공통/카탈로그 흐름의 300ms 상세 미리 읽기와 페이지·스크롤·펼친 행 전체 복원도 구현되지 않았다. 필터 기억과 현재 지원 링크가 동작하는 것은 별도로 인정한다.
6. **G06 · Pearl 워크플로 시각화 적용 범위 일부 (8.3·12.5).** 새 그래프는 공개 템플릿과 직원 초안에 연결됐다. 그러나 조직 전문 관리의 typed-flow 편집기는 여전히 JSON textarea 중심이며 동일한 단계/상태 그래프가 없다. 기존 모든 워크플로와 최근 실행 표현까지 시각화를 완료한 것으로 표시하면 안 된다. 고객의 비공개 내용을 그래프 명목으로 열람할 권한을 추가해서도 안 된다. 근거: `areas/panel-flow.js`와 `pearl-flow.js`를 실제 사용하는 두 영역.

**이미 미완료/보류로 기록된 항목도 남아 있다.** 전용 페이싱 지연·완전한 후보 적격 전환 이력·실행 경로 정책/지표 통합은 제한된 기록 조회로 대체되지 않았다. 일별 헬스 요약과 영속 스냅샷은 있지만 5.3의 전체 요약 계열을 모두 구현한 것은 아니며, 게이트웨이 분 단위 집계는 13.10에서 보류했다. TOTP·일 단위 파티션·운영 보존 기간 변경/삭제는 기존 미적용 사항이다. 참고 데이터 L2는 13.0의 ‘아직 사용하지 않음’ 상태이며 비민감 허용 목록에 한정한 L1 캐시는 의도된 안전 경계다. 데이터 전체를 캐시하지 않는 것을 결함으로 보지 않는다. 인증 후 p95·cold·재방문 100ms·L1 적중률·304 비율 등 6.2/11.8의 운영 수용 목표는 현재 SQL/정적 GET 측정만으로 합격 판정할 수 없다. 관리자 모바일은 사용자 후속 지시에 따라 제외하며 누락으로 세지 않는다. 단독 최고관리자 승인 예외는 후속 결정에 따른 정책이며 새 결함으로 계산하지 않는다.

**전환/폐기:** `/admin/next`와 `/admin/ui` 병행 및 기존 링크 6개, 구 API·웹앱 v1/v12·옛 SQLite 유지가 남아 있다. 30일 완전한 무사용 관측·고객 배포 확인·복원/롤백 자료가 필요하다. 현재 관측 범위/누락을 증명한 연속 30일 자료는 미확인으로, 30일을 단순히 기다리면 끝나는 상태라고 안내하지 않는다. 앞선 9번 도구는 인벤토리 도구이지 무사용 집계를 시작하거나 삭제를 승인하는 도구가 아니다.

**검증 범위:** 이번에는 현재 소스와 설계/후속 결정, 기존 검증 기록을 대조하고 API 격리 검증 **20건(기존 회귀 19 + 결함 재현 1)**을 통과했다. 브라우저 검사 1건은 이 실행에서 선택하지 않았다. 재현 검사의 통과는 누락이 존재함을 확인했다는 뜻이며 보안 문제 해결 합격을 뜻하지 않는다. 새 전체 브라우저·전체 PostgreSQL·운영 부하/침투 검사는 하지 않았고 기존 검증 수를 중복 합산하지 않았다. 소스 지문 54개를 기록했으나 모든 파일을 개별 테스트했다는 의미는 아니다. 운영 데이터/서비스/자격증명은 변경하지 않았으며 서버 재시작은 필요 없다.

**마감 기준:** 위 G01~G06을 처리하거나 명시적으로 범위에서 제외하고, 기존 미완료/보류·성능 수용·기본 화면 전환/폐기를 각각 확정하기 전에는 ‘설계 전체 완료’라고 표기하지 않는다. 다음 개발을 요청하면 **G01 → G02·G05 공통 기반 → G03·G04 운영 화면 → G06 시각화**로 묶어 진행한다. 조건부 운영 수용과 보류 항목은 이 목록에 반복해서 새 기능처럼 추가하지 않는다. 이번 요청은 점검이므로 이 항목의 런타임 수정은 시작하지 않았다.

### 13.25 G01~G06 누락 및 리뉴얼 데스크톱 화면 보완 (2026-10-23)

사용자 요청에 따라 **화면의 미흡한 구성·배치·표현도 U01 작업으로 포함**했다. 권장 순서는 **운영 위험 경계 → v2·표·이동 공통 기반 → 홈/저장소 업무 화면 → 7개 영역 UI 보완 → typed-flow 시각화 → 기능·보안 검증 → 일괄 반영/운영 읽기 확인**으로 고정해 실행했다.

**개발·격리 검증 완료:** G01의 개발 전용 차단/사유/감사, G02의 v2 인증·상세·고객 운영 별칭/오류/cursor, G03의 실제 업무 요약과 권한별 감사, G04의 일별 크기 표본·백업/복원/보관 근거 조회, G05의 제한된 정렬/열/CSV/워크플로 검색/상세 URL·스크롤·로딩 복원, G06의 허용된 typed-flow Pearl 미리보기를 적용했다. 홈 카드 중복·순서, 폼/버튼/탭 일관성·표 도구 모음·사이드바·레이어를 정리했다. 수신·광고 동의/실행 권한/고객 비공개 조회 경계는 확대하지 않았다. 원본 호환 링크와 API는 유지한다.

**검증:** 고유 선택 범위 230건을 검증했다. 마지막 통합은 228건 통과·2건 실패였으며, 고객 v2 경로로 mock을 보완한 뒤 해당 두 건과 지연 로그아웃을 포함한 3건이 모두 통과했다. 단일 실행 230건 전부 통과로 합산하지 않는다. 최초 통합의 실패 7건은 v2 인증 mock 보완 후 모두 재검증했으며, 실행별 중복 수를 합산하지 않았다. 실제 PostgreSQL cursor 타입 추론 오류도 수정했고 임시 PostgreSQL 최종 검증을 통과했다. 7개 영역×2테마 데스크톱 브라우저 검사, 관련 전문 패널 여정, JS 42개 문법, 생성물/SQL 카탈로그 동기화, 공개 콘텐츠 249개 위반 0건을 확인했다. 기존 미사용 import/변수 정적 경고 13건은 별도 기록했다. 운영 부하·실제 복원/장기 성능 수용으로 확대 해석하지 않는다.
