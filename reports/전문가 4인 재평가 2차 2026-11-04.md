| 분야 | 1차 | 2차 | 바뀐 이유 |
|---|---|---|---|
| UI/UX 기획 | 3.7 | **3.9** | 첫 방문 배너가 첫 동작을 가리지 않는다. 되묻기에 선택지가 있다. 숫자 위계가 생겼다 |

### 3.1. UI/UX 기획 (3.9/5)
- **좋아진 점:** 첫 방문자가 처음 보는 화면에서 과업 입력과 "Find matches"가 가려지지 않는다. 모호한 요청에 누를 수 있는 선택지가 나온다. 홈의 숫자가 "지금 연결 가능"을 앞세운다.
- **남은 지적**
  - B3: 조건이 없는 일반 과업의 추천 카드에는 "왜 이 후보인가"가 여전히 단어 일치("the listing covers …")다. 검색과 RAG 세션에 넘겼다.
  - 폰에서 배너가 위쪽에 있는 동안은 메뉴 버튼이 가려진다. 선택하거나 닫으면 사라지지만, 닫기(×)가 무엇을 선택한 것인지(필수만 유지) 배너에 적어 두면 좋다.

### 3.2. 웹 디자인 (4.3/5)
- **좋아진 점:** 다크 테마의 모든 주 버튼이 기준을 넘는다. 폰 네 화면에서 12px 미만 글자가 0이다. 배너의 나타남이 깨끗하다.
- **남은 지적**
  - 숫자 위계는 CSS 순서(2번째 카드)에 기대므로, 카드 순서가 바뀌면 다른 숫자가 커진다. 마크업에 강조 표시(예: `data-primary`)를 두는 편이 안전하다.
  - D2(아래 3.4)는 디자인보다는 구현 문제다.

### 3.3. AI 개발 (3.4/5)
- **좋아진 점:** 에이전트가 읽는 `task_fit`이 요청 조건마다 판정을 담는다(키 없음, 언어쌍, 지역, 예보, PDF 입력). 정책 이름이 응답에 나온다. 모호하면 선택지를 준다.
- **남은 지적(검색과 RAG 세션의 계획이 다룸)**
  - PDF 요약(rv2)과 영→한 번역(rv3)의 1위, 웹사이트 상태(rv10)의 1위가 과업 핵심과 어긋난다.
  - 날씨 1위의 예보 기간이 unknown인데, 2위는 matched다. 같은 적합도라면 조건을 더 충족한 후보가 앞서야 한다.
  - 정책 파일 변경마다 평가를 자동으로 돌리는 단계(A-3)가 아직 없다.

### 3.4. 웹 개발 (4.5/5)
- **좋아진 점**
  - MCP 2025-11-25의 tasks를 공개 워크플로 실행에 붙였다. 새 권한 없이 REST와 같은 검사이고, 작업 ID가 실행 키를 품는다.
  - 브라우저 에이전트용 WebMCP 도구를 등록한다.
  - 수집기 요청 서명(RFC 9421)과 공개 키 주소를 준비했다.
  - edge 캐시가 10분 보관하고, 브라우저 쪽은 원 서버 값을 따른다.
- **남은 지적**
  - **Web Bot Auth:** 12:50에 frontend에서 켰다(4절). 수집기(jobs)는 다음 jobs 배포 때 켜진다.
  - **D2 숨은 화면은 보류했다.**
    - 공개 HTML 요소의 64~77%가 숨은 패널 템플릿 안에 있다. 패널 안 요소 ID 207개 중 116개를 `operating.js`가 직접 참조한다.
    - 늦게 펼치려면 116곳을 모두 "필요할 때 펼치기"로 바꿔야 한다. INP가 이미 최대 64ms(본 보고서 랩 측정)로 좋아 얻을 것이 적다. 반면 실패하면 버튼이 조용히 안 듣는 식으로 깨진다.
    - 다른 세션도 `operating.js`를 고치고 있다(작업본 미커밋 변경).
  - **탐색 3초:** 부하 10에서 처음 보는 검색어 1건이 서버 3.22초였다. 연결 재사용 기준으로 부하가 낮을 때 다시 재야 한다.

## 4. Web Bot Auth 켜기 (12:50, 사용자 지시로 실행)
- 사용자가 "직접 실행해줘"라고 지시해 아래 순서로 켰다.
  1. 키 생성: `gateway-data/web-bot-auth/ed25519.pem`(권한 600, git 제외). 키 ID `oQ8G-0gvuPA8h8SPzJ3q0Sh5ZFK_JexAZAmwnclNm3g`.
  2. 처음 안내한 대로 `gateway-data/agentcon.env`에 키 경로를 더했다. 그러자 배포 도구가 "unsupported setting name"으로 멈췄다.
     - 이 파일은 허용된 이름만 받고, 보관 중인 옛 릴리스도 모두 읽는다.
     - 바로 사본으로 되돌렸다. 두 슬롯은 바뀌지 않았고 운영 페이지는 200이었다.
  3. 키 경로를 별도 파일 `gateway-data/web-bot-signer.env`(권한 600, git 제외)에 두고, 새 코드만 읽게 했다.
     - `scripts/agentcon_config.read_web_bot_signer_settings`, `service_host`가 읽고 절대 경로로 바꾼다.
     - 옛 릴리스는 이 파일을 모르므로 다시 시작해도 영향이 없다.
  4. `bot-auth-frontend-20261104-r2`(small-text-r1 위 2개 파일)로 배포했다(활성 a, 배포 전 점검 통과).
- **운영 확인**
  - `/.well-known/http-message-signatures-directory`가 200이다(`application/http-message-signatures-directory+json`, 공개 키 1개).
  - 응답 서명(`tag="http-message-signatures-directory"`)이 공개 키로 검증된다.
  - frontend가 남의 서버로 보내는 요청(`public_client`)에도 서명이 붙는다.
- **jobs:** 수집기는 jobs 릴리스에 `web_bot_signer.py`, `broker/discovery.py`, `service_host.py`, `scripts/agentcon_config.py`가 실린 뒤부터 서명한다. 백엔드 세션에 알렸다(jobs 배포는 사용자 승인 필요).
- **끄기:** `gateway-data/web-bot-signer.env`를 지우거나 이름을 바꾸고 frontend를 다시 배포한다.
