# 페이지 본문 전송 시간과 1초 넘는 페이지 (PM 11-13 20:2x 지시 ①②)

측정: 11-13 20:25~20:33, 이 맥(한국)에서 공개 주소로 잼. 표본마다 새 연결을 쓰고 1초 간격으로 보냈으며, 빼낸 표본은 없다. 도구는 `scripts.user_slo`와 같은 httpx 연결(HTTP/1.1, gzip)이고, 덩어리마다 도착 시각을 기록했다(`probe.py`). 원자료는 `probe-*.json`(61표본), `origin-times.txt`(원서버 57개 페이지), `slow-pages-1831.txt`(18:31 전수 점검에서 1초를 넘은 57개)다.

## 결론

- 원서버는 느리지 않다.
  - 원서버(127.0.0.1:8400, Caddy 경유)에서 페이지 57개 모두 본문 끝까지 0.07초 안에 나왔다.
  - 첫 바이트와 마지막 바이트의 차이는 2ms 안이다. 본문을 천천히 흘려보내지 않는다.
- 엣지도 기다리지 않는다.
  - UPDATING(묵은 사본을 주면서 뒤에서 갱신)과 HIT는 TLS가 끝난 뒤 첫 바이트까지 똑같이 약 0.33초가 걸렸다(왕복 1번).
  - Cache-Control은 `public, max-age=300, stale-while-revalidate=86400`이다. 묵은 사본을 바로 주고 있으므로 헤더는 바꿀 필요가 없다(s-maxage는 쓰지 않음).
- 느린 원인은 한국→LAX 경로의 패킷 손실이다.
  - 본문 중간이 0.32·0.63·1.08초씩 멈췄다. 두 배씩 늘어나는 TCP 재전송 대기 모양이다.
  - TLS 핸드셰이크가 0.46초 대신 1.0~3.2초가 된 표본도 같은 원인이다.
  - 엣지 캐시 적중(HIT)에서도 똑같이 일어났다.
- **응답이 클수록 많이 멈춘다.** 같은 시간대, 같은 경로에서 잰 결과다.

| 압축 뒤 크기 | 표본 | 1초 넘음 | 본문 멈춤(0.25초 넘는 공백) |
|---|---|---|---|
| 14.6KB 이하(첫 전송 한 번에 들어감) | 26 | 10 (38%) | 1 (4%) |
| 14.6KB 넘음 | 35 | 25 (71%) | 19 (54%) |

- 멈춤 없이 깨끗했던 표본 27개의 시간: 최소 0.74초, 중앙값 0.81초.
  - 구간은 TCP 0.135초, TLS 약 0.33초, 요청·응답 약 0.33초다.
  - ping 왕복은 0.32초다. 한국에서는 TCP를 가까운 곳이 받고, TLS와 응답은 LAX에서 온다(무료 플랜 경로).
  - 그래서 1초 목표의 여유는 약 0.2초뿐이다. 손실이 한 번만 나도 넘는다.

## ① HTML 본문: 크기와 줄이는 안

| 페이지 | 압축 전 | gzip(전송) | 본문에 넣은 CSS(압축 전) | meta | svg | 인라인 script |
|---|---|---|---|---|---|---|
| / | 151.6KB | 34.8KB | 65.8KB | 20.9KB | 17.3KB | 8.7KB |
| chat.html | 140.8KB | 31.6KB | 80.4KB | 18.3KB | 9.6KB | 6.2KB |
| explore.html | 146.5KB | 32.5KB | 86.9KB | 18.3KB | 8.0KB | 6.2KB |

- Cloudflare 압축 크기(chat): gzip 31.6KB, br 32.0KB, zstd 34.0KB. br로 바꿔도 작아지지 않는다.
- 첫 화면 CSS만 gzip 15.7~17.1KB다. 이것 하나로 이미 14.6KB를 넘는다.

안:
1. **(이미 승인된 14KB 과제 A·B·C를 이 근거로 먼저 함)**
   - A: 첫 화면 CSS를 첫 뷰포트에 실제로 그려지는 규칙만으로 줄인다.
   - B: CSP meta를 지운다. 헤더와 같다는 시험을 붙인다.
   - C: 중복 SVG 아이콘을 합친다.
   - 목표는 세 화면(/, chat, explore) 모두 gzip 14.6KB 이하다. 위 표대로라면 본문 멈춤이 54%에서 약 4% 수준으로 준다.
2. 그래도 넘으면 PM이 사용자에게 지연 로딩 예외를 묻는다(기존 결정 그대로).
3. 엣지 캐시 헤더는 바꾸지 않는다. 이미 묵은 사본을 바로 주고 있어 얻을 것이 없다.

나머지 49개도 원서버 0.00~0.06초다(`origin-times.txt`).

- 이 페이지들은 이미 스냅샷·캐시에서 나온다. 스냅샷을 더 만들어도 1초 안으로 들어오지 않는다.
- 느린 표본은 모두 TLS나 본문에서 손실 대기가 생긴 것이다.
- 18:31 같은 시각의 경로 바닥값도 1.80초였다(전수 점검의 `ref.edge_s`).

남은 안(무료, 요청 경로에 실시간 DB 재확인 없음):
1. **고지 페이지 5개 엣지 캐시.**
   - 대상: disclosures, privacy, cookies, accessibility, contact.
   - 지금은 `presentation_only_pages`라서 `no-store`(DYNAMIC)이다. 매 요청이 LAX→터널→이 맥까지 다녀온다.
   - 방문자마다 같은 바이트이므로 live 페이지와 같은 `PUBLIC_PAGE_CACHE`를 주면 HIT가 된다. X-Robots-Tag(noindex)는 그대로 둔다.
   - pearl_view.py 한 줄과 시험이면 된다. PM이 승인하면 다음 frontend 묶음에 넣는다.
   - 같은 `presentation_only_pages`인 terms.html, service-disclosures.html도 고지 문서라 같이 넣을 수 있다.
   - 시안·시험용 화면(components, gallery, workspace-* 등)은 넣지 않는다. 명시한 목록만 캐시한다.
2. **sitemap.xml을 sitemap 색인과 종류별 sitemap으로 나눈다.** 각각 gzip 14KB 이하로 만든다(sitemap 규약 안). 지금 35.5KB는 HIT에서도 본문 멈춤이 난다.
3. 큰 HTML 화면(learn 31KB, workflows 40.6KB, test 37.7KB, agent-status 29.7KB, /customer/sign-in 42.7KB)은 ①의 첫 화면 CSS 축소로 함께 줄어든다.
4. 바꿀 수 없는 것: 한국→LAX 경로(무료 플랜)와 그 경로의 손실.
   - 작은 페이지(2~5KB)의 1초 초과는 TLS 손실 대기라서 원서버로는 줄일 수 없다.
   - 유료 경로(Argo 등)는 지출 0 결정으로 쓰지 않는다.
5. 참고: `/api/agents/42683`(41.7KB, no-store)는 페이지가 아니라 API다. 크기를 줄이는 일은 담당 팀 몫이다.

## 측정하다 생긴 일

원서버에 직접 1초 간격 없이 약 100회 요청해서 127.0.0.1이 분당 60회 읽기 한도에 걸렸다(429 23건, 1분 뒤 풀림, 가둠 없음).
- 공개 방문자는 CF-Connecting-IP로 따로 세므로 영향이 없다. 공개 주소는 그동안 200이었다.
- 이후 원서버 측정은 1.2초 간격으로 했다.

## 14KB 과제 A·B·C 결과 (11-13 21시, PM 20:5x 지시 ①)

| 항목 | 결과 | 이번 묶음 |
|---|---|---|
| B: CSP meta 제거 | 압축 뒤 약 0.12KB. live 화면의 빌드 기본 meta만 빼고, 응답 헤더가 모든 지시어에서 같거나 더 엄격한지 시험한다. 고지 화면에는 더 엄격한 별도 meta(인라인 style 금지, connect-src 'none')가 있어 그대로 남긴다 | 넣음 |
| C: SVG 아이콘 합치기(`<use>`) | 압축 뒤 오히려 48~57바이트 커짐. gzip이 이미 같은 아이콘을 줄이고 있다 | 하지 않음 |
| A: 첫 뷰포트 CSS | 접힌 선 아래만 쓰는 규칙을 빼면 화면당 압축 뒤 0.8~1.9KB 준다(홈 14.6→13.2, chat 16.6→15.7, explore 17.5→16.7KB). 그러나 데이터에 따라 달라지는 요소(explore MCP 카드 색, 홈 숨김 요소 2개, workflows 레이아웃 이동)가 시험에서 전체 CSS와 달랐다 | 넣지 않음. 빌더에 `--first-viewport` 선택지로만 남김 |

- 14KB 안에 들어가지 못하는 이유(압축 뒤 크기)
  - 첫 화면 CSS를 아예 빼도 홈 17.2KB, chat·explore 약 14.6KB다.
  - 화면마다 다른 화면 8개 분량의 `page:*` meta가 2.0~2.5KB 들어 있다(chat 67개). agent:* meta는 0.5~1.2KB다.
  - 그래서 meta를 그대로 두는 한 14KB는 어렵다. 다른 화면 몫의 page:* meta를 옮길지는 PM 결정 사항이다(외부 등록처가 읽는지 확인되지 않음).
