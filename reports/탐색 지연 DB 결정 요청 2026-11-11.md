- 리허설 판정: application_refuses_changed_database.

  - 차가운 사본에서 5초 제한을 넘은 것으로 보인다. 다만 확인 전까지는 "통과 못 함"으로 둔다.

결론:
- halfvec는 메모리를 절반으로 줄인다. 하지만 진짜 문제는 필터다.
- 활성 MCP는 40,486개로, 임베딩 33만 개의 12%뿐이다. 그래서 전체 그래프를 3만 블록이나 훑고도 결과는 60개, 재현율은 0.26에 그친다.
- 이것은 속도 문제이면서 품질 문제다. MCP 질의의 임베딩 후보 4개 중 3개를 놓친다.

## 3. 권하는 안: D' = 종류별 halfvec 부분 HNSW (리허설 필요)

- 바꾸는 것:
  - `agentcon_search.embeddings`에 `kind text`를 추가한다.
  - 저장 코드(postgres_ann.store)가 kind를 함께 쓴다.
  - 33만 행을 한 번 채운다.
  - 종류마다 `CREATE INDEX CONCURRENTLY … USING hnsw ((embedding::halfvec(768)) halfvec_cosine_ops) WHERE kind='mcp'`을 만든다(a2a, x402도 같은 방식).
  - 검색 SQL은 `AND e.kind=%s`와 halfvec 정렬을 쓴다. 등록 SQL에 추가해야 한다.
  - public 스키마에는 트리거를 만들지 않는다(앱 불변식 5개 유지).
- 예상 크기(halfvec 668MB를 비율로 나눔):
  - mcp 약 85MB, a2a 약 320MB, x402 약 265MB
  - 질의 하나는 자기 종류 그래프만 본다. MCP 검색의 작업 집합은 1,336MB에서 약 85MB가 된다.
- 기대 효과:
  - 필터가 거의 없어진다. 그래서 재현율이 필터 없는 값(0.97 안팎)에 가까워지고, 블록 수가 크게 준다.
  - 이 값은 리허설로 재야 한다. 지금은 추정이다.
- 적용 시간과 잠금:
  - ADD COLUMN(기본값 없음)은 짧은 ACCESS EXCLUSIVE 잠금이다(밀리초).
  - 채우기는 1만 행씩 나눠 UPDATE한다. embeddings는 HNSW가 걸린 표라 행마다 색인 갱신이 일어난다. 예상 10~20분, 새벽에 한다.
  - 색인 3개는 CONCURRENTLY로 만든다. 합계는 halfvec 하나와 비슷한 약 10분이고, 쓰기를 막지 않는다.
  - 마지막으로 옛 vector HNSW를 `DROP INDEX CONCURRENTLY`로 지운다. 1.34GB가 확보된다.
- 복구 SQL:
  ```sql
  -- 앱을 옛 버전으로 되돌린 뒤
  DROP INDEX CONCURRENTLY IF EXISTS agentcon_search.embeddings_half_mcp;
  DROP INDEX CONCURRENTLY IF EXISTS agentcon_search.embeddings_half_a2a;
  DROP INDEX CONCURRENTLY IF EXISTS agentcon_search.embeddings_half_x402;
  ALTER TABLE agentcon_search.embeddings DROP COLUMN IF EXISTS kind;
  -- 옛 색인을 이미 지웠다면 다시 만든다(약 10분, 그동안 탐색은 느림)
  CREATE INDEX CONCURRENTLY embeddings_cosine_hnsw ON agentcon_search.embeddings
    USING hnsw (embedding vector_cosine_ops) WITH (m='16', ef_construction='64');
  ```
- 순서: 코드 → 사본 리허설(새벽, 병렬 0, nice 10) → 결정 → 적용(새벽) → 공개 주소 재측정. 옛 색인 삭제는 1주 관찰 뒤에 한다.

## 4. projection·documents 축소안

| 단계 | 읽는 표 | 크기(본표 + TOAST + 색인) | 쿼리 평균 | 호출당 디스크 블록 |
|---|---|---|---|---|
| projection | resources ⨝ capability_text ⨝ resource_observation_generations | 701+1,108+539MB, 269+223+11MB, 29MB | 46ms | 248 |
| documents | explore_documents | 286+439+13MB | (Server-Timing 97~1,023ms) | - |

활성 행은 24만 개다. 후보 100~600개를 무작위 id로 읽으므로 큰 행이 섞인 페이지를 통째로 읽게 된다(resources 한 행 평균 약 1.9KB).

- P1(권함): 작은 투영 표 `agentcon_search.rank_projection`
  - 열: resource_id, kind, 필터 열(active, health, security), eval_score, name, description, rank_text, rank_hash, generation, document
  - 활성 행만 담는다. 약 24만 × 1.1KB ≈ 270MB로, 메모리에 계속 머물 수 있는 크기다.
  - projection과 documents가 이 표 하나만 읽는다.
  - 갱신은 이미 있는 문서 큐(jobs)가 함께 쓴다.
  - 정책 해시 파일을 건드리지 않게 설계해야 한다. 큰 작업이고, 리허설이 필요하다.
- P2(작음): resources 덮개 색인 `(id) INCLUDE (kind, active, health_status, eval_security, eval_score)`
  - 필터 확인만 색인으로 한다. name과 description은 여전히 본표에서 읽어야 해서 효과가 제한적이다(추정 20~30%).
  - 색인 크기는 약 30MB, CONCURRENTLY로 만들 수 있다.
