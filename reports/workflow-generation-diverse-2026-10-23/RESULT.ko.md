# 워크스페이스 워크플로우 생성 점검·수정 결과

2026-10-23 · 소스 수정·검증 및 사용자 재시작 후 배포 확인 완료

고객 API의 생성 후처리까지 검증 범위를 넓혀 첫 44개 요청 중 21개 문제를 발견했습니다. 수정 후 기존 44개와 추가 경계 사례 8개를 합한 52개가 모두 예상 처리 기준을 충족했습니다.

## 시험 범위와 결과

- 실제 맥미니 모델 `gemma4-e4b-mlx`를 사용한 고객 워크플로우 API 요청 52개.
- 최종 처리: 검토 가능한 워크플로우 31개, 보완 안내 17개, 민감하거나 유효하지 않은 입력 차단 4개.
- PASS는 모든 입력을 워크플로우로 만들었다는 뜻이 아닙니다. 지원되지 않는 업무·모호한 조건·범위를 넘는 요청은 생성하지 않고 안내해야 통과입니다.
- 생성 자체가 에이전트 실행이나 저장을 일으키지 않는 것을 확인했습니다. 31개 생성에서 모델은 각 1회 호출됐고 제공자 실행은 0회입니다.
- 대표 8개를 실제 Chromium의 고객 화면에서 검증했습니다. 6개는 생성 → 별도 저장 동의 → 저장 → 별도 실행 동의 → 격리 MCP 실행까지 성공했고, 2개는 보완 안내와 입력 거절을 확인했습니다. 데스크톱·모바일 화면 캡처 22개를 남겼습니다.

모든 계정·카탈로그·제공자는 일회성 합성 데이터입니다. 운영 고객 계정의 크레딧·저장된 워크플로우·실행 기록을 사용하거나 변경하지 않았습니다. 실제 외부 제공자 가용성 시험과는 구분됩니다.

## 발견한 문제와 해결

1. **뉴스·문서 혼합 구성이 생성 후 덮어써짐**
   모델이 뉴스→문서 또는 문서→뉴스 구조를 만들어도 후처리가 이를 문서 주제 목록으로 해석해 문서 전용 구성으로 변경했습니다. 실제 고객 API에서는 HTTP 400으로 끝났습니다. 혼합 계약 연결과 같은 계약의 다중 주제를 분리해 처리하고 최종 그래프의 계약 종류·순서를 다시 확인하도록 수정했습니다. 모델 어댑터만으로는 이 고객 API 후처리 오류를 확인하지 못했습니다.

2. **독립 검색과 결과 연결이 구분되지 않음**
   독립적으로 검색하라는 요청에도 두 번째 검색어를 첫 결과 제목으로 대체했습니다. 명시된 독립 요청과 여러 문서 주제는 각자의 검색어를 사용하고 바인딩·의존 관계를 없앴습니다. 연결 요청은 이전 단계의 첫 title만 전달합니다. 주제별 승인 후보도 기존 순서를 지키면서 가능한 한 나눠 사용합니다.

3. **단계 수·주제 수·부정 조건 오류**
   `without news using 3 steps`에서 부정 문구와 함께 단계 수까지 지워졌습니다. `eleven steps`는 기본 2단계로 생성됐고, 11개 주제는 10개로 조용히 잘렸습니다. 숫자·영문 수사·한국어 숫자 단계 표현을 처리하고, 2~10단계와 주제 수의 일치 여부를 먼저 검사합니다. 초과·충돌은 자르지 않고 보완 안내를 반환합니다. `Do not send emails`는 전송 요청으로 취급하지 않습니다.

4. **결과 수·뉴스 기간 무시**
   3개·5개 결과를 요청해도 항상 1개, 7일·12시간을 요청해도 항상 24시간으로 구성됐습니다. 명시한 결과 수와 뉴스 시작 시각을 실제 노드 입력에 적용했습니다. 현재 검토 프로필의 결과 수 1~5개, 뉴스 기간 1~168시간을 넘거나 서로 충돌하는 조건에는 해당 제한을 구체적으로 안내합니다.

5. **한국어 요청 처리 누락**
   한국어 3단계를 2단계로 만들고, 뉴스→문서 순서와 뉴스 제외 조건을 잘못 처리했습니다. 계약 이름·순서·단계·요약/번역 업무에 대한 입력 별칭을 정규화했습니다. 제품 화면 문구는 영어를 유지했습니다.

6. **지원하지 않는 업무를 검색으로 대체**
   날씨 예보나 번역 요청에도 뉴스·문서 검색 그래프를 제안했습니다. 현재 승인된 검색 계약으로 충족할 수 없는 업무는 모델을 호출하기 전에 보완 안내를 반환합니다. 요약·번역을 실제 수행하라는 요청과, 요약·번역 알고리즘의 문서를 찾으라는 요청은 구분합니다.

7. **검색 주제와 작업 종류 혼동**
   `documentation about news APIs`의 news를 별도 뉴스 작업으로 판단했습니다. 작업 종류는 주제를 설명하는 about/on 등의 앞부분에서 판별합니다. `API`와 `APIs`처럼 단순 복수형 차이도 허용해 정상 생성 결과가 거절되지 않게 했습니다.

8. **검색어에 구성 지시·임의 버전 혼입**
   수동 검토에서 검색어에 `two steps`가 포함되는 사례를 발견했습니다. 원래 주제에 없는 단계 지시는 제거합니다. 명시된 버전은 유지하고, 임의 버전 추가·삭제·교체는 차단합니다. 검색 주제 검증 실패는 저장/실행이 불확실하다는 오류 대신 주제를 보완하라는 안내로 반환합니다.

## 수정 후 실제 생성 예

- `Find battery recycling news then supporting documentation using exactly two steps`: 뉴스 → 문서, 두 번째 query는 첫 뉴스 결과 title에 연결.
- `Find Python documentation then related news using exactly two steps`: 문서 → 뉴스 순서를 유지.
- `Find documentation for 3 topics: Docker, Kubernetes and Terraform`: 독립된 검색 3개, 각 검색어를 유지하며 이전 결과에 묶지 않음.
- 한국어 Python 문서 3단계 요청: 문서 검색 3개, 첫 검색어 `Python documentation`.
- `Return 3 results per step`: 각 노드 limit=3. `last 7 days`: 뉴스 from_utc에 실제 168시간 전 시각 적용.
- 날씨·번역·요약 실행 요청: 지원 범위 보완 안내, 모델 호출 0회. URL·토큰·빈 문자열·초과 길이 입력은 거절.

전체 52개 원문 요청, 생성된 단계·검색어·연결·기간과 수정 전후 판정은 엑셀 및 `GENERATED-RESULTS.ko.md`에 기록했습니다.
