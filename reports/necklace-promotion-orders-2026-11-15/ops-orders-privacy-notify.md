# 주문 제작: 저장·보존·접근과 무료 알림 경로 (운영·SRE, 2026-11-15)

PM 14:57 지시 2·3번. 계획은 같은 폴더의 README.md 3.3절이다. 여기서는 연락처(개인정보)를 어디에, 얼마 동안, 누가 보게 두는지와 완성 안내를 보내는 무료 경로를 정한다. 운영 DB에는 아직 아무것도 만들지 않았다.

## 1. 저장 위치

- **운영 PostgreSQL의 자기 스키마 `necklace_orders`**(새 스키마)에 표 2개를 둔다. public 스키마에는 표·트리거·함수를 만들지 않는다. 운영 앱은 연결마다 public 트리거가 정확히 5개인지 검사하기 때문이다(11-10 장애).
  - `necklace_orders.orders`
    - 칸: 주문 id, 받은 시각, 상태(received·building·done·declined·expired), 하려는 일, 입력 예시, 원하는 출력, 거절 이유, 완성된 목걸이 slug, 안내 보낸 시각
    - 하려는 일·입력 예시·원하는 출력 칸에는 길이 상한을 두고 주입 문구 검사를 거친다.
  - `necklace_orders.contacts`
    - 칸: 주문 id, 연락 종류(email·callback), **봉인된 연락처**, 연락처 HMAC, 동의 시각, 동의 문구 버전, 지운 시각
- **봉인**: 연락처 원문은 서버 키로 봉인(Fernet)해서만 저장한다. `customer_identity`의 방식과 같다. 키는 지금 쓰는 서비스 키에서 용도 문자열(`necklace-order-contact`)로 HMAC 파생하므로, 새 비밀값 파일이 생기지 않는다.
  - 같은 연락처의 반복 주문 묶기와 속도 제한은 HMAC 값으로만 한다. 원문을 풀지 않는다.
- **로그·현황판·보고서에는 연락처를 쓰지 않는다.** 주문 id와 연락 종류만 쓴다. 에러 메시지에도 넣지 않는다.
- **구조 변경 절차**: 스키마 SQL과 복구 SQL(`DROP SCHEMA necklace_orders CASCADE`)을 만든다. `scripts.db_change_rehearsal run`으로 사본에서 네 역할 연결까지 통과시킨 뒤 PM이 실행한다(사용자 11-15 위임). 트리거와 함수는 두지 않는다. 표만 둔다.
- 표가 생기기 전에는 주문을 받지 않는다. 임시로 파일에 연락처를 쌓는 길은 쓰지 않는다. 여러 프로세스가 쓰는 데다 백업·권한이 따로 놀기 때문이다.

## 2. 보존 기간

| 무엇 | 기간 | 끝나면 |
|---|---|---|
| 연락처 원문(봉인값) | 완성 안내를 보낸 뒤 30일, 또는 만들 수 없다는 답을 보낸 뒤 30일. 안내를 못 보낸 주문은 받은 뒤 90일 | 봉인값과 HMAC을 지우고 `지운 시각`만 남긴다(행은 남김) |
| 주문 내용(할 일·예시·출력) | 1년 | 연락처가 지워진 뒤에는 개인을 알 수 없는 통계용으로만 남긴다. 1년 뒤 지운다 |
| 동의 기록(시각·문구 버전) | 연락처와 같이 지운다 | — |

- 지우기는 jobs의 하루 1번 단계로 한다. 지운 건수만 한 줄 기록한다.
- 요청자가 지워 달라고 하면 바로 지운다(주문 상태 화면에 "연락처 지우기"). 지운 뒤에는 안내를 보낼 수 없다는 것을 알린다.
- 연락처는 그 주문의 완성 안내에만 쓴다(계획 2절). 광고성 연락, 다른 주문과의 연결, 외부 전달에는 쓰지 않는다.

## 3. 접근 범위

| 누가 | 무엇을 | 어떻게 |
|---|---|---|
| frontend(주문 받기) | orders·contacts에 넣기만 함 | 등록된 SQL의 INSERT뿐. 읽기·고치기 없음 |
| jobs(지우기·안내 보내기) | 연락처를 풀어 안내 1건 보내기, 기간 지난 것 지우기 | 등록된 SQL. 푼 값은 메모리에서만 쓴다 |
| admin 화면 | 주문 목록(연락 종류만, 원문 없음) | 원문을 보여 주는 화면은 만들지 않는다 |
| PM 보고(안내 경로가 생기기 전) | 주문 id·할 일·상태 | 연락처 원문은 보고에 넣지 않는다. 사용자가 직접 답할 때 필요하면 사용자 본인이 admin에서 한 건씩 연다(원문 열람 기록을 남김) |
| 팀 세션 | `scripts.prod_ro_sql`로 orders 집계 | contacts 표는 prod_ro_sql 허용 목록에 넣지 않는다 |

## 4. 완성 안내의 무료 경로

| 경로 | 비용 | 계정·권한 | 판단 |
|---|---|---|---|
| **A. 주문 상태 주소(끌어가기)**: 접수 때 비밀 토큰이 든 주소 `/orders/<token>`를 준다. 완성되면 그 주소에 확인 결과(토큰 절약·속도·정확도)와 사용법이 뜬다. 에이전트용으로는 같은 내용을 JSON과 MCP 도구 `order_status`로 준다 | 0 | 없음 | **바로 할 수 있다. 1순위.** 보낼 것이 없어 실패할 일이 없다. 메일을 주지 않은 요청자도 받는다 |
| **B. 에이전트 콜백(HTTPS POST)**: 요청자가 준 https 주소로 완성 알림을 보낸다 | 0 | 없음 | 할 수 있다. 조건은 아래와 같다. |
| C. 사용자 Gmail로 보내기(@agentconcierge.biz는 이미 Gmail로 들어옴) | 0(Gmail 하루 약 500통) | **사용자 몫**: Gmail "다른 주소로 보내기"에 contact@ 등록(인증 메일 확인), 서버가 보내려면 앱 비밀번호나 OAuth 동의 | 서버 자동 발송은 사용자 계정 작업과 비밀값 입력이 필요하다. 사용자가 원할 때만 |
| D. Claude의 Gmail 연결로 보내기 | 0 | **사용자 몫**: 메시지마다(또는 규칙으로) 사용자 승인 | 자동이 아니다. 주문이 적은 지금은 PM이 목록을 보고하고, 사용자가 승인하면 보낼 수 있다 |
| E. Cloudflare Email Routing의 Worker 발송 | 0 | 받는 주소를 미리 인증해야 함 | 처음 보는 요청자 주소로는 못 보낸다. 쓰지 않는다 |
| F. 유료 메일 발송 서비스 | 있음 | 계정 생성 | 지출 0 원칙으로 쓰지 않는다 |

B의 조건은 다음과 같다.
- `check_public_url` 검사를 하고 사설 주소는 막는다.
- 리다이렉트는 따라가지 않는다.
- 본문에는 개인정보 없이 주문 id·상태·상태 주소만 넣고, HMAC 서명을 붙인다.
- 5초 시간 제한, 재시도 3회(1분·10분·1시간), 결과 기록을 둔다.
- 받는 쪽이 4xx로 답하면 멈춘다.

**권장 순서**
1. A를 먼저 만든다. 메일 주소는 받되 "완성되면 이 주소에서 확인"을 기본 안내로 한다.
2. 콜백 주소를 준 에이전트에게는 B로 알린다.
3. 메일 발송(C)은 사용자가 계정 작업을 해 줄 때까지 보류한다. 그동안 메일만 남긴 주문은 PM이 목록(연락처 원문 없이)을 사용자에게 보고한다.
