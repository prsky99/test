# 방문 기록 재현·요청 품질 개선 결과

2026-10-25, Agent Concierge. 운영 카탈로그·공개 서비스·실제 공급자 응답과 격리된 브라우저/API 앱을 함께 확인했다. 이 문서는 이번 코드 수정의 검증 기록이다. 원본 토큰·IP·방문자 식별자·연락처는 포함하지 않는다.

## 결론

실제 품질 문제가 있었다. 단어가 비슷한 에이전트를 찾거나 HTTP/프로토콜 응답을 받았다는 사실을, 요청을 수행했다는 사실과 혼동하는 경로가 있었다. `ai news`의 AI가 검색어 처리에서 빠졌고, 암호화폐·특정 지역 뉴스·단순 도구 안내·빈 응답·pong이 좋은 후보처럼 표시될 수 있었다. 일부 A2A 연결은 실제 JSON-RPC 실행을 지원하지 않았다.

확인된 문제를 수정했다. 최종 재현에서 AI 뉴스의 첫 추천은 실제 기사 반환을 검증한 MCP Technology News로 바뀌었다. 스포츠 뉴스에는 기술 뉴스 전용 도구를 추천하지 않는다. 수집 단계에도 동일한 결과 검사를 추가해 새로 조사하는 에이전트가 형식적인 완료 응답으로 성공 판정을 받지 않게 했다.

다만 ‘재방문이 적으므로 전부 결과 불만족’이라는 인과관계는 현재 데이터로 증명할 수 없다. 실제 실패는 확인했지만 내부 점검 호출, 추정 브라우저 접속, 자동화 클라이언트가 섞여 있다. 사용자 만족도와 재방문 개선은 배포 후 별도 관찰이 필요하다.

## 기록의 범위와 재방문 해석

기록 보존 구간은 2026-10-14 15:32:44부터 2026-10-25 16:51:21 KST 직전까지다. 이 시각 이후 이번 점검에서 발생한 호출은 초기 방문 통계에 포함하지 않았다.

- 대화 프로필 269개, 수신 메시지 494개, 응답 메시지 483개.
- 브라우저와 비슷한 User-Agent를 가진 프로필은 30개·메시지 44개였다. 그중 2개 프로필에서 여러 날짜의 대화가 관찰됐다. 이는 인증된 사람 30명과 같지 않다.
- 명시적인 내부 점검 프로필 102개·메시지 121개, 프로그램 클라이언트 80개·81개, 봇을 명시한 프로필 1개·2개, 분류 불명 56개·246개였다. 프로그램 클라이언트와 분류 불명 전체를 외부 자율형 에이전트라고 계산하지 않았다.
- 수신 경로는 REST 439건, A2A 34건, MCP 21건이다. REST도 자동화가 사용할 수 있으므로 REST=사람, MCP/A2A=실제 고객이라는 가정은 하지 않았다.
- 루트 접속에는 브라우저 유사 지문 묶음 587개가 남아 있다. 오늘 관찰된 22개 중 7개는 이전 날짜의 접속도 있었다. 지문 묶음은 사람이 아니며, 이 집계로 전체 재방문율을 계산할 수 없다.
- 최신 대화 39쌍은 요청 메시지 ID로 연결됐다. 이전 444쌍은 같은 프로필의 직전 요청을 기준으로 추정한 연결이다. 오래된 병렬 대화에서는 완전한 요청·응답 관계를 복원할 수 없다.

홈 접속 기록은 최초·최종 시각과 누적 횟수 중심이다. 보존되지 않은 메뉴 클릭, 전체 이동 경로, 이탈 이유, 브라우저 세션이 바뀐 동일인의 연속 방문까지 복원하지 않았다. 재방문 수치를 높이기 위한 추가 식별 추적이나 동의 없는 마케팅은 도입하지 않았다.

## 같은 요청을 재현한 결과

보존된 메시지에서 개인정보가 마스킹된 요청, 제어 명령, 워크플로우 생성 요청 등을 제외하고 검색 요청·프로토콜 조합 83종을 선정했다. 오래된 구조화 선택값이 없는 경우에는 보존된 텍스트와 확인 가능한 프로토콜 정보만 사용했다.

- 초기 코드: 83종 중 조회 오류 0, 결과가 있는 요청 75종.
- 최종 코드: 83종 중 조회 오류 0, 결과가 있는 요청 75종.
- 결과 개수가 늘었다는 것을 개선 점수로 사용하지 않았다. 문제 후보의 제외, 범위 일치, 무응답의 실패 처리, 후속 동작을 별도로 확인했다.
- 12종은 실제 REST `/chat`, A2A `message/send`, MCP `chat` HTTP 어댑터로 재현했다. 12종 모두 추천 ID가 일치했다. 실행 가능한 후보가 있는 11종은 `details 1`의 대상도 일치했다. 불가능한 요청은 세 경로 모두 결과가 없었다.
- 대화·세션·관측 쓰기는 임시 DB에 격리하고 카탈로그는 읽기 전용으로 조회했다. 브라우저 화면도 격리 앱으로 실제 클릭했다. 보존되지 않은 사용자의 인증·결제 정보는 복제하지 않았다.

주요 재현 사례:

- AI 뉴스: 암호화폐/지역 전용 뉴스와 실행 대신 도구 설명을 주는 후보를 제외했다. 첫 추천은 실제 실행을 확인한 Technology News다.
- 스포츠 뉴스: `query` 입력이 있다는 이유만으로 기술 뉴스 전용 피드를 범용 뉴스 검색으로 취급하지 않는다.
- 일반 개발 문서 검색: 날씨 업체의 가입 안내, 특정 사이트 문서, Svelte 전용 문서를 범용 문서 검색으로 제시하지 않는다. 범용 라이브러리 검색이나 사용자가 특정한 문서 범위가 맞아야 한다.
- 서울 날씨: 캄차카·지중해 항해 전용 서비스, A2A로는 목록 안내만 하는 서비스, 지원하지 않는 HTTP+JSON 연결을 제외했다.
- 추상적인 `AI agent`: 임의 후보 대신 원하는 작업을 묻는다.
- 존재하지 않는 작업: 비슷한 단어로 결과를 채우지 않는다.

## 실제 외부 실행에서 발견한 문제와 정상 경로

사람이 사용하는 테스트 API와 에이전트용 연결 경로로 뉴스·날씨 후보를 실제 호출했다. 공개 읽기 작업만 사용했고 결제·크레딧·메일·SNS 발송·기존 워크플로우 변경은 하지 않았다.

문제 응답에는 `[MCP 응답 없음]`, `pong`, ‘100% schema conformance로 작업을 수행했다’는 고정 문구, 잘못된 프로토콜 응답이 있었다. 고정 문구에는 요청했던 실제 기사 제목·발행일·출처가 없었다. 기존 코드가 일부를 완료로 판정했던 사실을 확인했다.

새 판정은 빈 완료·명시적 무응답·일반 작업에 대한 pong·확인된 고정 완료 문구를 실행 실패로 처리한다. 정상적인 ‘검색 결과 0개’나 명시적인 ping에 대한 pong, 유효한 구조화 결과·파일은 구분한다. A2A 0.3/1.0 형식도 유지했다. 이 검사는 보편적인 사실성 판단 모델이나 완전한 의미 평가기는 아니다.

실제 재실행으로 실패가 확인되고 기존 연결 버전을 검증할 수 있었던 3개에 정식 실패 증거를 남겼다. 실제 시작·종료 시각, 작업 참조, 결과 해시를 사용하고 버전이 바뀌면 기록하지 않도록 했다. 기존 보고서를 삭제하거나 과거 실행 시각을 만들어 넣지 않았다. 버전이 확인되지 않은 후보에는 검증 증거를 억지로 생성하지 않았다.

정상 대조군으로 공개 서비스의 `Technology News`에 같은 AI 뉴스 검색을 두 경로로 실행했다. 두 경로가 기사 2건의 제목·URL·발행일을 동일하게 반환했다. 테스트 API는 약 2.97초, MCP는 약 1.11초였다. 두 번째 요청은 신선한 캐시를 사용했으므로 이 숫자로 경로별 속도 우열을 주장하지 않는다. 기사 내용 전체의 사실성을 독립 검증한 것은 아니다.

## 코드 변경

1. AI 약어를 명시적인 검색어로 확장하고 원래 요청의 언어·지역·입력 조건을 최종 후보 판정까지 보존했다.
2. 요청한 주제를 다루는 검색과 특정 주제 전용 피드를 구분했다. 범용 문서 요청에 특정 업체의 문서만 추천하는 경로도 제한했다.
3. 명시적인 API 키/계정 입력 조건, 보안 검토 상태, 지원하지 않는 A2A 바인딩·메서드·출처를 검사한다. A2A의 카드/헬스 확인만으로 실제 작업을 검증한 도구를 밀어내지 않는다.
4. 동일한 이름·설명의 미러 후보를 중복 추천으로 세지 않는다. 관련성과 안전성 조건을 통과한 뒤 기존 검증 시점·활동·등급 순위와 A2A 우선/MCP 보완 정책을 유지했다.
5. A2A 실행과 수집 시험에 공통 결과 검사를 적용했다. 처리 중인 작업도 성공으로 기록하지 않는다.
6. Chat 카드의 `Review task in Test`를 통해 원래 요청을 테스트 입력으로 가져간다. A2A 메시지는 보존하고 MCP는 명확한 문자열 입력 하나에만 대응한다. 모호한 입력은 추측하지 않고 원래 요청을 표시한다. 자동 실행은 하지 않는다.
7. 늦은 예제 로딩이 사용자의 선택을 덮어쓰지 않게 했고, 다른 에이전트를 선택하면 이전 준비 안내를 제거한다. 원래 요청을 URL에 넣지 않으며 표시 영역은 분석 마스킹을 적용했다.
8. 탐색의 자연어 검색에도 원래 범위와 입력·연결 조건 검사를 적용했다. 카탈로그 자체를 삭제하지 않았다.

## 논문·SNS에서 반영한 원칙

[Ragas](https://arxiv.org/abs/2309.15217)는 검색 문맥의 관련성, 근거에 대한 충실성, 최종 응답 품질을 나누어 평가한다. 이번에도 검색 성공/후보 존재와 실제 작업 결과를 분리했다. Ragas 패키지를 설치해 전면 평가한 것으로 표현하지 않는다.

[Corrective RAG](https://arxiv.org/abs/2401.15884)는 검색 결과의 품질을 평가하고 그 결과에 따라 보정하는 접근이다. 이번에는 운영 지연과 검증 가능성을 고려해 명세·검증 이력·명확한 실패 응답을 사용하는 가벼운 차단 검사를 적용했다. 논문의 전체 알고리즘을 재현했다는 의미는 아니다.

[Microsoft Marketplace 커뮤니티의 실제 논의](https://techcommunity.microsoft.com/discussions/marketplace-forum/could-marketplace-become-an-ai-discovery-agent/4502259)는 사용자가 쓰는 표현과 분류/키워드가 다르면 적합한 앱을 찾기 어렵다는 문제를 지적한다. 단어 하나가 겹쳤다는 이유로 후보를 채택하지 않고 실제 기능 설명과 입력 범위를 검토하는 데 참고했다.

[Reddit RAG 운영 경험](https://www.reddit.com/r/Rag/comments/1rvfzd4/improving_rag_retrieval_when_your_document/)에서도 오래되거나 맥락 정보가 부족한 자료가 검색 품질을 떨어뜨리는 사례가 논의됐다. SNS는 보조적인 실무 경험이며, 이 서비스의 재방문 감소 원인이나 개선 효과에 대한 통계적 근거로 사용하지 않았다.

## 검증·성능·남은 범위

최종 API·선택·수집·실행 회귀 266개, 브라우저/보안 회귀 123개가 통과했다. 새 Chat→Test 기능의 레거시 화면용 5개는 의도적으로 제외하고 실제 공개 퍼블리싱 화면에서 검증했다. 작업 중 반영된 CV 동의어 변경을 보존한 후 영향 검사 56개도 통과했다. 별도 jobs 릴리스에서는 수집 관련 48개가 통과했다. 이 숫자들은 전체 서비스의 모든 기능을 전수검사했다는 의미가 아니다.

출력 이스케이프·마스킹·XSS·SSRF·인증 경계·보안 헤더·입력 검증·실행 안전 경계 관련 기존 회귀를 포함했다. 272개 공개 프론트엔드 파일의 콘텐츠 검사에서 위반이 없었고, JS 문법 검사와 HTML/CSS/JS 재생성 결과가 일치했다. SQL 변경 없이 소스 해시 목록만 정합성을 맞췄다.

83종 조회의 관측 지연은 초기 중앙값 0.64초/P95 1.61초, 최종 중앙값 1.11초/P95 1.79초/최대 2.72초였다. 중간에 운영 카탈로그·릴리스가 바뀌었고 검증 작업이 함께 실행됐으므로 통제된 성능 비교가 아니다. 속도 향상을 주장하지 않는다. 이번에는 확인된 잘못된 추천과 가짜 성공을 제거하는 품질을 우선했다.

모든 공급자의 모든 도구, 지원 언어, 계정별 연동, 실제 유료 작업을 실행한 것은 아니다. 개인정보를 제거한 과거 요청만 재현했고 저장되지 않은 원본 입력 조건은 복구하지 않았다. 재방문율 개선은 아직 측정되지 않았다.
