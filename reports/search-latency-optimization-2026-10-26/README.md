# Explore 검색 지연 개선

2026-10-26. 범위는 공개 Explore의 후보 검색·역량 검사·카드 메타데이터 읽기다. 검색 관련성, A2A 우선/MCP 채움, 명시적 x402, 현재 상태·권한·증거·보고서 경계를 유지하면서 반복 계산과 DB 왕복을 줄였다. 운영 서버와 설정은 변경하지 않았으며, 운영 DB는 세션 자체가 읽기 전용인 연결로만 프로파일링했다.

## 조사와 판단

- [RRF 원 논문, SIGIR 2009](https://cormack.uwaterloo.ca/cormacksigir09-rrf.pdf): 서로 다른 검색 순위를 결합하는 근거다. 이번 개선은 기존 RRF와 후보 창·최종 순위를 유지한다. 후보를 임의로 줄이거나 ANN 정확도를 낮춰 속도를 만든 변경은 없다.
- [Proximity, Middleware 2025](https://arxiv.org/abs/2503.05530): 검색 재사용을 통한 비용 절감 가능성을 검토했다. 논문의 근사 질의 결과 캐시를 그대로 도입한 것은 아니다. 이 서비스에서 재사용하는 것은 정확히 같은 내용의 도구 명세 파싱과 오프라인 스키마 지원 여부뿐이다. 검색 결과, 사용자 입력, 활성 상태, 권한, 현재 검증 여부는 이 캐시에 저장하지 않는다.
- [The Tail at Scale](https://research.google/pubs/the-tail-at-scale/): 단일 평균만으로 응답성을 설명하지 않으며 최초/반복 요청과 지연 변동을 구분한다. 이번 소규모 측정은 운영 p95/SLA 인증이 아니다.
- [Reddit 개발자 논의](https://www.reddit.com/r/programming/comments/1mggpu5/n1_query_problem_what_it_is_why_it_hurts/): 추상화 뒤에 숨은 반복 DB 호출 사례를 조사 방향으로 참고했다. 게시자의 성능 수치를 이 서비스의 성과로 사용하지 않았다.
- [PostgreSQL 18 EXPLAIN 문서](https://www.postgresql.org/docs/18/using-explain.html), [트랜잭션 격리 문서](https://www.postgresql.org/docs/18/transaction-iso.html): 왕복 호출과 동일한 읽기 스냅샷을 구분했다. 측정에서 주된 비용은 Python 명세 처리와 카드별 반복 트랜잭션이었다. 인덱스·DB 전역 설정·운영 스키마는 변경하지 않았다.

## 적용 내용

1. `discovery_contracts.py`: 한 검색 요청 안에서 동일한 도구 계약의 파싱을 재사용한다. 실제 compact/full 원문과 full hash를 길이 구분한 SHA-256 키에 묶고, 키 계산과 파싱에 같은 관찰 사본을 사용한다. 최대 768개/16MiB, 항목당 512KiB로 제한하며 큰·가변 입력은 기존 경로를 사용한다. 반환값은 별도 JSON 객체로 복원하여 호출자의 변경이 캐시를 오염시키지 않는다. 요청 종료·예외 시 해제한다.
2. 스키마 지원 여부는 실제 입력 스키마 내용의 SHA-256과 boolean만 최대 2,048개 보관한다. 거부된 명세의 반복 검사도 줄인다. 기존 object 제한·24,000자 제한·비정상 수치 거부·참조/패턴 제한은 공유한다. 실제 실행의 `supported_schema`와 `validate_arguments`는 계속 호출되며, 이 발견용 표식을 실행 허가로 사용하지 않는다.
3. `task_scope_matches`에 이미 읽은 도구 집합을 내부적으로 전달하여 같은 자원을 다시 파싱하지 않는다. 기존 호출 방식과 역량 검사 조건은 유지한다.
4. PostgreSQL 카드의 버전·검증·보고서 표시는 한 번의 현재 read-only snapshot 안에서 조회한다. 복원·이전 보호와 네이티브 불변조건 검사 자체를 제거하지 않고, 동일 요청에서 반복하던 트랜잭션 시작/종료를 줄인다. 임베딩·외부 호출은 이 카드 스냅샷 밖에 있다. 실행 시 권한 재검증은 그대로다.
5. 동일한 core/term 검색식은 한 번만 조회한다. 서로 다른 AND/OR 검색식은 유지한다.

별도 작업의 완료 통보를 받은 최신 검색어 자동 보정·화면 변경을 보존했다. `wether`가 이제 공통 보정으로 실제 결과를 반환하므로 명시적 대체 검색 분기는 `clima`로 검사했다. 통합 과정에서 기존 새 역량 게이트가 명시적인 건설·지붕 작업용 날씨까지 거부하던 문제도 보완했다. 범용 날씨 검색에 특화 도구가 섞이지 않도록 도메인 경계는 유지한다.

## 같은 데이터에서 전후 비교

`compare_native.py`는 PostgreSQL의 같은 exported read-only snapshot을 이전 불변 릴리스와 현재 소스에 제공한다. 백그라운드 수집으로 행이 달라지는 효과를 배제한다. `native-comparison.json`의 내부 6개 조건과 API 4개 조건에서 **결과 ID 순서와 개수가 모두 일치**했다.

읽기 전용 실제 PostgreSQL 검색 데이터를 사용한 in-process API 결과:

- `weather`, 최초 API 표본: **1.944초 → 1.556초**, 20.0% 단축.
- `weather`, 반복 API 표본: **1.962초 → 1.462초**, 25.5% 단축.
- `translate`, 최초 API 표본: **4.533초 → 3.809초**, 16.0% 단축.
- `translate`, 반복 API 표본: **4.218초 → 1.874초**, 55.6% 단축.
- SQL 호출: 날씨 **868 → 154회**, 번역 **2,038 → 286회**. 이 수에는 트랜잭션·보호 검사도 포함된다.

개별 내부 경로 2건은 실행 시간 변동으로 약 5~9% 느리게 측정됐다. 4개 API 표본은 모두 단축됐지만 표본이 작으므로 일관된 개선 비율을 보장하지 않는다. 최초 번역은 여전히 약 3.8초다. 초기 실험/요청 내 캐시 용량 조정 자료는 별도 JSON으로 남겼고 최종 결과로 혼합하지 않았다.

여기서 최초 표본은 API 반복 묶음의 첫 호출이다. DB 버퍼와 명세 캐시를 모두 비운 서비스 최초 접속 시험은 아니다. 이전·개선 코드를 순서대로 측정한 소규모 비교이며 DB/호스트 부하 변동을 제거한 대규모 통계 시험으로 해석하지 않는다.

비교 조건은 실제 네이티브 DB + 격리 메모리 보안/세션 scaffold + in-process HTTP다. 운영 생성자가 보안 테이블 초기화를 시도하여 읽기 전용 세션에서 차단됐기 때문에 scaffold 초기화는 별도 메모리 DB에서 수행하고 검색 데이터만 실제 DB로 읽는다. 운영 보호를 해제하거나 쓰기 권한을 켜지 않았다. 임베딩·생성 모델·외부 제공자 호출은 0이며 네트워크/Cloudflare 시간은 포함하지 않는다. 따라서 위 수치는 배포된 인터넷 API의 전체 응답 시간과 동일하지 않다.

## 검증 기록

- 전용 PostgreSQL 스키마 계약 **11개 통과**: 검색·프로토콜·중복·페이지·스키마와 더불어 캐시 사용 후 kill switch, 새 실패 증거, 비활성화가 반영되는지 확인했다. 검증 스키마를 삭제했고 운영 애플리케이션 테이블 쓰기는 0이다. `native-freshness.json`.
- 공개 검색/중앙 로딩/필터/CSP/XSS 브라우저 **50건 통과**, `public-browser-final.log`.
- 캐시 변조·원문 변경·메모리 경계·동시성·오프라인 스키마·실행 인자 경계 검사: `cache-security-final.log`.
- 기존/최신 자연어 역량 게이트 호환성 검사: `compatibility-final.log`.
- 최종 고정 소스의 영향 파일 23개 통합 검증: **610 passed / 실패 0 / skip 0**, `integration-final.log`, `integration-final.xml`. 위 개별 회귀의 중복 사례는 이 합계에 다시 더하지 않는다.
- 공개 콘텐츠: **300개 파일, 위반 0**, `content-final.log`.
- SQL 카탈로그: **3,801문/232테이블**, unique SQL 추가·삭제 0, 최종 재생성 불필요 상태 확인. `sql-catalog-diff.json`, `sql-catalog-final.log`. 변경은 현행 소스 위치 정보이며 실행 SQL/스키마 마이그레이션이 아니다.
- Bandit: 새 캐시와 스키마 재사용 코드에는 경고 0. 전체 영향 파일에서는 High 0 / Medium 4 / Low 0이다. 고정 SQL 조각을 조합하는 기존 저신뢰도 B608 경고 4건이며 값 바인딩을 유지함을 검토했다. 정적 스캔 종료 코드는 이 경고로 1이다. `bandit.json`을 저장소 전체 취약점 0건으로 해석하지 않는다.
- 통합 검사 도중 HTML 원본 두 파일이 다시 기록됐지만 backend 함수 AST는 이전 배포본과 동일했다. 현재 원본으로 임시 디렉터리에 발행한 HTML/JS/CSS **57개가 기존 발행 자산과 바이트 단위로 모두 일치**하고, HTML과 발행 manifest의 해시도 일치했다. 소스 표기는 최신 상태로 고정하되 동일 화면에 대한 전체 회귀 반복은 하지 않았다. `publication-equivalence.json`, `source-freeze.json`.

추가로 선택했던 예전 관리자/공개 상세 브라우저 테스트 5건은 옛 `errors` 탭, 일정 전역 함수, 이미 숨긴 쿠키 버튼을 찾다가 실패했다. 같은 테스트가 **이전 불변 릴리스에서도 같은 5건 실패**함을 확인했다(`legacy-browser-baseline.log`). 이 검색 최적화의 신규 회귀로 계산하거나 통과 건수에 포함하지 않았으며 관리자 화면 이전 작업을 이 범위에 추가하지 않았다.

검증 도구에서 발견한 SQL 레지스트리 밖의 조회는 고정된 네이티브 테스트 SQL로 수정했으며 운영 SQL 허용 범위를 넓히지 않았다. Playwright 응답 완료와 teardown의 경합은 테스트의 route 상태 기록 순서를 고쳐 해결했다. 검색이 끝난 것처럼 표시하거나 응답을 생략하는 제품 변경으로 해결하지 않았다.

## 최종 판정은 불변 릴리스 기준

사용자가 다른 수정 완료를 알린 후에도 `fast_chat.py`와 화면 원본·발행 자산이 추가로 갱신됐다. 작업 디렉터리의 갱신에 따라 같은 검사를 계속 반복하지 않도록 **`explore-search-speed-20261026-r1`을 먼저 고정한 뒤 그 복사본에서 검증**했다.

- 릴리스 복사본: **610 passed / 실패 0 / skip 0**, `release-integration-final.log`, `release-integration-final.xml`.
- 같은 릴리스 복사본의 PostgreSQL 전용 스키마 계약 **11개 통과**, `release-native-freshness.json`.
- 릴리스 콘텐츠 검사: **300개 파일/위반 0**, `release-content-final.log`. 검사 도구가 함께 읽는 가이드와 테스트 도구 모듈은 검증 scaffold에 별도로 복사했고 배포 코드에는 추가하지 않았다.
- 릴리스 정적 검사: **High 0 / 기존 Medium 4 / Low 0**, `release-bandit.json`. Node의 발행 JavaScript 구문 검사 통과.
- 릴리스 복사본의 코드·화면 자산 **1,278개 파일이 manifest 해시와 일치**하고 불변 릴리스 전체 manifest도 확인했다. `release-source-freeze.json`, `package.json`, `validation-summary.json`. 측정에 사용한 검색 핵심 파일 9개도 릴리스와 동일하다.
- 최초 작업 디렉터리의 610건과 릴리스의 610건을 더해 1,220건으로 부풀리지 않는다. 최종 고유 pytest 사례는 610건이다. 테스트 원본 식별자는 `test-source-hashes.json`에 보존했다.

이후의 작업 디렉터리 변경은 이 릴리스에 자동 반영되지 않는다. 재배포·재시작이나 운영 권한 설정 변경은 실행하지 않았다.

## 운영 반영

서버 교체는 사용자가 터미널에서 진행한다. 최종 검사·소스 해시 확인 후 `explore-search-speed-20261026-r1` 불변 패키지에 frontend의 코드·자산을 함께 고정한다. 검증된 원본/패키지 해시 일치 결과는 `package.json`이다. 관리자·jobs·execution 교체와 DB 마이그레이션은 필요하지 않다.

```bash
./agentcon deploy frontend explore-search-speed-20261026-r1
```

배포 후 실제 인터넷 검색의 응답 시간은 별도 확인해야 한다.

## 사용자 배포 후 운영 확인

사용자의 실행 완료 통보 후 frontend 활성 B 슬롯이 `explore-search-speed-20261026-r1`임을 확인했다. 불변 릴리스 manifest가 유효하고, 로컬 서비스와 공개 도메인에서 받은 `operating.js`가 해당 릴리스와 일치했다. 공개 정적 자산의 Cloudflare 상태는 BYPASS였다.

실제 API를 `limit=45`, 기본 A2A+MCP 범위로 각 2회 조회했다. 8회 모두 HTTP 200이며 기본 범위에 x402가 포함되지 않았다. `rollout-api.json` 참조.

- 로컬 날씨: **3.957초 / 2.463초**.
- 로컬 번역: **6.243초 / 3.132초**.
- 공개 도메인 날씨: **4.860초 / 4.109초**.
- 공개 도메인 번역: **4.850초 / 3.871초**.

앞의 1~2초 수치는 임베딩과 인터넷 전송을 제외한 격리 비교다. 이 운영 측정에는 실제 서비스 처리와 전송이 포함되어 직접적인 개선율 비교로 사용하지 않는다. 서비스 부하와 카탈로그도 이전 측정 이후 변할 수 있다. 이번 실제 공개 표본은 약 **3.9~4.9초**이며, 모든 운영 검색이 2초 이내가 됐다고 주장하지 않는다. 추가 지연의 개별 원인 비중은 이 GET 표본만으로 확정하지 않았다.

별도 Chromium 임시 프로필로 실제 로컬 배포 화면의 5개 흐름을 확인했다: 명시적 오타 제안·MCP 선택 복원, 입력 즉시 중앙 로딩, 응답 후 로딩 종료와 주소 반영, 새로고침·캐시 갱신 완료, 390px 모바일 버튼 표기. 페이지 JavaScript 오류는 0건이었다. `rollout-browser.json`, `screenshots/deployed-progress.png`, `screenshots/deployed-mobile.png`.

검증 클라이언트는 GET/HEAD만 사용했으며 계정·워크플로우·크레딧 변경 요청은 0건이다. 배포·재시작은 사용자가 수행했으며 점검 과정에서 서버 설정은 변경하지 않았다.
