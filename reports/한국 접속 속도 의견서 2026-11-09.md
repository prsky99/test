# 한국 접속 속도 의견서 (2026-11-09, 운영·SRE)

결론부터: **지금 설정을 바꾸거나 돈을 쓰지 않는다.** 한국 사용자가 아직 거의 없고(주간 외부 요청 27건), 확실한 해결책(서울 접속점 고정)은 비용이 크고 확인되지 않았다. 대신 무료로 할 수 있는 코드 쪽 개선 2가지를 먼저 하고, 한국 사용자 지표가 생기면 다시 판단한다. 아래 항목은 모두 **사용자 승인 대상**(Cloudflare 설정·지출)이며, 이 의견서는 실행하지 않았다.

## 1. 실측 (11-09 21시, 이 맥 = 한국 회선)
| 항목 | 값 |
|---|---|
| 방문자 접속점 | `colo=LAX`, `loc=KR` (`/cdn-cgi/trace` 3회 모두) |
| 터널(cloudflared) 접속점 | `icn06`, `icn07` (서울) |
| 한국→LAX TCP 연결 | 약 135ms |
| 새 연결 첫 요청(`/robots.txt`) | 0.74~1.8초, 한 번 4.5초(TLS 지연) |
| 같은 연결 재사용 요청 | 중앙값 0.31초, 최대 1.2초 |
| 서버 자체(로컬 직접) | 0.02초 |
| 같은 회선에서 1.1.1.1(Cloudflare DNS) | 3ms (서울 접속점에 닿음) |
| HTTP/3 | 이미 켜져 있음(`alt-svc: h3`) |

**경로:** 한국 사용자 → LAX(태평양 1회) → Cloudflare 내부망 → 서울(ICN) → 터널 → 이 맥 → 같은 길로 되돌아감. 요청 하나가 태평양을 두 번 왕복한다. 재사용 연결 0.31초가 거의 이 두 왕복이고, 서버 시간은 2%뿐이다.

**왜 LAX인가:** 같은 회선에서 1.1.1.1은 서울로 가므로 회선이 서울 접속점에 못 가는 것은 아니다. 공개 자료에는 "한국 통신사와의 망 비용 때문에 무료·Pro 요금제 웹 트래픽은 LAX·도쿄 등으로 보내고, 서울은 상위 요금제에 우선한다"는 사용자 경험담이 여럿 있다. Cloudflare 공식 문서로 요금제별 정책을 확인하지는 못했다(근거 수준: 경험담).

## 3. 지금 할 것 (무료, 위임 범위 안: 코드 변경)
1. **첫 화면 왕복 수 줄이기:** 첫 화면이 여는 독립 요청을 HTTP/2 한 연결에서 병렬로 보내는지, 순차 대기(요청 끝나면 다음 요청)가 없는지 점검한다. 한국에선 순차 요청 하나가 0.3초다. (프론트 화면 정책의 "독립 요청은 병렬"과 같은 방향)
2. **정적 자산 엣지 캐시 확인:** `new/en/assets/*`가 `cf-cache-status: HIT`로 LAX에서 바로 나가는지 확인하고, 해시된 파일은 긴 캐시를 준다. HIT이면 서울까지 가지 않아 0.15초 정도 줄어든다.
