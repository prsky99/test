# 관리자 업무 중심 UI/UX 재설계와 첫 구현 명세

2026-10-24 · 범위: 기존 21개 메뉴, 비교 감사의 62개 업무 묶음, 리뉴얼 71개 진입 화면. 이번 구현 기준 화면은 결제·정산 U09입니다. 71개 화면 전체 구현 완료나 기능 동등성 회복을 뜻하지 않습니다.

전체 71개 화면의 개별 첫 판단·배치·완료 기준은 `SCREEN-SPEC.ko.md`, 기존 업무 62개 이관 흐름은 `COVERAGE.ko.md`에서 이어서 확인할 수 있습니다.

## 1. 판단 기준

관리자는 메뉴를 탐색하기 위해 이 서비스를 사용하지 않습니다. 문제가 있는 대상을 찾고, 원인과 영향을 확인하고, 권한에 맞는 조치를 실행한 뒤 실제 결과를 확인하기 위해 사용합니다. 기존 리뉴얼의 문제는 메뉴 수가 아니라 이 흐름이 끊긴 것입니다. 다음 기준으로 모든 화면의 완료 여부를 판단합니다.

- 첫 화면에서 오늘 해야 할 일과 단순 참고 정보를 구분할 수 있어야 합니다.
- 선택한 대상·검색 조건을 유지하면서 근거 확인, 조치 검토, 실행 결과 확인이 이어져야 합니다.
- ‘접수됨’, ‘실행 중’, ‘완료’, ‘결과 미확인’을 서로 다른 상태로 보여야 합니다.
- API나 권한이 없으면 정상 수치, 완료 메시지, 동작하지 않는 버튼으로 대체하지 않습니다.
- 표와 원시 JSON을 그대로 노출하는 것은 업무 설계의 완료가 아닙니다.

주 사용자 역할은 운영 담당자(발견·검증·복구), 고객 담당자(지원·동의·고객 이용), 최고관리자(금융·보안·승인), 조회 담당자(읽기)입니다. 역할별 허용 데이터와 변경 범위를 같은 기준으로 메뉴·버튼·API에 적용합니다.

## 2. 전체 업무 구조

### 운영 데스크

‘오늘 처리할 일’이 첫 영역입니다. 영향이 큰 사고, 승인 대기, 오래된 실행, 검증 실패, 지원 대기를 근거 시각과 함께 정렬합니다. 수집량 등 규모 지표는 그 아래에 둡니다. 각 항목은 대상·원인·다음 행동을 포함하며 클릭하면 해당 업무의 조건이 적용된 목록으로 이동합니다. 지표와 문제 목록은 같은 기간을 사용합니다. 불명확한 건강 점수 하나로 정상 여부를 대신하지 않습니다.

### 에이전트 운영

발견 → 후보 확인 → 연결·도구 확인 → 시험 → 보고서 → 운영 상태의 한 흐름입니다. 대상을 선택하면 동일한 상세 공간에서 요약, 연결 정보, 검증 근거, 최근 실행, 변경 이력을 확인합니다. 이름·주소 검색과 자연어 추천은 입력 목적을 구분하되 같은 결과 목록을 사용합니다. 출처·프로토콜·카테고리·등급·활성 여부·검증 여부를 서버 조건으로 적용합니다. 추천 근거와 마지막 검증 시각을 보여주고 추천 결과를 정상 검증으로 오인하게 하지 않습니다.

### 워크플로 운영

전역 서비스, 직원 개인, 고객 워크스페이스는 서로 다른 소유·실행 권한을 가진 자산입니다. 상단 범위 선택과 소유자 표시를 유지합니다. ‘AI 초안 → 단계 편집 → 입력·연결 검증 → 시험 실행 → 결과 분석 → 예약·전달 → 배포’는 하나의 상세 화면 안의 단계입니다. 단계마다 에이전트 진주와 연결선을 실제 단계 수에 맞춰 표시합니다. AI 수정은 기존 버전과 차이를 검토하고 저장하도록 하며 실행·게시와 분리합니다. 실행 기록에서는 단계별 입력·출력, 실패 원인, 취소 가능 여부, 비교 결과와 검토표를 연결합니다. 앱·SDK·연결 권한은 릴리스 상세에 포함합니다.

### 고객 대응

고객/조직 중심으로 요청, 추천 제안, 지원 케이스, 작업 알림, 이용 크레딧을 연결합니다. 추천 요청의 재평가는 수집 재검색으로 표현하지 않습니다. 방문·연락처 인증·작업 알림 동의·마케팅 동의는 서로 별도 상태로 보입니다. 취소 요청을 임의 활성화하거나 방문을 광고 동의로 해석하지 않습니다. 개인정보 열람은 목적·권한·만료 조건을 유지합니다.

### 금융 운영

에이전트 금융 장부, 고객 무료 이용 크레딧, x402 결제 기록을 서로 다른 원장으로 설명합니다. 보류 확인, 계정 잔액, 변경 요청, 적용 증빙을 같은 작업 공간에서 처리합니다. 내부 장부의 대사 일치와 외부 준비금 검증을 구분합니다. 현재 구현은 외부 송금 서비스가 아니므로 ‘출금 완료’라고 표시하지 않습니다. 정산 완료 거래의 현금 환불도 보류 해제와 구분합니다.

### 운영 기반·보안

수집·평가·헬스·벡터 인덱스는 작업 종류로 필터링하는 운영 목록과 개별 작업 상세를 공유합니다. 종류에 따라 재시도·중지·제한 배치가 달라지며 검토 화면에 대상 수, 범위, 중복 처리 방지, 예상 영향이 표시됩니다. 오류 코드에서 관련 호스트·체인·실행 사례로 이동합니다. 보안 사건은 실제 대응과 연결하고 감사 기록은 변경 전후·사유·요청자·승인자·결과를 보여줍니다. 설정은 읽기 정보와 변경 가능 설정을 나누고 반영 방식과 미확인 상태를 명시합니다.

이 구조는 목표 정보 구조입니다. 이번 배포에서 구현되지 않은 센터로 기존 메뉴를 일괄 이동해 빈 화면을 만들지 않습니다. 실제 업무를 끝까지 구현한 단위로 기존 경로를 대체하고 이전 즐겨찾기를 유지합니다. 첫 교체는 기존 U09 경로입니다.

## 3. 공통 화면 구성 규칙

1. 제목: 대상 업무와 현재 범위. 우측 행동은 하나의 주 행동과 최대 두 개의 보조 행동을 우선 노출합니다.
2. 현황: 의사결정에 필요한 3–4개 지표. 숫자에는 단위·시점·대상 범위를 붙입니다. 표본 지표는 표본이라고 명시합니다.
3. 작업 영역: 업무 상태별 필터, 서버 검색, 표, 대상별 상세 문맥을 배치합니다. 관리 표는 데스크톱에서 한 화면에 여러 행을 비교할 수 있게 하고 불필요한 카드 반복을 피합니다.
4. 상세: 요약 → 실제 근거 → 가능한 행동 → 변경 이력 순서입니다. 기술 ID는 보조 정보로 줄바꿈하고 금액·시간은 정렬합니다.
5. 조치: 입력 → 최신값 검토 → 요청/승인 → 실제 결과 확인. 전체 페이지 이동이나 검색 조건 초기화를 하지 않습니다.
6. 비어 있음: 조건 결과 없음, 실제 데이터 없음, 권한 없음, 연결 실패를 구분합니다. 실패를 0건으로 바꾸지 않습니다.
7. 비동기: 사용자가 누른 행동에만 진행 표시를 연결합니다. 이전 데이터를 유지하고 새 결과 기준 시각을 갱신합니다. 입력 중인 내용과 필터를 주기적 새로고침으로 지우지 않습니다.
8. 미확인 변경: 쓰기 응답 유실은 실패와 다릅니다. 다시 실행하지 말고 요청 ID와 최신 원장을 조회하는 경로를 제공합니다.
9. 접근성: 키보드 도달, 명시적 레이블, 보이는 초점, 상태 텍스트, 대화상자 내부 초점 유지와 종료 시 초점 복원을 적용합니다. 좁은 화면에서 문서 전체가 가로로 넘치지 않고 표 안에서만 스크롤합니다.

금융 변경의 최종 검토와 오류 방지는 [WCAG 2.2 금융·데이터 오류 방지 기준](https://www.w3.org/WAI/WCAG22/Understanding/error-prevention-legal-financial-data.html)을 참고했습니다. 대화상자의 초점·Escape·복원 동작은 [WAI-ARIA Dialog Pattern](https://www.w3.org/WAI/ARIA/apg/patterns/dialog-modal/)을 기준으로 검증합니다. 출처를 참고했다고 접근성 인증을 받은 것은 아닙니다.

## 4. AI 기능 설계

AI는 결과를 대신 보증하는 주체가 아니라 관리자의 탐색·판단을 돕는 도구입니다.

- 에이전트 탐색: 자연어 요구를 구조화된 조건으로 보여주고 관련 후보·추천 근거·최근 검증을 제공합니다. 관리자 조건이 모델 추론보다 우선합니다.
- 워크플로: 목표·입력·산출물·외부 연결 제약을 먼저 받습니다. 초안의 실제 에이전트, 필요한 권한, 예상 데이터 흐름을 검증한 뒤 저장합니다. 없는 에이전트나 도구를 생성해 정상 연결처럼 보이지 않습니다.
- 시험 분석: 실제 실행과 보고서를 근거로 요약하고 원인 추정과 확인 사실을 구분합니다. 실패를 모델의 설명만으로 성공 처리하지 않습니다.
- 고객 대응: 답변 초안과 검토 근거를 제공하되 외부 전송은 별도 의도와 권한으로 실행합니다.
- 금융·보안: 설명·이상 징후 정리까지만 돕습니다. AI가 장부 변경, 권한 부여, 지급, 재시도를 자동 승인하지 않습니다.

## 5. 첫 기준 화면: 결제·정산 U09

기존 경로 `/admin/next#/customers/u09`를 유지합니다. 역할은 최고관리자입니다. 메뉴 노출과 본문/API 권한을 일치시킵니다.

### 사용 순서

1. 사용 가능 잔액·보류 금액·오래된 보류·검토 대기를 확인합니다.
2. 기본 ‘보류 확인’에서 계정·금액·경과 시간으로 대상을 고릅니다.
3. 상세에서 대상 거래의 상태·검증 기록과 가능한 행동을 확인합니다.
4. 충전/회수/보류 해제/오래된 보류 해제의 사유와 필요한 입력을 작성합니다.
5. 서버가 읽은 최신값으로 전체 잔액·보류·사용 가능 금액의 변경 전후를 확인합니다. 새 계정 생성도 표시합니다.
6. 검토 요청을 저장합니다. 이 시점에는 장부가 바뀌지 않습니다.
7. 다른 최고관리자가 승인합니다. 활성 최고관리자가 한 명뿐인 경우에만 기존의 최근 로그인·명시 확인 정책으로 직접 승인할 수 있습니다.
8. 적용 결과와 증빙 참조·최종 잔액을 확인합니다. 실패 또는 미확인 상태는 별도로 표시하고 자동 재시도하지 않습니다.

### 금액과 안전 경계

- 화면 입력은 USDC, 저장은 정수 micro-USDC입니다. 1 USDC = 1,000,000 micro-USDC이며 고객 이용 크레딧으로 환산하지 않습니다.
- 금액은 소수점 6자리까지, 요청별 0 초과 최대 1,000,000 USDC입니다. API 전송 금액과 JavaScript 표시는 문자열/BigInt로 정밀도를 보존합니다.
- 보류 해제는 전체 잔액을 늘리지 않고 보류만 해제합니다. 정산 완료 거래에 이 행동을 제공하지 않습니다.
- 회수는 내부 장부 차감·기록이며 외부 지갑 송금을 실행하지 않습니다. 주소는 기록 목적임을 입력 전에 설명합니다.
- 오래된 보류 해제는 15분 이상 보류된 정산 거래 중 오래된 최대 20건의 정확한 ID를 검토합니다. 검토 후 새로 들어온 거래를 포함하지 않습니다. 진행 중 거래인지 관리자가 확인해야 하며 결제 원장 pending 삭제는 이 구현의 범위가 아닙니다.
- 최신 장부 검토는 5분 유효합니다. 검토 후 잔액·보류·대상 거래가 달라지면 전체 적용을 차단합니다.
- 검토 시 발급한 요청 ID로 응답 유실 후에도 정확히 조회하고 동일 요청을 중복 등록하지 않습니다. 적용 응답이 유실되면 해당 ID의 장부 감사 증빙을 대조합니다. 서명된 검토 내용만 승인 저장소에 등록하며 대기 요청 중복, 재승인, 권한 우회, 다른 출처 쓰기를 차단합니다. 변경과 장부 감사는 같은 트랜잭션에 기록합니다.
- 승인 저장소가 준비되지 않으면 조회는 가능하고 변경은 차단합니다. 요청 중 유실은 재실행으로 복구하지 않습니다.

## 6. 구현 순서와 화면별 완료 기준

단계 1: U09를 기준 구현으로 교체합니다. 네 가지 장부 조치의 실제 입력·검토·승인·결과, 권한, 빈 결과, 오류, 반응형을 검증합니다. 같은 감사에서 발견한 통합 검색 실행 오류는 함께 수정합니다.

단계 2: 에이전트 탐색–상세–시험–보고서 한 흐름을 복원합니다. AI 추천·전체 필터·비활성 대상·시험 사용자 입력·보고서 비교·이력을 실제 API까지 연결합니다.

단계 3: 기존 전역 워크플로 생명주기를 구현합니다. 직원 typed 기능과 범위를 합치지 않고 AI 수정·취소·예약·수신처·검토표·앱·SDK·권한을 해당 객체 안에서 연결합니다.

단계 4: 고객 요청/제안과 수집·평가·벡터·보안 진단을 연결합니다. 영향 설명과 제한 실행, 오류 사례에서 복구까지 검증합니다.

단계 5: 전 화면 역할별 반복 사용성을 검증합니다. 각 화면에서 클릭 전·처리 중·성공 후·실패 후 증적과 데이터 변화 증거를 남깁니다. 단순 HTTP 200, 화면 개수, 스크린샷 파일 존재를 기능 완료로 인정하지 않습니다.

작업별 이관 위치와 남은 범위는 `coverage-map.json`에 비교 감사의 F01–F62 전체를 보존해 연결합니다. 이행 상태는 ‘이번 구현’, ‘설계 반영·구현 대기’, ‘기존 제한/오류 별도 판단’을 구분합니다.
