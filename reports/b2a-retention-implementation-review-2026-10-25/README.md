# B2A 재방문 설계·구현 대조 검토

후속 수정: 이번 감사의 결함을 수정했고 정규 B2A 54개 조건(원래 23개 포함)이 통과했다. 사용자가 다른 수정 진행 중이라고 확인하여 최종 통합·패키지 확정은 대기 중이다. 최신 구현 상태는 [수정 보고서](../b2a-retention-remediation-2026-10-25/README.md)를 참고한다. 아래 실패/404 기록은 수정 전 감사 이력이다.

후속 재시작 점검: 신규 경로의 운영 반영은 확인됐다. 기존 추가 검사 17건은 여전히 실패하며, 공개 resume의 약한 ETag 처리 문제도 확인했다. 최신 상태는 [두 번째 재점검](recheck-2/README.md)을 우선 참고한다. 아래 운영 404 기록은 최초 검토 당시 결과다.

검토일: 2026-10-25. 대상은 첨부 구현 보고서와 `autonomous_agent_retention_and_b2a_design.md`의 Phase 1~4 및 상세 모듈 1~5다. 기존 검색·추천 개선 전체를 다시 개발하는 작업은 포함하지 않는다. 제품 소스·운영 설정·계정·서버는 변경하지 않았다.

## 판정

**엔드포인트와 기본 흐름은 구현됐지만, 설계 전체 완료로 판정할 수 없다.** 기존 54개 테스트 통과는 재현했으나, 설계의 실패·변경 경계를 검증하는 추가 23개 조건 중 17개가 실패했다. 이는 17개 독립 결함이라는 뜻은 아니며, 아래 공통 원인으로 묶인다.

공개 서버 반영도 별개다. 로컬 프론트엔드(8400)와 공개 도메인 모두 `/skill.md`, `/.well-known/skill.md`, 배지 경로는 404이고, 기존 entry JSON은 200이지만 `interfaces.skill`이 없다. 현재 소스의 격리 앱에서는 해당 경로가 존재한다. 새 B2A 소스가 운영에 반영됐다고 주장할 수 없다.

## 검증 결과와 증거

- 첨부와 같은 기존 세 파일 회귀: **54 passed**. `baseline-pytest.log`.
- Inertia·자율형 방문 API 확대 회귀: **16 passed, 1 failed**. 실패는 과거 문자열 `[AutoTool 0ms Prefetching]`을 기대하는 테스트이며, 현재 응답은 `[Next-tool suggestions]`다. 이 실패를 제품 기능 장애로 분류하지 않는다.
- 실제 Chromium 공개 화면·CSP·XSS·개인정보/상업 문구 회귀: **27 passed**. `browser-pytest.log`, `browser-results.xml`.
- 설계 적합성 추가 검사: **6 passed, 17 failed, skip 0**. `audit_cases.py`, `audit-cases.log`, `audit-results.xml`. 이 파일은 일반 테스트 자동 수집 이름을 사용하지 않으며 명시 실행하는 감사용 검사다.
- 공개 콘텐츠 검사: **267개 파일, 위반 0건**. embedded HTML과 `extracted_html.txt` 일치 포함. 이 검사는 배지의 진실성이나 추천 필터의 실행 경계를 보증하지 않는다.
- 초기 브라우저 검사에서는 macOS 샌드박스가 Chromium 시작을 차단했다. 실행 권한을 확보한 브라우저 전용 재검증에서 27개 모두 통과했다. 처음의 브라우저 준비 오류를 제품 결함이나 최종 실패 건수로 중복 집계하지 않는다.
- 격리 SQLite와 합성 방문자·주입된 transport를 사용했다. 새 감사 케이스에는 외부 HTTP 차단을 적용했다. PostgreSQL 운영 상태·실제 제공자 실행·실제 고객 계정·결제·광고 발송·외부 배포 채널의 성과는 검증하지 않았다.

## 설계와 일치하는 부분

### Phase 1 — 문서 진입점: 기본 구현 일치

`agent_entry.py:42`의 영어 스킬 본문과 두 경로, ETag/304, entry의 재방문 정책, HTML/Link 헤더의 머신 링크는 존재한다. 프론트엔드 생성물의 기존 보안·표시 회귀도 통과했다.

다만 URL을 공개하는 것과 외부 에이전트에 설치·채택되는 것은 다르다. 외부 레지스트리 등록, 저장소의 배지 채택, 실제 재방문 증가는 이번 구현·검사로 증명되지 않는다. 공식 Agent Skills 형식의 설치 단위는 이름이 맞는 디렉터리의 `SKILL.md`이며, URL을 한 번 읽었다는 사실만으로 모든 클라이언트에 자동 설치되는 것은 아니다. 참고: https://agentskills.io/specification

### Phase 2 — 재방문 상태: 부분 일치

유효한 방문 토큰을 요구하고, 무토큰 401, 세션별 실패 목록, 변경 없는 응답의 빈 본문 304가 동작한다. 무캐시 정책도 존재한다. 그러나 같은 에이전트의 계약 변경 감지와 갱신된 후보 반환이 빠져 있다(F03, F07).

### Phase 3 — 후속 탐색·실패 복구: 부분 일치

최상위 에이전트의 도구를 기준으로 후속 스키마를 두 개까지 조회하고, 공개 응답의 주소를 게이트웨이로 바꾸는 동작은 확인했다. MCP 실패 기록과 누적 실패 ID 제외도 동작한다. 게이트웨이 주소 은닉 실패는 이번 검사에서 재현되지 않았다.

그러나 안전·프로토콜 필터가 후속 도구 경로에서 누락되고, 실패 복구의 장애 독립성·프로토콜 유지·상세 응답 계약도 설계와 다르다(F02, F04~F08).

### Phase 4 — 검증 배지: 경로는 일치, 판정 조건 불일치

SVG와 CSP, 허용된 등급 값만 출력하는 처리, 없는 리소스의 Unverified 응답은 확인했다. 최신 24시간 검증 여부를 판단하는 로직은 없다(F01). 300초 공개 캐시도 사용하므로 이를 즉각적인 실시간 상태라고 설명하면 안 된다.

## 우선 조치할 결함

### F01 · P1 — 오래되거나 실패한 에이전트에 Verified 배지 표시

위치: `agent_market/concierge/agent_entry.py:109-119`.

`active`, 건강 상태 문자열, `quarantine` 여부만 검사한다. 검증 시각, 현재 버전의 성공 증거, 최신 실패, `review` 상태를 검사하지 않는다. 48시간 지난 건강 시각, review 상태, 최신 실패 보고서를 각각 가진 합성 에이전트 모두 **Verified Grade A**를 반환했다.

개선: 기존 보고서/레지스트리의 현재 버전·최신 증거 판정을 재사용한다. 만료·실패·review·격리·지원되지 않는 연결이면 검증 배지를 내려야 한다. 등급과 검증 상태를 분리하고 `checked_at`·유효 범위를 설명한다. 캐시 TTL도 증거 만료까지의 남은 시간 이하로 제한한다.

### F02 · P1 — next_steps가 추천 정책과 안전 필터를 우회

위치: `fast_chat.py:114-120`, `inertia.py:42-93`, `front.py:384-393`.

경험 기반 전이는 `active`만 확인하고, 형제 도구는 사실상 순서대로 제안한다. 공개 투영은 주소를 바꾸지만 적격성을 검증하지 않는다. 다음 네 조건을 각각 재현했다: Auto에서 x402 후속 도구 노출, 명시적 MCP에서 A2A 노출, down/quarantine 대상 노출, review 대상 노출.

개선: 프로토콜 범위와 세션 실패 제외 목록을 전달하고, 현재 건강·검증·격리 상태와 도구별 지원 스키마/실행 정책을 공통 게이트로 검증한다. A2A 우선/MCP 보충과 x402 명시 선택 원칙을 후속 힌트에도 적용한다. 통계적 다음 도구 추천을 입력·출력 호환성 보장이나 실행 권한으로 표현하지 않는다. **실제 실행 권한 우회가 확인된 것은 아니며, 추천 데이터가 잘못 노출되는 문제다.**

### F03 · P1 — 같은 에이전트의 계약 변경에도 잘못된 304 반환

위치: `agent_entry.py:100-105,164-171`.

현재 비교 대상은 후보 ID 목록과 선두 등급이다. 동일 ID의 필수 입력을 `city`에서 `place`로 바꿔도 ETag가 그대로여서 304를 반환했다. 사용자는 오래된 호출 계약을 계속 사용할 수 있다.

개선: 현재 불변 연결 버전·도구/스키마 해시·검증 상태/만료를 재방문 상태와 ETag에 포함한다. 정체성·등급 변화, 호출 계약 변화, 증거 갱신을 구분하고 변경된 현재 후보를 제공한다. 워크플로우도 선두 하나뿐 아니라 반환한 후보 전체의 버전/가용성 변화를 정의한다.

### F04 · P1 — 선택적 프리페치 오류가 본 추천을 500으로 중단

위치: `fast_chat.py:114-116`, `inertia.py:74,96`.

정상 `usage_guide`가 있지만 `usage_tools`가 잘못된 JSON인 A2A 에이전트로 재현했다. 본 추천은 가능한데 추가 프리페치에서 JSONDecodeError가 발생해 `/chat`이 500이 된다. 해당 예외는 공개 응답에서 일반 오류로 마스킹되지만 기능은 중단된다.

개선: 데이터 구조·크기·JSON을 검증하고, 선택적 힌트 실패는 빈 `next_steps`와 내부 관측으로 격리한다. 기존 추천 응답을 보존한다. 모든 예외를 조용히 무시하는 방식 대신 예상 데이터 오류와 저장소 장애를 구분한다.

### F05 · P1 — 실패 복구가 같은 장애 호스트와 다른 프로토콜을 반환

위치: `front.py:3297-3309`.

누적 실패 **ID**만 제외하며 이전 프로토콜을 `rec.search`에 전달하지 않는다. 서로 다른 리소스 ID가 같은 호스트의 다른 경로를 가리키는 경우 대체로 반환했다. MCP를 선택한 세션에서 실패 보고 후 A2A 대체가 반환되는 것도 재현했다.

개선: 명시적 프로토콜과 기존 요청 범위를 유지한다. 같은 정규화 endpoint·별칭·같은 호스트를 우선 제외하며, 가능한 경우 운영자/상위 제공자/장애 도메인의 독립성도 확인한다. 다른 호스트만으로 완전한 장애 독립성을 증명하지는 못한다. 후보가 없으면 `no_alternative`로 응답하고 기존 조건을 몰래 완화하지 않는다. 이 검색 복구와 기존 승인 기반 워크플로우 폴백 실행은 분리한다.

## 설계상 누락·보완 사항

### F06 · P2 — 실패 보고 계약과 경로 미완성

설계에는 REST `/api/agent/v1/report`, `error_type` enum, 대체 에이전트 Top-3 및 대체 워크플로우가 있다. 구현은 MCP `report`만 있고 REST는 격리 앱에서도 404다. MCP 스키마에도 `error_type`이 없다. 대체 응답은 단일 `alternative`뿐이며 워크플로우 대체는 없다.

기존 `alternative`는 하위 호환 필드로 유지하고 `alternatives`, 적절한 워크플로우 대체, 구조화된 원인·범위·선택 경계를 공통 서비스에서 제공하는 것이 좋다. 대체 제안은 실행 승인으로 간주하지 않는다. REST와 MCP의 입력/인가/오류 처리를 중복 구현하지 않는다.

### F07 · P2 — 머신 응답의 계약 요약과 후속 정보 누락

`follow_up_query`, 카드별 `capability_contract(input_required, protocol, verified_within_24h)`, 카드별 재확인 주기가 없다. 주 응답에만 `revalidate_after_sec`가 있다. Agent resume은 변경 시 `current_top_id`만 주고 설계의 갱신 Top-3는 주지 않는다. `next_action`으로 추가 검색은 가능하지만 설계의 단일 재방문 응답 계약과는 다르다.

실제 계약과 검증 증거에서 파생한 요약을 제공한다. 단순 건강 체크를 `verified_within_24h=true`로 확대하지 않으며, MCP/A2A의 서로 다른 입력 형식을 동일한 보장으로 표현하지 않는다.

### F08 · P2 — 오류 분류가 일반 단어를 제한 오류로 오인

위치: `front.py:3282-3292`. `"rate" in err_lower` 때문에 **Unable to generate report**가 `rate_limit`으로 분류됐다. `auth` 같은 부분 문자열도 비슷한 위험이 있다.

명시적이고 검증된 `error_type`/HTTP 상태를 우선하며, 하위 호환 텍스트 해석은 단어 경계와 보수적인 unspecified 분류를 사용한다. 제공자 오류 원문은 민감정보 제거 후 내부에만 제한적으로 보관한다.

### F09 · P2 — 304와 모델 토큰·성능 절약을 혼동

304는 응답 본문을 생략하는 HTTP 조건부 응답이다. LLM 호출·도구 요청·도구 결과 메타데이터를 외부 클라이언트가 어떻게 처리하는지까지 통제하지 않으므로 **0토큰 보장**으로 표현할 수 없다. HTTP 의미 참고: https://www.rfc-editor.org/rfc/rfc9110.html#name-304-not-modified

구현도 결과를 전부 계산한 뒤 해시를 비교한다. 단일 합성 목록의 연속 304 요청 5회 모두 추천 검색 1회씩, 총 5회가 수행됐다(`resume-measurements.json`). 약 2.0~2.35ms라는 이 격리 결과는 운영의 10ms·3초 SLA나 11만 건 카탈로그 성능을 입증하지 않는다. 사용자별 캐시와 변경 세대를 도입한다면 계약/증거/정책/실패 목록 변경 및 만료에 반드시 무효화돼야 한다.

설계의 논문·SNS 성과 수치와 특정 클라이언트 자동 설치/재방문 보장은 출처와 실험 조건이 제시되지 않아 이번 리뷰에서 검증된 사실로 채택하지 않았다. 이 스킬 문서는 opt-in 사용 안내이며, 사용자가 승인한 외부 호출 범위를 넓히는 강제 지침이 되어서는 안 된다.

### F10 · P2 — 운영 반영과 완료 기준 분리 필요

`live-get-results.json`에 로컬8400·공개 도메인 GET 결과를 남겼다. 신규 스킬/배지는 아직 404다. 작업 중 검사에 잘못 사용했던 관리자8200 결과는 공개 반영 판정에 사용하지 않았다.

소스 수정·격리 합격 → 같은 소스의 패키지 검증 → 사용자 배포 → 공개 경로/헤더/반환 계약 확인을 완료 조건으로 구분한다. 이번에는 제품 수정을 요청받은 것이 아니므로 배포·재시작을 수행하지 않았다. 핵심 결함 수정 전에 단순 재시작으로 완료 처리하지 않는다.

### F11 · P2 — 기존 테스트 기대값과 수용 기준 정리

`tests/test_inertia.py:169`의 오래된 문구 기대는 현재의 사실적인 `Next-tool suggestions`에 맞춰 조정해야 한다. 0ms라는 문구를 다시 제품에 넣어 통과시키면 안 된다. 동시에 이번 감사 케이스를 해결 후 정규 회귀에 옮겨서 happy path 54개만으로 완료 선언하는 일이 반복되지 않게 한다.

## 권장 작업 순서와 종료 조건

1. **공통 적격성·프로토콜 판정**을 정의하고 next_steps/배지에 적용한다(F01~F02). 기존 추천·실행 인가는 보존한다.
2. **선택적 프리페치 장애 격리**를 적용해 정상 추천의 500 전파를 막는다(F04).
3. **재방문 버전/증거 fingerprint와 Delta 응답**을 구현한다(F03, F07). 동일 ID의 스키마 변경, 증거 만료/실패, 워크플로우 버전 변경으로 이전 ETag가 무효화돼야 한다.
4. **실패 복구 공통 서비스**에서 프로토콜·실패 도메인 제외, Top-3, error_type, REST/MCP, 안전한 오류 분류를 함께 완성한다(F05~F08).
5. **문서·검사·성능 수용 기준**을 고정하고 0토큰/0ms 보장을 정정한다(F09, F11). 소규모 지연 수치를 운영 성능으로 확대하지 않는다.
6. **한 번의 최종 통합 검증과 사용자 배포 후 GET 점검**으로 마무리한다(F10). 배포 전후 검증을 별개 미완료 항목으로 무한 확장하지 않는다.

종료 기준: 합의한 상세 설계의 모든 필수 필드/경로가 존재하고, 이번 17개 실패 조건이 모두 해소되고, 기존 정상 회귀·브라우저 보안 검사에 기능 퇴행이 없으며, 사용자 배포 후 공개 경로가 확인되는 것. 외부 마케팅 채택률·모델 토큰 절약 효과·추가 연구는 개발 완료와 분리해 측정 과제로 남긴다.
