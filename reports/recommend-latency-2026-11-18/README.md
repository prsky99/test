# 추천 검색 지연(prefetch_hit) 원인과 처리안 (검색과 RAG, 2026-11-18)

PM 과제(11-18 오전, 마감 11:00). 근거는 user_slo 정시 측정(공개 주소, 처음 보는 질의, 새 연결, 시간당 추천 표본 2개)의 Server-Timing 단계 값이다. 단계 값은 서버 내부 수치다.

## 1. 결론

- **prefetch_hit은 "적중해서 아낀 시간"이 아니다.** A2A 검색과 MCP 검색을 동시에 시작한 뒤, A2A 검색이 끝나고 MCP 검색이 끝나기를 기다린 시간이다(`protocol_prefetch.py` 84~90행, `future.result()` 대기). 적중 뒤에 재검증, DB 조회, 직렬화는 없다.
  - 그래서 prefetch_hit이 크다는 것은 MCP 검색이 A2A 검색보다 그만큼 오래 걸렸다는 뜻이다. step_search는 대략 max(A2A, MCP)다.
- **늘어난 몫은 MCP 검색의 후보 확인 단계(admission_loop)다.** step_search가 1초를 넘은 표본은 모두 admission_loop가 크고(892~1,181ms), 그 안의 계약 행 읽기 resource_read도 크다(343~745ms). 벡터 검색 ann은 140~472ms로 병목이 아니다.
- **원인에서 뺀 것**
  - fd5cb26d: r12에 없었고 11-18 00:40 r13으로 처음 나갔다. 11-17 저녁의 증가와 관계없다.
  - r11→r12의 추천 경로 변경(release.json 해시 비교): gateway_exposure의 stated_price 검사는 설명 1개에 0.08ms이고, 검색 뒤 exposure 단계에서 돈다. retrieval_metrics는 단계 이름만 늘었다. auto_run은 우리 측정에서 켜지지 않는다.
  - x402 후보: MCP 검색은 kind='mcp'를 검색 전에 거른다. 낱말 검색은 SQL WHERE, 벡터 검색은 MCP 전용 그래프 embeddings_half_mcp를 쓴다. MCP 활성 목록은 2일에 약 3%(1,295개)만 늘었다.
- **부하**: 11-17 23:06(1분 부하 9.86, 밤 전체 시험과 겹침)은 비교에서 뺐다. 11-18 07:04도 부하 7.29다.

## 3. MCP 그래프 cap은 하지 않는다 (PM 06:52 결정)

- 임베딩: a2a 244,041행/3,969호스트, x402 99,845행/3,597호스트, mcp 44,666행/31,373호스트.
- MCP에서 1,000행을 넘는 호스트는 4곳(api.alpharc.app 3,347, nolimit-observatory 2,364, gateway.pipeworx.io 1,937, mcp.apify.com 1,218)뿐이다. 호스트당 1,000 cap으로 빠지는 행은 약 4,900개(11%)이고, 200으로 낮춰도 약 19%다.
- A2A는 한 호스트가 232천 행을 차지해 cap 뒤 ann이 520→239ms로 줄었다. MCP는 쏠림이 없고 ann도 병목이 아니라 cap의 효과가 작다. 리허설과 복구 SQL은 쓰지 않는다.

## 4. 기록의 빈칸과 이미 한 일

- 운영 로그(frontend concierge 로그)에는 요청별 단계 시간이 없다. 표본은 정시 측정뿐이다.
- 789bd1ad(user_slo, 11-18 01:10 반영): prefetch_hit, miss, skip, unused 네 칸을 0을 포함해 항상 남긴다.
  - 다만 서버의 Server-Timing은 큰 값 순서로 24개만 내보내서(`request_timing.py`), 0ms 표시가 거기서 잘릴 수 있다. 07:04 표본은 둘 다 hit이라 아직 확인하지 못했다.
  - unused나 skip 표본이 나오면 확인한다. 잘린다면 request_timing이 prefetch_* 네 칸을 순위와 상관없이 늘 내보내게 하는 작은 frontend 변경을 제안한다.
- b210709f(낮 frontend 묶음): MCP 스레드의 시작부터 끝까지를 prefetch_run 단계로 기록한다. ann과 admission_loop는 두 스레드의 합이라, 지금은 MCP 검색만의 시간을 알 수 없다.
