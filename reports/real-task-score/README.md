# 실제 과제 채점 (정답 세트 30개, 공개 주소)

품질 목표 100%의 기준: 추천받은 에이전트에 우리 게이트웨이로 실제로 연결해 과제를 해내는 비율.

- 정답 세트: `tests/data/real_tasks_30.json` (사람 과제 p01~p15 성장·유통, 에이전트 과제 a01~a15 검색과 RAG). 과제마다 자동 채점 패턴 `check`를 붙였습니다. "최근 N일" 조건은 올해 날짜 문자열로 근사합니다.
- 채점기: `scripts/real_task_score.py`
  1. 공개 MCP `find_agents`(읽기 전용, 대화 저장 안 함)로 추천을 받습니다.
  2. 1순위를 `/api/gateway/{mcp|a2a}/{id}`로 호출합니다. MCP는 initialize → tools/list → 읽기 전용 tools/call 한 번, A2A는 message/send입니다.
  3. `check` 패턴으로 채점합니다.
- 결제·자격 증명은 보내지 않습니다. 이름이 쓰기 동작(create, delete, send …)인 도구는 부르지 않고, 게이트웨이도 등록된 정보 조회 도구만 허용합니다.
- 실행: 하루 2번(밤 04~05시, 오후 15~17시) `ops_auto watch`가 heavy_slot으로 낮은 우선순위로 시작합니다(11-12 PM). 결과는 `reports/real-task-score/<날짜>.json`, `logs/ops/real-task-score.jsonl`에 남고, 아래 '최신 점수'가 실행마다 자동으로 바뀝니다.

## 게이트웨이 분당 10회 제한이 실제 에이전트를 막는가

막습니다. 판단 근거:
- MCP 과제 하나는 게이트웨이 호출 3번(initialize, tools/list, tools/call)이 필요합니다. 그래서 주소 하나에서 1분에 과제 3개 정도가 한계입니다.
- 여러 과제를 연달아 하는 자율형 에이전트나 평가 도구는 첫 측정처럼 4번째 과제부터 429를 받습니다.
- 클라우드 에이전트는 출구 주소를 여럿이 함께 쓰는 경우가 많아, 서로의 한도를 나눠 쓰게 됩니다.
- 응답에 `RateLimit`·`Retry-After` 헤더는 있어 잘 만든 클라이언트는 기다릴 수 있습니다. 하지만 많은 에이전트는 429를 실패로 처리합니다.

제안(운영·SRE·PM 결정):
- initialize·tools/list는 제공자를 부르지 않으므로 한도에서 빼고, 실제 제공자 호출(tools/call, message/send)만 세기
- 또는 한도를 분당 30회로 올리기
