# 에이전트별 기능 텍스트 사전 저장 설계 (2026-10-28)

## 목적
Explore에서 처음 보는 검색어의 응답 시간(질문 6개 기준 1.6~4.5초)을 줄인다. 검색 결과는 지금과 같아야 한다.

## 측정으로 확인한 병목
처음 보는 검색어 6개, 운영 DB 읽기 전용:

| 구간 | 시간 |
|---|---|
| 1차 단어 검사(`text_may_match`) | 0.15~1.20초 |
| 후보 검색(`candidates`) | 0.49~1.38초 |
| 도구 목록 해석(`_advertised_tools`) | 0.08~0.69초 |
| 검색어별 적합성 검사(`task_scope_matches`) | 0.10~0.92초 |
| 스키마 지원 판정 | 0.01~0.39초 |
| DB 행 읽기 | 0.2~0.6초 |

- 한 페이지에서 읽는 행의 약 70%가 1차 단어 검사에서 탈락한다.
- 1차 검사는 이름·설명·도구 목록·도구 스키마 JSON·사용 안내·세부 정보를 모두 이어 붙인 원문(평균 9.5KB)을 정규식으로 여러 번 훑는다.

## 핵심 관찰
- 모든 통과 경로는 검색 단어가 에이전트 이름·설명, 또는 광고된 도구의 이름·설명 안에 있기를 요구한다(`_coherent_capability`).
- 스키마 JSON, 사용 안내 전문, 세부 정보 안의 단어만으로는 통과할 수 없다.
- 따라서 "이름 + 설명 + 광고된 도구의 이름·id·설명"(기능 텍스트, 평균 1.6KB)에서 1차 검사를 해도 판정이 같다.
  - 이 텍스트는 실제 판정에 쓰는 글의 상위 집합이다.
  - 밑줄은 공백으로 바꾼다. 이렇게 하면 단어 경계가 늘어 일치가 늘 뿐 줄지 않는다.
- 다만 기능 텍스트를 만들려면 도구 목록을 해석해야 하고, 그것이 비싸다. 그래서 미리 만들어 저장한다.

## 저장 구조
`agentcon_search` 스키마(임베딩·전문 검색 색인과 같은 곳)에 둔다.

```sql
CREATE TABLE agentcon_search.capability_text_configuration(id BIGINT PRIMARY KEY CHECK(id=1), profile TEXT NOT NULL);
CREATE TABLE agentcon_search.capability_text(
  resource_id BIGINT PRIMARY KEY,
  source_hash TEXT NOT NULL,   -- 원문 필드의 SHA-256
  version INTEGER NOT NULL,    -- 생성 규칙 버전
  body TEXT NOT NULL,          -- 기능 텍스트(소문자, 밑줄은 공백)
  updated_at DOUBLE PRECISION NOT NULL);
```

- 설치는 `install(store)` 한 번이다. 확인은 `available(store)`로 하며, 프로필이 다르면 쓰지 않는다.
- 용량: 약 18만 건 × 평균 1.6KB ≈ 290MB(압축 전)이다. 큰 값은 PostgreSQL TOAST가 압축한다.

## 무효화 규칙
- `source_hash`는 판정과 해석에 쓰는 원문 필드 전부의 해시다: kind, name, description, category, cap_tool_names, usage_tools, usage_full_tools, usage_full_hash, usage_guide, details.
- 검색할 때 현재 행의 해시와 저장된 해시, 생성 규칙 버전이 모두 같을 때만 저장된 텍스트를 쓴다. 하나라도 다르면 지금처럼 원문 전체로 검사한다. 따라서 오래된 값 때문에 결과가 달라지지 않는다.
- 생성 규칙(`_advertised_tools` 등)을 바꾸면 `VERSION`을 올린다. 올리면 저장된 값은 모두 무시되고 다시 만들어진다.

## 갱신
- jobs 역할이 주기적으로 처리한다.
- 검색 대상(활성, 연결 가능, 격리·검토 아님) 행을 id 순으로 200건씩 읽는다. 해시가 다르거나 없는 행만 다시 만들어 저장한다.
- 한 번에 정해진 건수만 처리하고 쉬면서, 한 바퀴를 마치면 6시간 뒤 다시 돈다.
- 검색 요청 중에는 쓰지 않는다. 검색은 읽기 전용 스냅샷만 쓴다.

## 검색에서 사용
- `hybrid_explore._in_ranked_batches`가 행 묶음을 읽을 때 같은 id의 기능 텍스트를 한 번에 읽는다.
- 해시와 버전이 맞으면 행에 `_capability_text`를 붙인다.
- `text_may_match`는 이 값이 있으면 원문 대신 기능 텍스트를 검사한다.
- 공개 응답에는 정해진 열만 담기 때문에 이 값은 노출되지 않는다.

## 검증 계획
1. 운영 DB 읽기 전용으로 기존 경로와 새 경로의 Explore 결과(id 순서까지)가 같은지, 질문 여러 개로 비교한다.
2. 처음 보는 검색어 시간을 전후로 비교한다.
3. 단위 시험:
   - 해시 불일치·버전 불일치이면 원문으로 검사한다.
   - 기능 텍스트만으로도 같은 판정이 나온다.

## 2단계(이번 범위 밖)
- 도구 목록 해석 결과와 도구별 스키마 지원 여부를 함께 저장해, 1차 검사를 통과한 행의 해석 비용도 줄인다.
- 기능 텍스트를 Chat 후보 검사에도 쓴다.


## 구현 결과
- 모듈: `agent_market/postgres_capability_text.py`
  - `install`, `available`: 테이블 설치와 확인
  - `source_hash`, `build`: 원문 해시와 기능 텍스트 생성
  - `stored`, `attach`: 저장값 읽기와 행에 붙이기
  - `Refresher`: jobs 역할의 정기 갱신
- 검색 연결:
  - `hybrid_explore._in_ranked_batches`가 행 묶음마다 `attach`를 부른다.
  - `selection.text_may_match`는 `_capability_text`가 있으면 그것을 검사한다.
- jobs 연결: `service_host`가 계약 재검증이 없을 때 갱신 라운드(200건 × 10묶음)를 돌린다. 실패하면 5분 쉰다.
- 테이블이 없으면 아무것도 바뀌지 않는다. 검색은 원문으로, 갱신기는 대기한다.

## 검증
- **안전성(전수):** 운영 DB 읽기 전용으로 에이전트 8,330건 × 질문 24개 = 199,416쌍을 비교했다. "기존 경로라면 통과하는데 새 1차 검사가 탈락시킨" 경우는 0건이다.
- **1차 검사 시간:** 182.2초 → 27.5초(6.6배). 1차 검사 통과 행은 33,069 → 19,016으로 줄어 뒤 단계 해석도 줄었다.
- **Explore 전체(질문 20개, 처음 보는 검색어):** 54.6초 → 49.9초(약 9%).
  - 결과 id 집합은 같다. 차이 2건은 기존 경로끼리도 생기는 실행 간 변동으로 확인했다(해당 행의 판정은 두 경로가 같음).
- **테스트:**
  - `tests/test_capability_text.py` 6건(실제 PostgreSQL에서 설치·갱신·붙이기·변경 무효화·검색 대상 이탈 정리 포함)
  - Explore·Chat·서비스 관련 727건 중 723건 통과. 실패 4건은 이전 운영 릴리스에서도 실패하던 첫 화면 테스트다.

## 효과의 한계
- 전체 개선이 9%에 그치는 이유는 후보 검색(질문당 0.5~1.4초)과 통과 행의 검색어별 검사가 남기 때문이다.
- 더 줄이려면 2단계(도구 해석 결과·스키마 지원 여부 저장)와 후보 검색 자체의 개선이 필요하다.

## 운영 적용 절차(승인 필요)
1. 운영 DB에 `install`을 실행한다. 빈 테이블 2개만 만들고 기존 데이터는 바꾸지 않는다.
2. `captext-*-20261028-r1` 네 역할을 배포한다.
3. jobs가 검색 대상 약 18만 건을 채운다. 예상 4~5분 CPU를 쓰며, 묶음 사이에 다른 jobs 명령이 끼어들 수 있다.
4. 채운 뒤 Explore 처음 보는 검색어 시간을 다시 측정한다.

- 운영 측정(처음 보는 검색어 20개, 같은 시각에 연이어 측정):

- 다음 단계: 효과를 키우려면 2단계(도구 해석 결과·스키마 지원 여부 저장)와 후보 검색(질문당 0.5~1.4초) 개선이 필요하다.
