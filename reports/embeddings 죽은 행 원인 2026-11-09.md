# embeddings 죽은 행·임베딩 낭비 원인 (2026-11-09 밤, 운영·SRE)

결론: **`agentcon_search.embeddings`의 죽은 행과 Ollama 임베딩의 약 46%는 같은 글을 다시 임베딩한 낭비다.** 가장 큰 원인은 자원 629개의 카테고리를 두 작성자가 약 30분마다 서로 덮어쓰는 것이다. 이 부분 고치기가 가장 효과가 크고 싸다. 표 단위 autovacuum 설정 변경은 원인을 고친 뒤 다시 보면 되므로 지금 승인 요청하지 않는다.

## 1. 숫자 (운영 DB 읽기 전용, 11-09 22시 기준)
- 표: 살아 있는 행 27.5만. 11-01 통계 초기화 이후 삽입 285만, 삭제 258만, 갱신 42만 → 9일 동안 행마다 약 10번 지웠다 넣음. 벡터 인덱스(HNSW)가 있어 이 표의 autovacuum은 30분 넘게 디스크를 점유한다(11-09 20:56~21:23+, 115MB/s).
- 최근 24시간 색인 완료된 벡터 작업: **17.5만 건, 자원 8.0만 개** → 자원마다 하루 2.2번 다시 임베딩. Ollama 임베딩 하루 약 17만 건과 같은 규모.
- 같은 자원의 연속된 색인 작업 9.5만 쌍 분석:

| 경우 | 건수 | 의미 |
|---|---|---|
| source_hash 같음 | 2.15만 | 임베딩 입력과 원천 필드가 그대로인데 다시 임베딩(트리거 잡음) |
| source는 바뀌고 임베딩 입력(corpus) 같음 | 1.09만 | 다시 임베딩할 필요 없음 |
| 임베딩 입력이 바뀜 | 6.28만 | 그중 **4.88만이 A→B→A 되돌아가기**, 자원 629개에서만 발생 |
| 합계 낭비 추정 | **약 8.1만/일(46%)** | 2.15만 + 1.09만 + 4.88만 |

## 2. 원인
### 2.1 카테고리 줄다리기 (가장 큼, 629개 자원에서 4.9만/일)
예: 자원 87082(a2a-registry 출처). 약 30분 간격으로 corpus가 `31be…` ↔ `e2a7…`로 반복(20:23, 20:26, 20:53, 21:03, 21:27, 21:32, 21:57). 
1. `gateway/crawler.py` `parse_a2a_item`: `cat = item.get("category") or classify(...)` → 레지스트리의 원본 카테고리(`developer-tools`, `demo-test`, `agent-communities` 등 우리 14개 체계 밖)를 그대로 저장. 증분 수집마다 `upsert_page`의 `UPDATE ... category=?`가 덮어씀.
2. 몇 분 뒤 `collector/a2a.py` `_record`가 카드 내용으로 `classify(...)` 해서 `set_category`로 우리 카테고리로 바꿈.
3. 임베딩 입력은 `이름 [카테고리]: 설명`이라 카테고리가 바뀔 때마다 새 벡터 작업 → 다시 임베딩 → 표에서 지우고 다시 넣음.
- 부작용: 지금 하이픈 원본 카테고리를 가진 자원이 478개. 이 자원들은 절반의 시간 동안 우리 카테고리 페이지·카테고리 필터에서 빠진다.

### 2.2 넓은 무효화 트리거 (2.15만/일)
운영 DB 함수 `application_vector_invalidate`는 resources의 33개 필드 중 하나라도 바뀌면 벡터 provenance를 지우고 새 작업을 만든다(`health_status`, `details`, `auth_*`, `usage_guide` 등 포함). 그런데 source_hash는 11개 필드(`_RAW`), 임베딩 입력은 이름·카테고리·설명뿐이다. 헬스체크 상태가 바뀔 때마다 같은 글을 다시 임베딩한다.

### 2.3 같은 벡터도 지웠다 다시 넣음
`postgres_ann.cleanup`은 provenance가 없거나 다른 행을 먼저 지우고, `publish`는 `ON CONFLICT DO UPDATE`로 항상 다시 쓴다. 벡터가 같아도 죽은 행이 생긴다.

## 3. 수정안 (효과 큰 순)
1. **카테고리 줄다리기 멈추기(수집 코드, 위임 범위):** `parse_a2a_item`이 레지스트리 카테고리를 우리 체계로 바꾸거나(`classify` 사용), `upsert_page`의 UPDATE가 기존 자원의 카테고리를 덮어쓰지 않게(우리 14개 체계 값이 이미 있으면 유지). 그다음 하이픈 카테고리 478개를 한 번 다시 분류. 예상: 임베딩 하루 약 4.9만 감소(28%), 카테고리 페이지 누락 해소.
2. **같은 입력이면 다시 임베딩하지 않기(벡터 작업 코드):** 작업을 집을 때 corpus_hash·descriptor가 지금 embeddings 행을 만든 것과 같으면 Ollama를 부르지 않고 provenance만 새 작업으로 옮긴다. `cleanup`은 대기 중 작업이 있는 자원의 행은 지우지 않고, `publish`는 `vector_hash`가 같으면 갱신하지 않는다(`ON CONFLICT ... DO UPDATE ... WHERE embeddings.vector_hash IS DISTINCT FROM EXCLUDED.vector_hash`). 이 SQL은 등록 SQL 목록(application_store_sql.json)에 같이 등록해야 한다. 예상: 나머지 약 3.2만/일 감소.
3. **트리거 범위 좁히기(운영 DB 함수 변경, 승인 필요):** 무효화 필드를 `_RAW` 11개로 줄이면 2.2의 잡음이 사라진다. provenance 보안 설계(원천 필드에 묶인 증명)와 관련되어 검색과 RAG 팀 검토가 먼저 필요하다. 2번을 하면 효과가 대부분 겹치므로 우선순위 낮음.
4. **표 단위 autovacuum 설정:** 1·2를 한 뒤 죽은 행 생성 속도를 다시 재고, 여전히 vacuum이 길면 그때 근거를 붙여 승인 요청한다.

## 4. 왜 지금 직접 고치지 않았나
- `gateway/crawler.py`, `gateway/store.py`, `application_store_vector.py`는 다른 세션이 작업본에서 고치는 중이다(미커밋 변경 있음). 같은 파일을 동시에 고치지 않는다.
- 수집·분류 규칙은 검색과 RAG 팀 영역이다. 총괄 PM이 정해 주면 운영·SRE가 1번을 맡을 수 있다.
