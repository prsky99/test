# AI AD Coin 소스 분석과 개선사항 (2026-11-09)

- **대상:**
  - v1: `agent_market/ad_coin/` 20개 파일, 약 5,800줄. 커밋됐고 운영에 배포됐으며 기능은 꺼져 있다.
  - v2: `agent_market/ad_coin/v2/` 44개 파이썬 파일 약 10,100줄, 웹 3개, Solidity 계약 1개. **커밋되지 않았다.** 다른 세션이 설계 v6.2에 따라 작업 중이다.
  - 관련 시험, 스크립트, 문서
- **방법:**
  - 정적 지표: 파일·함수 규모와 분기 수(순환 복잡도 근사)
  - 정적 분석: pyflakes, bandit
  - 시험 실행과 커버리지
  - 프로젝트 규칙 대조: 영어 전용, 숨은 문자, 디자인 체계, 등록 SQL, 보안
  - 핵심 모듈 읽기

## 2. 개선사항

중요도는 보안 > 품질 > 속도 순서(사용자 결정)로 매겼다.

### 2.1 보안 (높음)

1. **토큰 계약의 준비금 검사가 "실패 시 열림"이다**(`v2/contracts/AIADCoin.sol` `mint`).
   - 오라클이 설정되지 않았거나(주소 0), 0이나 음수를 돌려주면 검사를 건너뛰고 제한 없이 발행한다.
   - 오라클 값이 언제 것인지(`latestTimestamp`)도 보지 않는다.
   - **개선:** 오라클이 없거나, 값이 0 이하이거나, 오래됐으면 발행을 거부한다(fail closed). 단위와 소수점 자릿수 일치도 검사한다.
2. **계약 소유자가 단일 키이고 바꿀 수 없다.**
   - 소유권 이전 함수가 없어 키를 잃거나 유출되면 영구적으로 되돌릴 수 없다.
   - 발행자와 오라클 교체에 지연(timelock)이 없고, 0 주소 검사도 없다.
   - **개선:** 다중 서명 소유자, 2단계 소유권 이전, 발행자·오라클 교체 timelock을 넣고, 외부 감사 전에는 메인넷에 배포하지 않는다.
   - 설계 DEC-07("실제 가치 모드는 법·감사 확정 뒤")을 계약 코드에서도 강제해야 한다.
3. **실험 그룹 배정에 MD5를 쓴다**(`v2/advertiser_platform.py:357`, bandit 높음).
   - 보안 용도는 아니지만 규칙상 고쳐야 한다.
   - **개선:** `hashlib.sha256` 또는 `md5(..., usedforsecurity=False)`.
4. **공개 경로에 자체 속도 제한이 없다**(v1 `/status`·`/offer-feed`·`/account`).
   - **개선:** 기능을 켜기 전에 Cloudflare·Caddy 경계 제한을 확인한다. 또는 IP 기준의 가벼운 제한을 둔다.
5. **속도 제한이 프로세스 메모리 안에만 있다**(`broker.server.RateLimiter`).
   - frontend 슬롯 두 개와 재시작 사이에 공유되지 않아, 실제 한도가 최대 두 배가 된다.
   - **개선:** 이미 있는 Redis 허브(`infra.redis_hub`)로 옮긴다.

### 2.2 품질·구조 (중간)

6. **v1과 v2가 두 벌로 존재한다.**
   - 원장, 영수증, API, 화면이 각각 따로 있다: v1 `ledger.py`·`receipts.py`·`/v1`·광고주 콘솔 대 v2 `ledger.py`·`receipts.py`·`/v2`·`v2/web`.
   - v2 설계는 "v1을 새 자산으로 재해석하지 않는다(DEC-02)"고 정했지만, v1을 어떻게 끝낼지는 정해지지 않았다.
   - **개선:** 다음 중 하나로 결정한다.
     - v1을 시험 모드 전용으로 동결한다.
     - v2 화면으로 옮긴 뒤 v1 화면과 경로를 정리한다.
   - 광고주 콘솔과 사람 보상 화면을 하나로 합치는 계획도 필요하다.
7. **v2 화면이 사이트 디자인 체계를 따르지 않는다**(`v2/web/app.css`, `index.html`).
   - 공용 `styles.css`·`pearl-live.css`·`app.js`를 쓰지 않고, 자체 색상값을 쓴다. 글자색 `#203634`(사이트는 `#103540`), 제목 글꼴은 시스템 글꼴(사이트는 세리프)이다.
   - 11-05 사용자 결정("사이트 디자인·UI/UX를 그대로 유지")과 어긋난다.
   - **개선:** v1 광고주 콘솔처럼 공용 파일과 워크스페이스 틀(`ws-top`·`ws-sidebar`·`page-heading`·`card`)로 바꾸고, 디자인 유지 시험을 v2 화면에도 적용한다.
   - 스크립트의 주석(`/* Optional advertising workspace… */`)도 지운다(화면에 주석을 두지 않는 규칙).
8. **거대 함수와 파일**
   - `v1 api.router_for`: 687줄, 분기 143개. 광고주·사람·관리자 경로를 파일별 라우터로 나눈다.
   - `v1 service.py`: 1,338줄, 함수 83개. 경매·후보 조회, 자금 이동, 견적, 실행권, 오퍼로 나눈다.
   - `v1 service.quote`: 153줄, 분기 43개.
   - `v2 commercial.py`: 2,166줄. `_context`는 162줄, 분기 45개다.
   - 나누면 검토와 시험이 쉬워지고 변경 충돌(여러 세션 동시 작업)도 줄어든다.
9. **커버리지가 낮은 곳**(85% 미만)
   - v2:
     - HTTP 계층: `ad_relay_http` 71%, `advertiser_platform_http` 74%, `agent_payment_http` 80%, `real_value_http` 82%
     - `receipts` 75%, `key_vault` 76%, `workers` 77%, `agent_payments` 82%, `access` 83%, `real_value` 84%, `commercial` 84%
   - v1: `private_workflows` 74%, `sql_registry` 77%, `api` 84%
   - 돈·키·서명과 관련된 모듈부터 95% 이상을 목표로 한다. 실패 경로와 권한 거부 경로가 주로 빠져 있다.
10. **v1 화면이 파이썬 문자열 안에 있다**(`advertiser_page.py`·`page.py`·`admin_page.py`).
    - HTML과 JS가 한 줄로 길게 들어 있어 읽기 어렵고, JS 문법 검사와 자동 정리 도구를 쓸 수 없다.
    - **개선:** v2처럼 정적 파일로 분리하고 공용 자산과 함께 내보낸다.
11. **백그라운드 작업이 웹 프로세스 안에 있다**(v1 만료 정리, 전체 재계산, 견적 삭제, 세션 정리 스레드).
    - frontend 슬롯마다 같은 일을 중복으로 돈다(멱등이라 결과는 안전하지만 낭비다).
    - **개선:** 프로젝트의 jobs 서비스로 옮기거나, advisory lock으로 한 프로세스만 실행하게 한다.
12. **문서가 흩어져 있다.**
    - AD Coin 문서와 명세가 19개다(v5·v6.1·v6.2 설계, 정책, 로드맵, OpenAPI 2개 등). 어느 것이 최신 기준인지 찾기 어렵다.
    - **개선:** 최상위 색인 문서 하나(현재 기준·역사본 구분)를 두고, 지난 판본은 보관 폴더로 옮긴다.

### 2.3 운영·절차 (중간)

13. **v2가 1만 줄 넘게 커밋되지 않았다.**
    - 작업본을 여러 세션이 같이 쓰므로 유실이나 섞임 위험이 있다.
    - 시험 파일 14개도 추적되지 않는다.
    - **개선:** 담당 세션이 작은 단위로 나눠 커밋한다.
    - 작업본 `front.py`의 v2 연결도 함께 커밋해야 배포 오버레이에서 빠지지 않는다.
14. **기능을 켜는 경로가 막혀 있다.** 운영 설정 허용 목록(`scripts/agentcon_config.ALLOWED_KEYS`)에 `AD_COIN_*`와 `AD_COIN_V2_ENABLED`가 없다. 그랜드 오픈 준비 때 함께 추가해야 한다.
15. **실제 운영 경로의 동적 점검이 필요하다.** 기능을 켠 뒤 실제 고객 로그인, Cloudflare 경계, Web Bot Auth로 다시 점검한다(`scripts/ad_coin_dynamic_security.py`). v2에도 같은 공격 점검 스크립트가 필요하다.

### 2.4 속도 (낮음)

16. **리허설 속도 재측정**
    - 11-05 등록 SQL 검사를 넣은 뒤의 중량 단계는 기계 부하(12) 때문에 관문을 넘었다(검사 비용은 1.3µs로 원인 아님).
    - 한가한 시간에 모든 단계를 다시 잰다. v2는 대용량 리허설을 아직 하지 않았다.
17. **v2 이름 붙인 SQL**은 실행 계획(인덱스) 점검이 없다. v1처럼 대용량 데이터로 EXPLAIN 점검을 한다.

## 3. 잘된 점(유지할 것)

- **돈의 정합성:** 이중 기록 원장, 잔액 음수 금지, 멱등 키, 백킹 불변식과 회로 차단을 갖췄다. 동시성 시험도 있다(v1 리허설: 동시 이중 결제 0, 교착 시 자동 재시도).
- **추천과 광고의 분리:** `selection_digest`로 증명하고, 매달 감사로 확인한다.
- **보안 기본기:** 등록 SQL, CSRF, 상수 시간 비교, 해시로 저장하는 키, 보안 이벤트 로그(비밀 없음). 동적 점검 219개를 통과했다(v1).
- **v2의 설계 원칙:** 서버가 주체를 정하고(DEC-04), 모델과 돈 실행을 분리하며(DEC-05), outbox와 inbox로 외부 효과를 분리한다(DEC-06). 이 방향은 맞다.
- 시험 269개, 커버리지 87%, pyflakes 0건.

## 4. 권장 처리 순서

1. v2 담당 세션: 커밋(13), MD5(3), 화면 디자인 체계(7)
2. 계약: 준비금 fail-closed와 소유권·발행자 관리(1, 2). 실제 가치 모드 전 외부 감사
3. v1과 v2 정리 방향 결정(6). 사용자 결정이 필요하다
4. 큰 함수 분리와 커버리지 보강(8, 9), 백그라운드 작업 이동(11), 속도 제한 공유(5)
5. 문서 색인(12), 화면 정적 파일 분리(10)
6. 기능을 켤 때: 허용 목록(14), 경계 제한(4), 운영 동적 점검(15), 리허설 재측정(16, 17)
