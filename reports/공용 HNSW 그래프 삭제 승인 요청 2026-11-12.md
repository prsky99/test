## 6. 운영 DB 변경 절차 (deploy/DATABASE_OPERATIONS.md)

1. **리허설.** 시간은 00:00~08:00이고, heavy_slot 밤 칸을 쓴다. 명령은 아래와 같다.
   `scripts.db_change_rehearsal run --sql <drop.sql>`
   - 사본에는 `DROP INDEX agentcon_search.embeddings_cosine_hnsw;`를 쓴다. 리허설 도구가 psql -1로 한 트랜잭션 안에서 실행하는데, CONCURRENTLY는 트랜잭션 안에서 쓸 수 없다.
   - 그 시점의 네 역할 운영 버전을 붙여서 attach, 쓰기 트랜잭션, 탐색이 통과하는지 본다.
   - 5f9eb28d가 없는 버전이 붙으면 attach가 실패해야 정상이다. 리허설은 이 경우를 걸러내는 장치다.
   - 사본에서 복구 SQL(아래)을 실행하는 데 걸리는 시간도 잰다.
2. **복구 SQL을 준비한다.**
   ```sql
   -- 공용 그래프를 다시 만든다. 쓰기는 막지 않는다. 그동안 검색은 종류별 그래프로 하므로 사용자 영향이 없다.
   CREATE INDEX CONCURRENTLY embeddings_cosine_hnsw ON agentcon_search.embeddings
     USING hnsw (embedding vector_cosine_ops) WITH (m='16', ef_construction='64');
   -- 확인
   SELECT indisvalid, indisready FROM pg_index WHERE indexrelid='agentcon_search.embeddings_cosine_hnsw'::regclass;
   ```
   - 다시 만드는 시간은 추정이다. 39만 행, 768차원에 약 10~20분이 걸린다(11-11 결정 요청의 halfvec 추정을 바탕으로 했다). 리허설에서 실제로 잰다.
   - 실패하면 INVALID 색인이 남는다. 그때는 `DROP INDEX CONCURRENTLY IF EXISTS`로 지운 뒤 다시 만든다.
   - 12c9129e 이전 버전으로 되돌려야 하면, 복구 SQL을 먼저 끝낸 뒤 앱을 되돌린다. 순서가 바뀌면 옛 버전의 `available()`이 거부한다.
3. **사용자 승인을 받는다.** PM이 모아서 묻는다.
4. **실행 직전에 check가 0인지 본다.** 0이 아니면 실행하지 않는다. 운영에서는 다음을 실행한다.
   ```sql
   DROP INDEX CONCURRENTLY agentcon_search.embeddings_cosine_hnsw;
   ```
   - 트리거, 함수, 표 구조는 바꾸지 않는다. 따라서 public 트리거 5개 불변식에는 영향이 없다.
   - 실행 전후로 네 역할의 오류 로그와 탐색·추천 공개 측정을 본다.
