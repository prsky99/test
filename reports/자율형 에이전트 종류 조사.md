# 자율형 에이전트 종류 조사 — 현행 재작성본

작성일: 2026-10-27. 원본 문서를 찾지 못해 현재 소스·공식 문서·논문·개발자 커뮤니티를 대조하여 재작성했다. 이 문서의 12종은 제품 브랜드를 나눈 공식 분류가 아니라 **접속 방식과 권한 경계를 기준으로 한 시험 역할**이다. 하나의 에이전트가 여러 역할을 수행할 수 있다. 특정 상용 에이전트 12개에 실제 로그인했다는 뜻이 아니다.

계획은 총 76개이며 `scripts/agent_scenario_catalog.py`가 단일 목록이다. 실제 공개 접속 검사는 `scripts/agent_scenarios.py`가 실행한다. 전체 계획과 공개 스모크 검사의 판정 수는 같지 않다. 계획의 모드는 live 25개, isolated 43개, source 1개, manual 7개다. 아직 하지 않은 작업을 PASS로 채우지 않는다.

## 1. 검색엔진·일반 크롤러 — 8개 시나리오

진입점은 robots.txt, sitemap.xml, 공개 카테고리 페이지다. GET 성공, HEAD 일치, 사이트맵 파싱·연결, 증거 만료 후 URL 안정성, 출력 이스케이프를 확인한다. 비공개 정보는 robots 지시가 아닌 실제 인증으로 차단해야 한다. 실제 검색엔진 색인은 별도 미실행 항목이다.

근거: [Google robots 지침](https://developers.google.com/search/docs/crawling-indexing/robots/intro?hl=en), [사이트맵 작성 지침](https://developers.google.com/search/docs/crawling-indexing/sitemaps/build-sitemap). robots가 읽힌다는 사실은 검색 결과 노출을 보장하지 않는다.

## 2. LLM 문서 열람·검색 에이전트 — 8개

llms.txt, llms-full.txt, skill.md와 기계용 진입 문서를 읽고 적절한 API를 선택한다. 단순 접근 가능성 외에 통계의 모집단, 검증의 유효기간, 실제 실행 권한을 혼동하지 않는지 확인한다. 제공자 설명에 들어 있는 지시를 시스템 명령처럼 취급하면 안 된다. 실제 타사 LLM 세션은 별도 미실행 항목이다.

근거: [llms.txt 제안](https://llmstxt.org/). llms.txt는 웹 활용을 위한 제안이며 인증·검색엔진 색인 보증 수단이 아니다. 현재 소스의 문서 존재 확인과 제안 최신판 전체 준수 인증은 별개다.

## 3. 브라우저 조작 에이전트 — 6개

페이지와 DOM, 버튼, 키보드, 반응형 화면을 이용한다. 텍스트 API가 성공해도 실제 브라우저의 CORS, CSP, 세션 헤더 노출, 로컬 네트워크 권한 때문에 실패할 수 있다. 신뢰한 출처와 미허용 출처를 각각 실제 TLS로 시험하는 격리 Chromium 검증을 사용한다.

근거: [WebArena](https://arxiv.org/abs/2307.13854), [VisualWebArena](https://arxiv.org/abs/2401.13649). 두 논문은 현실적인 웹 작업과 시각 정보를 포함한 평가의 필요성을 보여 준다. 논문의 성공률을 이 서비스 성공률로 사용하지 않는다.

## 4. 코딩·개발 도구 에이전트 — 6개

공개 매니페스트와 명세를 읽어 Python·Node 클라이언트를 구성하는 역할이다. 내부 구현을 알아야만 성공하는 시험을 피하고, 광고된 인자명으로 검색·상세 조회를 수행한다. 공개 방문 권한에 사용자 워크스페이스의 실행 권한이 섞이지 않는지도 확인한다.

근거: [SWE-agent](https://arxiv.org/abs/2405.15793)는 에이전트가 사용하는 인터페이스 설계가 작업 수행에 영향을 준다고 보고한다. 이를 클라이언트 계약·오류·다음 행동 안내를 검증하는 근거로 삼았다. 실제 외부 코딩 제품 전체의 호환성 인증을 의미하지 않는다.

## 5. MCP 클라이언트 — 8개

버전 협상, tools/list, 검색 도구, 출력 스키마와 행동 표시, 상세 조회, 커서, SSE 미지원 처리를 확인한다. 도구별 선택 사항의 누락은 WARN으로 구분하고, 잘못된 타입이나 깨진 스키마는 FAIL로 처리한다. 현재 서버가 실제 구현한 버전과 알리는 버전이 맞아야 한다.

근거: [MCP 도구 규격](https://modelcontextprotocol.io/specification/2025-11-25/server/tools), [전송 규격](https://modelcontextprotocol.io/specification/2025-11-25/basic/transports). annotations는 권한 부여가 아니며, SSE가 없는 서버의 GET 405를 일괄 장애로 판단하지 않는다.

## 6. A2A 클라이언트 — 8개

에이전트 카드로 시작하여 message/send, text/data part와 contextId로 대화를 이어 간다. 문맥은 소유권과 함께 검사해야 하며, 충돌하는 토큰·추측한 문맥에 다른 사용자 정보를 보여주면 안 된다. 실제 서명 원격 에이전트 처리는 미실행이다.

근거: [A2A 공식 명세](https://github.com/a2aproject/A2A/blob/main/docs/specification.md). 대화 문맥 유지, 구조화 데이터 제공, 실제 실행 권한을 각각 확인한다.

## 7. REST·OpenAPI 도구 에이전트 — 6개

JSON 요청·응답으로 검색하고 선택된 프로토콜을 유지하며 상세 내용을 조회한다. 제한 정책·재시도 시간·오류 형식과 지연을 확인한다. 결과 카드가 있다는 사실은 제공자 실행 성공을 뜻하지 않는다.

근거: [ToolRet](https://arxiv.org/abs/2503.01763)는 도구 검색 품질이 실제 작업 수행에 영향을 준다고 보고한다. 따라서 응답 200이나 추천 개수만으로 성공을 판정하지 않고 도구 계약·후속 결과를 함께 본다.

## 8. x402 결제 역할 에이전트 — 6개

명시적 x402 선택과 자동 검색의 제외 정책, 격리된 402 요구 응답, Chat에서의 민감 결제 정보 비노출을 시험한다. **실제 결제·정산과 Bazaar 등재는 미실행**이다. 결제 정보를 읽거나 402를 받았다는 이유로 결제 성공으로 판정하지 않는다.

근거: [x402 공식 안내](https://docs.x402.org/introduction). HTTP 결제 요구와 실제 자금 이동은 다른 단계다. 실제 지갑·서명·정산을 사용하는 시험에는 별도의 명확한 실행 범위가 필요하다.

## 9. 워크플로우·다중 도구 에이전트 — 6개

적절한 공개 템플릿을 찾고 입력·연결·실행 준비 상태를 확인한다. 고객 승인, 실행 키의 범위, 중복 실행 방지를 격리 데이터로 검사한다. 실제 제공자 워크플로우 실행은 미실행이다.

근거: [ToolLLM](https://arxiv.org/abs/2307.16789)은 도구 검색과 다중 도구 사용·평가를 함께 다룬다. 이번 시험은 도구를 찾는 단계와 권한을 받아 실행하는 단계를 분리한다. 제공자 설명에서 확인되지 않은 기능을 만들어내지 않는다.

## 10. 재방문·지속 대화 에이전트 — 4개

MCP와 REST를 오가도 선택과 문맥을 유지하는지, 알 수 없는 토큰의 초기화를 설명하는지 확인한다. 재방문 시 과거 성공만 믿지 않고 현재 버전과 최신 실패를 재검사해야 한다. 보고서 일괄 조회 최적화에서도 같은 결과가 나와야 한다.

관련 소스: `agent_market/concierge/memory.py`, `report_evidence.py`, `selection.py`. 근거: [A2A 문맥 의미](https://github.com/a2aproject/A2A/blob/main/docs/specification.md). 재방문율이 낮다는 관찰만으로 추천 품질이 유일한 원인이라고 단정하지 않는다.

## 11. 작업 알림·콜백 에이전트 — 4개

작업 목적별 동의, 수신지 확인, 철회와 독립적인 마케팅 동의를 검사한다. 실제 운영 수신 확인은 미실행이다. 방문·콜백 요청을 마케팅 동의로 해석하지 않는다.

관련 소스: `agent_market/concierge/task_updates.py` 및 알림 보안 회귀. 이 분류는 현재 서비스의 권한·수신지 검증 설계에서 도출했다. 알림 등록 API가 있다는 사실을 실제 도달 보장으로 표현하지 않는다.

## 12. 적대적·잘못된 입력 에이전트 — 6개

과대 입력, 없는 도구를 부르는 요청, SSRF, XSS, 불확실한 실행의 재시도, 비밀값 노출을 격리 환경에서 확인한다. 운영에 1MB 공격·자격 증명 유출·실제 실행을 반복하지 않는다.

근거: [InjecAgent](https://arxiv.org/abs/2403.02691)는 도구 연동 에이전트가 외부 콘텐츠의 간접 지시로 위해 행동·정보 유출을 할 수 있음을 평가한다. 관련 회귀는 위험 경계를 검증하며 완전한 무취약 보증은 아니다.

## SNS·개발자 커뮤니티 조사에서 적용한 점

[Reddit의 MCP 보안 점검 논의](https://www.reddit.com/r/mcp/comments/1uk3tw2/most_mcp_servers_ive_tested_ship_with_zero/)는 Origin·권한·실행 중 정책 확인과 도구 설명의 비신뢰 처리를 강조한다. 경험담을 규격으로 취급하지 않고 보안 시험 가설로 사용했다.

[MCP 유지보수자 논의 #1624](https://github.com/modelcontextprotocol/modelcontextprotocol/issues/1624)는 클라이언트별 content/structuredContent 처리 차이를 다룬다. 기계용 결과를 별도로 확인해야 하는 이유다. [VS Code 구현 이슈 #290063](https://github.com/microsoft/vscode/issues/290063)도 같은 위험의 실제 사례로 참고했다.
