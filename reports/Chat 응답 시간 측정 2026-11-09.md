# Chat 응답 시간 측정 (2026-11-09 밤, 운영·SRE)

목표: Chat(RAG) 5초 안(CLAUDE.md 응답 시간 정책). **결과: 목표 초과. 중앙값 7.3초, p95 11.8초, 20건 중 19건이 5초 초과.**

## 1. 방법
- 서버에서 직접: `http://127.0.0.1:8400/chat`, `Host: agentconcierge.biz`, 연결 하나 재사용(순차), 처음 보는 질문 20개(영어, 분야 고르게).
- `Accept: text/event-stream`으로 단계 이벤트(`review/understand/search/cover/split/narrow/prepare`)의 서버 경과 ms를 함께 받음. 요청마다 1분 부하 기록.
- 시작 조건: 1분 부하 5 이하 1분 유지(21:17:56 시작, 부하 4.30). 스크립트는 세션 scratchpad `chat_time.py`.
- 대조: 일반 JSON `/chat` 5건(`Server-Timing: concierge;dur=`).
- 측정 대상 frontend: 측정 직전(약 21:09) 다른 세션이 `growth-frontend-20261109-r1`을 배포해 그 판을 쟀다.

## 3. 원인 가르기
| 후보 | 판정 | 근거 |
|---|---|---|
| 로컬 LLM(생성) | **아님** | 측정 3분 동안 Ollama `/api/generate`·`/api/chat` 호출 0건. Chat 경로에서 생성 모델을 쓰지 않음 |
| 임베딩(Ollama) | **부분 원인** | 측정 중 `/api/embed` 258건 중 16건이 1.6~2.5초 대기 뒤 취소(499) = 앱 예산(semantic 0.8초, strong 1.5초) 소진. 오늘 499가 30건(11-07 2건, 11-08 0건). 정상 임베딩은 중앙값 39ms, p95 265ms. 하루 임베딩 양은 11-05(25만 건)보다 오히려 적음(17만 건) → 양이 아니라 대기열·디스크 경합 때문 |
| DB·디스크 | **주 원인 추정** | `agentcon_search.embeddings`(2.3GB, 살아 있는 행 27만·죽은 행 5.7만, 누적 쓰기 584만) autovacuum이 측정 내내 벡터 인덱스 정리 중(21:23 기준 27분째). 디스크 115~120MB/s, 초당 5~7천 IO. 이 표는 오늘까지 81번 autovacuum. jobs가 임베딩·검색 문서를 계속 고쳐 써서 죽은 행이 쌓이고, 그 정리가 IO를 오래 점유한다 |
| 시스템 부하 | **악화 요인** | CPU 합계는 약 3코어인데 부하가 13~21. 실행 대기보다 IO 대기가 많음. 다른 세션의 pytest(AD Coin)·driver_agent 시험·frontend 배포가 겹친 시간대. 부하 4~5일 때도 5.2~8.0초라 부하만으로 설명 안 됨 |

정리: **Chat 로직 자체보다 운영 환경(벡터 표 autovacuum의 디스크 경합 + 임베딩 대기열) 때문에 단계마다 0.5~2초씩 늘어난 것**으로 본다. 다만 1.5초 임베딩 예산을 다 쓰고 포기하는 구조라, 경합이 있으면 요청당 최대 0.8+1.5초가 그대로 더해진다(로직 쪽 개선 여지).

## 4. 제안
운영·SRE(위임 범위 안, 다음 점검에서 진행)
1. autovacuum이 끝난 뒤 같은 질문 세트로 다시 잰다(원인 확인용 A/B). 이번 질문 20개는 이제 캐시·기록에 남았으니 새 질문 20개로.
2. `agentcon_search.embeddings` 죽은 행이 생기는 원인(jobs의 임베딩 갱신 주기, 같은 값 다시 쓰기 여부)을 조사한다. 같은 내용을 다시 쓰는 갱신이면 건너뛰게 고치는 것이 가장 싸다(jobs 코드, 검색과 RAG 팀과 협의).
3. 표 단위 autovacuum 설정(`ALTER TABLE ... SET (autovacuum_vacuum_cost_limit …)`)은 DB 재시작 없이 바뀌지만 운영 DB 설정 변경이라 **사용자 승인 대상**으로 올린다.

검색과 RAG 팀(Chat 로직, 총괄 PM 경유)
4. `strong_closeness`(1.5초)·`semantic_rank`(0.8초) 예산을 경합 때 짧게(예: 최근 임베딩 p95의 2배) 또는 둘을 한 번의 임베딩 호출로 합치기.
5. `prepare` 뒤 결과 저장·다음 단계 예측(DB 쓰기·읽기)을 응답 뒤로 미루기(답을 먼저 보내고 기록은 이어서).
6. `split→narrow` 다시 거르기 경로(4건, 11.5~12.5초)에 전체 시간 예산을 두기.
