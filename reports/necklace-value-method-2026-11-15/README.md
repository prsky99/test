# 목걸이 값 증명 측정 방법 (워크플로우, 2026-11-15)

PM 계획 3.1(`reports/necklace-promotion-orders-2026-11-15`)의 "토큰 절약·빠른 답·정확한 답"에 쓸 숫자를 어떻게 재는지 적는다. 코드는 `agent_market/necklaces/value.py`이다.

## 1. 무엇과 무엇을 비교하나

- **목걸이 길:** 에이전트가 우리 목걸이를 한 번 부른다.
- **직접 길:** 목걸이 없이 에이전트가 각 멤버 도구를 스스로 찾아 부르고, 답을 모아 정리한다.

두 길은 같은 재시험 실행에서 같은 보류 사례로 잰다. 관문 Δ(R23)의 "같은 사례·같은 날" 짝과 같은 기준이다. 그래서 날짜나 사례가 달라 생기는 차이가 없다.

## 2. 사례마다 재는 것

| 값 | 목걸이 길 | 직접 길 |
|---|---|---|
| 호출 수 | 1 | 이번 실행에서 실제로 멤버에게 나간 호출 수. 선두가 실패해 다음 멤버를 부른 것도 센다(직접 하는 에이전트도 그만큼 불러야 한다). 마감·용량·장부 때문에 나가지 않은 시도는 세지 않는다 |
| 토큰(추정) | (보낸 입력 글자 + 받은 목걸이 답 글자) ÷ 4 | 멤버 호출마다 (보낸 인자 글자 + 받은 답 글자)를 더한 뒤 ÷ 4 |
| 걸린 시간 | 목걸이 실행 시간 | 단계마다 가장 느린 칸의 시간을 더한 값. 같은 단계의 칸들은 동시에 불렀다고 본다. 한 칸 안의 재시도는 차례로 본다 |
| 정답 | 그 사례가 목걸이 채점을 통과했는가 | 통과했고, 모든 필수 칸을 선두 멤버가 답했는가. 대체가 살린 칸이 있으면 직접 길은 틀린 것으로 센다(대체 사슬이 없기 때문) |

- 글자 수는 JSON으로 바꾼 길이다(`ensure_ascii=False`).
- 4글자 = 1토큰은 영어 기준의 어림값이다. 두 길에 같은 비율을 쓰므로 비교에는 영향이 없다.

## 3. 보수적인 값과 전체 값 (PM 11-15 15:11)

두 값을 함께 낸다.

- **보수적인 값**(`direct`): 위 2절의 직접 길이다. 아래 두 비용을 뺀다. 화면의 기본 숫자로 쓴다. 빼도 목걸이가 실제보다 좋아 보이는 일은 없다. 화면 문장 끝에 "찾기와 정리 비용은 양쪽 모두 세지 않음"을 밝힌다(성장·유통).
  - 도구 찾기: find_agents 응답, 멤버 서버마다 tools/list와 스키마 읽기
  - 에이전트의 정리: 모은 답을 읽고 최종 답으로 합치기
- **전체 값**(`direct_full`): 직접 길에 위 두 비용을 넣는다. 사용자가 말한 절약의 핵심이 이 부분이다.
  - 찾기: 칸마다 find_agents 1번 + 이번 실행에서 부른 멤버 서버마다 tools/list 1번. 호출 수·토큰·시간에 더한다. 시간은 단계마다 찾기 한 번씩(같은 단계의 칸은 동시)으로 센다.
  - 정리: 실제로 받은 멤버 답 전체 + 과제 입력을 읽고 최종 답(목걸이 답 크기)을 쓰는 한 번. 토큰에 더한다. 받은 답 크기는 실측이라 추정이 아니다.
  - **추정 항목:** find_agents 응답 크기·시간(6,000자·1.5초), tools/list 크기·시간(4,000자·0.6초). `estimated` 목록에 이름이 남고, 화면에도 "finding sizes estimated"로 밝힌다. 11-16 낮에 검색과 RAG가 재는 방법으로 실측값을 넣고 목록에서 뺀다.
- **정답:** 두 값 모두 같은 채점기의 판정을 쓴다. 직접 길은 그 판정에 "모든 필수 칸을 선두가 답함"을 더한다(대체 사슬이 없기 때문). 목걸이가 더 나쁘게 나온 사례도 그대로 싣는다.

## 4. 묶어서 싣는 것

- 일일 요약(`necklaces.daily`)이 최근 7일 재시험 사례를 묶는다.
- 담는 값: 호출 수·토큰·시간의 중앙값, 정답 비율, 사례 수, 첫·마지막 사례 시각
- 판정 스냅샷(`necklaces.json`) 항목의 `value` 칸에 싣는다. **관문을 통과한 목걸이만** 싣고, 나머지는 null이다.
- 화면용으로 같은 값을 `comparison` 칸에도 싣는다(성장·유통 형식, `necklace_surface.comparison`): `{cases, measured_at, since, with, without, without_full}`, 각 쪽은 `{calls, tokens, seconds, accuracy}`이고 accuracy는 0~1 비율이다. with = 목걸이, without = 직접 길(보수적), without_full = 직접 길(전체, `estimated` 목록 포함).
- 채점하지 못한 사례(기준값을 못 받음, 우리 쪽 한도)는 세지 않는다.
- 값이 나빠지면 나빠진 그대로 실린다. 고르거나 빼지 않는다.

## 5. 첫 대상

11-17 관문의 book-author-brief와 quakes-near-address부터다. 관문 회차와 그 뒤 재시험 사례가 쌓이면 값이 나온다. 공개는 관문 통과 뒤 그 목걸이가 live가 될 때부터다.

- 장부 몫(necklace_retest)과 relay 동시 2칸 안에서 돈다. 공유 캐시는 쓰지 않는다.
- 결과

  - 일일 요약 `summary.json`의 `drill` 칸(마지막 훈련·7일 사례·통과)
