## 3. 로그인 세션 확인 방식
- 모든 워크스페이스 화면이 먼저 `GET /api/customer-auth/session`(중앙값 0.53초, 최대 0.64초)을 부릅니다. 이 응답(CSRF 토큰 포함)을 받은 뒤에야 다른 API를 시작해, 화면마다 왕복 1번(약 0.5초)이 더해집니다.
- 서버는 같은 요청에서 세션을 두 번 확인합니다(`customer_actor(request, core)` 뒤에 `invoke('session', cookie)`).
- 화면을 옮길 때마다 처음부터 다시 확인합니다. 같은 탭 안에서도 결과를 재사용하지 않습니다.
- 화면 HTML 자체는 이미 쿠키를 받은 서버가 만들지만, 세션 정보를 HTML에 담지 않습니다.

## 4. 개선 방안 (효과 큰 순)
1. **세션 정보를 HTML에 넣기**
   - 로그인 화면 응답을 만들 때 서버가 고객 요약과 CSRF 토큰을 넣고, 클라이언트는 `/session` 호출을 건너뜁니다.
   - 효과: 모든 화면에서 약 0.5초 감소. 쿠키가 없거나 만료됐으면 지금처럼 로그인 화면으로 보냅니다.
2. **직렬 호출을 병렬로**
   - 개요: organizations·invitations·상세를 동시에 부르면 2.6초 → 약 1.2초.
   - 지원: options·cases 동시 호출로 2.5초 → 약 1.6초.
   - 워크플로: templates/drafts를 첫 묶음에 넣으면 4.2초 → 약 3.2초.
3. **화면별 묶음 API(bootstrap)**: 워크플로 화면의 상세·options·credits·flows·drafts를 한 번에 돌려주면 왕복 5회가 1회로 줄어듭니다. 가장 느린 `typed/options`(2.2초)는 짧은 서버 캐시 대상입니다(카탈로그 후보는 자주 바뀌지 않음).
4. **실행 중 중복 조회 제거**: `POST runs`가 결과를 기다리는 동안에는 1초 간격 GET을 멈추거나, 2·4·8초 간격으로 늘립니다. 서버가 단계별 진행을 이벤트 스트림으로 보내면 "Waiting"만 보이는 시간도 줄어듭니다.
5. **저장 흐름 정리**: commit 응답에 저장된 flow와 잔액을 담으면 flow 재조회와 credits 2회를 없앨 수 있습니다(7회 → 3회).
6. **세션 확인 한 번만**: 서버에서 `customer_actor`의 결과를 `session` 응답에 재사용합니다.
7. **정적 자산 분리**: 워크플로 화면 HTML 328KB가 매번 내려옵니다. 공통 스크립트·스타일을 해시가 붙은 정적 파일로 빼면 두 번째 방문부터 브라우저 캐시를 씁니다.
8. **탭 안 세션 재사용**: 세션 확인 결과를 `sessionStorage`에 짧게(예: 60초) 두고, 화면은 바로 그리면서 뒤에서 다시 확인합니다. 만료되면 즉시 로그인으로 보냅니다.

### 승인이 빠진 원인(코드 근거)
- 기능 승인은 연결 버전(`cv_` = 주소, 도구 스키마, 프로필의 해시)에 붙습니다. 도구 스키마가 바뀌면 새 버전이 생기고, 승인은 따라오지 않습니다.
- 자체 에이전트 설치(`owned_data_agents/activation.install`, frontend 시작 때 실행)는 도구가 그대로일 때만 승인을 새 버전으로 옮깁니다(`usage_full_hash` 비교, 의도된 동작).
- 10-29 자체 에이전트 스키마 개정(`SCHEMA_REVISION = 'public-data-contracts-2026-10-29'`)으로 도구 스키마가 바뀌면서 승인이 빠진 것으로 보입니다. 운영 DB를 직접 확인하지는 않았습니다.
- 실행 기록은 새 버전에도 쌓여(헬스체크·Test 화면) 화면에는 "verified"로 보입니다. 그래서 승인만 빠진 상태가 드러나지 않았습니다.
