## 2. TCP+TLS 1.5초 이상 표본 18개
- **TCP는 정상(중앙값 0.15초, 한국↔LAX 왕복 약 0.13초)이고, TLS만 1.6~10.4초(중앙값 2.24초)** 걸렸다. 정상 TLS 1.3은 왕복 1번, 0.14~0.3초다.
- **이 맥의 부하 때문이 아니다**
  - 18개 중 12개는 load 1.6~2.8이었다. 정상 표본의 중앙값 2.75와 같은 수준이다.
  - 8 이상이었던 것은 11-12 21:08 relay 배포 때와 11-13 09:00 정렬 묶음 배포 때 표본뿐이다.
- **이 맥의 회선·DNS 때문도 아니다**
  - 같은 분의 LAN 응답은 0.3~0.8ms, 인터넷 응답은 2.8~3.5ms, 인터페이스 오류는 0, DNS는 0초(캐시)였다.
- **경로 쪽이다**
  - 같은 분 net-path의 독립 엣지 측정(curl)도 TLS가 1.1~4.1초로 함께 늘어난 때가 있다(11-13 13:04·14:05·15:07·21:05).
  - 11-13 13~16시에는 엣지가 SEA로 바뀐 시간대에 몰려 있다.
  - TLS 시간이 1.6·2.2·3.3초 근처에 모이는 것은 재전송 대기(1초, 2초 …)와 맞는다. 큰 서버 쪽 핸드셰이크 묶음(인증서)에서 손실이 나 다시 보낸 것으로 본다.
- 지금(04:38) 다시 재면 정상이다
  - curl 새 연결 30회: TLS 0.14~0.17초
  - user_slo와 같은 httpx 새 연결 20회: 전체 0.58~0.66초, 클라이언트 생성 5ms
  - 엣지 ping 60회: 손실 0%, 128.7ms
  - → 문제는 저녁·낮 시간대의 간헐 손실이다.

## 3. 터널 request_errors (성장·유통 질문, 02:22→02:26, 101→104)
- cloudflared 로그(`/Library/Logs/com.cloudflare.cloudflared.err.log`)의 02:24:55·02:25:58·02:26:13 오류 3건은 모두 `Incoming request ended abruptly: context canceled`다.
  - 엣지 쪽 호출자가 원서버 응답 전에 끊은 것이다.
  - 대상은 `/a2a/` 2건, `/api/workflow-connections` 1건이고, compare 페이지가 아니다.
- 최근 24시간의 터널 오류 19건도 전부 같은 종류다.
  - `/api/explore` 6, `/api/pearl/status` 5, rum·overview·a2a 각 2, 기타
  - 연결 재설정, QUIC 손실, 원서버 시간 초과 같은 전송 오류는 0건이다.
- → request_errors 증가는 터널 고장이 아니다. 그 시각 부하 9~12(02:19·02:21 배포, 사본 게이트, 밤 작업)로 원서버가 느려져 호출자가 포기한 것이다.
- compare 페이지 4.15초(REVALIDATED)는 엣지가 원서버에 다시 확인하는 동안 같은 부하를 만난 것으로 본다. 성장·유통의 max-age 21600 안이 재확인 횟수를 줄인다.

## 4. 고칠 수 있는 것과 없는 것
- **고칠 수 없음(무료 범위)**
  - 한국 → 미국 엣지(LAX·SEA) 배정은 무료 플랜의 경로라 바꿀 수 없다(Argo 등은 유료).
  - 그 경로의 간헐 손실도 우리 쪽에서 막을 수 없다.
  - 브라우저 사용자는 이미 켜 둔 HTTP/3을 쓴다. 측정은 방식을 바꾸지 않고 TCP 새 연결로 잰다.
- **이미 하는 것**
  - 매시 측정 :55~:10에는 무거운 작업과 배포를 시작하지 않는다(heavy_slot, 배포 실행기).
  - 높은 부하에서 생긴 표본은 배포 시각과 겹친 것뿐이다.
- **선택지(효과 작음, 사용자 승인 필요)**
  - 지금 인증서는 ECDSA·TLS 1.3이지만 사슬이 4개(Let's Encrypt YE1 → Root YE → ISRG Root X2 → X1 교차 서명)라 서버가 보내는 핸드셰이크가 3,743바이트(약 3패킷)다.
  - Cloudflare Universal SSL의 인증 기관을 사슬이 짧은 곳으로 바꾸면 2패킷 정도로 줄어 손실에 덜 노출된다. 무료다.
  - 다만 인증서를 다시 발급하는 설정 변경이라 PM을 통해 사용자 승인을 받아야 한다. 기대 효과도 작아 권하지 않는다(우선순위 낮음).
- **기록 보강(운영·SRE)**: 미달 원인 집계(`reports/interim-target-causes-2026-11-14`)에 "경로: TLS 재전송" 분류를 따로 두어, 서버 문제로 오인하지 않게 한다.
