# 유료 에이전트 연결·중개 사업 준비안

검토 기준일: 2026-10-21. 현재 저장소의 관련 실행 경로와 공식 결제·프로토콜·금융당국 자료를 확인했습니다. 아래 사업 모델·가격·출시 순서는 제안이며, 현재 제공 중인 유료 상품이나 완료된 결제·공급자 계약을 뜻하지 않습니다. 운영 코드·정책·계약·결제 설정은 변경하지 않았습니다.

## 1. 권장 결정

**유료 에이전트 연결은 지원하되, 첫 단계부터 이용 대금을 모두 받아 정산하는 중개사가 될 필요는 없습니다.** 먼저 고객이 보유한 제공자 계정을 연결하고 제공자에게 직접 비용을 내는 BYOC/BYOK 방식을 지원하는 것이 적합합니다. Agent Concierge는 워크플로우 구성·실행 관리·팀 협업·권한·감사 기록 등 자체 소프트웨어의 가치로 이용료를 받는 구조를 제안합니다.

다음으로 재판매·대행 실행이 허용된 소수 제휴사에 한해 관리형 상품을 검증하고, 반복 거래와 수익성이 확인된 뒤 다수 판매자 결제·정산을 포함하는 마켓플레이스로 확장합니다. 이는 제품·자금 흐름의 복잡성을 단계적으로 늘리는 전략적 판단이며, 시장 수요가 검증됐다는 의미는 아닙니다.

핵심은 **에이전트를 연결하는 역할, 인증을 위임받는 역할, 비용을 부담하는 역할, 고객에게 판매하고 환불하는 역할을 구분하는 것**입니다. 유료 연결 자체가 모든 역할을 플랫폼에 맡겨야 한다는 뜻은 아닙니다.

## 2. 현재 서비스에서 확인한 사실

- 현재 실행 정책은 관측된 가격과 별도 인증 요구를 검사합니다. `admit()`는 기본적으로 `authorize_charge=False`이며 가격이 있으면 추가 승인이 필요하다고 차단합니다. 단순히 무료 검색 결과만 보여주는 필터보다 실행 승인 경계에 가깝습니다.
- 현재 고객 DAG 스튜디오의 해당 경로는 승인된 MCP 도구·계약과 버전을 검사하고 읽기 전용·비파괴·멱등 힌트를 요구합니다. 인증 관련 필드가 있으면 실행을 허용하지 않습니다. 유료 키 입력 화면만 추가해서는 동작하지 않으며 현재 보안 경계를 새 인증·지출 정책으로 확장해야 합니다.
- 별도 A2A 연결 경로도 인증·지출 제한이 있습니다. 한 경로의 제한을 풀었다고 모든 프로토콜과 유료 제공자가 지원되는 것은 아닙니다.
- 현재 고객 크레딧은 워크플로우 저장·다운로드 권한을 위한 비금전성 크레딧입니다. 약관은 현금 가치·양도를 부인하고 결제·자동 청구·충전은 향후 별도 동의 대상으로 정합니다. 이를 조용히 현금 잔액이나 외부 제공자 결제 수단으로 전환하면 안 됩니다.
- 저장소에 TEST_UNIT 샌드박스 결제와 Base Sepolia x402 서명 검증 코드는 있습니다. 해당 모듈은 실제 자금 이동·제공자 정산·상용 결제 승인을 제공하지 않는다고 명시합니다. 다른 온체인 검증 코드의 존재 역시 고객 워크스페이스의 상용 중개 결제가 완성됐다는 증거는 아닙니다.
- 등록 정보에 가격이 없거나 0으로 보이는 것과 공급자가 계약상 무과금을 보장하는 것은 다릅니다. 인증 여부와 과금 여부를 별개로 관리하고 가격 미확인은 별도 상태로 남겨야 합니다.

## 3. 선택 가능한 사업 모델

### A. 고객 직접 결제형 — 우선 권장

고객은 제공자와 직접 계약하고 OAuth 또는 자신의 API 키로 연결합니다. 제공자 사용료는 고객의 제공자 계정에 청구됩니다. Agent Concierge는 자체 워크스페이스 이용료를 별도로 청구합니다. 따라서 제공자 이용료는 플랫폼의 매출이나 중개 거래액으로 자동 계산하지 않습니다.

장점은 유료 에이전트를 연결하면서도 제공자 이용 대금을 플랫폼이 수납·정산할 필요를 줄일 수 있다는 점입니다. 플랫폼은 여러 제공자 연결, 실행 추적, 입력·출력 정합성, 팀 권한, 예산 관리와 반복 업무의 가치를 판매합니다. 단점은 고객이 제공자별 계정을 준비해야 하고, 제공자가 사용량·잔액 API를 제공하지 않으면 비용 확인이 추정에 머무를 수 있다는 점입니다.

준비할 것은 제공자의 대행 호출 허용 범위 확인, OAuth 앱 등록·최소 권한, 안전한 자격증명 보관·철회, 워크스페이스별 연결 소유권, 이용량 표시와 비용 상한 지원 여부입니다. Google·GitHub 로그인은 해당 계정으로 서비스에 로그인하는 기능이며 다른 제공자의 유료 사용 권한이 아닙니다. MCP 인증 토큰은 대상 리소스에 맞게 검증해야 하며 로그인 토큰을 임의의 도구로 전달하는 구조는 허용되는 대체 방식이 아닙니다. [MCP 인증 명세](https://modelcontextprotocol.io/specification/2026-07-28/basic/authorization)

이 모델도 플랫폼 자체 SaaS 결제의 약관·환불·세무 및 개인정보 처리는 필요합니다. 결제를 제공자에게 맡긴다는 이유로 모든 사업 책임이 없어지지는 않습니다.

### B. 제휴 제공자 관리형 판매 — 두 번째 단계

플랫폼이 고객에게 승인된 이용 범위와 가격으로 상품을 판매하고, 제휴 제공자에게 계약한 API 이용료를 지급합니다. 고객은 플랫폼과 일관된 사용 경험을 얻습니다. 제공자가 직접 청구하는 A와 함께 제공할 수도 있습니다.

수익은 자체 이용료와 계약상 허용된 사용량 요금·번들 마진입니다. 핵심 준비는 공급자별 상업적 이용·대행 호출·재판매 권한, 도매 조건, 사용량 증빙, 가격 변경 통지, SLA, 장애·취소·환불 책임과 데이터 조건입니다. API 접근 권한만으로 별도 계약 없는 재판매가 모두 허용된다고 가정하지 않습니다.

플랫폼이 자기 이름으로 판매한다면 고객은 플랫폼에 환불과 분쟁 해결을 기대할 수 있습니다. 실제 판매 주체(MoR)는 상품 화면·약관·영수증·명세와 일치해야 하며 기술 파라미터만으로 정하는 것이 아닙니다. [Stripe의 판매 주체 판단 기준](https://docs.stripe.com/connect/merchant-of-record)

예산 초과·미수금·환불·공급자 청구 지연은 플랫폼 손익과 운전자금에 영향을 줍니다. 공급자별 계약 한도와 고객별 신용·사용 한도를 함께 정해야 합니다. 회사 API 키 하나로 불특정 고객에게 무제한 실행을 제공하는 방식은 이 모델의 출시 준비를 대신하지 못합니다.

### C. 판매자 입점·결제·정산형 마켓플레이스 — 거래 검증 후

판매자가 입점하고 고객 결제에서 제공자 정산금과 플랫폼 수수료를 나누는 모델입니다. 분배는 적합한 PSP의 연결 계정·지급대행 기능을 검토하되, 누가 판매자인지와 누가 고객에게 책임지는지를 계약으로 먼저 정합니다.

입점 심사, 사업자·실소유자 확인, 정산 계좌, 거래 원장, 수수료, 취소·환불·차지백, 정산 보류·마이너스 잔액, 세무 증빙과 해외 정산 조건이 추가됩니다. 결제대행사를 쓴다고 플랫폼의 판매·분쟁 책임이나 등록 검토가 자동으로 없어지지는 않습니다. Stripe Connect의 결제 방식에 따라 환불·차지백의 잔액 부담이 달라지고, 토스 지급대행도 셀러 등록·KYC와 계약을 요구하는 별도 서비스입니다. [Stripe 결제 구조](https://docs.stripe.com/connect/charges), [토스 지급대행](https://docs.tosspayments.com/guides/v2/payouts)

초기 수익 모델로 이 복잡성을 모두 떠안을 근거는 아직 확인하지 않았습니다. 공급자와 구매자의 반복 거래가 확인될 때 확장하는 안을 권장합니다.

## 4. 법인·계약·자금 흐름 준비

설립국과 판매 대상 국가가 아직 제공되지 않았으므로, 한국 운영 주체를 가정한 검토 항목이며 등록 필요 여부의 확정 판정은 아닙니다. 출시 시 실제 계약과 자금 흐름으로 결제사·법무·세무 검토를 마쳐야 합니다.

1. **판매 주체와 계약 관계:** 고객이 누구의 서비스를 구매하는지, 공급자와 플랫폼 중 누가 영수증을 발행하고 환불하는지, 플랫폼은 SaaS 판매자·재판매자·판매 중개자 중 어떤 역할인지 문서화합니다. 상품 화면과 실제 운영을 일치시킵니다.
2. **PG·정산 관련 검토:** 타인의 상품 대금을 받아 정산하는 구조는 전자지급결제대행 관련 검토 대상이 될 수 있습니다. 금융위는 정산에 관여하는 결제대행의 등록 문제를 안내하고 있습니다. 실제 돈의 흐름을 보여주는 구조도를 기준으로 검토해야 합니다. [금융위 PG 설명](https://www.fsc.go.kr/no010102/82523)
3. **충전금·크레딧:** 향후 고객이 돈을 충전해 여러 외부 제공자에게 쓰게 하려면 선불 지급수단 해당 여부·고객 자금 보호·환급·잔액 처리 등을 먼저 검토합니다. 현행 무상 크레딧과 유상 사용료·부채·환불 기록은 분리합니다. 명칭을 크레딧으로 바꾸는 것만으로 자금의 법적 성격이 바뀌는 것은 아닙니다.
4. **세무·회계:** 공급자 이용료, 플랫폼 매출, 수수료, 세금, 환불과 정산 채무를 분리합니다. 매출 총액·순액 인식은 계약의 본인·대리인 관계에 따라 판단해야 합니다. GMV나 고객이 제공자에게 직접 낸 금액을 모두 플랫폼 매출로 표시하지 않습니다. 해외 판매·송금의 증빙, 환율과 세금 처리도 정합니다.
5. **개인정보·공급자 계약:** 고객 입력의 처리 목적·보관·재전송·모델 학습 사용·국외 이전·삭제·침해 대응을 확인합니다. 초기는 현재의 공개 정보·읽기 전용 실행 범위를 유지하고, 기밀 데이터 처리는 별도 준비 후 확장하는 안입니다.
6. **서비스·환불 정책:** 무료 체험, 유료 이용료와 제공자 사용료, 언제 과금되는지, 부분 실패·중복 호출·다운로드 후 외부 실행의 책임을 구분합니다. 기존 크레딧이나 저장물에 과거 동의를 근거로 새 비용을 소급 부과하지 않습니다.
7. **결제사 선정:** 지원 법인 국가·판매자 국가·업종·통화·정산 방식과 AI/API 사업 허용 여부를 계약 전 확인합니다. 국내 법인에서 Stripe를 그대로 사용할 수 있다고 전제하지 않습니다. 제품 예시는 선정 완료가 아닙니다. [Stripe 지원 국가 안내](https://stripe.com/global)

## 5. x402는 무엇을 해주고, 무엇이 별도 준비인가

x402는 요청에 가격·수취인·결제 조건을 제시하고, 클라이언트의 지불 증명을 검증·정산하는 흐름을 제공합니다. 플랫폼이 x402를 지원한다고 판매 계약·환불·세금·지갑 보관 책임까지 자동으로 정해지지는 않습니다. [Coinbase 공식 x402 흐름](https://docs.cdp.coinbase.com/x402/how-it-works)

처음에는 공급자 계정 직접 결제를 우선하고, x402는 검증된 제휴사와 한도를 둔 별도 실증으로 분리하는 안을 권장합니다. 검토할 것은 지원 체인·자산·스킴, 수취인, 금액과 만료 시각, 서명 범위, 실제 정산 결과, 결제 미확정 시 재확인, 이미 지급된 금액의 환불 절차입니다. 반복 요청의 새 서명이 중복 지불을 만들지 않도록 실행과 결제 식별자를 연결해야 합니다.

고객의 키를 보관하거나 고객 대신 이전·교환 등을 제공한다면 가상자산사업자 관련 판단도 별도로 필요할 수 있습니다. 금융위의 지갑 판단 기준은 개인키의 실질적 관리·서명 권한 등을 고려합니다. 비수탁형이라고 이름 붙인 것만으로 제외된다고 단정할 수 없습니다. [금융위 신고 매뉴얼·비수탁형 지갑 기준](https://fsc.go.kr/no010101/87521)

현재 저장소의 오프라인 서명 검증이나 테스트넷 코드를 상용 지갑·결제·정산 기능으로 홍보하지 않습니다. 확인한 코드에는 실제 서비스 지급이 완성됐다는 근거가 없습니다.

## 6. 제품과 실행 정책에서 추가할 것

### 연결·과금 상태를 구분

에이전트마다 인증 방식과 과금 방식을 별개로 표시합니다. 제안 상태는 `No charge verified`, `Provider billed directly`, `Managed billing`, `Pricing not verified`입니다. 단가·과금 단위·통화·세금 포함 여부·확인 시각·상한 지원 여부를 별도로 보관합니다. 로그인 필요가 유료라는 뜻도, 가격 필드 누락이 무료라는 뜻도 아닙니다.

### 사용자 화면 여섯 곳

1. **에이전트 선택:** 연결 가능 여부, 제공자 계정 필요 여부, 누가 청구하는지와 가격 확인 상태를 진주 노드 카드에 구분해 표시합니다. 비용 확인 전에는 유료 자동 실행을 시작하지 않습니다.
2. **Provider connections:** 제공자 OAuth 또는 API 키 연결·연결 테스트·소유권·철회·만료 상태를 관리합니다. 키를 Chat이나 AI 질문 입력에 붙여 넣게 하지 않습니다. 키는 서버의 자격증명 저장소에서 워크스페이스별로 격리합니다.
3. **Budget & approvals:** 비용 부담 주체, 실행 권한자, 허용 에이전트, 1회·일·월 한도와 유효기간을 정합니다. 초기에는 소유자 승인, 반복 작업은 명시적으로 승인된 제한 범위 내 실행으로 설계합니다.
4. **실행 전 검토:** 단계별 예상 사용량, 최대 허용 비용, 전체 상한과 가격 유효기간을 제시하고 입력 전송 동의와 비용 동의를 구분합니다. 승인 범위를 넘는 가격·경로 변경은 다시 승인받습니다. 무료 연결 실패 시 유료 대체를 몰래 선택하지 않습니다.
5. **실행 결과:** 작업 성공·실패·미확정과 과금 확정·미확정·환불 진행을 각각 표시합니다. 후속 단계 실패가 앞 단계의 이미 발생한 제공자 비용을 자동 취소한다는 약속을 하지 않습니다.
6. **이용 내역·정산:** 제공자 사용량, 플랫폼 이용료, 실제 청구와 환불을 워크스페이스/관리 화면에서 확인합니다. 기존 프로젝트 지침에 따라 공개 Chat의 답변·상세에 가격·결제·업셀을 끼워 넣지 않습니다.

### 백엔드의 최소 경계

- 소유자·실행자·비용 부담자·판매자·수취인을 구분하고 워크스페이스 단위로 검증합니다.
- 연결 승인만으로 지출을 허용하지 않습니다. 호출 전에 자격증명·도구 버전·제공자·가격·금액·유효기간·예산을 확인합니다. 단순히 기존 `authorize_charge` 플래그를 켜는 것으로 끝내지 않습니다.
- 동시에 여러 실행을 해도 같은 예산을 중복으로 쓰지 않도록 한도를 원자적으로 예약합니다. 이 내부 예산 예약은 외부 결제 승인이 아닙니다. 공급자가 하드 상한을 제공하지 않으면 통제 가능한 수량을 제한하거나 자동 실행 대상에서 제외합니다.
- 실행과 청구를 서로 다른 상태 기계로 두고 고유 요청·영수증 참조를 연결합니다. 결과 미확정은 새 유료 호출을 무작정 재시도하는 대신 공급자 상태와 사용량을 대조합니다. 외부 API까지 포함한 무조건적인 정확히 한 번 실행을 약속하지 않습니다.
- 공급자 청구, 플랫폼 청구, 지급·환불·정산 채무와 비금전성 크레딧을 분리합니다. 정산 잔액을 관리한다면 변경 불가능한 거래 이력과 대사를 준비합니다. 웹훅·재전송·복원·중복 수신도 검증합니다.
- 월간 반복 작업·다운로드 앱·공개 배포에는 별도의 제한된 지출 권한이 필요합니다. ZIP·HTML·브라우저 저장소에 제공자 비밀 키를 넣지 않습니다. 고객 자신의 연결 또는 소유자가 승인한 앱별 예산을 서버 경유로 사용합니다. 플랫폼 키와 예산을 불특정 방문자에게 무제한 공개하지 않습니다.

## 7. 수익성: 수수료율보다 건당 공헌이익 확인

수익성은 플랫폼 매출에서 공급자 비용, 결제비, 실행 인프라·관측비, 환불·분쟁·지원 등 변동비를 뺀 값으로 봅니다. 아래는 실제 업체 요율이나 권장 판매가가 아닌 **가상의 계산 예시**입니다.

가정: 고객 판매가 호출당 $0.12, 제공자 비용 $0.10, 플랫폼 처리비 $0.005, 고객 결제 수수료는 결제 한 건당 3%+$0.30. 세금·환율·환불·인건비·추가 온체인 비용은 미반영입니다.

- 1회 호출을 한 번 결제하면 매출 $0.12에서 제공자 $0.10, 처리비 $0.005, 결제비 $0.3036을 빼 공헌이익은 **-$0.2886**입니다.
- 100회 사용을 한 번 청구하면 매출 $12, 제공자 $10, 처리비 $0.50, 결제비 $0.66으로 공헌이익은 **$0.84, 매출 대비 7%**입니다.
- 제공자 원가에 20%를 더한 것과 20% 공헌이익을 확보한 것은 다릅니다. 더 적은 정산 건수는 고정 결제비가 있는 계약에서만 해당 이점을 주며, 후불의 미수금이나 선불의 자금 규제 문제도 따로 검토해야 합니다.

초기 권장은 플랫폼 자체 SaaS 이용료를 명확하게 받고, 제공자 비용은 직접 결제하거나 계약한 범위에서 투명하게 별도 처리하는 것입니다. 무제한 실행 요금제나 검증되지 않은 수수료율을 먼저 약속하지 않습니다.

## 8. 실행 순서와 출시 기준

### 첫 단계 — 사업·상품 원칙 확정

법인·판매국, 목표 고객, 플랫폼의 역할, 비용 부담자, 자체 SaaS 요금 단위와 무료 체험 범위를 정합니다. 후보 제공자 1~3곳과 공개 정보용 읽기 전용 업무를 제안 대상으로 좁히고, 상업적 대행 호출 조건·비용 상한·청구 증빙을 확인합니다. 이는 제안 숫자이며 제휴가 체결됐다는 뜻은 아닙니다.

### 두 번째 단계 — 직접 연결형 유료 실증

Provider connections, 테넌트별 자격증명, 지출 승인·예산, 정확한 실행·비용 기록과 단순 SaaS 결제를 준비합니다. 외부 고객의 첫 유료 워크플로우가 반복 사용되는지 검증합니다. 출시 기준은 승인 없는 지출 차단, 키 미노출, 중복·실패·철회 대응, 실제 제공자 청구와 이용 기록 대조입니다.

### 세 번째 단계 — 제한된 관리형 판매

재판매·대행 계약이 있는 제공자와만 실제 자금이 오가는 작은 범위의 거래를 검증합니다. 거래별 공헌이익, 환불과 공급자 장애 처리, 판매 주체·세무, 지급 시점 차이에 따른 운전자금이 준비돼야 합니다.

### 마지막 단계 — 마켓플레이스 확장

반복 구매와 공급자의 정산 참여 수요가 확인된 후 입점 심사·PSP 계약·법적 역할·원장·환불·정산을 확장합니다. x402도 이와 별개로 지원 스킴·체인과 책임 범위를 정한 뒤 활성화합니다. 기술 지원 프로토콜 수보다 안전하게 반복 완료되는 업무와 남는 공헌이익을 기준으로 확장합니다.

## 9. 투자자에게 설명할 사업 정체성

제안하는 방향은 **“무료·유료 에이전트를 목적에 맞게 연결하고, 실행 권한·예산·결과 근거를 관리하는 워크플로우 플랫폼”**입니다. 진주 하나의 가격보다, 서로 다른 제공자를 연결해 반복 가능한 결과와 비용 통제를 제공하는 가치가 핵심입니다.

수익은 초기 SaaS 반복 매출, 이후 제휴 사용량 마진·거래 수수료 순서로 검증합니다. 추적할 지표는 실제 외부 유료 활성 워크스페이스, 반복 업무 완료, 실제 청구를 반영한 공헌이익, 재사용·해지, 오류·환불률입니다. 카탈로그 수나 중개 GMV를 매출·수익성 검증으로 대체하지 않습니다. 견적·협의 중인 제휴와 운영 중인 상품도 구분해서 제안서에 표시해야 합니다.

## 검토 범위와 남은 확인

공식 자료는 결제 구조·인증·x402 및 한국 관련 준비 항목을 확인하기 위한 것입니다. 특정 제공자의 재판매 허용, PSP 가입·국가 지원, 법적 등록 여부, 실제 수수료·세금과 사업 수익성은 해당 계약과 법인·거래 구조가 정해져야 확정할 수 있습니다. 이번에는 코드 변경, 공급자 계정 연결, 계약 체결, 결제·송금·지갑 발급, 서버 재시작을 하지 않았습니다.
