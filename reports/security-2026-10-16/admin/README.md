# 백엔드·어드민 보안 점검

2026-10-16 KST · A2A_Discovery · 로컬 소스 수정 및 격리 동적 검증

최종 전체 테스트 결과: **703개 통과**, 실패·오류·건너뜀 0개. 기존 GET/HEAD 중복 OpenAPI Operation ID 경고 1건. 최종 실행 178.54초. 운영 배포는 수행하지 않았다.

## 범위와 방법

Python 애플리케이션 전체 58개 파일, 관리자 HTML, 인증·세션·권한·DB·결제·수집기·공유 HTTP·TLS·배포 설정을 확인했다. Bandit 정적 분석과 설치 패키지 53개에 대한 pip-audit를 실행했다. 외부 서비스·온체인 결제는 모의 객체로 대체하고, 임시 SQLite DB에 실제 FastAPI 요청을 보내 상태 변화를 검증했다. Chromium은 응답 CSP를 그대로 적용했다.

게이트웨이 관리자 API 95개 작업 중 공개 로그인 외 94개에 대해 인증 누락 시 차단을 검증했다. 관리자 UI 18개 메뉴와 Markdown·워크플로우 속성 주입, CSP 실행 차단, 고정 콜백 버튼, 내보낸 HTML의 script 종료 공격을 브라우저에서 확인했다. 별도 수집기 관리 API 2개와 브로커·판매자 관리 통계 API도 잘못된 토큰 및 비 ASCII 헤더로 점검했다.

## 수정 결과

분류한 조치 항목 15개와 소스 위치는 `findings.json` 및 함께 제공한 Canvas에 있다. 영향도는 수동 우선순위이며 공식 CVSS 점수가 아니다.

- 권한: 계정의 현재 역할을 사용하고, 역할·활성화·비밀번호 변경 시 해당 사용자의 세션을 폐기한다. operator는 조회를 담당하고 결제·보안·TLS·인증키·운영 작업은 superadmin으로 제한한다. 로컬 무인증 상태에서 변경 작업을 금지한다.
- 인증: 새 비밀번호는 15~128자, 새 해시는 PBKDF2-SHA256 600,000회다. 기존 해시는 성공 로그인 시 갱신한다. 신규 세션은 8시간, 사용자당 최대 10개이며 DB에는 토큰 해시를 저장한다. 기존 세션의 전환은 파일 DB 쓰기 트랜잭션으로 처리한다.
- 추측 공격·감사: 로그인은 IP당 10회/분, 전역 60회/분, 비밀번호 변경 시도는 사용자당 5회/분으로 제한한다. 로그인·비밀번호 실패 감사 기록의 롤백 문제를 수정했다. 보안·인증키·인증서 변경도 감사 기록에 남긴다.
- XSS·CSP: Markdown 입력을 이스케이프하고 동적 속성·좌표를 검증한다. 관리자 HTML은 응답마다 새 nonce를 사용하며 `script-src-attr 'none'`, `base-uri 'none'`를 적용한다. 인라인 이벤트 46개를 정해진 콜백 42개로 바꿨고 외부 QR 서비스로 공유 주소를 보내는 폴백을 제거했다. 인라인 CSS는 기존 UI 호환을 위해 유지한다.
- 외부 호출: 관리자 실시간 테스트는 TLS 검증, 최종 카드 URL 검사, 공인 IP 고정, 환경 프록시·리다이렉트 차단, 응답 1 MiB 및 HTTP 요청당 25초 제한을 적용한다. 등록 사전 검사는 동일한 제한을 사용하는 작업 스레드에서 실행하고 클라이언트를 닫는다. 공유 HTTP 클라이언트도 검증 실패 시 차단한다.
- 입력·자원: 관리자 본문 256 KiB, 본문 수신 10초, 비동기 작업 전체 35초, 동시 요청 32개, 쿼리 8 KiB, 그래프 노드 100개·간선 500개로 제한한다. JSON 객체·유한 수·역할·금액·주요 필드 자료형을 확인한다.
- 결제: API와 저장소에서 bool·소수·문자열 금액을 거부하고 누적 정수 오버플로를 막는다. 출금은 명시적인 비영(非零) 20바이트 주소를 요구한다. 환불 재실행 거부와 동시 출금 시 잔액 보존을 검증했다. 이 저장소의 해당 출금 경로는 가상 원장 처리이며 실제 온체인 송금 검증을 의미하지 않는다.
- 파일·TLS: DB·WAL·SHM을 0600으로 제한하고 로컬 실행 파일 12개의 권한도 수정했다. 실행 인증서·개인키·DB·저널을 Git 제외 목록에 추가했다. 개발용 자체서명 인증서의 운영 갱신과 사용자 홈 복사를 막고 OpenSSL 시간·입력 제한을 추가했다.
- 기타: 변경 감지용 SHA-1 4곳을 SHA-256으로 바꾸고 SQLite 확장 로드 실패 시에도 권한을 복구한다.

## 결과 해석

Bandit의 High 경고는 0개다. Medium 원시 경고 77개는 제거하거나 숨기지 않았다. 75개는 상수·허용 목록으로 구성한 SQL 구조에 값을 바인딩하는 경로이며, 2개는 와일드카드 주소를 비교하는 문자열이다. Low 75개는 선택적 실패 처리·스케줄 난수·개발 기본값·OpenSSL 호출 등을 검토했다. 개별 위치와 판단 근거는 `bandit-triage.json`에 있다. 경고 수와 실제 취약점 수는 같지 않다.

패키지 53개에서 점검 시점에 알려진 취약점은 발견되지 않았다. 미래 취약점이나 모든 버전의 안전을 보장하는 결과는 아니다. SQL 주입 공격 문자열은 필터·정렬·로그인 경로로 보내 테이블과 인증 경계가 유지되는지 확인했다.

## 운영 상태와 남은 조치

로컬 DB 4개를 읽기 전용으로 조사했다. 활성 기본 관리자 계정 3개, 유효한 기존 평문 형식 세션 4개가 남아 있다. 계정·비밀번호·세션 값은 보고서에 기록하지 않았고, 이 점검에서 계정이나 세션을 일괄 변경하지 않았다. 새 코드를 배포한 뒤 기본 비밀번호 변경 및 기존 세션 폐기를 진행해야 한다. 운영 시작 방어는 기본 계정 상태에서 시작을 거부한다. 시스템 `ADMIN_TOKEN`은 사용자 세션과 별개이므로 환경 설정에서 독립적으로 회전해야 한다. 기존 세션이 인증되면 해시로 바뀌지만 과거 발급 만료 시간까지 일괄 단축하지는 않는다.

플랫폼 인증키 테이블의 비어 있지 않은 값은 현재 0건이다. 테이블 자체는 평문 저장 구조다. 향후 키를 저장할 때에는 OS·디스크 암호화 또는 별도 비밀 관리자를 적용해야 한다. DB 0600과 관리자 접근 제한은 DB 파일 유출에 대한 암호화를 대신하지 않는다.

초기 인증서 재현 검사 및 기존 테스트 fixture에서 로컬 개발용 `deploy/ssl` 인증서·키·메타데이터가 재생성되었다. 원래 인증서로 복구된 상태는 아니다. 이후 fixture를 임시 디렉터리와 모의 객체로 고쳐 실제 경로에 쓰지 않도록 격리했다. 외부 운영 TLS 인증서에는 요청하거나 변경하지 않았다.

이 결과는 소스와 로컬 실행에 대한 평가다. 운영 서버 대상 공격성 DAST·부하 검사, 외부 수집 대상 전체의 악성 응답 시험, 실시간 블록체인 결제, 고객 알림 전달은 검증하지 않았다. 운영 배포와 재시작도 수행하지 않았다. 백그라운드 수집기는 공유 연결 정책을 적용하지만 모든 외부 서비스의 시간·응답 크기 특성을 통합 시험한 것은 아니다.

## 증거와 재실행

- `full-suite.xml`, `full-suite.txt`: 최종 전체 회귀 검증.
- `browser.xml`: 관리자 메뉴 18개 및 공격·내보내기 브라우저 검증. 최종 전체 결과에는 고정 콜백의 실제 설정 변경 확인도 포함한다.
- `route-inventory.json`: 관리 API와 권한 정책.
- `findings.json`: 조치 항목과 소스.
- `bandit.json`, `bandit-triage.json`: 정적 분석 원본과 분류.
- `pip-audit.json`: 설치 환경 패키지 점검.
- `operational-inventory.json`: 민감값을 제외한 기존 계정·세션·파일 권한 수량.

원시 초기 재현 파일은 실패 상태 추적을 위해 남겨 두었다. `before.xml`에는 초기 fixture 정리 코드 오류도 있으며, 최종 통과 근거로 사용하지 않는다. 기존 CSP를 기대하던 검증식과 HTTPX 속성 검증을 실제 강화 정책에 맞게 수정했다.

재실행 명령:

```sh
.venv/bin/pytest -q --tb=short --junitxml=reports/security-2026-10-16/admin/full-suite.xml

/tmp/a2a-security-tools/bin/pip-audit --path .venv/lib/python3.11/site-packages --format=json --output reports/security-2026-10-16/admin/pip-audit.json
```

정책 근거: [OWASP Authentication](https://cheatsheetseries.owasp.org/cheatsheets/Authentication_Cheat_Sheet.html), [Password Storage](https://cheatsheetseries.owasp.org/cheatsheets/Password_Storage_Cheat_Sheet.html), [CSP](https://cheatsheetseries.owasp.org/cheatsheets/Content_Security_Policy_Cheat_Sheet.html). CSP는 이스케이프 처리를 보완하는 방어이며 이를 대체하지 않는다.
