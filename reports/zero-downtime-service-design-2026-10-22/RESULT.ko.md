# 독립 서비스 및 A/B 배포 적용 결과

2026-10-22, 권장 작업 1–8의 구현·격리 검증·운영 전환을 완료했다. 현재 프론트앤드와 어드민은 각각 독립 배포되며, 웹 교체가 수집·헬스·평가 작업과 사용자 실행 worker의 재시작을 유발하지 않는다.

## 적용한 구성

- Caddy: 기존 공개 진입 포트 8400과 어드민 진입 포트 8200을 유지한다. Cloudflare 원격 설정은 변경하지 않았다. 최초 설계의 별도 9000/9001 제안 대신 기존 origin 주소를 유지하는 방식으로 적용했다.
- 프론트앤드: 8401/8402 두 슬롯. 어드민: 8201/8202 두 슬롯. 새 후보가 DB·준비 상태·화면·자산·인증 경계 검사를 통과한 후 해당 역할만 전환한다.
- jobs: 수집·헬스·평가 관련 기존 작업과 유지 관리 작업을 웹과 독립 운영한다. 개별 작업 종류는 이 서비스 내부의 기존 스케줄러/스레드를 사용한다.
- execution: 접수된 워크플로우 및 워크스페이스 typed/private 실행을 별도 처리한다.
- PostgreSQL 18.6 + 기존 pgvector 데이터, Redis와 서명 키를 공유한다. 운영 DB를 재적재하거나 보고서를 삭제하지 않았다.
- 새 명령 테이블은 서명·중복 접수 방지·트랜잭션 선점·소유자 확인을 적용한다. 외부 실행 결과가 불확실한 작업은 자동 재실행하지 않는다.
- 소스와 가상환경을 배포본으로 보존한다. 현재 웹은 r2, 이전 웹과 worker는 r1이다. 두 배포본의 서비스 실행 코드는 같고 r2에는 브라우저 방식의 배포 점검 수정이 포함된다.

## 단계별 완료 근거

1. **백업·복구 준비:** DB 1.37 GB와 소스 462 MB, 비공개 설정 백업 및 SHA256 확인. 별도 PostgreSQL 18에서 실제 복원 성공. 복원된 DB의 쓰기 격리 보호도 유지했다.
2. **작업 소유권·중복 방지:** 전용 스키마, 서명된 명령, 단일 소유권과 미확정 실행 처리 구현·시험.
3. **자동 작업 분리:** jobs/execution 독립 프로세스 가동. 웹 배포 중 두 PID 유지 확인.
4. **프론트앤드·어드민 분리:** 각각 A/B 실행 및 단독 전환 완료.
5. **실행·공유 상태:** 영속 접수와 worker 처리 적용. 격리 환경에서 실행·인증·세션 연속성 검사.
6. **배포·복귀:** 새 슬롯 준비, Caddy 전환, 이전 슬롯 보존, 개별 rollback, 중단된 전환 기록 복구 기능 적용.
7. **회귀·보안·장애 시험:** 보안/브라우저/API 183개 통과, 마지막 영향 범위 82개 통과, 콘텐츠 245파일 위반 0개. 각 시험군은 중복되므로 합산하지 않는다.
8. **운영 이행:** 실제 프론트앤드 교체 → 어드민 교체 → 프론트앤드 이전 버전 복귀 → 최신 버전 재전환 완료.

## 실제 측정

운영 A/B 및 복귀 중 요청은 총 **195건, 실패 0건**이었다. 로컬 프론트앤드 67건, 어드민 95건, 외부 공개 도메인 33건을 확인했다. 각 변경에서 다른 웹 서비스와 jobs/execution 프로세스가 유지됐다. 별도 격리 시험에서도 Caddy 80건, 전체 분리 프로세스 20건이 모두 성공했고, 느린 기존 요청 완료와 어드민 세션 유지가 확인됐다.

최초 단일 서버에서 Caddy로 포트를 넘기는 전환은 **약 47.6초의 공개 origin 연결 공백**이 있었다. 따라서 최초 전환까지 무중단이었다고 볼 수 없다. 이 최초 측정에서는 과도한 점검 빈도로 기존 rate limit에 걸린 429 응답 108건도 있었으며, 연결 공백과 구분해 기록했다. 이후 점검 도구의 호출 간격을 낮췄다. 신규 A/B 교체의 실패 0건은 별도 실측 결과다.

최종 공개 홈·탐색·테스트·워크플로우·채팅·로그인 페이지가 200으로 응답했다. 미로그인 워크스페이스는 실제 로그인 주소로 303 이동했다. 공개 `/admin`과 `/internal`은 404, 인증 없는 어드민 API는 403이다. 최초 점검에서 잘못 추정한 두 URL은 기록에 별도로 표시하고 실제 메뉴/리다이렉트 주소로 재확인했다.

전환 후 데이터는 에이전트 리소스 136,799건, 테스트 보고서 928건이다. 백업 시점 대비 리소스는 117건 증가했고 보고서·기존 실행 기록 건수는 유지됐다. 자동 수집 스레드 8개와 두 worker heartbeat가 정상이다.

서비스 프로세스 RSS 합계는 이전 슬롯 두 개를 포함해 약 **933 MiB**, DB 연결 18개, 확인 순간 잠금 대기 0개였다. RSS는 공유 페이지 중복이 포함될 수 있고 PostgreSQL/Redis 전체 메모리를 뜻하지 않는다. 실사용 최대 부하 성능을 보장하는 부하 시험 수치는 아니다.

## 앞으로 사용할 명령

프로젝트 터미널에서 다음 명령을 사용한다.

```bash
./agentcon restart frontend
./agentcon restart admin
./agentcon restart
./agentcon rollback frontend
./agentcon rollback admin
./agentcon status
```

인자 없는 `restart`는 프론트앤드와 어드민만 순서대로 A/B 교체한다. 수집/실행 worker는 유지된다. 현재 반영은 완료되어 사용자가 다시 재시작할 필요가 없다.

작업 서비스 수정은 별도 배포본을 만들어 `worker-deploy jobs` 또는 `worker-deploy execution`으로 반영한다. `./agentcon stop`은 모든 서비스가 중단되는 명령이다. 자세한 운영·복구 절차는 [운영 안내](../../deploy/NATIVE_SERVICES.ko.md)에 있다.

## 보장 범위와 후속 운영 조건

이 구성은 **애플리케이션 배포 시 중단을 줄이는 단일 호스트 A/B 구성**이다. Mac 절전·로그아웃·전원·네트워크·DB 장애까지 무중단으로 보장하지 않는다. 현재 LaunchAgent는 사용자 로그인 환경을 사용한다.

구버전과 신버전이 함께 실행되는 동안 API·정적 자산·DB 스키마·작업 계약의 호환성을 유지해야 한다. 정적 자산 해시 파이프라인과 자동 DB 스키마 확장/축소 도구를 추가한 것은 아니다. 기존 DB 무결성을 위한 전역 쓰기 잠금도 보존했다.

이번 운영 검증에서 실제 유료 외부 실행이나 Google/GitHub 계정 로그인은 추가 수행하지 않았다. 해당 실행·세션 보안 검증은 격리 데이터로 수행했다. 장시간 스트리밍, 최대 부하, 실제 외부 제공자의 장애까지 전부 보장하는 결과는 아니다.

## 증적 파일

- `live-deployment-verification.json`: 실제 교체/복귀 명령별 결과, 전후 PID, 195개 요청 기록.
- `initial-transition-summary.json`, `initial-transition.json`: 최초 전환 공백 및 rate limit을 구분한 측정.
- `process-rehearsal.json`: 격리 PostgreSQL 18 분리 프로세스 시험.
- `restore-rehearsal.json`: 백업 실제 복원 시험.
- `final-http-checks.json`, `live-resources.json`: 최종 페이지·경계·데이터·자원 확인.
- 비공개 원본 백업과 배포본은 `gateway-data`에 보존한다. 인증 정보와 DB 덤프는 이 보고서에 포함하지 않는다.
