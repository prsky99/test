# P1 ① ann 호출 줄이기: registry 구간과 ann 구간 분해 (2026-11-13 20시, 검색과 RAG)

PM 11-13 20:2x 지시 ①. 이 문서의 수치는 모두 **내부 수치**다.
- 측정 방법: 운영 PG에 읽기 전용 세션(`default_transaction_read_only`) 하나로 붙어, 운영과 같은 코드(공유 브랜치)의 `FastConcierge.lookup`을 이 맥에서 직접 돌렸다.
- 공개 주소·새 연결 측정이 아니므로 목표 달성의 근거로 쓰지 않는다. 질의는 모두 처음 보는 질의(뒤에 난수)다.
- 원자료는 scratchpad(`registry_live.py`, `gc_probe.py`, `ann_parts.py`, `ann_calls.py`)에 있다.

## 1. registry 1,538ms (20:04 user_slo, 추천 'image generation api 798')
- 같은 모양의 질의를 다시 돌렸다(`image generation api 4417`). `Registry.current` 21회와 `projection` 19회를 합쳐 **68ms**였다(후보마다 1~4ms, 20ms 넘는 후보 없음).
- 그때 Server-Timing의 `cpu`(요청 스레드 CPU 시간)는 2,000ms였다. 그래서 1.5초는 SQL을 기다린 시간이 아니라 그 스레드가 CPU를 쓴 시간이다.
  - 후보별 계산(version_parts, tools_for, safe_registered_tool, admit)은 후보 17개를 합쳐 0.1초 미만이다.
  - 계약 승인 표(`capability_approvals`)는 운영 전체에 12행뿐이다.
- 가설: 운영 frontend 프로세스(RSS 약 450MB) 안에서 전체 GC가 하필 이 구간에 돌았을 수 있다. 이 맥의 작은 프로세스(객체 9만 개)에서는 전체 GC가 10~14ms라 운영 규모의 값은 직접 잴 수 없다.
- 조치: `0bb26ac9`에서 Server-Timing에 두 구간을 더했다. user_slo는 이 둘을 상위 8개에 들지 않아도 남긴다.
  - `gc`: 요청 스레드가 직접 돈 GC 시간
  - `gc_all`: 그 요청 동안 프로세스 전체의 GC 시간. GC 중에는 인터프리터 잠금이 모든 스레드를 멈춘다.
  - 정책 해시 파일이 아니라 frontend만 배포하면 된다. 다음 frontend 배포에 들어가며, 그 뒤 user_slo로 가설을 판정한다.

- 시간은 큰 그래프를 처음 읽을 때 디스크와 캐시에서 들어온다.

## 3. 결론과 다음 단계
- 코드만으로 ann을 크게 줄일 길은 없다. 지렛대는 그래프 크기다.
- 11-13 03:1x에 채택한 K=1000 부분 색인 안(`in_kind_graph`)에 x402를 같은 규칙으로 넣는 것을 제안한다. 규칙: 한 호스트가 한 종류에서 그래프에 넣는 행은 상위 1000개.
  - a2a 그래프: 약 7천 행. 사본 실측은 409MB → 12.4MB, a2a ANN p50 24 → 5.6ms, 재현율@10 0.843 → 0.97.
  - x402 그래프: datapackvibe 82,201개가 1000개로 줄어 약 4만 7천 행이 된다(추정 약 90MB).
- 이 안은 DB 구조 변경(열 1개, 색인 2개)이다. 그래서 다음 순서를 거친다.
  1. 사본 리허설: db_change_rehearsal로 운영 버전 네 역할의 연결을 확인한다.
  2. 복구 SQL을 준비한다.
  3. 사용자 승인을 받는다.
  4. 실행 직전 check가 0인지 확인한다.
- 전후 수치는 공개 주소·새 질의·새 연결로 user_slo와 별도 30회 측정에서 잰다.
