## 1. 지켜야 할 규칙 (CLAUDE.md "수익과 지출은 코인으로만", 헌장 1절)

| 규칙 | 이 설계에서 |
|---|---|
| USDC on Base만, 법정화폐 없음 | 호출 1건 = 결제 1건, USDC on Base |
| 서버는 받기만, 개인키는 서버에 없음 | 받는 주소만 설정. 기존 `payments.PaymentVerifier`가 체인에서 입금을 확인한다 |
| 선충전·잔액·보관·환전·송금 대행 없음 | 잔액 계정을 두지 않는다. 결제 한 건은 그 요청 한 건에만 쓴다 |
| 환불은 사용자가 직접 | 자동 환불은 없다. 아래 4절 "같은 입력 다시 받기"로 실패 부담을 줄인다 |
| 제재 주소 대조, 원화 환산·거래 해시 기록, 월별 내보내기 | AD Coin v2 유료 예약(`ad_coin/v2/paid_audit.py`)과 같은 기록 방식을 쓴다 |
| AD Coin은 무상 크레딧이고 USDC 장부와 섞지 않음 | AD Coin으로 실행권을 사거나 바꾸는 경로는 만들지 않는다(5절) |

## 2. 무료 한도

- 공개 첫 단계는 모두 무료다. 과금은 사용자가 켤 때부터 시작한다.
- 켠 뒤에는 클라이언트(실행 기록의 출처 주소·주체)마다 하루 N회를 무료로 둔다. 시작값 제안은 20회다.
  - 지금 `limits.RunLimiter`(분당 6회)와는 별개로, 하루 단위 계수를 따로 둔다.
- 다음은 무료 한도에서 빼지 않는다.
  - 짧은 캐시로 준 답(멤버를 부르지 않았으므로)
  - 우리 쪽 용량 초과(`our_capacity`)
  - 실행 전에 거절된 요청(동의 없음, 입력 오류, 범위 밖, 속도 제한)
- 우리 시험(X-Agentcon-QA, 재시험, 관문)은 과금하지 않는다.

## 3. 402 흐름 (x402 형식)

1. **한도 안:** 지금처럼 실행한다.
2. **한도를 넘으면** HTTP 402와 x402 결제 요구를 돌려준다. 멤버는 부르지 않는다.
   - 결제 요구 항목: `accepts: [{scheme: "exact", network: "base", asset: USDC 주소, payTo: 받는 주소, maxAmountRequired: 가격, resource: /api/necklaces/<slug>/run 또는 MCP 도구 이름, description}]`
   - MCP·A2A에는 같은 내용을 도구 오류 본문(`error_code: payment_required`)으로 보낸다.
3. **클라이언트가 받는 주소로 USDC를 직접 보낸 뒤** 같은 요청을 다시 보낸다.
   - 헤더: `X-Payment-Tx`(거래 해시), `X-Payment-Signature`(요청 본문에 대한 송금 지갑의 서명)
4. **서버 확인** (`PaymentVerifier.verify(tx, sig, body, price)`)
   - 받는 주소로 들어온 USDC인지, 가격 이상인지, 확인 블록 수
   - 서명이 송금 지갑의 것인지(남의 거래 해시를 가로채 쓰는 것을 막음)
   - 제재 주소 대조
   - 거래 해시가 처음 쓰인 것인지
5. 통과하면 실행하고, 기록에 거래 해시·금액·원화 환산·목걸이·버전·결과를 남긴다(입력·답 본문은 남기지 않음).

## 4. 실패와 재시도 (보관 없이 부담 줄이기)

- 결제는 "그 입력으로 한 번 실행"의 값이다. 같은 거래 해시는 실행 기록이 성공으로 끝나면 다시 쓸 수 없다.
- 결제한 실행이 완주하지 못하면(`slot_failed`, `our_capacity`) 같은 거래 해시와 같은 입력으로 10분 안에 한 번 더 실행할 수 있다.
  - 서명이 요청 본문에 묶여 있어서 다른 입력에는 쓸 수 없다.
  - 잔액이나 크레딧을 만들지 않으므로 보관이 아니다.
- 그래도 완주하지 못하면 기록에 `refund_candidate`를 남긴다. 환불 송금은 사용자가 직접 한다.

## 5. AI AD Coin과의 관계

- **광고는 결제한 실행에도 그대로 나간다**(11-15 사용자 결정: 광고 항상 노출). 광고를 빼는 것은 별도 구독(매출 조사 2번)이다.
- AD Coin을 실행권으로 바꾸거나, 실행값을 AD Coin으로 받는 경로는 두지 않는다.
  - AD Coin은 무상 내부 크레딧이고, USDC 장부와 섞지 않는다는 규칙 때문이다.
  - 필요하면 나중에 "광고주에게 주는 무료 실행 한도 추가"처럼 무상 혜택으로만 다룬다(사용자 결정).

## 6. 저장소와 배포

- 결제 기록은 운영 PostgreSQL의 별도 스키마 표가 필요하다. 예: `necklace_payments`(거래 해시 유일, 금액, 원화, 목걸이, 버전, 결과, 시각).
  - **DB 구조 변경이므로** 리허설 → 복구 SQL → 사용자 승인 → check 0 순서를 따른다.
  - public 스키마 트리거 규칙(5개)을 건드리지 않게 자기 스키마에 둔다.
- 받는 주소, 가격, 하루 무료 한도는 코드 기본값으로 두고 켜는 스위치는 끈 상태로 시작한다.
  - `agentcon.env`는 허용 키만 받는다.
- 북극성: 결제한 실행도 외부 성공으로 같이 센다(`necklaces.north_star`). 매출은 별도 지표로 둔다.

## 7. 가격 (사용자 결정)

| 근거 | 값 |
|---|---|
| 매출 조사 시장 예 (x402·Cloudflare) | 호출당 $0.001~$0.01 |

- 지금 규모로는 하루 1 USDC 안팎이라 금액보다 구조를 갖추는 것이 목적이다(매출 조사 판단).

## 8. 구현 순서 (켜기는 사용자 결정 뒤)

1. 하루 무료 한도 계수(클라이언트별, 프로세스 공유 필요): `limits`에 하루 창을 더한다. 공유 계수는 Redis나 DB를 쓴다.
2. 402 응답 생성(Web·MCP·A2A 세 표면)과 결제 헤더 읽기를 `service.run_for_surface` 입구에 둔다.
3. `PaymentVerifier` 연결: 받는 주소·가격·확인 블록 수, 거래 해시 단일 사용, 서명 검증, 제재 대조.
4. 결제 기록 표(DB 변경 절차), 원화 환산, 월별 내보내기(`paid_audit` 방식).
5. 실패 재시도(같은 해시·같은 입력·10분·성공 1회)와 `refund_candidate` 표시.
6. 시험:
   - 가짜 체인으로 정상 결제, 금액 부족, 확인 부족, 남의 거래 해시, 같은 해시 재사용, 제재 주소
   - 결제했는데 실패한 뒤의 재시도
   - 402에서 멤버 호출 0
   - QA·캐시·용량 초과는 과금 안 함
7. 사본에서 운영 연결까지 확인한다. 실제 결제 시험은 사용자 승인 뒤 소액으로 한다.

## 9. 위험

- 확인 블록 대기로 응답이 늦어질 수 있다. Base는 블록이 짧지만 5초 응답 목표와 부딪칠 수 있다.
  - 확인 1블록과 재시도 안내로 처리하고, 실제 측정 뒤 정한다.
- 무료 한도 계수가 프로세스별이면 한도를 넘을 수 있다(관문 문서 7-1의 한계와 같다).
- x402 클라이언트마다 헤더 이름이 다를 수 있다. 공개 x402 형식(`X-PAYMENT`)도 함께 받을지는 구현 때 정한다.
