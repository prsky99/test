# 엣지 관리 출력 중계 실패 원인 (2026-11-11, 운영·SRE)

PM 지시(사용자 결정 "엣지 게이트웨이 오류·실패는 논문과 SNS 검색으로 근본 해결"). 대상은 `edge_gateway_events`의 `origin:admin:publish_failed`, `origin:admin:edge_not_ready`, 그리고 11-10 06:36 뒤 `edge:admin:delivered` 0건이다.

## 1. 관리 출력 중계가 도는 방식
- 관리 API 중 실행 결과 경로(`/admin/api/test-reports…`, `test/execute`, workflow runs 등)의 응답만 대상이다(`output_relay.OUTPUT`).
- 원 서버는 응답을 Worker에 게시한다(`POST /api/edge-gateway/v1/output-publish`). Worker는 결과를 암호화해 `caches.default`에 넣는다.
- 브라우저가 v1 전송을 쓰지 않으면, 원 서버가 같은 결과를 Worker에서 다시 읽어 맞는지 확인한다(호환 조회, `GET /outputs/er_…`).
  - Worker는 이 조회 한 번마다 `edge:admin:delivered`를 기록한다.
  - 캐시에 없으면 `origin_relay`를 기록한다.
- 게시나 확인이 실패하면 원 서버가 원래 응답을 그대로 돌려주고 `origin:admin:<사유>`를 남긴다. 실행은 다시 하지 않는다.

## 3. 11-09 실패의 원인 (판정)
기록에는 `publish_failed`만 남아 직접 원인이 없다. `output_relay`가 모든 예외를 하나의 이름으로 묶었기 때문이다. 아래는 같은 시간대 기록과 코드 경로로 좁힌 후보다.

| 후보 | 근거 | 판정 |
|---|---|---|
| A. 운영 DB 쓰기 잠금 대기 초과 | 게시 전에 `write_once`가 쓰기 거래를 연다. 쓰기 advisory lock의 `lock_timeout`은 1초다. 11-09에는 autovacuum, 대량 카탈로그 쓰기, Chat 7초대 지연, 같은 미들웨어의 세션 확인 lock timeout 500이 함께 기록돼 있다(WORKLOG 11-09, `actor()` 주석). 11-10에 `WriterBusy` 1회 재시도를 넣은 뒤 0건이다. | **가장 유력** |
| B. 부하 때문에 Worker 호출 시간 초과 | 게시·확인은 `bounded_client`로 공개 주소(Cloudflare)를 두 번 왕복한다. 11-09 부하 4~9에서 바깥 호출이 느렸다. 한국에서 공개 주소로 가는 요청은 무료 플랜에서 LAX를 거친다(11-10 측정). | 유력(A와 함께) |
| C. Worker CPU 한도(무료 10ms) 초과 → 1102 | 게시 한 번마다 HMAC 검증과 AES-GCM 암호화(최대 64KB)를 한다. 무료 플랜 CPU 한도는 10ms이고 넘으면 1102(Worker exceeded resource limits)다. 기다리는 시간은 CPU에 들어가지 않는다. 우리 준비 판정에도 `cpu_blocked`가 있다. | 가능(새 코드로 `publish_http_5xx`면 확정) |
| D. 서명 시각 차이 30초 초과 → 401 | Worker는 `X-Edge-Time`이 30초를 넘으면 401을 준다. 부하가 큰 맥에서 큐 대기로 늦어지면 생길 수 있다. | 가능(`publish_http_401`로 구분) |
| E. Cache API 저장 실패·데이터센터 차이 | `cache.put`은 저장에 실패해도 오류 없이 끝나고, 캐시는 그 데이터센터 안에서만 보인다. 그래서 확인 조회가 다른 데이터센터로 가면 캐시에 없어 `origin_relay`가 된다. 실패로 세지 않는다. | publish_failed 원인 아님 |
| F. 터널 재연결(502/530) | 터널이 끊긴 동안 Worker가 원 서버에 닿지 못하면 502다. 11-10 06:49 `origin_http_502` 1건은 05:38 트리거 장애 직후다. | 11-10 1건만 해당 |

`edge_not_ready` 35건(11-09 09시)은 실패가 아니라 정책이다. Worker 상태 관측이 오래됐거나 CPU 보호 중일 때 원 서버로 보낸다(`publish()`의 준비 판정). 같은 시간 배포·재시작과 겹친다.

## 4. 고친 것 (커밋 하나, 네 역할 배포)
- `output_relay.failure_reason(error, stage)`가 단계(`publish`|`readback`)와 실패 종류를 안전 코드로 남긴다. 메시지·주소·토큰·출력은 남기지 않고, 상태 코드만 숫자로 남긴다.
  - `publish_store_busy`(쓰기 잠금 대기 초과), `publish_store`
  - `publish_timeout`, `publish_connect`, `publish_transport`
  - `publish_http_401`·`publish_http_503` 같은 상태 코드, `publish_mismatch`
  - `readback_http_<코드>`, `readback_timeout` 등, `readback_mismatch`
  - 분류할 수 없는 예외만 예전처럼 `publish_failed`로 남는다.
- 같은 코드를 서버 로그에 경고로 남긴다(예외 종류 이름만).
- `output_monitor.REASONS`가 새 코드를 받는다. 관리 화면 엣지 모니터에 한국어 이름을 붙였다.
- 시험: `tests/test_edge_output_monitor.py`에 원인 코드별 시험을 더했다(엣지 시험 65개 통과).
