# 탐색 투영 표(P1) 설계 (2026-11-11, 검색과 RAG)

PM 지시: P1은 설계 문서만 먼저 쓴다. D'와 P2의 효과를 본 뒤 필요한지 판단한다.

## 1. 지금 무엇을 읽는가

탐색 한 번(종류 하나)은 후보 최대 600개를 다음 순서로 읽는다.

| 단계 | 코드 | 읽는 것 | 크기 |
|---|---|---|---|
| projection | `postgres_capability_text.ranking_rows`, 없으면 `resources(columns=RANKING_COLUMNS)` | resources ⨝ capability_text ⨝ resource_observation_generations: id, kind, name, description, eval_score, rank_text, rank_hash, generation | resources 본표 701MB(한 행 평균 약 1.9KB), capability_text 492MB |
| documents | `explore_document_reader.read`, `texts` | resources의 거의 모든 열(usage_full_tools만 뺌: usage_tools, details 등)과 explore_documents.document | resources 2.3GB(TOAST 포함), explore_documents 738MB |
| 카드 | `resources(hydrate_contracts=True)` | 최종 카드 대상(최대 45개)의 전체 행 | - |

- 후보 id는 무작위라 한 행을 읽으려고 8KB 페이지 하나를 통째로 읽는다. 큰 TOAST 값(usage_tools, details, document)은 따로 더 읽는다.
- 이것이 06시 측정에서 documents 97~1,023ms, projection 70~431ms로 나온 원인이다. 탐색 경로의 "넓은 행 읽기"는 documents 단계의 `read()`였다.

## 2. 제안

### P0: 코드만 바꾸기 (DB 변경 없음, 먼저 검토)

- `explore_document_reader.read()`가 카드와 작업어 확인에 실제로 쓰는 열만 읽게 한다.
- 처리 경로가 넓다. admission(task_advertised, input_requirements_match, supported_discovery_connection), hidden_from_public_list, _card, identity, provider_identity가 모두 이 행을 쓴다. 쓰는 열을 전수 조사해야 한다.
- 위험: 열 하나라도 빠지면 판단이 바뀐다(예: 인증 관측값, 계약 해시). 탐색 결과 비교(정답 세트 200개, 결과 동일 여부)로 확인한다.
- 정책 해시 파일(selection.py, task_requirements.py, explore_search.py, explore_documents.py, postgres_capability_text.py)은 건드리지 않는다. 그래서 탐색 문서 30만 개를 다시 만들 필요가 없다.

### P1: 작은 투영 표 `agentcon_search.explore_rank`

열과 크기:

| 열 | 출처 | 평균 크기 |
|---|---|---|
| resource_id | 기본 키 | 8 |
| kind, category, active, health_status, eval_security, auth_observed, auth_declared | resources | 약 40 |
| eval_score | resources | 8 |
| name, url | resources | 약 80 |
| description(최대 500자) | resources | 약 230 |
| rank_text, rank_hash | capability_text | 약 350 |
| document | explore_documents | 약 460(압축) |
| source_generation, policy_hash | 일관성 확인용 | 약 75 |

- 활성 행만 담는다(active=1, healthy/reachable, 격리·검토 아님, 약 24만 개). 한 행 약 1.2KB로 합계 약 290MB이고, 색인을 더해 약 300MB다.
- 지금 읽는 resources, capability_text, explore_documents(합계 약 3.5GB) 대신 이 표 하나만 읽는다. shared_buffers 2GB 안에 계속 머물 수 있는 크기다.

갱신 방식(일관성):
- 이미 있는 탐색 문서 큐(jobs, `explore_document_refresher.Refresher`)가 문서를 쓰는 같은 트랜잭션에서 이 행도 쓴다. 기준은 generation이 바뀐 행이다.
- 비활성·격리로 바뀌면 같은 큐가 행을 지운다. 지울 때까지의 짧은 틈은 기존처럼 카드 단계의 재확인(현재 행 읽기)이 막는다. 표가 늦더라도 노출 판단은 지금과 같다.
- 읽을 때 `source_generation = resource_observation_generations.generation`, `policy_hash = 현재 정책`인 행만 쓴다. 맞지 않으면 지금 경로(read)로 내려간다. 그래서 표가 늦어도 결과가 틀리지는 않고, 그 행만 느려진다.
- public 스키마에는 트리거를 두지 않는다(앱 불변식 5개).

전환 순서:
1. 표 생성(agentcon_search, 리허설)
2. jobs가 채우기(24만 행, 문서 큐 속도로 약 2시간)
3. frontend가 표를 먼저 읽고, 없으면 옛 경로로 간다(D'처럼 존재 확인 뒤 사용)
4. 1주 관찰

복구: frontend를 옛 버전으로 되돌린 뒤 `DROP TABLE agentcon_search.explore_rank`.

### P2: resources 덮개 색인 (D' 리허설에 포함)

- `CREATE INDEX CONCURRENTLY resources_id_filter_cover ON public.resources (id) INCLUDE (kind, active, health_status, eval_security, eval_score)`
- 필터만 확인하는 쿼리는 본표를 읽지 않는다. name, description, document가 필요한 단계에는 효과가 작다. 리허설에서 projection과 documents 단계 시간을 앞뒤로 잰다.

## 3. 판단 기준

- D'와 P2를 적용한 뒤 공개 주소 첫 질의 p50이 2초 안이고 documents와 projection 합계가 서버 시간의 30% 아래면, P1은 미룬다.
- 그렇지 않으면 P0(코드만)을 먼저 하고, 그래도 모자라면 P1을 리허설한다.
