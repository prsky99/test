측정: 2026-10-20 13:47 KST. 삭제, Git 정리, DB 변경, 서비스 재시작은 하지 않았습니다. 이 조사 보고서만 추가했습니다.

현재 파일 35,517개, 실제 할당 공간 **22.86 GB / 21.29 GiB**, 파일 내용 크기 합계 **22.73 GB**입니다. GB는 10억 바이트입니다. 운영 중 DB/WAL과 도구의 스냅샷 때문에 값은 이후 달라질 수 있습니다. 디렉터리 자체의 메타데이터를 포함하는 `du`와 파일별 할당 공간 합계에는 작은 차이가 있습니다.

## 큰 폴더와 원인

- `gateway-data/`: 약 **8.19 GB**. 실제 운영 DB, WAL, 이전 DB 백업, 워크플로우 실행 환경입니다.
- `.git/`: 약 **6.75 GB**. 대부분 생성 산출물이 들어간 Codex 작업 복구 스냅샷의 객체입니다.
- `output/`: 약 **6.20 GB**. 투자 제안서의 여러 버전, 한국어/영어 PPTX·PDF·ZIP, 이미지, 중간 빌드입니다.
- `new/`: 약 **483 MB**. 새 프론트엔드와 디자인 원본·화면 검증 증적입니다. `new/qa/`만 약 330 MB입니다.
- `outputs/`: 약 **481 MB**. 클릭 검증 화면, 엑셀 체크리스트, 증적 ZIP 등이 있습니다.
- `reports/`: 약 **369 MB**. 검증·복구 보고서, 테스트 증거, 소스 동결 ZIP 등입니다.
- `.venv/`: 약 **298 MB**. 현재 Python 의존성과 Playwright 실행 파일입니다.
- `logs/`: 약 **8.5 MB**. 앞서 정리한 운영 로그는 지금 전체 용량의 주요 원인이 아닙니다.

## 우선 검토할 정리 후보: 합계 약 692 MB

서로 겹치지 않는 아래 세 종류를 합한 값입니다. 아직 삭제하지 않았습니다.

1. **최종본과 SHA-256이 같은 build 중간 파일 13개: 372,274,907 bytes.**
   최종본 쪽 동일 파일을 유지할 수 있습니다. 예: `output/investor-proposal-detailed-review-2026-10-19/build/ko-candidate.pptx`는 같은 폴더의 `ko/agentconcierge-investor-proposal-ko.pptx`와 내용이 같습니다. 전체 경로와 보존할 동일 사본은 `cleanup-candidates.json`에 기록했습니다. 해당 중간 파일을 직접 참조하는 빌드 작업은 정리 전에 확인해야 합니다.
2. **재생성 가능한 캐시: 43,367,315 bytes.**
   프로젝트의 `__pycache__`, `.pytest_cache`, `.ruff_cache`입니다. `.venv` 자체는 포함하지 않습니다.
3. **이전 DB 백업 폴더의 restart.log: 276,702,269 bytes.**
   `gateway-data/database-backups/20261016T225112Z/restart.log`입니다. 10월 17일 KST에 마지막 수정된 오래된 기동 로그이며, 현재 `logs/`의 운영 로그와 별개입니다. 앞선 운영 로그 정리에서 DB 복구 폴더를 보존하면서 남아 있었습니다. 복구 당시 진단 기록을 보관할 필요가 없다면 정리 후보입니다.

## 추가로 줄일 수 있는 영역

- **아티팩트의 동일 내용 중복: 205그룹, 사본 1개씩 보존 시 이론상 약 1.20 GB.** `output/`, `outputs/`, `new/`, `reports/`의 1 MiB 이상 같은 크기 파일을 SHA-256으로 비교했습니다. 위 372 MB 중간 파일이 여기에 포함됩니다. 이미지·문서 경로는 배포본/제안서가 참조할 수 있으므로 같은 내용이라는 이유만으로 일괄 삭제하면 안 됩니다.
- **output의 build/renders 경로: 약 887 MB.** 렌더 이미지와 작업 중간본을 포함합니다. 위 중복 수치와 겹칩니다. 편집 소스, 원본 이미지, 재생성 방법이 남아 있는지 확인 후 정리할 수 있습니다.
- **output의 ZIP만 약 2.42 GB.** PPTX/PDF/이미지 원본과 패키지가 함께 있고, 제안서 버전도 여러 개입니다. 최종 제출 버전을 정한 후 이전 버전은 외부 보관 위치로 옮기는 방법이 효과적입니다. `output/` 전체를 불필요하다고 판정한 것은 아닙니다. 같은 프로젝트 안에서 폴더만 옮기면 전체 용량은 줄지 않습니다.
- **DB 백업 계열: 약 3.11 GB**의 SQLite/BAK/손상 당시 보존본이 있습니다. 위 오래된 기동 로그는 제외한 값입니다. 운영 DB와 별개지만 복구 자료이므로 최신 검증 백업과 복구 이력을 확보한 뒤 보존 범위를 정해야 합니다. 같은 크기인 `gateway.sqlite3.bak`와 백업 폴더의 `gateway.sqlite3`도 SHA-256이 달라 완전 중복이 아닙니다.

## Git 용량을 단순 삭제로 줄일 수 없는 이유

일반 브랜치·원격 브랜치에서 참조하는 Git 객체의 저장 크기는 약 **1.39 MB**입니다. 반면 `refs/codex/turn-diffs/...` 작업 복구 스냅샷이 참조하는 객체는 약 **5.75 GB**입니다. 이 중 `output/` 객체가 약 **4.84 GB**입니다. 두 참조 집합은 겹치므로 합산하지 않습니다.

현재 Git 인덱스에는 92개 경로만 있습니다. 제안서들이 일반 커밋에 대량 추가된 것이 아니라, 추적되지 않은 생성물도 작업 복구 스냅샷에 들어간 상태입니다. 큰 파일이 작업 폴더와 Git 객체 양쪽에 저장된 것이 증가 원인입니다.

- Git이 garbage로 표시하는 `tmp_obj_*` 8개도 약 **136 MB** 있습니다. 오래된 임시 객체지만 작성 중 프로세스 여부를 확인한 뒤 Git 정리 절차로 처리해야 합니다.
- 참조 중인 객체를 `.git/objects`에서 직접 삭제하면 작업 복구와 저장소가 손상될 수 있습니다.
- 일반 `git gc`만으로 스냅샷에서 여전히 참조하는 5.75 GB가 모두 없어지지는 않습니다. ZIP·이미지는 이미 압축되어 재압축 효과도 제한적일 수 있습니다.
- 재발 방지 후보는 `output/`, `outputs/`, `new/qa/` 같은 대용량 생성물의 보관 위치·ignore 정책 정리입니다. 이미 존재하는 스냅샷에는 소급 적용되지 않습니다. 디자인 원본·현재 서비스 파일은 제외 범위를 별도 결정해야 합니다.

## 운영 데이터는 보존

PID 41500이 `collector.sqlite3`와 `collector.sqlite3-wal`을 실제로 열고 있습니다. 운영 DB는 약 **3.51 GB**, WAL은 약 **782 MB**입니다. WAL/SHM을 임의 삭제하면 안 됩니다.

운영 DB의 읽기 전용 PRAGMA 조회에서 재사용 가능한 빈 페이지가 약 **471 MB** 확인됐습니다. 이 공간은 DB 안에서 재사용될 수 있으며 파일 삭제 대상은 아닙니다. 파일을 축소하려면 별도의 유지보수 작업이 필요합니다. 이번 조사에서 체크포인트, VACUUM, 업무 데이터 삭제는 실행하지 않았습니다.

사용자가 요청한 **엑셀 체크리스트, 클릭 전·후 및 수정 후 캡처, 디자인 원본, 최종 투자 제안서, 테스트 보고서 복구 자료**는 일괄 삭제 대상으로 분류하지 않았습니다.

## 조사 파일

- `inventory.json`: 폴더별 물리/논리 용량, 큰 파일, Git 참조별 크기, DB 메타데이터
- `duplicates.json`: 해시로 확인한 동일 파일 그룹과 경로, DB 백업 비교
- `cleanup-candidates.json`: 중복 중간 파일 13개와 보존할 동일 사본, 캐시, Git 임시 객체, 이전 기동 로그

정리 용량은 서로 중첩되는 후보를 단순 합산하지 않았습니다. 약 692 MB는 우선 검토할 후보 합계이며, 실제 삭제·이동 후 확보 공간을 보장하는 수치는 아닙니다. Git 스냅샷이 가진 사본은 작업 폴더 파일을 삭제한 뒤에도 남을 수 있습니다.
