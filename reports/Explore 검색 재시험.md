# Explore 검색 재시험 (agentconcierge.biz/#explore)

- **일시:** 2026-10-27
- **비교 대상:** `reports/Explore 검색 브라우저 테스트.md`(2026-10-26, 개선 17건)
- **방법:**
  - 지난번과 같은 Chromium(Playwright), 같은 화면 크기(1366×900, 390×844), 같은 검색어 48개로 시험했습니다.
  - 속도는 화면에서 한 번, API(`/api/explore`)에 직접 두 번 재서 화면 처리 시간을 뺀 서버 응답 시간도 봤습니다.
  - 요청 간격은 1.5~2초입니다.

## 요약
- **17건 결과:** 개선 9건, 일부 개선 5건, 그대로 3건
- **확실히 좋아진 것:**
  - 주소에 검색어 유지(`#explore?q=pdf`), 새로고침·뒤로 가기
  - 필터를 바꾸면 바로 재검색
  - 더 보기(`offset`)
  - 카드의 카테고리 이름이 필터와 같아짐
  - 프로토콜 버튼 겹침 해소
  - 모바일에서 결과로 스크롤
  - 긴 검색어 처리(입력 500자 제한, "Search unavailable" 없어짐)
- **남은 문제:**
  - 칩 중 **Weather가 여전히 검색을 하지 않음**
  - 오타·스페인어는 여전히 0건이고 제안이 없음
  - 의미 없는 검색어에도 결과가 나옴
  - 결과 중복
  - 날씨 API가 금융으로 분류됨
- **속도는 개선되지 않았습니다.** 화면 기준 중앙값 1.6초 → 1.8초, 상위 10% 4.6초 → 5.1초, 최대 8.9초 → 11.5초입니다. 같은 검색을 다시 해도 빨라지지 않아 캐시가 없는 것으로 보입니다.

- **캐시 없음:** 같은 검색어를 다시 불러도 빨라지지 않습니다. 응답은 Cloudflare `cf-cache-status: DYNAMIC`, `Cache-Control: no-store`입니다.
- **원인 구분:** 화면 시간에서 API 시간을 빼면 화면 쪽은 0.5초 안팎입니다. 느린 원인은 대부분 서버 검색입니다.

### 속도 개선 방안
1. **같은 검색 결과 캐시:**
   - 정규화한 검색어 + 필터 + `limit`·`offset`을 키로 30~60초 메모리 캐시를 둡니다(예: LRU 1,000개).
   - 카탈로그가 갱신될 때만 비웁니다.
   - 응답에 `Cache-Control: public, max-age=30`을 주면 Cloudflare도 캐시할 수 있습니다.
   - 같은 검색이 반복될 때 응답이 수 ms로 줄어듭니다.
2. **검색어 정규화와 단어 제한:**
   - 소문자로 바꾸고, 반복 단어를 하나로 줄이고, 불용어(the, and, of, a)와 기호만 있는 검색어를 정리합니다. 이것만으로 7번(의미 없는 검색어)도 함께 해결됩니다.
   - 단어는 최대 8개까지만 씁니다.
   - 기호만 남으면 검색하지 않고 최신 목록과 안내를 보여 줍니다.
3. **FTS5 질의 줄이기:**
   - 결과 수를 세는 쿼리를 따로 돌리지 말고 `limit+1`만 받아 "더 있음"만 판단합니다. 문구도 "45+ matches"로 바꾸면 11번의 "up to"도 해결됩니다.
   - 구문 검색(`"web search"`)은 FTS5 `NEAR`나 접두어 인덱스(`prefix='2 3'`)를 써서 비용을 줄입니다.
   - 정렬에 쓰는 품질 점수와 검증 시각은 FTS 결과 rowid로 한 번에 조인하고, 인덱스(`resource(id)`, `checks(resource_id, ts)`)가 있는지 확인합니다.
4. **응답 크기 줄이기:** 목록에는 카드에 필요한 필드만 보냅니다. 지금 `limit=100`이면 약 97KB입니다. 상세는 카드를 열 때 받습니다.
5. **측정:**
   - 응답에 `Server-Timing: fts;dur=…, rank;dur=…, total;dur=…`을 넣어 어디서 느린지 보이게 합니다.
   - 3초가 넘는 검색은 서버 로그에 검색어와 단계별 시간을 남깁니다.
6. **화면:**
   - 입력 중 미리 검색(300ms 디바운스)은 서버 부담이 커지므로 캐시를 넣은 뒤에 검토합니다.
   - 검색 중에는 이전 결과를 흐리게 두고 "검색 중…"을 보여 줍니다.
- **목표:** 중앙값 0.5초 이하, 상위 10% 1.5초 이하, 3초 초과 0건(같은 48개 검색어 기준)

## 남은 개선 필요 (우선순위 순)
1. **Weather 칩 고치기(1번):** 다른 칩과 같은 처리기를 쓰는지 확인합니다. 지금 기본 목록 상태에서 Weather를 누르면 요청이 나가지 않습니다.
2. **속도(6번):** 위 1~3번, 캐시·정규화·카운트 쿼리 정리
3. **오타·다국어 제안(4번):**
   - `translte`·`gihtub` 같은 오타에는 카탈로그 단어 사전으로 편집 거리 1~2의 제안("translate를 찾으셨나요?")을 보여 줍니다.
   - `clima` 같은 흔한 외국어는 영어 동의어로 함께 검색합니다(`날씨`·`天气`는 이미 동작함).
4. **관련성(3번):**
   - 이름·설명에 맞은 결과를 스킬 본문에만 맞은 결과보다 앞에 둡니다(`translate` 1위 Sats4AI).
   - 숫자 검색어(`8004`)는 ERC-8004 출처 필터로 연결합니다.
5. **분류(12번):**
   - "Other"를 14개 카테고리 중 하나로 다시 분류하거나 필터에 "기타"를 추가합니다.
   - 날씨 API가 금융으로 분류되는 오류는 분류 규칙 회귀 시험에 넣습니다(`gateway/classify.py`).
6. **의미 없는 검색어(7번), 중복(9번), 칩 검색어(16번), 결과 수 문구(11번):** 지난 보고서의 개선안 그대로입니다.
