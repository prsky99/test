# CSS 구조 정리 (PM 11-14 00:3x 안 3: "보이는 화면은 그대로, CSS만 줄이기")

목표는 첫 화면 CSS와 전체 CSS 묶음을 줄이는 것이다. 보이는 결과는 바꾸지 않는다. 기준은 화면 10개 × 1280·375 × 라이트·다크(40장)의 픽셀 차이 0이다. 디자인 시스템(Pearl Connection 토큰, 공용 assets)을 그대로 따르고, 페이지 전용 스타일은 만들지 않는다.

## 기준과 도구 (1단계, 11-14 01:2x 완료)

- 도구: `scripts/css_pixel_compare.py`
  - `shoot <단계>`: 작업본을 고정 카탈로그(8개)로 띄운 앱에서 40장을 찍는다. 네트워크는 쓰지 않고, 애니메이션·전환을 끄고, 글꼴이 다 오기를 기다린다.
  - `diff <기준> <단계> --noise <기준 두 번째>`: 그림마다 다른 픽셀 수를 세고, 다르면 빨간 차이 그림을 남긴다.
- 대상 화면 10개: 홈, agent-status, explore, learn, test, workflows, chat, list-agent, about, privacy.
- 잡음 확인: 같은 작업본을 두 번 찍었다.
  - 처음에는 화면에 나오는 현재 시각(16:23 → 16:24 UTC) 때문에 8장이 달랐다. 찍기 전에 "시:분" 글자를 고정값으로 바꾸게 했다.
  - 그 뒤 40장 중 39장이 같았다. 남은 1장(chat 375 다크)은 패널 테두리 7픽셀의 안티앨리어싱이다.
  - 이것은 기준을 두 번 찍어 흔들린 픽셀로 빼고 센다(`--noise`). 같은 작업본끼리 0.
- 기준 사진: `gateway-data/css-pixels/baseline/`, `baseline-2/`(git 제외). 안 1 작업본(34b064a4) 기준이다.

## 단계 계획 (단계마다 40장 픽셀 차이 0, 현황판에 진행 기록)

1. 기준과 도구 — 끝.
2. 원본 파일의 같은 선택자 덮어쓰기 정리: 뒤 파일(pearl-live)에서 이기는 값을 앞 파일 규칙 자리에 합치지 않는다. 앞 파일의 진 선언만 지운다(prune 규칙 그대로, 원본에 적용). 예상: 묶음 −10KB, 첫 화면 −1~2KB 추가.
3. 어떤 화면에서도 맞는 요소가 없는 규칙 찾기: 공개 화면 전부와 상태(메뉴 열림, 다크, 결과 카드 종류, 대화 진행 중)에서 coverage를 모은다. 한 번도 쓰이지 않은 규칙 후보를 목록으로 만든다. 지우기 전에 목록을 PM에 올린다(상태를 놓치면 그 화면이 깨지므로).
4. 다른 선택자로 같은 요소를 겹쳐 쓰는 부분(styles → pearl-live)을 컴포넌트별로 하나로 합친다. Pearl 토큰 값을 쓰고, 화면별 전용 규칙은 만들지 않는다.
5. 첫 화면 CSS를 다시 만들고, 공개 주소에서 전후 크기와 본문 시간을 잰다.

- 차이가 0이 아닌 단계는 그 화면만 사진과 함께 PM에 올리고, 사용자 화면 승인 전에는 내보내지 않는다.

## 2단계 결과 (11-14 01:4x, 배포 대기: PM 01:4x 결정으로 11-14 낮 묶음 뒤 첫 frontend 묶음)

- 원본 파일을 고치지 않는 쪽으로 바꿨다.
  - `styles.css`는 묶음 밖에서도 단독으로 쓰인다(category 화면 `agent_access/pages.py`, 고객 작업 공간, 관리 웹앱). 다른 파일이 덮어쓴다고 원본에서 지우면 그 화면들이 바뀐다.
  - 그래서 bundle.css를 보낼 때만 정리한다: `pearl_view.bundle_body` → `css_compact.prune`. 같은 묶음 안, 같은 파일 순서에서 같은 선택자·같은 맥락에 뒤에서 다시 정의되는 선언을 빼고 공백·주석을 줄인다.
  - 결과는 원본 내용 해시로 기억한다. 처음 0.1초, 그 뒤 1ms.
- 옛 HTML 대조: 엣지에 남은 옛 HTML은 정리 전 묶음 해시를 부른다. 옛 릴리스 묶음을 찾을 때 정리 전·후 두 해시를 모두 대조한다(시험 `test_a_bundle_served_before_compaction_is_still_found_by_its_digest`).
- 크기: bundle.css 압축 뒤 58.4KB → 48.0KB(−18%).
  - 첫 화면 CSS는 이 묶음에서 다시 만들었고 0.1~0.2KB가 더 줄었다(홈 13.3→13.2KB, chat 15.0→14.7KB).
- 픽셀: 40장 모두 기준과 차이 0. 정리만 넣었을 때(step2)와 첫 화면 CSS까지 다시 만든 최종(step2b) 둘 다 0이다.
- 시험
  - 게이트 목록과 관련 시험 477개 통과.
  - 1건(daily home 화면 전환)은 시험의 기다리기 방식이 페이지 CSP(eval 금지)에 막힌 것이었다. eval을 쓰지 않는 `expect(...).to_have_attribute`로 바꾼 뒤 4번 연속 통과했다.
- 사진: `gateway-data/css-pixels/`의 `baseline/`, `baseline-2/`, `step2/`, `step2b/`(80MB, git 제외).
- 다음 3단계: 한 번도 쓰이지 않는 규칙 후보 목록(상태 포함 coverage)을 만들어 PM에 올린다.

## 3단계: 어떤 화면·상태에서도 맞지 않는 규칙 후보 (11-14, 목록만, 지우지 않음)

- 도구: `scripts/css_unused_candidates.py`(무거운 작업 칸에서 실행)
  - 화면 10개 × 1280·375 × 밝음·어두움 = 40개 상태
  - 상태마다 접힌 것 펼치기(`[aria-expanded=false]`, `<details>`), Explore·Chat은 질의 한 번까지 모은다.
  - 의사 클래스(:hover 등)는 떼고 요소가 있는지만 본다.
- 결과(`unused-candidates.json`)
  - 선택자 3,833개 중 맞음 2,940, 형식상 확인 불가 10, **한 번도 맞지 않음 883**
  - 883개 가운데 808개는 클래스·id 이름이 페이지 JS나 서버 코드에 나온다("dynamic"). 이 도구가 몰지 않은 상태(로그인, 워크스페이스, 오류, 결과 종류)에서 쓰일 수 있어 후보에서 뺐다.
  - **후보 75개**: bundle.css 60, 인라인 critical 15
- 주의: 후보에도 직접 확인이 필요한 것이 섞여 있다.
  - `.necklace-thread`: About 진주 목걸이 그림 쪽(11-13 시안 그림 유지 결정, `keep-design-visuals`)
  - `.chat-message`·`.chat-user-bubble`·`.chat-assistant-bubble`: 대화 말풍선. JS가 이름을 이어 붙여 만들면 코드 검색에 안 걸린다.
  - `.binary-loader`·`.fake-lines`: 로딩 표시
  - 그래서 **지우기 전에 PM 검토**를 받고, 지운 뒤에는 픽셀 비교(0)와 화면 시험을 다시 돈다.
- 크기: 후보 75개를 모두 지워도 bundle.css에서 줄어드는 양은 작다(규칙 2,339개 중 60개). 3단계의 효과는 크기보다 "남은 규칙은 쓰인다"는 정리에 있다.
