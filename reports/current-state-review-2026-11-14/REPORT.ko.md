기준: 2026-11-14T12:40:32+09:00 KST. 분석 스냅샷 HEAD `f73e348c412ba841dd5c60857c1f9cccbd52c6e4`. **개발은 크게 진행됐지만, 실제 과제 품질·일관된 진주 인증·첫 검증 목걸이 완주를 우선 보강해야 한다.**

## 범위와 해석

11월 3일 이후 처음 기록한 785개 커밋에서 감사 스냅샷 시점 792개까지의 변경 흐름을 확인했다. 런타임·스크립트·테스트·게시물·문서·배포 파일 2,605개의 경로/크기 목록을 만들고 핵심 실행·검증·검색·결제·운영 경로를 집중 검토했다. 모든 파일의 모든 줄을 정밀 감사한 것은 아니다. Claude의 대화 전체에 접근한 것이 아니라 저장소의 CLAUDE.md·WORKLOG·헌장·현황판·보고서·커밋·운영 증적을 분석했다.

이 요청에서는 앱 소스·운영 설정·DB·프로세스를 수정하지 않았다. 격리된 가짜 호출과 임시 디렉터리로 재현하고 공개 주소에 직렬 GET 9건만 보냈다. 로그인 후 모든 업무·실제 결제·지갑 송금·공격적 동적 보안 검사는 수행하지 않았다. 운영 서버에서 전체 pytest/부하 시험을 중복 실행하지 않고 순수 회귀 57개만 nice 10으로 실행해 통과했다.

검토 중 다른 Claude 작업이 계속 진행됐다. 소스와 역할별 활성 릴리스 비교, 핵심 파일 해시를 남겼다. 역할별 코드가 다른 사실만으로 결함이라고 판정하지 않으며, 구현·배포·공개·실제 성공을 구별했다.

## 현재까지 진행된 내용

### 제품과 전략

Agent Concierge 디렉터리 중심에서 AgentValCon — Agent Value Gateway로 재정의됐다. 수집→품질 등급→과제 시험 보고서 v2→역할별 진주→대체 사슬을 갖춘 목걸이→외부 공급→결과 재검증의 방향이 정리됐다. 등급 A는 진주 후보, v2 85점 이상·서로 다른 날 성공은 검증 진주, 역할 1위는 최종 진주라는 기준과 자체 대체의 별도 취급도 생겼다.

### 수집·데이터·검색

PostgreSQL/pgvector 운영, 종류별 HNSW·호스트 상한·문서 투영·백그라운드 갱신·등록 SQL 검증·OpenSearch 후보 검색과 폴백이 개발됐다. 로컬 OpenSearch는 이미 on 설정이다. Neo4j는 야간 계산 결과를 PG에 내보내는 설계가 있으나, 이번에 Neo4j 서버의 실제 데이터 적재와 요청 연결까지 확인한 것은 아니다. x402 수집 중지와 결제 전 연결 근거의 등급 상한도 최신 정책에 반영돼 있다.

### 추천·워크플로·증거

과업·프로토콜·역할·지역·중계 가능성의 적격성, 실제 호출 증거, 보고서 판·서명·도구 fingerprint, 32개 역할 계약, 자체 대체, 목걸이 정의·실행기·감시·95% 관문·중단 안내·공개 표면이 추가됐다. 일반 운영자 워크플로와 새 검증 목걸이는 별개다. 공개 목걸이 목록은 실제 GET에서도 0개이며, 실행기 코드가 있어도 RUN 연결과 실제 공개 종단 검증이 남는다.

### 사용자 화면·어드민·운영

진주 브랜드 UI, 공개/고객 화면, 관리자 업무 패널, 고정 첫 화면·비차단 진행·세션·캐시가 발전했다. frontend/admin/jobs/execution 분리, 활성 판 overlay, 릴리스 게이트, standby 정리, 무거운 작업 칸, DB 사본 리허설·복구 SQL, 설정 검사, SLO/전수 점검/오류 장부/보관 정책/복구 훈련 체계가 생겼다. 과거보다 보호 장치가 많아진 것은 명확한 진전이다.

### 광고·수익·보안

무상 AD Coin과 USDC Sponsored 예약 장부를 분리하고, 정확한 금액·받는 주소·체인·중복 tx·제재 검토·늦은 결제 review·수동 환불·월별 기록을 구현했다. 광고가 추천 판정을 바꾸지 않는 검사를 추가했다. 결제 스위치는 최신 사용자 결정으로 이미 켜졌다. 안정성 관문이 닫혔다는 이유로 이 결정을 임의로 위반 또는 차단 대상으로 판정하지 않았다.

P1은 현재 과업/증거 신뢰나 첫 상품 출시 전에 우선 해결할 항목, P2는 구조·확장·운영 보강이다. 새로 확인한 운영 침해나 자금 유출 증거가 없으므로 임의의 P0를 부여하지 않았다. 재현은 해당 함수·조건의 결함 증명이며 실제 운영 사고의 발생 건수는 아니다.

### F04 · P1 · 총 실행 마감과 지연 응답의 성공 판정을 강제하기

**분야:** 워크플로·목걸이 · **근거:** 격리 재현 · **권장 담당:** 워크플로우 + 운영·SRE · **초기 작업량:** 1~2일

**완료 기준:** 협조하지 않는 caller, 첫 후보 지연, 선택 슬롯 지연, 부분 성공에서 반환 시간·남은 작업 수·결과 상태를 검증한다.

## 기술 판단의 외부 근거

- Python 공식 concurrent.futures 문서는 executor context manager가 기본적으로 작업 종료를 기다리며 실행 중 Future는 취소할 수 없다고 설명한다. F04의 단순 timeout 추가만으로 충분하지 않다는 판단에 사용했다. [Python 공식 문서](https://docs.python.org/3/library/concurrent.futures.html)

- 이미 설치한 jsonschema는 스키마 자체 검사와 재사용 Validator를 제공한다. F11은 새 제품 도입이 아니라 현재 의존성의 명시적 계약 사용 제안이다. [jsonschema 공식 문서](https://python-jsonschema.readthedocs.io/en/stable/validate/)

- pgvector 공식 문서의 필터·부분 색인·iterative scan 특성은 필터 후 후보 부족과 종류별 검색의 재현율 검증 필요성을 뒷받침한다. 이 서비스에서 효과가 검증됐다는 뜻은 아니다. [pgvector 공식 문서](https://github.com/pgvector/pgvector)

- Base 공식 프로토콜 문서는 unsafe/safe/finalized 상태를 구분한다. 로컬 확인 블록 수와 최종성을 동일하게 부르지 않고 결제 상태/복구 시험을 설계할 근거다. 법률·세무 적합성에 대한 결론은 내리지 않았다. [Base 공식 문서](https://docs.base.org/base-chain/specs/protocol/consensus/derivation)
