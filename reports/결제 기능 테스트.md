# 결제 기능 테스트 (agentconcierge.biz)

- **일시:** 2026-10-27
- **방법:** 소스 코드를 보지 않고 공개 API로 시험했습니다. 요청은 4~7초 간격으로 약 60건 보냈습니다.
- **돈은 쓰지 않았습니다.** 결제 서명은 잔액이 0인 일회용 지갑(`0x23e8…AfE4c`)으로 만들었습니다. 그래서 정산되더라도 옮겨질 돈이 없습니다.
- **대상 기능:**
  1. x402 유료 API 중계: `/api/gateway/x402/{id}`, 결제 요구(402)와 결제 헤더 검증
  2. MCP 게이트웨이의 유료 도구(`_payment` 인자)
  3. MCP `call`(크레딧 차감 실행)과 `credit`(잔액·충전)
  4. 고객 크레딧: `/api/customer-credits`, `quote`, `enroll`, `close`
  5. 실행 승인: `preparations/{id}/authorize`, `grants`, `gateway-execution`, 내부 edge 경로

## 요약
- **잘 된 점:**
  - 결제 요구 응답(402)이 x402 v2 규격에 맞습니다. 가격을 확인한 12개 모두 카탈로그와 같았습니다.
  - 잘못된 결제 서명 15가지 모두 통과하지 못했고, 자료도 나오지 않았습니다.
  - 크레딧·승인 경로는 로그인이나 세션 없이 모두 막혀 있습니다.
- **가장 큰 문제:** 결제가 실패한 이유를 알려 주지 않습니다. 15가지 모두 처음과 똑같은 "Payment required"입니다. 에이전트는 서명이 틀렸는지, 잔액이 없는지, 네트워크가 틀렸는지 구분할 수 없습니다.
- **확인하지 못한 것:** 실제 결제가 성공하는 흐름(정산, 응답 전달, 결제 영수증 헤더)은 돈을 써야 해서 시험하지 않았습니다.

## 시험 결과

### 1. 결제 요구 응답(402) — 표본 15개
| 결과 | 개수 | 내용 |
|---|---|---|
| v2 402, 정상 | 12 | `PAYMENT-REQUIRED` 헤더(base64)와 본문이 같습니다. `exact`, `eip155:8453`, Base USDC, `maxTimeoutSeconds 300`, `extra: USD Coin / 2`, 자원 설명이 있습니다. |
| v1 402 | 1 | 108808: `X-PAYMENT header is required`, `maxAmountRequired`, network `base`. v1 형식이라 헤더 없이 본문만 옵니다. |
| 503 | 1 | 122024: "The approved execution is unavailable." 카탈로그에는 `active`로 나옵니다. |
| 429 | 5(나중에 재확인) | 게이트웨이 경로는 20초에 10번쯤 부르면 429가 나옵니다. |

- **가격:** 다시 확인한 것까지 12개 모두 `amount`가 카탈로그 `price_usdc`와 같았습니다. 0.001~0.05 USDC입니다.
- **받는 주소(payTo):** 제공자마다 다릅니다. 게이트웨이를 지나도 돈은 제공자 지갑으로 갑니다.
- **결제 방법 수:** 1개가 대부분이고, 2개·10개인 것도 있었습니다(8193은 `accepts` 10개).

### 3. MCP 게이트웨이 유료 도구
결제 없이 `tools/call`을 부르면, 무엇을 서명해서 어떻게 다시 보낼지 문장으로 안내합니다. 예: "Sign an EIP-3009 TransferWithAuthorization for accepts[0] (mind extra.name/extra.version …) and retry this tool with `_payment`". HTTP 게이트웨이보다 친절합니다.

### 5. 고객 크레딧·실행 승인
- 로그인 없이 부르면 모두 401 또는 403이었습니다.
  - 고객 크레딧: 조회, `quote`, `enroll`, `close`
  - 실행 승인: `authorize`, `grants` 삭제, `gateway-execution` 준비
  - 내부 경로: `edge-gateway-internal` `claim`·`complete`
- 공개 워크플로 실행은 없는 템플릿이면 404입니다.

## 개선 필요 (우선순위 순)

### 높음
1. **결제가 실패한 이유를 알려 주지 않습니다.**
   - 깨진 헤더, 버전·네트워크·방식 오류, 금액 부족, 주소 오류, 만료, 서명 오류, 잔액 없음, 재사용이 모두 처음과 같은 402 "Payment required"입니다.
   - 영향:
     - 에이전트는 무엇을 고쳐야 할지 모르고 같은 결제를 반복합니다.
     - 결제 헤더를 읽기는 하는지조차 밖에서 확인할 수 없습니다.
   - 개선: x402 v2처럼 `PAYMENT-REQUIRED`의 `error` 필드에 이유 코드를 넣습니다.

     | 경우 | 코드 예 |
     |---|---|
     | base64·JSON 오류 | `invalid_payload` |
     | 지원하지 않는 버전 | `invalid_x402_version` |
     | 네트워크·방식 불일치 | `invalid_network`, `invalid_scheme` |
     | 금액 부족, 받는 주소 불일치 | `invalid_exact_evm_payload_authorization_value`, `invalid_exact_evm_payload_recipient_mismatch` |
     | 만료 | `invalid_exact_evm_payload_authorization_valid_before` |
     | 서명 오류 | `invalid_exact_evm_payload_signature` |
     | 잔액 부족 | `insufficient_funds` |
     | 재사용 | `nonce_already_used`(또는 settle 실패 사유) |

   - 깨진 헤더는 정산 시도 없이 400으로 바로 거절해도 됩니다.
2. **실제 결제 성공 흐름을 아직 확인하지 못했습니다.**
   - 결제 → 정산 → 제공자 응답 → `PAYMENT-RESPONSE` 영수증까지 한 번도 끝까지 시험되지 않았습니다.
   - 실패 응답만으로는 정상 결제가 되는지 알 수 없습니다.
   - 개선: 운영자 지갑으로 0.001 USDC짜리 자원에 1번 결제해서 확인합니다(아래 "확인하지 못한 것").

### 중간
3. **카탈로그와 실제 상태가 다릅니다.**
   - 122024는 카탈로그에 `active`인데 게이트웨이가 503 "The approved execution is unavailable."를 돌려줍니다.
   - 결제하려는 에이전트가 시간과 요청을 낭비합니다.
   - 개선: 게이트웨이가 503을 돌려주는 항목은 추천에서 빼고, 상태를 바꿉니다.
4. **x402 v1·v2가 섞여 있습니다.** 108808처럼 v1(`X-PAYMENT`, `maxAmountRequired`, network `base`)로 답하는 항목이 있습니다.
   - 게이트웨이가 바깥으로는 한 버전(v2)으로 통일해 주면, 에이전트가 한 가지 방식만 구현하면 됩니다.
   - 아니면 카탈로그에 `x402_version`을 표시합니다.
5. **결제 경로의 요청 한도가 엄격하고, 다시 시도할 시각을 알려 주지 않습니다.**
   - 게이트웨이 x402 경로는 20초에 10번쯤에서 429가 나옵니다.
   - 결제 에이전트는 402 → 서명 → 재요청으로 한 번에 2번씩 부르므로 한도에 빨리 닿습니다.
   - 개선:
     - 429에 `Retry-After`를 넣습니다.
     - 결제 헤더가 붙은 재요청은 한도를 따로 셉니다.
6. **`credit add`가 한 번 응답 없이 연결을 끊었습니다.**
   - 다시 시도하니 정상 오류가 나와 재현되지는 않았습니다.
   - 서버 로그에서 2026-10-27 00:08 UTC 무렵 `credit` 도구의 예외를 확인해 보세요.

### 낮음
7. **문구가 겹치거나 모호합니다.**
   - "Insufficient available credits: Insufficient available credits: needed 1000 …"처럼 같은 말이 두 번 나옵니다.
   - 없는 자원에 `call`하면 "The agent execution was refused or failed."라고 합니다. "Resource not found."가 맞습니다.
   - 결제가 필요한데 크레딧 충전이 막혀 있습니다("Public deposits are unavailable"). 그런데 `call` 문구는 "credit account with sufficient balance"를 요구합니다. 크레딧을 얻는 방법(고객 계정 로그인, 직접 x402 결제)을 함께 알려야 합니다.
8. **내부 경로가 공개 OpenAPI에 나옵니다.**
   - `/api/edge-gateway-internal/v1/*`, `/api/origin-gateway/*`가 공개 `openapi.json`에 보입니다.
   - 인증으로 막혀 있지만, 공격 표면이 드러납니다. 공개 문서에서는 빼는 것이 좋습니다.

## 문제없었던 항목
- **402 응답:**
  - 헤더와 본문이 같습니다.
  - `resource.url`이 게이트웨이 주소와 맞고, 설명이 있습니다.
  - EIP-712 도메인 정보(`extra.name`·`version`)가 Base USDC와 맞습니다.
- **가격:** 확인한 12개 모두 카탈로그 가격과 결제 요구 금액이 같았습니다.
- **결제 검증:** 잘못된 결제 15가지에서 유료 응답이 하나도 나오지 않았고, 5xx도 없었습니다.
- **크레딧:**
  - 잔액 조회가 정확합니다.
  - 결제 없는 충전, 음수 금액은 통하지 않았습니다.
  - 고객 크레딧·승인·내부 실행 경로는 인증 없이 모두 막혀 있습니다.
- **MCP 게이트웨이:** 유료 도구가 결제 방법을 구체적으로 안내합니다.

## 확인하지 못한 것
- **실제 결제 성공 흐름:**
  - 결제 → 정산 → 응답 → `PAYMENT-RESPONSE`가 이어지는지
  - 같은 결제를 다시 쓰면 막히는지(이미 정산된 nonce)
  - 결제했는데 제공자가 실패하면 환불·재시도가 되는지
  - 이 시험에는 실제 USDC가 필요합니다. 운영자 지갑과 금액(예: 0.001 USDC 1~2회)을 정해 주시면 진행할 수 있습니다.
- **고객 크레딧 흐름:** 충전 견적, 등록, 차감, 해지는 고객 로그인(Google/GitHub)이 필요해 시험하지 않았습니다.
- **기타:** Solana 등 Base 외 네트워크 결제는 시험하지 않았습니다.

## 참고: 시험 중 보낸 결제 데이터
