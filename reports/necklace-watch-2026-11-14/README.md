## 2. 매시간 감시 (외부 호출 0건)
- 언제: jobs 정비 칸의 새 작업 `NecklaceWatch`(`due()`·`run()`, 기존 insights·availability와 같은 모양). 매시 :20에 돌고, :55~:10과 03:50~05:10에는 시작하지 않습니다.
- 멤버마다 읽는 것(남의 서버를 부르지 않음)
  1. 헬스: `store.resource(rid)`(등록 SQL `SELECT * FROM resources WHERE id=?` 재사용) → `active`, `health_status`, `consecutive_failures`, `last_ok_at`, `inactive_reason`. 수집기가 이미 15분마다 헬스를 잽니다.
  2. 표시: 같은 행의 `usage_full_tools`에서 그 도구의 readOnlyHint·destructiveHint를 다시 확인하고 `_DENY` 동사를 검사합니다. 도구 조사가 하루 1번 정의를 갱신하므로, 표시가 바뀌면 다음 시간에 잡힙니다.
  3. 지문: 운영·SRE `fingerprints/pearls.json`의 분류(동적 설명 / 일반 변경 / 위험 신호)
- 목걸이 60개 멤버 기준으로 시간당 DB 점 조회 60번입니다.

## 3. 자동 조치
### 3-1. 실행 중 사슬 순서 조정 (정의·digest는 그대로)
- 정의 파일(git)은 승인받은 사슬입니다. 감시는 그 안에서 **순서만** 바꿉니다(`watch/state.json`의 `demoted`·`excluded`). 실행기와 판정 작업이 이 상태를 읽습니다.
- 그래서 approvals.json의 digest가 바뀌지 않고, 재승인 없이 바로 적용됩니다. 새 멤버 추가나 사슬 밖 멤버 투입은 정의 변경(버전 올림)이라 관문을 다시 거칩니다.
- 규칙
  - 주 멤버가 2시간 연속 비정상(헬스 실패, 또는 매일 재시험에서 그 멤버 실패 2회 연속) → 강등. 다음 순위가 주가 됩니다.
  - 강등된 멤버가 6시간 연속 정상이고 다음 매일 재시험을 통과 → 원래 순위로 복귀
  - 비활성(`active=0`)이거나 격리 → 제외(복귀는 재자격 시험 뒤)
  - 자리의 쓸 수 있는 외부 멤버가 2개 아래 → 경보 + 검색과 RAG에 그 역할 후보 요청(현황판)

### 3-2. 즉시 보류 (감시 보류, `watch/state.json`의 holds)
| 조건 | 이유 코드 |
|---|---|
| 사슬 멤버의 도구 표시가 readOnly 아님·destructive·실행·결제 동사로 바뀜 | `security` |
| 지문 위험 신호(주입 패턴, 표시 악화, relay 안전하지 않은 새 도구) | `security` |
| 지문 일반 변경(동적 설명 제외)이 **사슬에서 실제로 쓰는 멤버**에 생김 | `fingerprint_changed`(아래 결정 1) |
| 매일 재시험 종단 성공률 80% 미만 | `quality_low` |
| 필수 자리에 쓸 수 있는 멤버 0개 | `no_member` |
| Δ ≤ 0이 2일 연속, 48시간 재시험 없음 | `delta_nonpositive`, `stale_retest`(판정 작업 규칙 그대로) |

- 판정 작업(judge.py)은 감시 보류를 approvals와 같은 무게로 읽어 `held`를 씁니다. 판정 규칙이 하나라 표면과 감시가 어긋나지 않습니다.
- **풀기는 운영·SRE 승인으로만**(PM 지시): 감시는 보류를 스스로 풀지 않습니다. 원인이 해소되면 감시가 "해소됨"을 기록하고 현황판으로 운영·SRE에 넘깁니다. 운영·SRE가 approvals 항목을 보류 시각보다 늦은 `at`으로 다시 approved 하면, 판정 작업이 그때 live로 씁니다.
- 80~95%는 즉시 보류가 아니라 운영·SRE의 재실행 규칙(관문 7절)을 따릅니다. 감시는 경보만 냅니다.

- 매일 돌리는 것: 목걸이 종단 30건(보류 세트 60건을 이틀에 한 바퀴. 재시험 결과는 조정에 쓰지 않음), 멤버별 계약 시험 3건. 호스트당 하루 35회 이하(관문 7절 상한: 정답 30 + 계약 3 + 여유 2), 2초 간격, 429면 Retry-After만큼 쉬고 그날 남은 호출을 미룹니다.

## 10. PM 결정 (11-14, 설계 승인)
1. **지문 일반 변경**: 권장안대로 합니다. 위험 신호는 즉시 보류합니다. 일반 변경이 지금 부르는 멤버(주·fan-out)에 생기면 즉시 보류하고, **그날 안에 그 멤버만 재시험**합니다(`watch/state.json`의 `retest_requests`). 통과하면 운영·SRE에 다시 승인을 요청합니다. 대기 대체 멤버면 그 멤버만 뺍니다. 판정은 운영·SRE 지문의 정규화 형태로 합니다(동적 설명 제외). 구현: `watch.HOLD_ON_STANDBY_CHANGE = False`, `_retest_request`.
2. **경보 전달 예약 작업 1개** 승인: 매시 :25에 돌고, `alerts.jsonl`에 새 줄이 있을 때만 워크플로우 세션을 깨웁니다. 경보가 없으면 깨우지 않습니다(토큰 0). 감시가 jobs에 연결되는 날 만듭니다.
3. **재시험 실행기는 하나**(워크플로우가 만듦). 공개 목걸이는 운영·SRE 예약이, 시험 중 목걸이는 워크플로우가 부릅니다.
   - 03:10 공개 재시험은 **03:50 전에 끝냅니다**. 시간 예산은 최대 35분이고, 넘으면 남은 것은 다음 날로 넘깁니다.
   - 01:15 시험 중 재시험은 네트워크 호출이라 리허설 전용 시간과 겹쳐도 됩니다. heavy_slot 칸은 쓰지 않습니다.
- 경보와 현황판 줄의 "Agentcon 사용률"은 **"AgentValCon 사용률"**로 적습니다(브랜드 결정). 공개 문구에서 대체 에이전트는 "AgentValCon fallback"입니다. 내부 식별자(`kind: "agentcon"`, 파일 이름)는 그대로입니다.

## 11. 목걸이 단계별 대응 (헌장 956c74b3, 사용자 11-14)
- 매일 집계가 자리마다 단계를 계산합니다(`summary.json`의 `stage`, 현황판 줄의 "N단계").
  - 1단계: 정상
  - 2단계: 외부 대체가 실제로 실행됨
  - 3단계: AgentValCon fallback이 실행됨
  - 4단계: 모든 대체가 실패해 완주하지 못함
- 2단계 이상이면 그날 경보(`stage2`·`stage3`·`stage4`)를 내고, 워크플로우 세션이 PM에 보고합니다. PM이 에이전트 팀에 그 자리의 자체 대체 개발을 지시합니다. 이미 자체 대체가 있으면 그것을 다시 시험합니다.
- 4단계가 이어지면 워크플로우 팀이 같은 과제의 새 목걸이를 만들어 관문을 거쳐 대체하고, 정지·대체 공지를 성장·유통과 맞춥니다(외부 발송은 사용자 승인 뒤).
