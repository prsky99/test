# Industry tools, scanners and registries that score or check MCP servers for security and quality (through Oct 2026)

Research date: 2026-10-13. Primary sources (GitHub READMEs fetched raw from `main`/`HEAD` on 2026-10-13, vendor docs/blogs, arXiv) are preferred; secondary sources are flagged "(secondary)". Claims I could not verify against a primary source are flagged "UNVERIFIED".

## Q1. Security scanners: what do they check, how, open source, and which description patterns do they flag?

### Takeaway
The dominant scanners (Snyk Agent Scan, formerly Invariant mcp-scan; Cisco MCP Scanner; Trail of Bits mcp-context-protector) all work on the same artifact: the `tools/list` output (names, descriptions, schemas), plus server `instructions`, prompts and resources. They combine (a) cheap deterministic checks (hidden Unicode, hash/TOFU pinning for rug pulls, regex/YARA signatures such as coercive "MUST call this first" language, `<script>`, PII-exfil wording), with (b) LLM or proprietary-API judgment for prompt injection, toxic-flow classification and code/docstring mismatch. Independent evidence shows these scanners are noisy and disagree with each other: a July 2026 study of 8 scanners over 64,611 servers found 96.89% of servers flagged by at least one scanner, average precision 45.53%, and 15.66% pairwise Jaccard agreement.

### Cited Findings

**Attack patterns that define what scanners look for**
- Invariant Labs coined "tool poisoning" (Apr 1, 2025): an innocent `add` tool whose description, inside an `<IMPORTANT>` tag, tells the model to read `~/.cursor/mcp.json` and `~/.ssh/id_rsa` and pass contents via a hidden `sidenote` parameter while not telling the user; Cursor's confirmation dialog did not show the full arguments. Same post defines **rug pulls** (description changed after approval) and **shadowing** (a malicious server's description changes how the agent uses a trusted tool on another server, e.g., redirecting all `send_email` calls to an attacker address). Recommended mitigations: show full descriptions, **pin tool/package versions and verify each tool description against a hash/checksum**, cross-server dataflow boundaries — [Invariant Labs blog](https://invariantlabs.ai/blog/mcp-security-notification-tool-poisoning-attacks)
- Trail of Bits (Apr 21, 2025) calls the same thing "line jumping": servers attack at `tools/list` time, before any tool is invoked; recommends automated scanning of descriptions and **trust-on-first-use (TOFU) pinning** that alerts when a tool appears or a description changes; links a companion post on hiding instructions with ANSI terminal escape codes — [Trail of Bits blog](https://blog.trailofbits.com/2025/04/21/jumping-the-line-how-mcp-servers-can-attack-you-before-you-ever-use-them/)
- MCPTox benchmark (arXiv 2508.14925, AAAI-26): 45 live real-world MCP servers, 353 tools, 3 attack templates, 1,312 malicious cases; average attack success rate 36.5% across 20 agents, o1-mini 72.8%; more capable models were often more susceptible; refusal rate <3% even for the highest refuser (Claude-3.7-Sonnet). Note: paper versions report 1,312 / 1,348 / 1,497 cases — [arXiv](https://arxiv.org/abs/2508.14925); [AAAI](https://ojs.aaai.org/index.php/AAAI/article/view/40895)

**Snyk Agent Scan (formerly Invariant Labs mcp-scan)**
- Origin/status: Invariant Labs (ETH Zurich spin-off) was acquired by Snyk in June 2025; the `mcp-scan` package is now a redirect that installs `snyk-agent-scan` — [appsecsanta (secondary)](https://appsecsanta.com/mcp-scan). The `invariantlabs-ai/mcp-scan` README now resolves to the same Snyk Agent Scan README — [raw README](https://raw.githubusercontent.com/invariantlabs-ai/mcp-scan/HEAD/README.md)
- How it works: discovers agent configs (Claude Code/Desktop, Cursor, VS Code, Copilot, Windsurf, Gemini CLI, Codex, Kiro, etc.), **starts stdio servers / connects to remote URLs to retrieve tool descriptions** (live), runs "local checks and the Agent Scan API" — tool names/descriptions, server configs and signatures and skill content are sent to Snyk's API (secrets redacted). Requires a `SNYK_TOKEN`. CLI is open source but core analysis is a hosted API. v0.5.x uses issue codes and the `2025-09-02` analysis API; v0.6+ uses scored risk indicators and the `2026-07-10` API; output declared "experimental" — [snyk/agent-scan README](https://github.com/snyk/agent-scan)
- Its own SSRF hardening: remote requests refuse link-local and cloud-metadata destinations (`169.254.0.0/16`, `fe80::/10`, `fd00:ec2::254`, `100.100.100.200`), do not follow redirects; notes residual DNS-rebinding window — [snyk/agent-scan README](https://github.com/snyk/agent-scan)
- v0.5.x issue codes for MCP: **E001** prompt injection in tool description (critical, tool poisoning); **E002** cross-server tool reference / tool shadowing (high: "a tool from one MCP server references a tool belonging to a different server"); toxic-flow components **W015/W016** untrusted content (high/low confidence), **W017** sensitive private data (emails, DMs, financial, credential vaults), **W018** workspace data, **W019** destructive capabilities (shell exec, live browser, shared SaaS mutation, financial tx), **W020** local destructive; **W021** hidden Unicode (Cf/Cc categories, zero-width, bidi overrides, Unicode Tag chars U+E0000–E007F, which it decodes and surfaces; escalates to high with ≥3 distinct hidden char types or a decoded tag message). Skill codes: E004–E006, W007 (insecure credential handling), W008 (hardcoded secrets), W009, W011–W014. Snyk explicitly does not flag internet-egress capability separately "as most agents include network access tools (such as curl) by default" — [docs/issue-codes.md](https://github.com/snyk/agent-scan/blob/main/docs/issue-codes.md)
- v0.6+ risk indicators (score 0–1000; emitted levels 100/300/600/1000): MCP `prompt_injection_tool_desc`, `untrusted_content`, `private_data`, `destructive_capabilities`; skills: `prompt_injection_skill_instructions`, `suspicious_download_url`, `malicious_code`, `insecure_credential_handling`, `secret_detection`, `direct_money_access`, `third_party_content_exposure`, `unverifiable_dependencies`, `modifying_system_services`, `missing_skill_md` — [docs/risks.md](https://github.com/snyk/agent-scan/blob/main/docs/risks.md)
- Toxic flow definition: a data-leak flow needs an untrusted-content tool + private-data tool + public sink (Willison's "lethal trifecta") — [docs/issue-codes.md](https://github.com/snyk/agent-scan/blob/main/docs/issue-codes.md)
- Rug pull: earlier mcp-scan reported **W003 "Entity has changed"** (tool description changed since last scan; hashes stored in `~/.mcp-scan`) — [appsecsanta (secondary)](https://appsecsanta.com/mcp-scan). UNVERIFIED for current versions: the current v0.5.x issue-code doc no longer lists W003, although the CLI still has a `--storage-file` (default `~/.mcp-scan`) "to store scan state" — [snyk/agent-scan README](https://github.com/snyk/agent-scan)

**Cisco AI Defense MCP Scanner (open source, Apache-2.0)**
- Announced Oct 23, 2025 (open-sourced ~2025-09-24 per landscape listing); targets tool poisoning, rug pulls, over-privileged tools; three engines usable together or independently: **YARA rules**, **LLM-as-judge**, **Cisco AI Defense inspect API**; blog gives no accuracy numbers — [Cisco blog](https://blogs.cisco.com/ai/securing-the-ai-agent-supply-chain-with-ciscos-open-source-mcp-scanner); [landscape listing (secondary)](https://landscape.jimmysong.io/projects/mcp-scanner/)
- Additional analyzers in current README: **Readiness** (20 heuristic rules, no API keys), **Prompt Defense** ("pure regex — no API key", always on; checks descriptions/system prompts for *missing* defenses against 12 vectors: instruction override, data leakage, role escape, indirect injection, output weaponization, output manipulation, multilingual bypass, Unicode/homoglyph, context overflow, social engineering, input validation, abuse prevention), **Behavioral code scanning** (LLM-powered alignment check of docstring claims vs implementation + cross-file dataflow; Python/TS/Go/Java/Kotlin), **VirusTotal** hash lookups of bundled binaries, **PyPI/npm package scan** in Docker sandbox, **static/offline mode** scanning pre-generated `tools/list` JSON for CI/air-gapped use; scans server `instructions` from `InitializeResult`; maps findings to Cisco AI Threat taxonomy (AITech/AISubtech codes) — [cisco-ai-defense/mcp-scanner README](https://github.com/cisco-ai-defense/mcp-scanner)
- Readiness heuristics (HEUR-001..020): missing timeout; timeout >5 min; no retry limit; >10 or unlimited retries; no backoff; missing error schema / error code field; **missing output schema**; **vague or missing description**; **overloaded tool scope (>5 verbs or "any/all/everything")**; no required fields in input schema; no validation hints (pattern/enum); no rate limit; missing version; no observability; resource cleanup undocumented; no idempotency indication; **dangerous operation keywords (delete, drop, exec, eval)**; no auth context; circular self-reference. Score 0–100 with deductions CRITICAL −25, HIGH −15, MEDIUM −8, LOW −3, INFO −1; "production ready" = score ≥70 and no CRITICAL — [readiness-scanning.md](https://github.com/cisco-ai-defense/mcp-scanner/blob/main/docs/readiness-scanning.md)
- Example YARA rule names that fired in a practitioner audit: `coercive_injection_generic` (matched "You MUST call this function first"), `script_injection_in_description` (matched `<script>` mentions), `pii_exfiltration_tool_poisoning` (matched the word "name") — [AppSecSanta audit (secondary, blog)](https://appsecsanta.com/research/mcp-server-security-audit-2026)

**Trail of Bits mcp-context-protector (open source)**

**Docker MCP Catalog (agentic auditing)**

**Guidance frameworks**
- OWASP MCP Top 10 (2025 edition, Phase 3 beta; lead Vandana Verma Sehgal): MCP01 Token Mismanagement & Secret Exposure; MCP02 Privilege Escalation via Scope Creep; MCP03 Tool Poisoning; MCP04 Supply Chain & Dependency Tampering; MCP05 Command Injection & Execution; MCP06 Prompt Injection via Contextual Payloads; MCP07 Insufficient AuthN/AuthZ; MCP08 Lack of Audit & Telemetry; MCP09 Shadow MCP Servers; MCP10 Context Injection & Over-Sharing — [OWASP project page](https://owasp.org/www-project-mcp-top-10/)

**Evidence of effectiveness (independent)**
- "Rethinking MCP Security" (arXiv 2607.11086, Jul 13, 2026, Fudan-affiliated authors per author list): MCPZoo of 64,611 unique servers (37,288 dynamically analyzable); 8 scanners (static/dynamic/hybrid, names not on abstract page); 96.89% of servers flagged by ≥1 scanner, none flagged by all; average precision 45.53% (range 10.4% to >70%); best scanner found 74.29% of known-CVE servers, several high-precision scanners found none; pairwise Jaccard 15.66% overall, <6% for prompt injection, command execution, data leakage; 28.3% code-derived duplicates; 37.66% of tools high-risk — [arXiv](https://arxiv.org/abs/2607.11086); [EmergentMind summary (secondary)](https://www.emergentmind.com/papers/2607.11086)
- FlowGuard (arXiv 2607.14754): argues scanners reason on semantic signals not execution behavior; reports F1 0.879 (command injection) and 0.942 (file-system access) on 1,880 executable cases — [arXiv](https://arxiv.org/abs/2607.14754) (from search snippet; not fetched)
- AppSecSanta practitioner audit (Apr–Jun 2026; Cisco mcp-scanner v4.3.0, mcp-scan v0.4.3, mcp-audit v0.14.1; 33 local servers, 433 tools): Cisco produced 27 pattern detections, 6 genuine (~78% "false positive" incl. designed functionality); FP sources: coercive-language rule on normal tool-ordering instructions, `<script>` mention, the word "name", linters flagged for code execution, browser tools flagged for system manipulation — [AppSecSanta (blog, small n)](https://appsecsanta.com/research/mcp-server-security-audit-2026)

### Inferences
- The patterns most consistently flagged in descriptions are: instruction-to-model language (`<IMPORTANT>`, "ignore previous", "do not tell the user", "MUST call X first"), references to sensitive paths (`~/.ssh`, `mcp.json`, `.env`, `*.pem`), extra "sidecar" parameters used as exfil channels, references to other servers' tools (shadowing), and invisible characters (zero-width, bidi, Unicode Tags, ANSI escapes). Of these, Unicode/ANSI detection and cross-server name references are fully deterministic; imperative-language and sensitive-path rules are regex-able but generate many false positives on legitimate "call X first" instructions.
- Because scanners agree so little (Jaccard ~16%), any scale evaluation should report per-check signals separately rather than a single "secure/insecure" verdict, and should calibrate rule severities against a hand-labelled sample.
- Capability classification (untrusted content / private data / destructive / egress) is the basis for toxic-flow analysis; Snyk does it with an LLM/API, but a first approximation is possible from MCP annotations (`readOnlyHint`, `destructiveHint`, `openWorldHint`) plus keyword heuristics (Cisco HEUR-018 style).

## Q2. Conformance / quality testing: Inspector, official conformance suites, protocol checks, registry validation, Cloudflare readiness

### Takeaway
There is now an official, automatable conformance harness (`@modelcontextprotocol/conformance`) that connects to a live server URL, runs scenarios per spec revision (2025-11-25 stateful vs 2026-07-28 stateless), validates every JSON-RPC message against the spec JSON schema, and backs SDK tiering. The official registry validates namespace ownership (GitHub OAuth / DNS TXT / HTTP well-known) and package ownership via cheap metadata markers. MCP Inspector's CLI mode is the standard scriptable smoke test. Cloudflare's April 2026 agent-readiness scanner checks website discovery surfaces (including MCP server cards), not server security.

### Cited Findings
- **MCP Conformance Test Framework**: `npx @modelcontextprotocol/conformance server --url http://localhost:3000/mcp` connects as a client, sends test requests, runs checks; outputs `checks.json`; suites `active/all/draft/pending`; `--spec-version` (e.g., `2025-11-25`, `2026-07-28`); `--requirements <revision>` runs exactly what a frozen spec revision requires; **wire-schema checks** validate every message the implementation sends against the spec JSON schema (`wire-schema-valid`); `tier-check --repo <owner/repo> --conformance-server-url ... --requirements 2025-11-25,2026-07-28` (all must pass for SDK Tier 1); revisions through 2025-11-25 use stateful initialize handshake, 2026-07-28 is stateless with per-request `_meta`; `--expected-failures` YAML baselines — [modelcontextprotocol/conformance README](https://github.com/modelcontextprotocol/conformance)
- **MCP Inspector CLI**: `npx @modelcontextprotocol/inspector --cli <cmd> --method tools/list`; supports stdio, `--transport http`, `--config/--server`; `--tool-name`/`--tool-arg` for tool calls; exit codes usable in CI — [official CLI docs](https://modelcontextprotocol.io/docs/2026-07-28/tools/inspector/cli.md); [mcpservers.org guide (secondary)](https://blog.mcpservers.org/posts/mcp-inspector-guide)
- **Official MCP Registry namespace verification**: GitHub OAuth (`io.github.<user|org>/*`, org requires Owner role), DNS TXT record with public key at apex (`com.example.*/*`), or HTTP file at `/.well-known/mcp-registry-auth`; Ed25519/ECDSA P-384 keys — [registry docs: authentication](https://github.com/modelcontextprotocol/registry/blob/main/docs/modelcontextprotocol-io/authentication.mdx)
- **Official MCP Registry package ownership validation**: npm `package.json` `mcpName` MUST match `server.json` name; PyPI and NuGet README must contain `mcp-name: $SERVER_NAME` (may be in an HTML comment); Cargo same but visible text (crates.io strips comments); OCI images need annotation/label `io.modelcontextprotocol.server.name`; MCPB packages need URL containing "mcp" and a `fileSha256`, which the registry does **not** validate (clients do) — [registry docs: package types](https://github.com/modelcontextprotocol/registry/blob/main/docs/modelcontextprotocol-io/package-types.mdx)
- **Cloudflare "Is Your Site Agent-Ready?"**: launched ~Apr 18, 2026; checks robots.txt, MCP, OAuth, agent protocols — 16 checks in 5 categories; integrated into Cloudflare Radar and URL Scanner API; itself exposed as an MCP server — [Product Hunt (secondary)](https://www.producthunt.com/products/is-your-site-agent-ready/launches/is-your-site-agent-ready-by-cloudflare); [Search Engine Journal (secondary)](https://www.searchenginejournal.com/all-you-need-to-know-about-cloudflares-agent-readiness-score/)
- isitagentready.com's MCP Server Card skill: card at `/.well-known/mcp/server-card.json` with `serverInfo` name/version, transport endpoint, capabilities; validated via POST `/api/scan`, check `checks.discovery.mcpServerCard.status == pass`; cites SEP-1649 — [isitagentready skill](https://isitagentready.com/.well-known/agent-skills/mcp-server-card/SKILL.md). CONFLICT: a Cloudflare Radar "Heimdall" survey page describes probing `/.well-known/mcp.json` with a 0–5 score, and Lumar docs say the card format is draft; another listing cites SEP-2127 — [Heimdall](https://heimdall.testing.chambers.cfdata.org/); [Lumar](https://agentic-readiness.lumar.io/docs/capabilities/mcp-server)
- Cisco Readiness analyzer (see Q1) is the closest open-source "quality lint" for tool definitions (output schema, required fields, validation hints, version, overloaded scope) — [readiness-scanning.md](https://github.com/cisco-ai-defense/mcp-scanner/blob/main/docs/readiness-scanning.md)

### Inferences
- The conformance suite requires a running server URL (HTTP). For stdio-only packages at scale, one must build/launch in a sandbox first (as Glama does in Firecracker); this is the expensive part, not the checks themselves.
- Registry metadata checks (`mcpName`, `mcp-name:` marker, OCI label, namespace) are free, deterministic, and work without running the server; they are strong provenance/"is-this-registered-correctly" signals.

- Exact list of conformance scenarios (e.g., which server checks exist under `server-*`) not enumerated; would require `conformance list`.
- No evidence found on what fraction of public servers pass the conformance suite.
- Cloudflare's own blog post was not reached; details are secondary.

## Q3. Registry quality scores: Glama, Smithery, mcp.so, PulseMCP, MCP Market, Docker, official registry

### Takeaway
Glama is the only registry with a fully published, reimplementable scoring spec (TDQS, open source): deterministic context signals and hard gates + one cheap LLM rubric call per tool + an LLM coherence call per server, aggregated as 0.7 × (0.6·mean + 0.4·min TDQS) + 0.3 × coherence with A–F tiers. Glama also shows license and maintenance grades and runs sandboxed builds with syscall/network observation. Smithery's quality score, PulseMCP's popularity estimates, and mcp.so / MCP Market have no published formulas I could find. Docker relies on commit pinning, signing and LLM code review; the official registry does ownership validation, not quality scoring.

### Cited Findings
- **Glama TDQS** (spec published with blog post dated 2026-04-03): inputs exactly the `tools/list` fields (`name`, `title`, `description`, `inputSchema`, `outputSchema`, `annotations`) plus sibling tool names. Pipeline: (1) deterministic context signals (paramCount, required count, params with descriptions/enums, `schemaDescriptionCoverage`, nested objects, schema depth, union choices, invocation cost, hasOutputSchema, hasAnnotations, `titleIsMeaningful`, `definitionBytes`, `inputHash`); (2) hard gates: missing description → TDQS 1.0 + `No Description` flag (no LLM call); tautological description (equals name/title) → Purpose Clarity capped at 2; (3) one LLM call scoring six dimensions 1–5: Purpose Clarity 25%, Usage Guidelines 20%, Behavioral Transparency 20%, Parameter Semantics 15%, Conciseness & Structure 10%, Contextual Completeness 10%, plus `annotation_contradiction` boolean; (4) deterministic post-processing, "smells" = any dimension <3 — [glama-ai/tool-definition-quality-score](https://github.com/glama-ai/tool-definition-quality-score); [Glama blog 2026-04-03](https://glama.ai/blog/2026-04-03-tool-definition-quality-score-tdqs)
- Server rollup: `descriptionQualityScore = round1(0.6×mean(TDQS) + 0.4×min(TDQS))` computed only when ≥80% of tools scored; coherence = separate LLM call over all tool names/descriptions, 4 equal dimensions (Disambiguation, Naming Consistency, Tool Count Appropriateness — "typically 3–15" ideal, 50+ extreme, Completeness — CRUD/lifecycle coverage); `overall = round1(0.7×description + 0.3×coherence)`; tiers A ≥3.5, B ≥3.0 (passing), C ≥2.0, D ≥1.0, F <1.0; server flag `Shadowing Risk` from deterministic prefilter (dearer tool cost ≥2× cheaper and gap ≥4) + LLM confirmation, reported beside score — [TDQS spec](https://github.com/glama-ai/tool-definition-quality-score)
- Scale and cost: as of June 2026, 228,369 tools across 15,036 servers scored (99% coverage; 362,226 definitions incl. superseded); mean TDQS 3.57, 73.5% pass tier B; dimension means: Behavioral Transparency 2.90 (46.1% smell), Usage Guidelines 3.03 (44.5% smell); 1.26% of tools lack descriptions, 0.55% contradict annotations, 0.06% tautological; mean server overall 3.56. Re-scoring only when `inputHash` changes (sweep every 5 min); uses "a fast, inexpensive model behind an OpenAI-compatible API" — [TDQS spec](https://github.com/glama-ai/tool-definition-quality-score)
- Glama indexing methodology: builds run in Firecracker microVMs from an AI-inferred Dockerfile; if build fails, "distribution is withheld" and server hidden from search; tools captured via live introspection (`tools/list`); open-source servers observed at syscall and network layers in sandbox; findings classed **Malicious** (internal review, possible delisting) or **Risky** (shown publicly); "over one million" scans in past twelve months — [glama.ai/mcp/methodology](https://glama.ai/mcp/methodology)
- Glama listing grades also include "license", "quality", "maintenance" (e.g., "Activity: Inactive", "Responsiveness: No issues") — [Glama server score page](https://glama.ai/mcp/servers/druce/MCP/score). Security grade described as "checks for known vulnerabilities in the server or its dependencies" and license as "permissive open source license" — [goose blog (secondary, Mar 2025)](https://goose-docs.ai/blog/2025/03/26/mcp-security). UNVERIFIED: claim that servers without a LICENSE file cannot be installed on Glama (search snippet only).
- Motivating literature cited by TDQS: "MCP Tool Descriptions Are Smelly!" (arXiv 2602.14878): 856 tools / 103 servers, 97% have ≥1 defect, 56% unclear purpose; "From Docs to Descriptions" (arXiv 2602.18914): 10,831 servers, well-described tools selected ~260% more often, rewriting descriptions improves task success ~6 pp — [TDQS spec](https://github.com/glama-ai/tool-definition-quality-score) (figures as quoted there; papers not fetched)

- **Docker MCP Catalog**: "known publisher" vs community icon; commit pinning; cosign signatures; Claude Code + Codex audit — [Docker blog](https://www.docker.com/blog/enhancing-mcp-trust-with-the-docker-mcp-catalog/)
- **Official MCP Registry**: namespace + package ownership validation only (see Q2); no quality score found.
- Cross-market duplication: >90% overlap across markets; 28.3% code-derived duplicates — [arXiv 2607.11086 summary (secondary)](https://www.emergentmind.com/papers/2607.11086)

### Inferences
- Glama's design choices (min-term to penalise a single bad tool, hard gates before any LLM call, input-hash caching, annotation-relative grading) are directly reusable; the deterministic parts (no description, tautology, schema description coverage, annotations present/contradicting, output schema present, tool count band) can be computed with zero LLM calls.
- Popularity signals (PulseMCP visitors, downloads) are patchy and should not be treated as quality.

### Gaps
- mcp.so and MCP Market: no scoring methodology found.
- Smithery: no primary documentation of its quality score located.
- Glama security and license grade formulas: not published on the methodology page.

## Q4. Which checks are cheap, rule-based, and applicable at scale (tens of thousands of servers) without credentials or LLM calls?

### Takeaway
A large share of industry checks are deterministic and need only static metadata (repo, package manifest, `server.json`) or one unauthenticated `tools/list` capture. The expensive parts are launching stdio servers in sandboxes and any LLM judgment (prompt-injection intent, toxic-flow classification, TDQS rubric, code/docstring alignment, Docker-style agentic audit).

### Cited Findings (the specific deterministic checks, with where they are used)
- Hidden Unicode (Cf/Cc categories, zero-width, bidi, Unicode Tag U+E0000–E007F decode) — Snyk W021 — [issue-codes.md](https://github.com/snyk/agent-scan/blob/main/docs/issue-codes.md); ANSI escape sanitization — [mcp-context-protector](https://github.com/trailofbits/mcp-context-protector)
- Rug-pull / change detection by hashing tool definitions across captures (TOFU pinning) — [Invariant blog](https://invariantlabs.ai/blog/mcp-security-notification-tool-poisoning-attacks); [Trail of Bits](https://blog.trailofbits.com/2025/04/21/jumping-the-line-how-mcp-servers-can-attack-you-before-you-ever-use-them/); Glama's `inputHash` re-score-on-change — [TDQS spec](https://github.com/glama-ai/tool-definition-quality-score)
- Cross-server tool name references (shadowing): match descriptions against tool names of other servers in the corpus — Snyk E002 — [issue-codes.md](https://github.com/snyk/agent-scan/blob/main/docs/issue-codes.md)
- Regex/YARA signatures (coercive/instruction language, `<script>`, PII-exfil wording; Prompt Defense regex, "no API key") — [Cisco README](https://github.com/cisco-ai-defense/mcp-scanner); noisy per [AppSecSanta](https://appsecsanta.com/research/mcp-server-security-audit-2026)
- Readiness heuristics HEUR-001..020 with 0–100 deduction score, "no API keys" — [Cisco readiness doc](https://github.com/cisco-ai-defense/mcp-scanner/blob/main/docs/readiness-scanning.md)
- TDQS hard gates and context signals (missing/tautological description, schema description coverage, enums, output schema, annotations, tool count) — [TDQS spec](https://github.com/glama-ai/tool-definition-quality-score)
- Secrets detection (hardcoded API keys/private keys) — Snyk W008/`secret_detection` — [risks.md](https://github.com/snyk/agent-scan/blob/main/docs/risks.md)
- Malware hash lookups on bundled binaries (VirusTotal; free tier 4 req/min, 500/day — rate-limited at scale) — [Cisco README](https://github.com/cisco-ai-defense/mcp-scanner)
- Registry/provenance markers: `mcpName`, `mcp-name:`, OCI `io.modelcontextprotocol.server.name`, namespace verification, `fileSha256`; Docker `source.commit` pin + `org.opencontainers.image.revision` — [registry package types](https://github.com/modelcontextprotocol/registry/blob/main/docs/modelcontextprotocol-io/package-types.mdx); [Docker blog](https://www.docker.com/blog/enhancing-mcp-trust-with-the-docker-mcp-catalog/)
- Conformance + wire-schema validation (deterministic, but needs a running server; no LLM) — [conformance README](https://github.com/modelcontextprotocol/conformance)
- Remote-server/OAuth metadata SSRF checks: flag `resource_metadata`/`authorization_servers`/endpoint URLs pointing to private/link-local/loopback ranges or non-HTTPS, dangerous URL schemes, wildcard scopes in `scopes_supported` — [MCP security best practices](https://modelcontextprotocol.io/docs/tutorials/security/security_best_practices)
- License presence/permissiveness and maintenance activity (Glama grades) — [Glama score page](https://glama.ai/mcp/servers/druce/MCP/score)

### Inferences
- Tiering for scale (my synthesis):
  - Tier 0, no execution, no LLM (cheapest, all servers): repo/package metadata (license, last commit, archived flag, registry markers, commit pinning, declared transport), static secrets regex on repo, dependency CVE lookup, typosquat name similarity vs known packages.
  - Tier 1, one `tools/list` capture (remote servers without auth, or stdio in a sandbox): Unicode/ANSI detection, regex/YARA injection signatures, sensitive path mentions, cross-server name references, schema-quality signals (TDQS gates, Cisco HEUR rules), annotation presence and keyword-vs-annotation contradictions (e.g., "delete" in name but `readOnlyHint: true`), definition hashing for rug-pull diffing over time, capability classification from annotations + keywords for toxic-flow approximations.
  - Tier 2, live protocol: conformance suite + wire-schema validation; OAuth metadata SSRF inspection for remote servers.
  - Tier 3, expensive: LLM rubric (TDQS ~1 cheap call/tool), LLM injection judges, behavioral code analysis, sandbox syscall/network monitoring, agentic code audits.
- Given ~45% average scanner precision and ~16% inter-scanner agreement, regex signals should be weighted low and reported as "signals requiring review", with Unicode-tag/ANSI, cross-server references and description changes as the higher-precision deterministic signals (inference; no published precision per rule found).

### Gaps
- No published per-rule precision/recall for any deterministic check (e.g., how often Unicode-tag findings are malicious vs incidental).
- Dynamic-launch success rates bound coverage: only 19.6% of projects achieved complete native deployment in MCPZoo, which limits Tier 1/2 coverage for stdio servers — [EmergentMind summary of arXiv 2607.11086 (secondary)](https://www.emergentmind.com/papers/2607.11086)
