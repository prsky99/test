# Practitioner Habits for Efficient Claude Code Sessions (community advice and sentiment, 2025-2026)

Research date: 2026-10-20. Source note: reddit.com was blocked for both search and fetch in this environment, so no Reddit threads were read directly. The community signal below comes mainly from Hacker News (comment threads read in full or in large part), Substack/personal blogs, Korean blogs/GeekNews, and trade press that reports on Reddit/GitHub complaints. Weigh "many people say X" claims with that limit in mind.

## 1. Session hygiene: /clear frequency, manual vs auto-compact, "context rot"

### Takeaway
The near-universal habit is "/clear (or a new session) whenever the task changes; /compact only to continue the same task." Experienced users increasingly avoid letting auto-compact fire. Instead they compact or hand off by hand at roughly 50-65% of the window, because compaction is lossy and quality drops quietly ("context rot", the "dumb zone").

### Cited Findings
- Anthropic's own blog (the subject of a 319-point / 185-comment HN thread, Aug 2026) recommends: run /clear between tasks, set model and effort *before* starting (changing mid-conversation can bust the prompt cache), and compact before breaks, since the prompt cache expires after about an hour and summarizing is cheaper while the context is still cached — [Claude blog: Maximizing the value of your Claude Code sessions](https://claude.com/blog/maximizing-the-value-of-your-claude-code-sessions); [HN discussion, 319 pts](https://news.ycombinator.com/item?id=49300800)
- In that HN thread, the top comment (superasn) says a homemade `/handoff` skill (short summary of context plus next steps, then a fresh session with `/continue`), run "every 20 messages or so," is "much more useful than /compact or /clear." kxrm instead saves key points as memories and then runs /clear. mikeocool says /clear and starting a new session are effectively the same, and atsaloli notes that older versions leaked memory, so restarting was safer — [HN 49300800](https://news.ycombinator.com/item?id=49300800)
- Substack authors Wyndo & Dheeraj Sharma (June 28, 2026) advise /clear when the task changes ("Compact helps you continue. Clear helps you stop carrying the old thing."). They compact at about 60-70% of the window, not at the forced limit, with explicit keep/drop instructions. Keep: goal, success criteria, decisions, changed files, open tasks, exact next action. Drop: discarded ideas, verbose logs, old drafts — [AI Maker: What Actually Helps Me Stop Hitting Claude Code Usage Limits](https://aimaker.substack.com/p/claude-code-usage-limits-token-saving)
- Nathan Onn ("Never Let Claude Code Auto-Compact Again," May 1, 2026) gives heuristic "context zones": green 0-30%, yellow 30-50% (watch for task boundaries), orange 50-60% (finish the micro-task, then compact or hand off), red >60% (reset before new features or research). With 1M-context Opus he treats 15-20% as the practical reset band, and he cites Nate Herk's "reset around 120k tokens." His concrete failure: compaction dropped a "no parallel sub-agents" rule, Claude then spawned ten agents, and his 5-hour budget was gone. He also notes that path-scoped rules and nested CLAUDE.md files don't come back after compaction until their files are read again. He warns against interrupting a working implementation just because a threshold was crossed — [nathanonn.com](https://www.nathanonn.com/claude-code-never-auto-compact/)
- Vincent van Deth (VNX toolkit, says he has 3,000+ hours in Claude Code; updates in June and Oct 2026) lists context-rot symptoms: re-reading files it already read, contradicting its own earlier decisions, rewriting code it already wrote, all while the output "still looks polished." He first rotated sessions at 65% and now calls 65% "already late," experimenting with 55-60% for complex tasks. His early ledger data says rotating at 60-65% gives better handovers and faster resumption than rotating at 75% or later. All of this is anecdotal, with no formal benchmark — [vincentvandeth.nl](https://vincentvandeth.nl/blog/context-rot-claude-code-automatic-rotation)
- A Towards Data Science piece on context rot (not fetchable, 403; the search snippet only) says the agent's confidence stays high while output degrades. It recommends writing a handoff brief at healthy boundaries and having the next session check ground truth (files, tests, git status) — [TDS: Context Rot](https://towardsdatascience.com/governed-context-managing-context-rot-in-claude-code/) (snippet only)
- Disagreement on whether auto-compact should stay on: one guide turns it off to control the timing, while another recommends leaving it on as a fallback — summarized in [knightli.com](https://knightli.com/en/2026/04/19/claude-code-usage-context-compact-notes/) / [agenticcoding.substack tip 7](https://agenticcoding.substack.com/i/180970862/tip-7-proactively-compact-your-context) (search-summary level)
- Cost nuance raised on HN after Anthropic's April 2026 quality postmortem (942 pts / 732 comments): tedivm and others note that /compact can cost *more* than a cold cache, because compacting means reloading the whole context. doubleunplussed suggests compacting *before* cache eviction. winternewt proposed auto-compacting before context is dropped, and bcherny (Boris Cherny) replied "This is what we're trying next." — [HN 47878905](https://news.ycombinator.com/item?id=47878905)
- That postmortem's cause was itself a session-hygiene feature. On Mar 26, 2026, Claude Code began clearing older thinking from sessions idle for over an hour, and a bug made it clear on every turn until a fix on Apr 10 (it affected Sonnet 4.6 and Opus 4.6). Boris explained on HN that resuming an idle session causes a full cache miss, which "can use a large share of rate limits, especially on Pro." — [HN 47878905](https://news.ycombinator.com/item?id=47878905)
- Korean guide (heropy.dev, written "as of Oct 2026"): with a 1M window, auto-compact triggers around 967k tokens, and it can be pulled earlier with `/autocompact 300k` or `CLAUDE_AUTOCOMPACT_PCT_OVERRIDE` (e.g., 70). The guide also recommends resuming a long (>100k), idle (>1h) session in summarized form to save cost, using `/btw` for side questions, and using `/rewind` to back out of a wrong direction instead of arguing forward — [heropy.dev](https://www.heropy.dev/p/ODra43) (single source; the specific command names and numbers were not cross-verified)

### Inferences
- Thresholds people report cluster around 50-70% of the window (and much lower, roughly 120-200k tokens, on 1M windows). That convergence comes from independent practitioners, but every number is personal heuristic, not measurement.
- Since the cache TTL (about 5 minutes on API, about 1 hour on subscriptions per HN commenters) dominates cost, "compact or clear *before* a break" is gaining ground over "compact when full."

### Gaps
- No Reddit-native data (upvote counts, poll results) on how often people /clear, because reddit.com was inaccessible.
- No controlled measurement of quality loss after compaction. All degradation evidence is anecdotal.

## 2. Handoff patterns (HANDOFF.md / PLAN.md / progress files)

### Takeaway
Writing a structured handoff markdown file and resuming in a fresh session is the single most-repeated "power user" pattern on HN and blogs in 2026. It is often packaged as a `/handoff` or `/checkpoint` slash command or skill, and often committed to git. Fixed-section templates beat free-form summaries.

### Cited Findings
- HN user sillysaurusx (in the "Universal Claude.md" thread, roughly spring 2026) built a `/handoff` command. When a session nears compaction or has served its purpose, it "generates and commits a markdown file explaining everything it did or talked about" to `docs/agents/handoff/YYYY-MM-DD-NNN-topic.md`. A line in CLAUDE.md tells future sessions to read these files. He calls them a "permanent record of compacted sessions" and a daily report for his manager, and says the idea came from Anthropic's docs describing a "handoff file" pattern — [HN 47581897](https://news.ycombinator.com/item?id=47581897)
- Variants in replies: flashgordon's `/checkpoint` updates the architecture and workflow docs plus CLAUDE.md and then commits. dominotw keeps a running `task/{name}.md` per task. creamyhorror has Claude "write a summary handoff md" into a planning folder. tstrimple stores planned work as issues in a local Forgejo and indexes session JSONL files into a database. chermi is considering converting sessions to markdown for a RAG knowledge base — [HN 47581897](https://news.ycombinator.com/item?id=47581897)
- In the Aug 2026 HN thread, bombcar commits every handoff to git so it's easy to see what the agent did. dboreham avoids built-in mechanisms and has the model write documents so the work stays portable across tools. superasn and sjanes use handoffs to move work to ChatGPT/Codex when Claude limits hit. pixelsort uses numbered "docsets" (STRATEGY, PLAN, PROGRESS) — [HN 49300800](https://news.ycombinator.com/item?id=49300800)
- Nathan Onn's HANDOFF.md template should be complete enough that "a fresh Claude Code session can continue without reading this chat." Its sections: Goal, Current branch/state, Files changed, Decisions made, Commands run, What failed, What remains, Exact next step. His workflow: have Claude write it, review it, then either `/compact` with a focused instruction or `/clear` and read the file. "Rehydration" means re-reading PLAN.md and HANDOFF.md, checking `git diff --stat`, confirming goal and next step, and continuing from the pending task rather than from memory — [nathanonn.com](https://www.nathanonn.com/claude-code-never-auto-compact/)
- van Deth automates the handoff. A PreToolUse hook blocks the agent at the threshold and orders it to write `ROTATION-HANDOVER.md`, a PostToolUse hook detects the file, a script sends `/clear` via tmux, and a SessionStart hook injects the handover if it is under 300 seconds old. File structure: Dispatch-ID, context %, Completed Work, Remaining Tasks, Next Steps (with concrete PIDs and ports). He found free-form summaries written under context pressure "unreliable," so the Oct 2026 version validates the handover against a fixed schema — [vincentvandeth.nl](https://vincentvandeth.nl/blog/context-rot-claude-code-automatic-rotation)
- Disagreements: CBLT cited an argument that plan files aren't token-efficient, because the worker re-reads the source files anyway. hombre_fatal says plans should hold general ideas and invariants, not implementation detail. A commenter in another thread says a handoff file is effectively what Anthropic does under the hood with compaction. Another says Matt Pocock's "handoff" skill is useful, but staying in the session, /clear, a subagent, or /compact covers the ordinary end-of-phase case — [HN 49300800](https://news.ycombinator.com/item?id=49300800); search summary of [HN 49222824](https://news.ycombinator.com/item?id=49222824)
- skybrian and mlrtime want the harness to write handoffs automatically (when the cache is about to expire, or via hooks). fg137 suggests auto-compacting after idle time — [HN 49300800](https://news.ycombinator.com/item?id=49300800); [HN 47581897](https://news.ycombinator.com/item?id=47581897)

### Inferences
- The consensus template has about six fields (goal / state / changed files / decisions / failures / exact next step), and people strongly prefer that it be committed to the repo. For multi-week projects, the dated-file approach (one file per session, indexed from CLAUDE.md) gives both a resume point and an audit trail.
- Handoffs are also used as a *limit-arbitrage* tool, to carry work over to another vendor when the Claude quota runs out.

### Gaps
- No source quantified the token savings of handoff-then-clear versus /compact.

## 3. Task decomposition: one task per session, subagents, parallel sessions/worktrees

### Takeaway
Practitioners use subagents mainly to *protect the main context*: exploration, log analysis, and review run in a disposable context, and only the result returns. Parallel sessions in git worktrees are the norm among heavy users (Boris Cherny runs 5 local plus 5-10 web sessions). But parallelism multiplies quota burn, and people report a practical ceiling of about 3-5 sessions.

### Cited Findings
- Boris Cherny's workflow (via a Substack recap of his widely shared X thread): 5 local Claude Code instances in numbered terminal tabs with system notifications, plus 5-10 web sessions on claude.ai/code. Most sessions start in Plan mode (Shift+Tab twice), and he iterates on the plan, then switches to auto-accept, and Claude "can usually one-shot the PR." His subagents include Code Simplifier and Verify App. The recap's line: "Subagents are really about protecting context." He also hands sessions between local and web ("teleport") and starts sessions from the iOS app — [Push to Prod Substack](https://getpushtoprod.substack.com/p/how-the-creator-of-claude-code-actually) (secondary; original X thread not fetched)
- HN practitioners: subscribed plans with Opus, then opens a *new* session with an orchestrator running one implementer and one tester, and says it "uses much less tokens" and needs fewer corrections. ls612 writes a plan, then spawns an Opus subagent told to follow it strictly and report deviations. AlfeG runs code review in a separate session so earlier context doesn't bias it — [HN 49300800](https://news.ycombinator.com/item?id=49300800)
- Korean guide: delegate "read-heavy but not worth keeping" work (such as analyzing thousands of lines of logs) to a subagent so that only the result enters main context, and set `model: haiku` in the subagent definition for cheap runs — [heropy.dev](https://www.heropy.dev/p/ODra43)
- One practitioner says 3-5 parallel sessions is the sweet spot, because coordination and review costs grow beyond that — [codingwithroby Substack](https://codingwithroby.substack.com/p/git-worktrees-are-the-future-parallel). Another guide says a single session is faster when a change touches fewer than about 5 files — [morphllm](https://www.morphllm.com/run-claude-code-parallel). Another warns that spawning many agents easily leads developers to stop reading diffs — [Cobus Greyling](https://cobusgreyling.substack.com/p/claude-code-agent-view)
- Counter-signal: Anthropic's support docs state that running multiple Claude Code instances in parallel hits limits sooner — [Anthropic support: Max plan usage](https://support.anthropic.com/en/articles/11014257-about-claude-max-usage). Nathan Onn's runaway "ten sub-agents" incident burned a full 5-hour budget — [nathanonn.com](https://www.nathanonn.com/claude-code-never-auto-compact/)

### Inferences
- Subagents *save main-context tokens* but don't necessarily save *quota*: each subagent re-reads files in its own context. Users on Pro and lower Max tiers should use them for isolation and cheap-model offload (Haiku), not as a default for everything.
- Boris's workflow assumes an employee-scale budget. Individual subscribers who copy "5+5-10 parallel sessions" are a likely source of limit complaints.

### Gaps
- No quantitative comparison of quota burn with versus without subagents for the same task.

## 4. Prompting habits that waste or save tokens

### Takeaway
The repeated savers: name exact files (or @-mention them) instead of letting Claude search, keep noisy command and test output out of context (quiet flags, `| head`/`grep`, or a subagent), keep CLAUDE.md short and route to other docs, and audit fixed overhead with `/context` and `/usage`. Generic "be terse" CLAUDE.md rule packs are popular but contested.

### Cited Findings
- Anthropic's blog: @-mention files to skip a read/search step, keep command output lean (quiet flags or subagents), and run `/context` in a fresh session to audit startup load (CLAUDE.md, MCP tool definitions) — [Claude blog](https://claude.com/blog/maximizing-the-value-of-your-claude-code-sessions)
- HN pushback: BeetleB warns that @-mentioning a large file may read the whole file. zmmmmm asks how the cache holds up when Claude keeps editing the attached file — [HN 49300800](https://news.ycombinator.com/item?id=49300800)
- Wyndo & Sharma: point Claude at the exact file, folder, or section; keep CLAUDE.md lean and have it *route* to supporting files instead of containing everything; check which files Claude opens at task start to test that routing; use `/context` and `/usage` to diagnose. They found an automated WordPress workflow eating a large share of usage that they wouldn't have spotted otherwise — [AI Maker](https://aimaker.substack.com/p/claude-code-usage-limits-token-saving)
- Boris Cherny's team keeps a shared, git-tracked CLAUDE.md and adds a line whenever Claude makes a mistake. Secondary write-ups put its size at about 2.5k tokens, and his personal file is about two lines pointing to the shared one — [Push to Prod](https://getpushtoprod.substack.com/p/how-the-creator-of-claude-code-actually); size figure from search summary of [whyaiman / medium recaps](https://whyaiman.substack.com/p/tips-for-working-with-claude-code)
- Size targets vary by source: official guidance is reportedly under 200 lines. A Korean guide says 50-100 lines for Korean text, or under 2,000 tokens — [heropy.dev](https://www.heropy.dev/p/ODra43). Firecrawl/Metana say under 500 tokens — [firecrawl blog](https://www.firecrawl.dev/blog/claude-code-token-efficiency)
- Output handling (Korean guide, Oct 2026): Bash outputs over 30,000 chars are saved to a file and only about 2,000 chars enter the conversation, configurable via `bashOutputMaxChars`. Long *passing* test output doesn't trip that limit, so put quiet-test flags in CLAUDE.md. The guide also says output tokens cost about 5x input — [heropy.dev](https://www.heropy.dev/p/ODra43) (single source)
- Other common tips: a `.claudeignore` for generated directories, piping noisy output through `grep`/`head`, narrowing searches to a directory, and `npx ccusage@latest` for daily token tracking — [knightli.com](https://knightli.com/en/2026/04/19/claude-code-usage-context-compact-notes/) (search-summary level)
- "Universal Claude.md" (claude-token-efficient repo) claims about 63% output-token savings from anti-verbosity and anti-sycophancy rules. HN critics (as summarized by GeekNews) said the benchmark was biased toward a single descriptive task and asked whether verbose explanations help keep long agentic sessions coherent. A Korean wikidocs blog argues it is better to target your actual failure modes than to paste a generic rule set — [GeekNews summary](https://news.hada.io/topic?id=28077); [wikidocs critique](https://wikidocs.net/blog/@jaehong/10406/)
- Token-saving plugins ("Caveman," "RTK") are contested on HN. guessmyname calls them "useless," ed_mercer replies "If it can save 10% of tokens, how is that useless?", and gavmor says the indirection hurt his agent more than the savings helped — [HN 49300800](https://news.ycombinator.com/item?id=49300800)
- The Korean guide adds that the skill list is sent every turn whether or not skills are used, so set `disable-model-invocation: true` on manual-only skills — [heropy.dev](https://www.heropy.dev/p/ODra43)

### Inferences
- The habits with the strongest consensus are the boring ones: name the file, trim output, keep CLAUDE.md short. Compression gimmicks (terse-output rule packs, token plugins) have weak and disputed evidence.

### Gaps
- No independent measurement of @-mention versus letting Claude grep on real codebases.
- The `bashOutputMaxChars` and skill-list overhead details come from a single Korean source and weren't verified against docs.

## 5. Model choice, effort, and stretching Pro/Max limits; web/cloud vs local

### Takeaway
Community advice for subscribers on a budget: "plan with Opus, execute with Sonnet, offload trivia to Haiku" (or `opusplan`), and fix model and effort at session start to avoid cache busts. Power users at Anthropic (Boris) use Opus for everything, arguing that less steering saves time. Sentiment about limits is strongly negative in 2026 ("token anxiety"), shaped by bugs, limit changes, and cache-miss surprises.

### Cited Findings
- Model routing: Haiku for classification, extraction, formatting, and simple commits; Sonnet for most execution; Opus for planning and hard reasoning; "plan with Opus, then execute with Sonnet if Opus usage is a concern" — [AI Maker](https://aimaker.substack.com/p/claude-code-usage-limits-token-saving). The Korean guide adds that `/model opusplan` switches automatically (Opus plans, Sonnet implements), that the default effort is medium, which can be dropped to low for simple work, and that `/fast` costs 2x so should be used sparingly. It names current models (Opus 5.5 at about 2x Sonnet 5.5's price) and an `/advisor` mode — [heropy.dev](https://www.heropy.dev/p/ODra43) (single source for /advisor and pricing ratios)
- Opposite view: Boris Cherny uses "Opus with thinking for everything," because it needs less steering and is better at tool use, so it's faster overall — [Push to Prod](https://getpushtoprod.substack.com/p/how-the-creator-of-claude-code-actually)
- Effort and cache: HN users discovered that changing effort level changes the cache prefix. janalsncm attributes this to a hidden system-prompt line about the reasoning budget. Cache TTL is disputed: moebrowne cites docs saying 1 hour for subscriptions and 5 minutes for API, while swingboy says the $20 plan shows 5 minutes — [HN 49300800](https://news.ycombinator.com/item?id=49300800)
- Cache surprises: apt-apt-apt-apt reports about 2M cache writes in some sessions. Phemist argues vendors may have weak incentives to fix cache-busting — [HN 49300800](https://news.ycombinator.com/item?id=49300800)
- Complaints and sentiment: in the April 2026 postmortem thread (942 pts), jimkleiber dislikes per-token awareness, adam_patarino replies "Token anxiety is real mental overhead," and Folcon says Pro users hit quota, wait more than 2 hours, then one message eats 20%+ of the session quota. bede would "rather pay tokens than have sessions rot silently." Several users want visible cache timers in the UI — [HN 47878905](https://news.ycombinator.com/item?id=47878905). In the Aug 2026 thread, PeterStuer says one full review used about 3x his 5-hour budget on a 100€ plan, while a 20€ GPT plan never hit limits. mccoyb calls the tips post a way to shift cost management onto users, and DangitBobby counters that both sides want fewer tokens per task — [HN 49300800](https://news.ycombinator.com/item?id=49300800)
- Timeline of limit events (trade press): since March 2026, Max subscribers reported quota exhaustion in as little as 19 minutes, Anthropic acknowledged it was investigating, and some users downgraded Claude Code versions as a workaround — [devops.com](https://devops.com/claude-code-quota-limits-usage-problems/) (search summary; page 403). Anthropic doubled 5-hour limits on May 6, 2026. A weekly-limit counter bug on June 19 affected about 3% of Max/Pro users, whose limits were reset. Weekly Claude Code capacity was announced to drop 17% on Sept 14, 2026, with users described as "checking usage every 30 minutes and rationing their week" — [pasqualepillitteri.it](https://pasqualepillitteri.it/en/news/5428/claude-code-weekly-usage-limit-bug-3-percent); [implicator.ai](https://www.implicator.ai/anthropic-claude-code-weekly-limits-september-14.md) (search-summary level; not independently verified)
- Pooling: Pro/Max limits are shared between Claude chat and Claude Code, and /clear doesn't restore allowance or reset the 5-hour timer — [Anthropic support](https://support.anthropic.com/en/articles/11014257-about-claude-max-usage); [fast.inference.net guide](https://fast.inference.net/guides/claude-usage)
- Limit arbitrage: several HN users (superasn, sjanes) write a handoff and continue in ChatGPT/Codex when Claude limits hit. A Korean brunch post suggests doing design work in other tools, since each tool has its own limits — [HN 49300800](https://news.ycombinator.com/item?id=49300800); [brunch @lukas08](https://brunch.co.kr/@lukas08/203)
- Cloud sessions: Claude Code cloud sessions reportedly reached GA on Sept 23, 2026, with one-time trial credits ($100 Pro / $250 Max) — [SmartScope](https://smartscope.blog/en/blog/claude-code-cloud-sessions-credit-2026/) (secondary). Boris routinely runs 5-10 web sessions and teleports between web and local — [Push to Prod](https://getpushtoprod.substack.com/p/how-the-creator-of-claude-code-actually)
- Usage tooling: a GeekNews-featured local tool shows real-time token usage and predicts limit overruns, built because sessions kept stopping mid-run at the limit — [GeekNews](https://news.hada.io/topic?id=21560)

### Inferences
- The "Opus for everything" (Anthropic insiders) versus "Opus only for planning" (subscribers) split is really about budget, not quality, and the report should frame it that way.
- Resuming long, idle sessions is a hidden quota sink (a full cache miss on a big context). "Compact or hand off before you walk away" is the practical counter.

### Gaps
- No first-hand practitioner reports found on how cloud/web sessions are metered against plan limits versus local CLI, or whether habits differ there (beyond Boris's usage). Official metering docs for cloud sessions weren't located.
- Couldn't verify the Sept 14 weekly-cap reduction or the class-action mention.

## 6. Common mistakes people regret

### Takeaway
The regrets that come up most: very long single sessions that end in context rot and redo work, letting auto-compact silently drop rules, loading many MCP servers (tens of thousands of tokens before the first prompt), runaway parallel or subagent fan-out, resuming stale sessions (a cache miss), and unnoticed automated or background workflows draining quota.

### Cited Findings
- Long sessions: in the "dumb zone," the model sifts through stale logs and abandoned attempts every turn, and over-long sessions produce work that has to be redone — [nathanonn.com](https://www.nathanonn.com/claude-code-never-auto-compact/). Re-reading files and contradicting its own earlier decisions while the output looks polished — [vincentvandeth.nl](https://vincentvandeth.nl/blog/context-rot-claude-code-automatic-rotation)
- Compaction losing rules leads to a runaway sub-agent fan-out (ten agents) and a burned 5-hour budget — [nathanonn.com](https://www.nathanonn.com/claude-code-never-auto-compact/)
- MCP overhead: each connected server injects its full tool schemas every turn. Reported figures include 15,540 tokens for 84 tools, over 15k for a single Jira-style server, and 66k+ (33% of 200k) at startup, and "three servers ≈ 6-15k tokens before your first prompt" — [mindstudio](https://www.mindstudio.ai/blog/claude-code-mcp-server-token-overhead); [dev.to](https://dev.to/alvarito1983/the-mcp-servers-actually-worth-installing-in-claude-code-2026published-43lb); [claudelog FAQ](https://claudelog.com/faqs/do-mcp-servers-use-claude-code-context/) (mostly vendor/blog sources; numbers loose). Practitioners advise disabling unused connectors (Canva, Notion, PayPal, etc.) and preferring CLI-plus-skill wrappers that load only when called — [AI Maker](https://aimaker.substack.com/p/claude-code-usage-limits-token-saving); "CLI tools like gh/aws beat MCP for context efficiency" — [heropy.dev](https://www.heropy.dev/p/ODra43)
- Hidden automation draining quota: an automated WordPress workflow consumed a large share of usage, found only via `/usage` — [AI Maker](https://aimaker.substack.com/p/claude-code-usage-limits-token-saving)
- Resuming idle sessions: a full cache miss "can use a large share of rate limits, especially on Pro" (Boris Cherny) — [HN 47878905](https://news.ycombinator.com/item?id=47878905)
- Parallel instances hit limits sooner (official) — [Anthropic support](https://support.anthropic.com/en/articles/11014257-about-claude-max-usage)
- Huge or generic CLAUDE.md: it loads into every session and every turn, so routing to topic files is preferred over stuffing — [AI Maker](https://aimaker.substack.com/p/claude-code-usage-limits-token-saving); [heropy.dev](https://www.heropy.dev/p/ODra43)

### Inferences
- Background polling loops (e.g., `/loop`, watchers that re-prompt Claude) fit the "hidden automation" pattern above, but I found no first-person postmortem specifically about polling loops.

### Gaps
- First-person "I regret X" posts are mostly on Reddit/X, which were inaccessible. The MCP-overhead numbers come mostly from vendors selling gateways. Whether newer Claude Code versions defer MCP tool loading (tool search), which would reduce this cost, wasn't verified in this research.
