## 1. 완료의 정의 (모든 팀)

- **"완료" = 개발 브랜치(`claude/hopeful-darwin-i3qj6n`)에 들어간 sha.** 브랜치·worktree에만 있는 것은 "준비됨"이다. 보고에는 sha와 `git merge-base --is-ancestor <sha> origin/<개발 브랜치>` 결과를 붙인다.
- 승인받은 변경은 **승인받은 그 턴에** 개발 브랜치에 올린다(푸시 규칙은 그대로: fetch → origin..HEAD 확인 → 확인한 sha).
- 시험 결과는 "파일 수, passed, skipped, failed"를 함께 적는다. skipped가 있으면 이유를 한 줄로 적는다.
- 시각은 같은 턴 직전 `date` 값만 쓴다. 안 봤으면 시각을 쓰지 않는다.

## 2. PM 승인은 예외만

PM에 묻지 않고 진행하고 결과만 보고하는 것(시험 통과 + 1절 지키기):
- 시험만 바꾸는 커밋, 문서·보고서, 자기 팀 소유 파일의 결함 수정(시험 동반), 디자인 시스템 안의 화면 수정, 오프라인 초안.

PM 결정이 필요한 것(이것만 묻는다):
- 정책 해시 파일, `gate_rules.py`, `member_terms.json` 판정 방향, 운영 DB, launchd·예약 작업, 배포 시각·역할 범위, 다른 팀 소유 파일, 공개 문구의 숫자·주장, 돈·외부 게시·계정(사용자 확인).

결정은 한 번만 한다. PM은 결정을 `logs/ops/decisions.jsonl`에 한 줄로 남기고(시각·주제·결정·이유·대상 팀), 팀은 묻기 전에 그 파일을 먼저 본다. 같은 주제를 다시 묻지 않는다. 바꿀 때는 새 줄에 "대체: <이전 줄 시각>"을 쓴다.

## 3. 진행 중인 일은 팀마다 2개까지 (WIP)

- 팀마다 동시에 진행하는 과제는 2개까지다. 새 과제는 하나를 "완료"(1절)하거나 "막힘"으로 돌린 뒤 잡는다.
- 순서가 얽힌 일은 한 팀이 통째로 소유한다. 배포 묶음과 패키징은 운영·SRE, 관문 회차는 워크플로우, 약관 판정은 에이전트 팀이 맡는다.

## 4. 목걸이 생산 라인 (가장 중요한 변경)

목걸이는 아래 단계를 차례로 지난다. 단계마다 기계로 확인되는 조건만 쓴다.

1. **초안**(코덱스·워크플로우): 서로 다른 역할 자리 3개 이상, 실제 수요 근거 링크 1개, 과제 문장 3개, tuning 10건.
2. **후보**: 정의 검증 통과, 모든 필수 자리에 진주(final·verified)나 승인된 자체 대체 멤버, 약관 allowed·silent.
3. **미리보기 공개**(새로 넓힘, 품질 조건 포함):
   - 2단계 조건을 모두 충족한다.
   - 최근 24시간 tuning 실행 30건 중 27건 이상 통과하고, p95가 5초 이하다. holdout은 쓰지 않는다.
   - 감시(watch) 상태가 정상이다.
   - 화면에는 "Preview — test runs in progress"만 쓰고 숫자는 쓰지 않는다.
   - 72시간 안에 재시험이 없으면 자동으로 막힌다.
4. **정식 공개(live)**: 관문 통과(60건 중 57건, 회차마다 28/30, p95 5초) + delta>0. 기준은 그대로다.

라인 운영 규칙:
- **정답 세트 재고:** 관문 회차를 잡기 전에, 쓰지 않은 holdout 2세트(회차 2개분)가 파일로 있어야 한다(`ls`·줄 수·sha 확인). 정답은 장부 몫이 남는 밤에 미리 만든다. 원천 응답은 녹화해 두어(`fallback_cassettes` 방식), 몫이 바닥나도 판정을 다시 계산할 수 있게 한다. 녹화 응답을 정답 근거로 바꾸지는 않는다.
- **결과가 정해지면 멈춤:** 회차 중 실패가 기준을 넘어 탈락이 확정되면 남은 사례는 돌리지 않는다. 판정은 바뀌지 않고 원천 호출만 아낀다. 순차 판정(SPRT)은 검색과 RAG가 시뮬레이션을 검산한 뒤 PM이 정한다.
- **약한 멤버 먼저 바꿈:** 한 자리가 실패의 절반 이상을 내면, 다음 회차 전에 그 자리의 다음 진주나 대체로 바꾸고 tuning을 다시 돈다. 같은 멤버로 회차를 반복하지 않는다.
- **초안 컨베이어:** 워크플로우는 코덱스 초안을 하루 2개씩 채택·보류로 가리고, 채택한 것은 그날 후보 단계까지 올린다.

## 5. 통합과 배포

- 배포 묶기 전에 묶음 목록의 sha 전부를 cut의 조상인지 확인한다(`merge-base --is-ancestor`, 아니면 `git cherry`). 빠진 것이 있으면 cut 전에 알린다.
- 배포는 하루 두 번 정해진 차로 낸다. 정책 해시 배포는 하루 한 번이다. 시각은 시간대별 방문 자료(11-25 7일치)로 PM이 다시 정한다. 그 전까지는 그날 PM이 정한다.
- 한 팀의 묶음이 막혀도 다른 팀 묶음은 기다리지 않는다. 막힌 것만 다음 차로 넘긴다.

### 7-1. 목걸이 관문 = 연결 시험 3회 (사용자 결정 2026-11-18 19:3x, 7절의 60건 관문을 대체)

사용자: "테스트 통과 관문도 3회로 줄이고, 수집된 에이전트의 품질을 목걸이 개발 단계에서 하지마. … 목걸이 개발은 이미 확인된 진주이니 연결이 중요하고 연결되서 실행되게 하고 폴백과 자체 대체 에이전트가 잘 적용되어 목걸이 수명이 길게 적용되는 것이 중요함."

**목걸이에서 다시 하지 않는 것**
- 수집된 멤버(진주)의 답 품질 재채점
- holdout 60건 정답 대조와 57/60
- 정답 세트 재고 요구(목걸이용)

품질은 수집 등급, 시험 보고서 v2, 진주 85점에서 이미 확인했다.

**목걸이 관문에서 보는 것**(하루, 기계로 확인, 모두 통과해야 공개):
1. **연결 실행 3회:** 서로 다른 과제 입력 3개로 사슬 전체를 실제로 실행해 3회 모두 성공해야 한다.
   - 성공은 세 가지를 모두 뜻한다.
     - 모든 필수 자리가 계약 형식에 맞는 출력을 냈다.
     - 합성 답이 나왔다.
     - 전체가 예산 시간 안에 끝났다.
   - 답의 정확도를 채점하지는 않는다.
2. **폴백 적용:** 자리마다 대표 멤버를 일부러 빼고 한 번씩 실행한다. 외부 폴백 멤버가 대신 계약 형식 출력을 내야 한다.
3. **자체 대체 적용:** 자리마다 외부 멤버를 모두 빼고 한 번씩 실행한다. 승인된 자체 대체가 대신 출력을 내야 한다.
4. 약관 allowed·silent이고, 감시가 정상이다.

**목걸이가 오래 살게 하는 장치(공개 뒤 상시)**
- 감시(watch)가 멤버 실패를 보면 다음 진주나 폴백으로 자동 강등·교체한다.
- 자체 대체는 마지막 줄에 늘 붙어 있다.
- 매일 연결 실행 1회로 사슬이 살아 있는지 확인한다.
- 사슬이 끊기면 그 목걸이는 막히고(held), 고친 뒤 다시 연결 3회를 거친다.

**자체 대체 승인도 연결 시험 3회**(사용자 결정 2026-11-18 19:5x "연결 시험 3회로", 정답 대조 대체 관문을 대신함):
- 사슬 마지막 줄에 붙여 서로 다른 입력 3개(tuning이나 probe)로 실행한다. 3회 모두 계약 형식 출력을 예산 시간 안에 내면 승인한다. 승인은 운영·SRE가 approvals.json에 쓴다(두 열쇠 그대로).
- 정답 대조는 하지 않는다. 대체용 holdout도 만들지 않는다. 그래서 공개 문구는 자체 대체의 정확도를 주장하지 않는다("our own backup agent").
- 이미 revoked된 대체는 취소 사유를 고친 기록이 있어야 다시 연결 시험을 받는다.
- 정의 지문이 바뀌면 다시 연결 시험을 받는다(기존 지문 규칙).

**연결 시험 3회의 뜻(사용자 설명 2026-11-18 19:2x):**

사용자: "목걸이 연결을 단계별로 진행해서 전부 통과 실행이 확인되서 결과가 나온 상태에서, 다시 연결 테스트 3회를 했을 때 통과하면 공개."

순서는 다음과 같다.
1. **단계별 연결(개발):** 자리 하나씩 차례로 잇는다. 단계마다 그 자리까지 실제로 실행해 계약 형식 출력이 나오는지 확인하고 다음 자리로 간다. 마지막 자리까지 붙인 뒤 사슬 전체가 결과(합성 답)를 내는 것을 확인한다. 자리별 폴백 적용 확인도 이 단계에서 한다.
2. **연결 시험 3회(공개 관문):** 1단계가 모두 통과해 결과가 나온 상태에서, 사슬 전체를 서로 다른 입력으로 다시 3회 실행한다. 3회 모두 통과하면 공개한다. 한 번이라도 실패하면 원인 자리를 1단계로 돌려 고친 뒤 3회를 처음부터 다시 한다.
- 결과 파일에는 1단계 단계별 기록과 2단계 3회 기록을 모두 남긴다(`logs/ops/necklace-gate/connect/`).

**첫 공개에는 폴백만, 자체 대체는 공개 뒤 필요할 때**(사용자 결정 2026-11-18 19:5x, 위 2·3번 관문 항목을 이렇게 바꿈):

사용자: "목걸이에 연결되는 진주에 폴백 에이전트만 적용해서 공개하고, 자체 대체 에이전트는 공개 후에 폴백 에이전트 실행이 발생하면 그 백업으로 자체 대체 에이전트가 개발이 시작되는 것임. 목걸이 첫 공개에 자체 대체 에이전트를 적용하는 것이 아님. 목걸이 개발에 자체 대체 에이전트가 적용되어야 하는 경우는 제외됨."

- **첫 공개 관문:**
  - 연결 실행 3회
  - 자리마다 외부 폴백 적용 1회(대표 진주를 빼고 외부 폴백이 답함)
  - 약관과 감시
  - 자리마다 대표 진주 1개와 외부 폴백 1개 이상이 있어야 한다. 자체 대체 적용 실행(3번)은 첫 공개 조건에서 뺀다.
- **공개 뒤 자체 대체 개발 시작 조건:** 감시·실행 기록에서 어떤 자리의 폴백이 실제로 실행되면(대표가 실패하고 폴백이 답함), 그 역할의 자체 대체 개발 과제가 에이전트 팀에 자동으로 열린다. 완성되면 연결 시험 3회로 승인해 그 자리 마지막 줄에 붙인다.
- **예외(개발 단계부터 자체 대체):** 외부 폴백이 시장에 없는 역할(예: SEC registry·filings, 운세 계열)이나 자체 에이전트가 멤버인 목걸이다. 이런 자리는 자체 대체를 연결 시험 3회로 승인해 넣고 공개한다. 목걸이당 이런 자리 제한(1자리)은 두지 않는다. 대신 목걸이 전체에서 외부 진주가 2자리 이상이어야 한다.

**그대로인 것**
- 약관 판정, 홍보 숫자는 잰 값만 쓰는 원칙.

**공개 문구**
- About·방법론의 "57 of 60 runs pass, p95 5s"와 "two different days"는 새 관문 설명으로 고친다.
- 예: "connected end to end and run three times; every step has an outside fallback and our own backup agent".
- 규칙 변경과 같은 배포에서 고친다.
