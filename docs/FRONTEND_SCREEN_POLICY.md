# 프론트엔드 사용자 화면 정책 (2026-11-01, 사용자 결정)

공개 프론트(`new/en/*`)와 고객 워크스페이스(`/customer/*`)의 모든 사용자 화면에 적용한다. 새 화면을 만들거나 기존 화면을 고칠 때 이 규칙과 다른 방식(전체 화면 로딩, 접속 시 미리 불러오기 등)을 쓰지 않는다.

## 원칙
"화면은 바로 보이고, 기능은 사용자가 누를 때 동작한다." 사용자가 "이거 누르면 오래 걸릴까?" 걱정하게 만들지 않는다.

## 규칙
1. **고정 내용은 그냥 HTML/CSS다.**
   - 늘거나 바뀌지 않는 기본 내용(예: Test 화면 예시 5개, 그 연결 정보)은 페이지에 넣어 보낸다.
   - 접속할 때 서버·DB를 부르지 않는다.
   - 실행 가능 여부는 사용자가 실행을 누를 때 서버가 확인한다.
2. **화면 전체를 막지 않는다.**
   - 전체 화면 로딩 오버레이, 화면을 어둡게 덮는 막, 레이아웃을 숨기는 "준비될 때까지 대기"는 금지한다.
   - 화면 가운데의 작은 진행 표시(규칙 6)는 허용한다. 화면을 덮지 않고 클릭을 막지 않기 때문이다.
   - 메뉴, 머리글, 제목, 본문 틀은 첫 페인트에 보이고 바로 누를 수 있어야 한다.
3. **불러오는 것은 그 영역에만 표시한다.**
   - 데이터가 필요한 영역만 상태 문구, 작은 스피너, `aria-busy`로 표시한다.
   - 데이터가 끝나면 그 영역만 채운다. 다른 메뉴와 입력은 그동안에도 쓸 수 있다.
4. **사용자가 요청할 때만 불러온다.**
   - 선택 목록, 전체 카탈로그 같은 부가 데이터는 사용자가 그 영역을 열 때(클릭, 포커스, 펼치기) 요청한다.
   - 접속하자마자 미리 받지 않는다.
5. **서로 기다릴 필요 없는 요청은 동시에 보낸다.**
   - 세션 확인과 읽기 요청(GET)은 병렬로 보낸다.
   - 읽기는 쿠키로 인증되고, CSRF는 쓰기에만 필요하다.
   - 401이면 공통 처리기가 로그인으로 보낸다.
6. **진행 표시는 화면 가운데에 작게, 클릭을 막지 않게 한다.** (2026-11-01 사용자 결정: 가운데가 맞고, 오른쪽 위로 옮긴 것은 잘못이었다)
   - 사용자가 누른 동작의 진행은 누른 버튼의 `aria-busy` 스피너와 화면 가운데의 작은 표시(예: Explore의 "Finding agents…")로 보인다.
   - 가운데 표시는 내용 크기만 한 작은 상자다. 배경 막이 없고 `pointer-events:none`이다.
   - 백그라운드 읽기에는 표시하지 않는다.
7. **경과 시간을 보인다.**
   - 오래 걸리는 작업은 남은 시간 대신 경과 시간을 보인다.
   - 남은 시간 표시는 좌절감을 키운다(Tan & Nov, CHI 2026).
   - 표시가 전혀 없으면 더 길게 느낀다(같은 연구).

## 근거
- **응답 시간 한계(Nielsen, NN/g):**
  - 0.1초는 즉시로 느낀다.
  - 1초는 흐름이 유지된다.
  - 10초를 넘으면 주의가 떠난다.
  - 그래서 첫 화면은 0.1~1초 안에 보여야 하고, 데이터 대기는 그 뒤에 영역별로 처리한다.
- **Tan & Nov, "Counting the Wait", CHI 2026 (arXiv 2602.04138, n=425):**
  - 표시가 없으면 대기가 더 길고 모호하게 느껴진다.
  - 남은 시간 표시는 경과 시간 표시보다 좌절감이 컸다.
- **스켈레톤과 스피너 비교 실험(Viget, n=136):** 스켈레톤이 오히려 가장 길게 느껴졌다(2.82초, 스피너 2.41초, 빈 화면 2.29초). 그래서 화면 전체를 가짜 틀로 덮지 않는다. 실제 내용을 먼저 보이고, 필요한 영역에만 작은 표시를 둔다.
- **업계 지침(Stripe Apps loading 패턴, Next.js 구간별 loading, OpenReplay 정리):**
  - 고정 틀(메뉴, 머리글)은 즉시 그린다.
  - 로딩 경계는 영역 단위로 둔다.
  - 전체 화면 스피너는 모든 상호작용을 막는다.
- **Chrome Core Web Vitals:** 임계값을 지킨 사이트는 페이지 이탈이 약 24% 낮았다(Chrome 보고, 상관관계). INP 목표는 200ms 이하이고, 클릭 처리기에서는 최소한의 일만 한다(web.dev).

## 적용 현황 (11-01)
- **Test 화면**
  - 예시 5개와 연결 정보를 `new/en/test.html`의 `appBootstrapData`에 넣었다.
    - 접속 시 API 호출은 0회다(이전에는 presets, agents, explore 100을 차례로 불러 약 2.7초 걸렸다).
    - 서버가 페이지를 내보낼 때 frontend의 따뜻한 부트스트랩 캐시(홈 화면용으로 백그라운드에서 갱신됨)가 있으면 그 예시와 워크플로로 바꿔 넣는다(`pearl_view.current_fixed_content`). 그래서 손으로 다시 만들 필요가 없다. 요청 경로에서 DB를 읽지 않는다.
    - 캐시가 없을 때 쓰는 파일 속 값은 `python -m scripts.build_public_page_snapshots`로 다시 만든다.
  - 등록 에이전트 목록은 "Choose another agent"를 열 때 불러온다.
  - 페이지에 데이터가 없으면 예전 방식(서버 확인 후 다시 시도 버튼)으로 동작한다.
- **워크스페이스**
  - 전체 화면 게이트(`data-workspace-loading`이 레이아웃을 숨기던 것과 `#workspace-entry-progress`)를 없앴다.
  - 지금은 `#status` 줄에만 스피너가 붙는다.
  - 진행 표시를 오른쪽 위 배지로 옮겼으나, 사용자 결정(11-01)에 따라 화면 가운데의 작은 표시로 되돌린다.
  - 개요와 워크플로 화면은 세션 확인과 읽기를 동시에 보낸다.
- **회귀 시험**
  - `tests/test_front_first_entry_browser.py::test_fixed_examples_open_without_any_request`
  - `tests/test_workspace_entry_progress_browser.py::test_shell_shows_at_once_and_reads_run_beside_the_session_check`
  - `tests/test_workspace_entry_progress_browser.py::test_progress_sits_small_in_the_centre_for_clicks_and_hidden_for_background_and_errors`

- **Workflows 화면:** 공개 워크플로 25개를 `new/en/workflows.html`의 `appBootstrapData`에 넣었다. 템플릿 요청이 0회다.
- **Chat:** 결과 영역은 안쪽 스크롤 상자가 아니라 페이지와 함께 늘어난다.
  - 이전에는 300~520px 고정에 `overscroll-behavior:contain`이 걸려 결과 아래쪽이 보이지 않았다.
- **워크스페이스 Provider connections 메뉴:** 패널을 모달이 아니라 본문에 표시한다.
  - 이전에는 열자마자 모달이 화면 전체를 덮었다.
- **숨은 내용 감사:** `tests/data/screen_hidden_audit.js`와 `tests/test_screen_hidden_content_browser.py`
  - 공개 9개 화면, 결과가 있는 Chat, 워크스페이스 6개 화면을 1440px과 390px에서 검사한다.
  - 모든 화면에서 0건이어야 통과한다.

## 새 화면 점검표
- [ ] 스크롤로 닿지 않는 내용, 다른 요소에 가려진 버튼, 안쪽 고정 높이 스크롤 상자가 없는가(감사 시험에 화면 추가)
- [ ] 접속할 때 이 화면이 부르는 API 목록을 적고, 고정 내용이면 HTML로 옮겼는가
- [ ] 메뉴와 제목이 첫 페인트에 보이는가(데이터 요청을 막아 두고 시험)
- [ ] 로딩 표시가 해당 영역에만 있는가(전체 오버레이, 배경 막이 없는가)
- [ ] 누른 동작의 진행 표시가 화면 가운데에 작게 뜨고 클릭을 막지 않는가
- [ ] 부가 목록은 사용자가 열 때 요청하는가
- [ ] 서로 독립인 요청을 병렬로 보내는가
