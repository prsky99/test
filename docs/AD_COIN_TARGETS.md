# AI AD Coin 그랜드 오픈 기준: 보안 → 품질 → 속도

- 기준일: 2026-11-05. 사용자 결정 우선순위: **보안 > 품질 > 속도.**
- **품질:** 100%가 아니면 그랜드 오픈을 하지 않는다.
- **속도:** 화면은 3초 안에 보여야 하고, 내부 처리는 세계 최고 수준을 목표로 한다.

## 1. 근거로 쓴 자료

| 주제 | 근거 | 이 문서에서 쓴 방식 |
|---|---|---|
| 실시간 광고 판단 시간 | OpenRTB `tmax`는 네트워크를 포함한 입찰 대기 한도다. Google Authorized Buyers는 형식에 따라 80~1,000ms를 준다. 업계에서는 경매 전체를 약 80~120ms로 본다(2차 출처). 일부 거래소는 p99 10ms 미만을 내세운다(자기 신고) | 후원 판단은 네트워크를 뺀 내부 처리로 100ms 예산의 절반(50ms) 안에 끝낸다. 도전 목표는 자기 신고 최고치와 같은 10ms다 |
| 원장 처리량·지연 | TigerBeetle은 초당 10만~50만 건, P100 100ms를 내세운다(자기 신고). SoftwareMill 독립 비교에서 고정 5천 rps일 때 PostgreSQL 행 잠금 방식의 p99는 약 960ms, 핫 계정에서는 약 2.1초였다 | 단일 PostgreSQL 노드로 위 PostgreSQL 기준선보다 훨씬 낮은 꼬리 지연을 목표로 한다. 처리량은 운영 예상치의 10배 이상을 보장한다 |
| 꼬리 지연 | Dean·Barroso, "The Tail at Scale"(CACM 2013): 팬아웃에서는 p99가 사용자 경험을 정한다 | 평균이 아니라 p99·최대값으로 판정한다 |
| 측정 착시 | Gil Tene의 coordinated omission: 닫힌 루프 부하기는 멈춘 구간을 빼 먹는다. 해결책은 일정 도착률(open-loop)이다(k6 arrival-rate, wrk2) | 부하기는 일정 도착률로 요청을 보낸다. 지연은 "예정 시각"부터 잰다. 보내지 못한 요청도 실패로 센다 |
| 가상 데이터 | 운영과 데이터 크기·분포가 다르면 시험이 의미가 없다(100행 대 1천만 행, 균등 대 Zipf). 운영 원격 측정에서 도착률을 끌어낸다(Grafana k6) | 실제 카탈로그 가격 분포와 실측 Explore 응답을 쓴다. 사용자·광고주 행동은 Zipf 분포로 만든다. 고유 데이터는 최대 동시 사용자의 10배 이상을 준비한다 |
| 사용자 행동 | 보상형 광고 수락률 40~70%, 완료율 85~95% 이상(업계 2차 출처, 방향성) | 가상 사용자 모형: 수락 55%, 15초 완료 92%, 확인 답 정답 80% |
| 보안 기준 | OWASP ASVS 5.0.0(2025-05), OWASP API Security Top 10(객체 수준 권한 BOLA 등) | 보안 시험은 권한(객체·기능), 인증·세션·CSRF, 입력 주입, 금액 위변조, 재전송, 경쟁 조건, 속도 제한을 모두 다룬다 |
| 화면 | Core Web Vitals: LCP 2.5초, INP 200ms, CLS 0.1(75번째 백분위) | 프로젝트 정책 "3초 안에 화면 노출"을 LCP 2.5초 이하로 더 엄하게 적용한다 |

## 2. 그랜드 오픈 관문

### 2.1 보안(1순위): 하나라도 실패하면 오픈하지 않는다

| 영역 | 통과 조건 |
|---|---|
| 객체 수준 권한(BOLA) | 다른 사람의 지갑·실행권·실행·위임장·영수증·캠페인·보고서를 읽거나 바꾸는 시도는 모두 거부한다. 광고주 A는 광고주 B의 어떤 것도 보지 못한다 |
| 기능 수준 권한 | 관리자 API는 관리자 토큰만, 광고주 API는 그 광고주의 구성원 역할(소유자·편집자·보기)대로만 쓸 수 있다 |
| 인증·세션 | 쿠키 쓰기에는 CSRF가 있어야 한다. 교차 출처 요청은 거부한다. 에이전트 키는 해시로 저장하고, 철회하거나 초대를 거두면 즉시 멈춘다 |
| 금액 위변조 | 음수·소수·10원 단위가 아닌 금액, 범위를 넘는 금액, 다른 사람 계정은 모두 거부한다. 모든 분개 합계는 0이고 청구 계정은 음수가 되지 않는다 |
| 재전송·중복 | 같은 멱등 키·동의·노출·실행 기록·오퍼 토큰은 한 번만 반영한다 |
| 경쟁 조건 | 동시에 쏟아지는 노출·이전·결제에도 잔액이 음수가 되지 않는다. 이중 지급과 이중 차감이 0건이어야 한다 |
| 주입 | 광고 소재·메모·이름에 섞인 프롬프트 주입, 자기 보증, 지갑 요구, 숨은 문자, 마크업은 결정론으로 거부한다. SQL은 항상 매개변수로만 넘긴다 |
| 서명 | 영수증·견적·오퍼를 위조하거나 한 글자만 바꿔도 검증에 실패한다 |
| 정보 노출 | 오류 응답에 내부 경로·SQL·키가 나오지 않는다. 비공개 워크플로의 입력·출력·이름이 응답에 나오지 않는다 |

### 2.2 품질(2순위): 100%

- 모든 시험이 통과해야 한다(건너뜀 제외 0건 실패).
- 리허설 전 단계에서 재원 불변식 위반 0, 불균형 분개 0, 음수 청구 0이어야 한다. 의도하지 않은 회로 열림도 0이어야 한다.
- 오류 응답 비율 0%(의도한 거부 응답은 제외)이고, 보내지 못한 요청도 0이어야 한다.
- 월간 후원 감사에서 "바뀜"이 0건이어야 한다.

### 2.3 속도(3순위)

내부 처리 시간은 서버가 요청을 받아 응답을 만들 때까지의 시간이다. 네트워크와 TLS는 뺀다. 단일 운영 노드(PostgreSQL 18)에서 p99로 판정한다.

| 경로 | 관문(오픈 조건) p99 | 도전(세계 1위 목표) p99 |
|---|---|---|
| 업그레이드 확인(읽기) | 20ms | 5ms |
| 후원 견적(경매+예산 잠금 쓰기) | 50ms | 10ms |
| 동의·노출 보상·실행권 사용(원장 쓰기) | 50ms | 15ms |
| 지갑 이전·코인 결제 | 50ms | 15ms |
| 실행 기록 정산 | 200ms | 50ms |
| 광고주 콘솔 읽기(목록·보고서) | 200ms | 50ms |

- **처리량:** 운영 예상 최대치의 10배를 1% 미만의 p99 악화로 버틴다. 단일 노드 기준 관문은 원장 쓰기 초당 200건 이상, 도전은 초당 1,000건 이상이다.
- **화면:** 첫 화면 LCP 2.5초 이하(75번째 백분위), 버튼 반응 INP 200ms 이하. 프로젝트 정책은 3초다.

## 3. 리허설 단계

| 단계 | 규모 | 목적 |
|---|---|---|
| 0. 연기 시험 | 사용자 10, 광고주 3 | 전체 흐름이 끝까지 돈다 |
| 1. 소량 | 사용자 1천, 광고주 20, 캠페인 100 | 기능·정합성 |
| 2. 중량 | 사용자 1만, 광고주 200, 캠페인 1천 | 경합·예산 소진·빈도 상한 |
| 3. 대용량 | 사용자 10만, 광고주 1천, 캠페인 5천, 노출 수십만 건 | 처리량·꼬리 지연·데이터 크기 |
| 4. 극한 | 관문 처리량의 2~5배 순간 폭주 | 무너지는 지점과 그때의 행동(거부·대기, 잔액 보존) |

- **실행 환경:** 격리된 PostgreSQL 18 임시 클러스터를 쓰고, 운영 DB에는 접속하지 않는다.
- **부하 관리:** 운영 맥에서 돌리므로 `nice -n 10`을 쓰고, 동시 실행 수에 상한을 둔다. 운영 서비스 지연이 늘지 않는지 함께 본다.

## 4. 알려진 한계

- 단일 맥의 결과는 운영 하드웨어와 같다. 다만 운영 트래픽이 함께 도는 중이라 절대치에는 오차가 있다. 측정 때마다 부하(load average)를 기록한다.
- 도전 목표의 "세계 1위"는 공개된 자기 신고 수치와 비교한 것이다. 독립 감사를 받은 순위는 아니다.
