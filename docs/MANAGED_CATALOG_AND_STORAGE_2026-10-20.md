# 로컬 에이전트 관리와 저장소 개선 — 2026-10-20

## 적용 기준

제공자 목록은 발견과 중복 수집 방지를 위한 정보다. 해당 목록에서 사라졌다는 이유로 내부 에이전트를 비활성화하거나 벡터를 삭제하지 않는다.

- `registry_missing_since`: 완결된 제공자 목록에서 보이지 않기 시작한 시점. 재등장 시 해제한다.
- `managed_at`: 우리 시스템의 실제 헬스 체크가 기록된 시점. 기존 자료에는 `last_check_at`을 이관했다. 성공을 만들어 넣은 값이 아니다.
- `active`, `health_status`: 운영자 조작과 자체 점검 결과가 관리한다. 운영자 중지는 `inactive_reason=operator`로 보존하고 수집으로 자동 해제하지 않는다.
- 자체 장기 연결 실패에 따른 `retired` 및 보안 격리는 계속 유효하다. 외부 목록의 누락과 구분한다.
- 주소가 실제로 달라지면 새 주소의 과거 정상 상태를 주장하지 않고 다시 점검한다.

전체 목록의 페이지 한도 소진, 잘못된 응답, 빈 중간 페이지, 반복 커서는 완료로 간주하지 않는다. x402/A2A의 짧은 증분 수집은 다음 위치를 기억해 목록 앞부분만 반복하지 않는다. MCP 변경 목록은 원래 기준 시각과 커서를 끝까지 유지한다.

## 어드민 지연의 실제 원인과 수정

1. 세션 인증마다 전역 쓰기 잠금을 얻고 있었다. 현재 세션/권한은 계속 확인하되 일반 인증 조회는 별도 읽기 연결에서 처리한다. 구형 토큰의 최초 해시 전환만 쓰기를 사용한다.
2. 상태 변경 시 약 49만 벡터 작업 이력을 전체 검색하고 있었다. `legacy_vector_jobs(resource_id,status)` 인덱스를 추가해 해당 에이전트의 작업만 찾는다. 운영 DB에는 이 인덱스를 이미 적용했다.
3. 목록 정렬과 개요 집계가 큰 에이전트 레코드를 반복 읽었다. 이름/최근 순서, 출처, 평가, 보안, 점검, 은퇴 상태 및 ERC 상태 집계용 인덱스를 추가했다. 사용 가이드 개수는 부분 인덱스로 별도 집계한다.
4. SQLite 벡터 가상 테이블을 통계 조인에서 반복 탐색했다. 벡터 ID를 한 번 조회하는 비상관 `IN` 하위 조회로 바꾸었다. 벡터의 실제 존재, 세대, 작업 상태, 모델, 활성/격리 조건을 유지했다.
5. PostgreSQL에서는 최대 3개의 별도 읽기 세션을 지연 생성한다. 운영 쓰기 연결의 Python 잠금과 분리하고 DB 세션 자체도 읽기 전용으로 강제한다.

### 캐시 정책

- 브라우저 탭 메모리에서 허용된 목록/집계 GET만 보관한다. 인증·자격증명·보안·개인 상세 조회는 대상이 아니다.
- 10초 이내 결과는 즉시 재사용한다. 안전한 갱신 콜백이 있는 목록은 최대 60초 이내 결과를 표시하고 조용히 갱신한다.
- 최대 48개/8 MiB, 항목당 1 MiB로 제한한다. 같은 요청은 하나로 합친다.
- 계정 변경 및 정상 완료된 쓰기 후 폐기한다. 이전 계정 응답과 오래된 필터 응답은 새 화면을 덮어쓰지 못한다.
- 개요 서버 캐시는 5초, 갱신 중 이전 결과 사용은 최대 30초다. 매 HTTP 요청의 인증은 캐시 조회 전에 실행한다. 변경 작업 전후 무효화한다.
- 수동 새로고침은 브라우저와 서버 캐시를 우회한다. HTTP 브라우저 캐시와 공유 캐시는 사용하지 않는다.

읽기 전용 실데이터 사본에서 초기 개요 조회는 약 **61.23초 → 5.40초**, 캐시 조회는 **3–4 ms**였다. 이름순 50개 목록 API는 **약 24 ms**, 해당 정렬 SQL은 **약 1.9 ms**였다. 같은 하드웨어의 개별 측정이며 운영 부하 SLA나 p95는 아니다. 최초 통계 조회는 여전히 반복 캐시 조회보다 느리다.

## 저장소 결정과 완료된 이전 검증

**주 저장소는 전용 PostgreSQL 18, 벡터 검색은 같은 DB의 pgvector HNSW로 전환하는 방향으로 결정했다.** 현재 다른 프로젝트가 사용하는 PostgreSQL 14를 재사용하지 않았다. SQLite의 단일 쓰기 경합과 큰 레코드 반복 조회를 계속 늘리는 방식은 장기 대안으로 삼지 않는다.

프로젝트 전용 PostgreSQL **18.6**, pgvector **0.8.2**를 구성했다. 외부 TCP 수신을 끄고 소유자 전용 Unix 소켓과 peer 인증을 사용한다. 앱 계정에는 슈퍼유저·다른 DB 생성·역할 생성 권한을 부여하지 않았다. 사용자 재시작 후 운영 설정은 SQLite로 유지되며 관리 정책과 어드민 최적화가 반영되었다.

온라인 백업으로 만든 일관된 사본을 스트리밍 COPY로 이전했다. **228개 논리 테이블, 총 10,260,344행**, 헬스 체크 **7,812,740행**, 에이전트 **123,385행**이 포함된다. 복사와 전체 행 검증은 약 **317초**였다. 테이블별 건수와 키가 있는 다중집합 해시, ID 시퀀스를 확인했다. 실패한 시도는 전체 대상 트랜잭션을 롤백했다.

기존 작은 이전 프로파일의 행/메모리 한도를 무작정 해제하지 않았다. 명시적인 오프라인 대량 프로파일에서만 서버 커서, 스트리밍 COPY, 일정 메모리의 키 기반 다중집합 검증을 쓴다. 테이블 2천만 행/전체 4천만 행/32 GiB/6시간 제한이 있다. 타입·스키마·서명·소유권·복구 펜스는 유지한다.

검증 중 발견한 자료 형식 문제도 처리했다.

- 보고서 날짜가 숫자와 ISO 문자열로 섞여 있었다. 오프셋을 보존해 epoch 초로 변환한다. 과거 SQLite CURRENT_TIMESTAMP는 기존 정리 도구와 동일하게 UTC로 해석한다. 새 보고서는 시간대 없는 문자열을 거부한다.
- 제공자 설명문과 FTS 설명문 일부에 NUL 문자가 있었다. PostgreSQL에서 표현할 수 없는 해당 문자만 제거한다. 다른 본문·키·서명 필드는 임의로 정규화하지 않는다. 원래 값은 원본 SQLite 사본에 보존된다. 새 수집의 이름·설명에서도 NUL을 제거한다.

### 벡터 검색

79,480개의 출판 증거가 있는 벡터를 `vector(768)` cosine HNSW로 구축했다. 기본 `m=16`, `ef_construction=64`, 검색 `ef_search=200`, 후보 최대 100개다. 검색 전용 projection은 원본 벡터 바이트와 출판 증거를 대체하지 않는다.

새 벡터의 바이트/증거/HNSW 반영은 같은 트랜잭션에 속한다. 검색 후보는 기존 세대·출처·모델·벡터 해시와 최신 활성/격리 조건을 다시 통과해야 한다. 오래된 projection은 후보 검증에서 배제하고 작업 주기마다 최대 1,000개씩 정리한다. ANN은 근사 검색이며 결과 개수가 줄 수 있다. 별도 벡터 서비스는 초기 운영 구성에 추가하지 않았다.

실제 사본에서 HNSW 인덱스 사용을 확인했다. 100개 후보 조회는 첫 측정 약 245 ms, 후속 측정 약 4–6 ms였다. 공급자 호출이나 모델 추론 시간은 포함하지 않는다.

## 운영 전환 상태와 남은 조건

**사본 이전과 운영 전환은 다르다. 새 DB는 격리되어 있고 운영 쓰기는 활성화하지 않았다.** 운영 SQLite는 계속 변경되므로 현재 사본을 그대로 최종 DB로 선택하면 안 된다.

최종 전환은 다음 조건을 충족한 뒤 수행해야 한다.

1. 운영자에게 허가받은 서비스 중지와 워커 배출, 전환 시점 백업.
2. 미확정 외부 실행 결과 및 전송 상태의 확인. 재시작 후 읽기 전용 점검에서는 결과 미확정 워크플로우 7건, 실행 시도 10건, 실행 중/미확정 typed flow 1건, 대기 알림 8건이 보였다. 서로 겹칠 수 있는 건수다. 실행 시도는 `unknown` 7건과 `prepared` 3건이며, 대기 알림 8건은 `ready`, 전송 시도 0회다. 삭제하거나 완료로 바꾸지 않았다. 기존 이전 모듈의 `_quiescent`가 이러한 상태에서 운영 활성화를 막는다. 현재 운영자 검토 이벤트는 0건이다. 운영자 검토도 원래 `unknown`을 변경하지 않는 구조이므로 단순한 검토 메모만으로 현재 전환 게이트를 통과한다고 가정하지 않는다. 외부 결과 증거, 미전송 작업의 처리와 보존 정책, 서명된 전환 계약의 적합성을 먼저 확인해야 한다. 이 SQL 점검은 별도의 서명된 외부 효과 검증을 대체하지 않는다.
3. 정지한 원본에서 새 격리 대상에 최신 전체 복사와 재검증. 새 대상에 GIN과 HNSW projection을 재구축하고 검색을 검증한다. 현재 사본의 오래된 projection이나 이전 영수증을 재사용하지 않는다. 독립적인 전환 증거와 소스 쓰기 퇴역 펜스를 확인한 뒤에만 새 DB를 운영자로 활성화한다.
4. 키 파일, 보고서, 로그인, 워크플로우, 검색, 롤백을 검증하고 운영 설정을 전환한다. 키·DSN 값은 공개 파일에 넣지 않는다.

전체 코퍼스를 복제하던 검색 경로도 개선했다. 새 DB에는 `simple`/unaccent 기반 네이티브 GIN 전문 검색 인덱스를 명시적으로 구축했다. 탐색의 집계·페이지 조회, 브로커 검색과 하이브리드 검색은 PostgreSQL에서 처리한다. 채팅의 기존 상세 판정은 일치한 후보만 별도 메모리 투영으로 검증한다. 전체 DB가 20만 건을 넘었다는 이유로 검색이 중단되는 구조를 제거했다. 요청별 후보/메모리 제한은 유지하며 무제한 확장을 주장하지 않는다. 네이티브 검색의 토큰화와 관련도는 새 프로파일에 정의되어 있으며 기존 SQLite BM25와 완전히 같은 점수를 주장하지 않는다. 실데이터 사본에서 weather 45→90건 조회, news/market 조회 및 보고서 필터가 정상 작동했고 전체 코퍼스 복제를 생성하지 않았다. 헬스 이력은 전량 보존했고 월별 파티션과 집계 보관 정책은 별도 검증 후 적용할 대상이다. 광고·알림 동의나 과거 실행 이력은 용량 확보 수단으로 변경하지 않는다.

## 검증과 증적

- 관리 정책·어드민·인증·캐시·브라우저·대량 이전·PostgreSQL/HNSW 회귀: `reports/admin-performance-2026-10-20/`의 JUnit XML.
- 관리/어드민/인증/캐시/브라우저/이전 회귀 165개 통과: `final-regressions.xml`. 별도 브라우저·네이티브 읽기 보안 회귀 18개 통과: `final-browser-native-security.xml`. 최신 네이티브 전문 검색·벡터·전체 애플리케이션·대량 이전·런타임 회귀 98개 통과: `native-search-and-runtime-final.xml`. 검사 범위가 겹치므로 합계를 고유 테스트 수로 표시하지 않는다.
- 전문 검색과 벡터 검색의 설치 순서를 바꾼 실제 PostgreSQL 통합 검사와 벡터 검증 7개 통과: `native-search-profile-order.xml`. 두 검색 프로파일이 같은 전용 스키마를 안전하게 공유한다.
- 실제 사본 최초/캐시/목록 조회: `after-covering-indexes.json`.
- PostgreSQL SQL/HNSW 실행 계획 및 시간: `staged-postgres-performance.json`.
- HNSW 구축: `staged-pgvector.json`.
- 정적 보안 점검: `secure-coding-final.json`. 최신 대상 22개 파일에서 분석 오류 0건, HIGH 0건, MEDIUM 103건, LOW 26건이다. MEDIUM은 B608 SQL 문자열 조합 경고이며 새 전문 검색과 생성기의 조합 대상은 저장소의 고정 구문/식별자다. 사용자 검색어와 필터 값은 바인딩한다. LOW에는 기존 예외 처리와 비보안 난수 사용 등이 포함된다. 이 결과를 ‘경고 없음’이나 전체 저장소 보안 인증으로 표현하지 않는다.
- GIN 인덱스 및 실제 탐색: `staged-native-lexical.json`, `staged-native-explore.json`.
- 운영 전환 차단 상태의 읽기 전용 점검: `cutover-readiness.json`. 사용자 데이터, 토큰, 목적지, 실행 본문을 포함하지 않은 집계 증적이다.
- 공개 프론트엔드 콘텐츠 검사: 234개 파일, 위반 0건.
- 원본·DSN·키·전체 이전 영수증은 `gateway-data/postgres18/` 아래 비공개 권한으로 보관한다. 이 경로는 Git과 공개 정적 서비스 대상에서 제외된다.

사용자가 서버를 재시작했고 새 PID 85313에서 반영을 확인했다. 실제 어드민 개요 강제 갱신은 2.4419초, 캐시 조회는 6.7–8.9 ms, 이름순 50건 목록은 26.7 ms였다. 헤더 없는 요청과 외부 Origin을 차단했고 최종 캐시 코드 및 인덱스를 확인했다. 이는 현재 운영 SQLite의 측정이며 PostgreSQL 운영 전환 완료를 뜻하지 않는다. 증적: `live-after-user-restart.json`.

## 기술 근거

- [SQLite WAL의 동시성](https://www.sqlite.org/wal.html): 읽기/쓰기 동시성은 개선되지만 쓰기는 한 번에 하나다.
- [PostgreSQL 대량 적재](https://www.postgresql.org/docs/18/populate.html): COPY 및 적재 후 통계 관리.
- [PostgreSQL 파티셔닝](https://www.postgresql.org/docs/18/ddl-partitioning.html): 이력의 날짜 범위별 물리적 관리.
- [pgvector HNSW](https://github.com/pgvector/pgvector#hnsw): cosine 인덱스, 근사 검색과 탐색 폭의 절충.
