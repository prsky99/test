## Recommended implementation order and decisions

1. **P0 — repeated-primary failure routing.** Keep successful current evidence for both connections at policy configuration and shadow verification. In an already signed canary, the primary needs its current active/safe connection, exact schema and unchanged tool approval; its latest success is not a runtime prerequisite. The alternative always needs fresh successful execution/contract evidence. A failed primary therefore cannot lock out the next explicitly opted-in canary request. Bindings, safety/auth/health gates, control/policy revision, cancellation, deadline, candidate expiry and one alternative per entire run remain enforced. This creates no automatic repeat of an uncertain dispatched request within the same logical run.
2. **P1 — multi-node policy and grant reapproval.** The private admin editor adds/removes up to six explicit node/contract/alternative rows and preserves every loaded pair. Backend duplicate/unsupported/unsafe checks remain authoritative. Policy responses return the exact number of revoked delivery grants and a reapproval indicator. The UI explains the revocation and opens the selected workflow's schedule/inbox dialog with all consent unchecked. A separate schedule target preserves unrelated unsaved builder state; the shortcut never silently changes its graph or authorizes delivery.
3. **P1 — bounded budgets and heartbeat.** Preserve the standard 25-second total for public requests, downloaded apps, schedules/events and default admin runs. An explicit highest-admin `extended` choice plus `workflow-budget-v1` notice signs a separate run-bound 60-second total / 15-second baseline node budget in the admission transaction. Selected fallback calls still use nested primary 12 / alternative 8-second caps. Idempotency cannot switch profiles. Claim/resume preserves the original absolute deadline; malformed/tampered budget authorization cannot dispatch. A worker's heartbeat thread reuses one short-timeout SQLite connection and closes it on exit. Durability is not lowered to `synchronous=NORMAL`. Temporary busy/locked errors permit another bounded pulse, while lost/expired ownership cannot be revived. Global four-active/twelve-admitted limits remain. No 60-second public contract or expanded throughput/SLA is advertised.
4. **P1 — reconciliation before resending.** Append signed revision-CAS external review records to an original run, original unknown outbox event or unknown manual event. `received`, `not_received` and `reviewed` are operator statements with an opaque evidence reference, not machine proof. Original execution/delivery outcomes stay unknown. A successful retained result with an original unknown delivery can receive **one** new manual delivery per source event: latest not-received review, a currently verified workflow inbox, explicit resend permission, separate duplicate-risk acknowledgement, exact result/destination hash, current highest-admin principal and one-hour expiry are required. The new `wm_` event is separately claimed/fenced; no provider task is rerun and no old event ID reused. Claim-only worker death may recover to pending; dispatched death/lost acknowledgement becomes unknown and is never automatically repeated. Manual unknown events can be reviewed but cannot create an unbounded resend chain. Marketing permission and workflow delivery grants are not inferred.
5. **P1 — explicit bounded retention and restore inventory.** Default to preview. A highest-admin single-batch apply or explicit local `--apply` compacts at most twenty known terminal run bodies older than fourteen days. Signed archive proof preserves original definition/result digests and artifact hash; final summaries expose a factual English expiry marker. Checkpoint and intermediate node bodies are removed. After ninety days, selected execution/routing history and expired execution authority may be pruned. Active/unknown executions, unknown or pending/claimed/dispatched deliveries, manual deliveries and unresolved evidence remain protected. Run IDs, actor/idempotency keys, original attempt/outbox IDs, signed routing consent/budget tombstones and reconciliation audit are retained to prevent replay. Referenced versions remain while needed by live/unarchived runs, active grants or deployed apps. Freed SQLite pages are reusable; no automatic VACUUM/file-size-shrink claim is made. CLI preview opens the existing database read-only without runtime lease recovery or key writes. Restore emits a private `0600` sibling inventory with capped IDs/states/counts and reapproval steps, never old keys, URLs, sealed data or inputs. It remains fail-closed: no automatic unquarantine, deployment-key revival or pending manual resend.
6. **P1 — migration and regression acceptance.** Extend the rehearsal from the original fifteen execution tables plus seven routing tables to **twenty-seven** tables by including run budgets, two reconciliation/manual-delivery tables and two retention/audit tables. Trusted source DDL and fixed identifier allowlists replace any dependency on snapshot-provided schema SQL. Temporary Unix-socket PostgreSQL round-trips every row/payload/signature including quotes/backslashes; eight owner contenders produce one winner, canary admission respects a two-slot test cap and manual source-event uniqueness holds. This is execution/routing/operations state rehearsal, not a production Store/FTS/auth/collector PostgreSQL adapter or cutover.
7. **Deployment gate — user-managed restart and authenticated smoke.** The provided PID 83439 was absent; a different process served both local ports. Normal GET checks confirmed frontend/admin HTTP 200 and CSP, without executing providers, sending notifications or changing controls. The current live fallback control was off with no policies, read through an independent read-only connection. The user operates the project server in their terminal under `AGENTS.md`; this development task did not restart or replace it. New Python routes/schema require a user restart followed by highest-admin checks of controls, policy, budget, recovery/reconciliation and retention preview. No live canary, retention apply or manual delivery was triggered by this work.

Retention apply first takes the SQLite writer lock and refuses while any workflow is queued/running or any result delivery is claimed/dispatched. A cooperative half-second budget is checked between runs, not advertised as a hard transaction-latency guarantee. Snapshot digests and each retained checkpoint's signature, audience, run/node and definition scope are checked before compaction. Metadata pruning also verifies the signed archive proof. Invalid evidence is held for investigation and counted rather than silently deleted. Expanded-volume and writer-contention acceptance remains pending.

## Operational contracts

Private APIs require highest-admin authentication and `Cache-Control: no-store`:

- `GET/POST /admin/api/workflows/maintenance`: preview or explicit `workflow-retention-v1` single-batch apply. No caller-selected retention period or SQL/table input.
- `POST /admin/api/workflows/runs/{run_id}/reconciliation`: subject, current review revision, disposition, evidence reference and `workflow-reconciliation-v1` authorization.
- `POST /admin/api/workflows/runs/{run_id}/manual-deliveries`: original source event, review revision, verified destination and `workflow-manual-resend-v1` authorization plus duplicate-risk acknowledgement. Returns a pending new event; normal worker polling processes it.
- Existing private recovery adds fixed review/manual-event metadata and bounded execution-profile fields; it returns no signature, raw approval payload, key, destination URL or checkpoint body.
- Existing admin run accepts explicit `execution_profile=extended` and `execution_budget_notice=workflow-budget-v1`. Other roles/sources cannot gain the profile. Existing public SDK 1.0/admin SDK 1.1 packages keep their current behavior.

Local maintenance uses `python -m agent_market.workflow_maintenance --db <existing-current-database>` for read-only preview and the explicit `--apply --limit 20` for one batch. It starts no HTTP server, collector, queue execution or notification sender. Apply requires a current initialized schema and its correct workflow signing key. Restore returns the private inventory filename; its review instructions require fresh destination verification, grants, app keys and shadow approval rather than reactivating old credentials.
