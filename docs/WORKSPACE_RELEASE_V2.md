# Private executable releases and Workspace SDK 2

`workspace-executable-release-v1` is a separate, private release of one saved workspace snapshot. It supports exactly a manual trigger followed by one literal, read-only MCP tool call. It does not insert objects into the legacy workflow or public template tables.

A current workspace owner creates a release from a retained successful, dispatched private test. The current snapshot signature/revision, definition hash, resource binding/generation and tool must still match that test. The immutable release stores this pin and fixed input under a server signature. Revocation changes separately authenticated state through a revision check; it never edits the release definition. The downloaded JSON snapshot remains `executable:false`, `deployable:false`, `published:false`: the separate release and current authority enable execution, not possession of that artifact.

The owner separately issues a revocable deployment grant with one to five exact origins, a lifetime of300–86400 seconds capped by the release,1–30 admissions per minute and1–100 per day. HTTP is limited to explicit loopback origins for isolated preview; deployed service origins require HTTPS. The gateway reserves per-app admission quota atomically before execution. Reusing an accepted ticket does not consume another admission or call the provider again. Denied admissions may conservatively consume the reservation. A grant does not add customer membership or imply publication, scheduling, external webhooks, marketing, fallback or result delivery.

## Customer-only app authorization

Exported apps never request administrator passwords, staff tokens or embedded API keys. Customers sign in on the Agent Concierge origin using a host-configured provider and must have a separate, current workspace `runner` link. The gateway authorization page requires the current customer cookie and its CSRF proof. App authorization creates a one-time60-second code bound to the app, exact approved origin, fixed `/bff/callback`, customer session, workspace/link revisions and an S256 PKCE challenge. The callback cannot be an arbitrary redirect. No raw customer cookie or generic workspace token reaches the self-hosted app.

The app's server BFF holds the verifier and flow state in memory. Its exchange produces an opaque app-run capability lasting at most five minutes and no longer than the current customer session/deployment. Signed token payloads bind their opaque token references; changing database lookup hashes cannot retarget a capability. Every prepare/admission checks current customer authority and the release pin. The dedicated customer executor also invokes the app authority guard immediately before dispatch and before accepting a successful result. Withdrawing the deployment, release, customer session/link or current resource authority stops later calls and withholds unconfirmed output. Customer identifiers remain distinct from administrator identities.

Every run requires a fresh prepare, exact input/target/limit preview and unchecked purpose-specific authorization. Only the server ticket identifier and that authorization are submitted; the browser cannot replace the fixed input. The existing private executor retains the accepted ticket/run relationship, certainty and replay behavior. App-run capabilities cannot read arbitrary runs. Separate `run-status` capabilities bind one accepted app/run/customer/origin and permit no preparation or execution. A withdrawn deployment may still allow its already accepted result to be inspected while the short status capability and current customer read permission remain valid.

## Package and BFF

The ZIP contains `index.html`, `sdk-v2.js`, `app-v2.js`, `styles-v2.css`, `bff.py`, `app-manifest.json`, `requirements.txt` and `README.txt`. Static configuration contains app/release identifiers, the profile/version and approved origins only. The browser calls its same-origin BFF; the BFF calls only `https://agentconcierge.biz`. There is no provider URL or bearer credential in static configuration. Gateway app/status tokens stay in BFF memory. The browser receives an HttpOnly, same-site app cookie and a purpose-limited CSRF value, not those tokens.

Configure the exact `SDK2_ORIGIN`, install the package requirements and run the BFF behind a TLS reverse proxy. Preserve its restrictive CSP, `frame-ancestors 'none'`, no-store and referrer headers. The client additionally disables preparation/execution in a frame. The BFF bounds incoming JSON size/depth, rejects duplicate/non-finite JSON and compressed bodies, streams bounded gateway responses, and has finite request deadlines. BFF restarts end local app sessions. A customer identity provider must be explicitly configured by the service host; absent configuration fails closed. Export does not configure or validate an operating identity provider.

The client keeps review/consent/results in memory and clears them on disconnect/page exit. It sends one run POST and never automatically repeats it after a network failure or ambiguous response. `prepared`, `dispatched` and `unknown` lock fresh starts in the current visit; read-only history resolves accepted records. Closing a page does not claim to cancel server work. Output is untrusted bounded text, with no HTML or link interpretation, automatic winner or provider certification.

## Management and transport

Staff management is nested under `/admin/api/workflow-workspaces/{ws}/drafts/{draft}/snapshots/{snapshot}/release-v2`. The public customer app namespace is `/api/workspace-apps-v2/{app}` and exposes only app authorization, one-time exchange, fixed prepare/run, app history and exact-run status capability operations. Public and administrative routers are mounted separately. Staff authority never authenticates a customer app.

`workspace_release_restore_blocks` permanently blocks previously issued release/deployment identifiers after restore. Historical metadata can still be inspected, but changing workspace state or logging in again cannot revive those old grants. Fresh independently authorized releases/grants are required.

## Validation boundaries

Tests use isolated SQLite, actual private executor/MCP handshake behavior with `httpx.MockTransport`, synthetic preseeded customer identities and Chromium route transport to isolated FastAPI apps. They verify packaging bytes, separate customer authorization/PKCE, BFF cookies/CSRF, one explicit tool call, scoped result capabilities, withdrawal and replay boundaries. They do not establish a live Google/GitHub deployment, operating acceptance, external provider quality, multi-node execution or a universal security certification. See the completion report for exact current test counts and source hashes.
