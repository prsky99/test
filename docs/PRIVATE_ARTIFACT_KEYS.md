# Private artifact keys and backup policy

The optional `private-artifact-keys-v1` profile supplies versioned authentication
and AES-256-GCM encryption for explicitly supported private artifacts. It is
operator configuration, not a public API or an automatic KMS service. No operating
key or production database is changed by this implementation.

`AGENT_PRIVATE_ARTIFACT_KEYRING` names an existing owner-only regular file (0600 or
stricter, current effective user ownership, no symlink). It is limited to 32 KiB,
rejects duplicate JSON fields and contains exactly `profile`, `active_signing`,
`active_encryption`, `allow_legacy` and `keys`. Each of at most 16 key entries has
`id`, base64 `key` containing exactly 32 independently generated bytes,
`verify_until` as an absolute Unix timestamp and `revoked` as a boolean.
`active_encryption` may be null to enable signatures without enabling encryption.
There are no example secrets in the repository. Secrets must never be entered in
Chat, exported apps, frontend configuration or application logs.

## Rotation, grace and revocation

New signatures use `ak1.<key_id>.<mac>`. Keys are purpose separated: signing,
encryption and different artifact modules use independently derived keys.
Changing `active_signing` or `active_encryption` changes new writes. Retaining a
previous key with an unexpired `verify_until` permits bounded verification or
decryption of old artifacts. `revoked:true`, removal or expiry makes that key
unavailable. The active key itself must be present, unexpired and not revoked.
Invalid or unreadable configured files fail initialization; they do not silently
fall back to a plaintext or single-key mode.

Configuration is read during component construction. Replace the private file
atomically and reload the relevant process to apply a rotation or revocation.
This code does not perform that operating action. Previous components retain
their previously loaded configuration until replaced. Do not claim immediate
hot revocation across already running processes.

Without the setting, existing HMAC signatures and plaintext storage retain their
previous behavior. To adopt a keyring while reading older hex signatures, an
operator must explicitly choose `allow_legacy:true`. Set it false after the
required migration/retention period. A digest/HMAC authenticates data; it does
not encrypt it. No complete historical data migration or previous-key rewrapping
is performed automatically. Retiring a decryption key may make old retained data
unreadable; preserve authorized offline recovery material and verify restore
before doing so.

The profile covers workspace access/module signatures, private execution
tickets/results, lifecycle receipts/reviews, SDK 2 release/deployment and app
authority signatures, endpoint-control claims/transfers, and configured backup
manifests. Customer identity/session root hashes, legacy workflow authorities,
opaque SDK 2 token lookup references and unrelated platform secrets retain their
own lifecycle. This is not a claim that every platform secret has been rotated.

## Retained output

When authenticated encryption is configured, newly written non-null private-run
outputs are AES-256-GCM envelopes with fresh random 96-bit nonces. The row's
profile, run, workspace, draft, snapshot and ticket identifiers are authenticated
as additional data. A ciphertext copied between runs fails authentication even
if its outer row is re-signed. The normal outer signature is verified before
decryption. Output is returned only through the current private authorization
checks, with neither envelope nor key metadata added to its product DTO.

This encrypts the retained output field, not all database pages, resource URLs,
snapshots, all inputs, session data, WAL/history copies, process memory or network
traffic. Existing plaintext rows remain plaintext until an independently
authorized migration is implemented. The seven-day owner-controlled archive
removes the current output/envelope, stores a signed output hash and the hash of
the original stored signed payload, and preserves idempotency and unknown runs.
Logical archival is not guaranteed physical erasure from SQLite/WAL/backups.

## Backup and restoration

`python -m agent_market.workflow_backup backup --db <path> --directory <new-path>
--encrypt --retention-days 30` explicitly requests authenticated encryption.
Missing encryption configuration fails before creating the backup directory.
Each online SQLite snapshot and optional existing local updates key is sealed
separately with artifact identity and snapshot time authenticated. Final encrypted
packages contain `.sealed` artifacts and an authenticated manifest; the private
artifact keyring is never included. Snapshot encryption is bounded to 128 MiB per
plaintext artifact. Larger backups fail instead of changing to plaintext. A
future streaming/remote-KMS backend is a separate extension.

The initial consistent snapshot exists as an owner-only plaintext file while
being sealed; it is removed after successful encryption. This does not guarantee
physical media erasure. Existing unencrypted backups remain supported, with
accurate `encrypted:false` metadata. If a signing keyring is configured, new
manifests are signed even when encryption is not requested. Legacy unsigned
backups require the explicit legacy-verification allowance when a keyring is
configured. Manifest signature, ciphertext checksum and authenticated decryption
must all pass before a restored target is created.

The manifest records creation, a 1–365-day retention policy, an advisory review
date and `automatic_deletion:false`. There is no unattended deletion or claim
that external backup copies expire. Operators review and remove expired copies
according to their separate recovery obligations.

Restore still requires new paths and quarantines uncertain work. It pauses
workspaces/customer organizations, revokes pending customer invitations and
sessions/links/tickets, and permanently blocks old executable releases,
deployments and provider transfer offers. It preserves signed historical receipts
and unknown outcomes. Current-owner review requires independently established
current ownership and fresh authority; old backup owner rows, an old proof, a new
login or key rotation cannot reactivate an old grant or run.

## Verification boundaries

Synthetic tests exercise old-key grace, expiry/revocation, strict file policy,
purpose/AAD tampering, actual private-run encryption and archival, release state
rotation, encrypted online backup and fail-closed restoration. Real production
key custody, an external KMS, operating restore acceptance, media erasure and
organization ownership recovery remain independent operating work.
