# AI AD Coin 개발 현황 (시험 모드)

- 기준: 2026-11-04. 기획은 `reports/AI-AD-Coin-business-plan-v3-2026-11-04.md`, 결정은 그 문서의 0.3절.
- 상태: 기능 플래그 뒤의 닫힌 시험이다. 기본값은 꺼짐이다.
  - 예산·코인은 가상 값이다.
  - 결제·실제 광고주 집행·외부 체인 출고는 그랜드 오픈 전까지 닫혀 있다.
  - 법률·기관 검토는 그랜드 오픈 전에 한다.

## 켜는 법

| 환경 변수 | 뜻 | 기본값 |
|---|---|---|
| `AD_COIN_ENABLED` | `1`이면 라우트가 생긴다. 끄면 모든 경로가 404 | 꺼짐 |
| `AD_COIN_DB` | 전용 SQLite 파일. 카탈로그·운영 PG와 분리 | `gateway-data/ad_coin.sqlite3` |

| `AD_COIN_ADMIN_TOKEN` | 캠페인·설정·정산 관리용 Bearer 토큰 | 없음(관리 불가) |
| `AD_COIN_INVITED` | (예전 방식, 시험 호환용) 초대한 visitor token의 sha256 hex 목록(쉼표 구분). 정식 초대는 관리자 화면의 고객 계정 초대를 쓴다 | 없음 |
| `AD_COIN_ISSUER` | 영수증 발급자 | `https://agentconcierge.biz` |

## 구성

| 모듈 | 하는 일 |
|---|---|
| `ad_coin/ledger.py` | 원 단위 복식부기 원장. 모든 분개 합계 0, 청구 계정 음수 금지, 같은 멱등 키 재전송은 한 번만 반영. 재원 불변식: 남을 위해 보관 중인 금액(에스크로·잠금·지갑·실행권·진행 중 작업·지급 예정) ≤ 신탁 잔액 |
| `ad_coin/exchange.py` | 작업 후원 입찰. 최저가 = 작업 가격 ÷ 0.6, 관련도 가중 2위 가격. 50코인 미만 작업은 후원하지 않는다. 일반 추천 결과의 해시(`selection_digest`) 생성 |
| `ad_coin/screening.py` | 광고 소재의 에이전트 지시문·자기 보증·지갑 요구·숨은 문자·마크업을 결정론으로 거부 |
| `ad_coin/service.py` | 견적 패킷, 동의, 15초 노출 확인, 보상(코인) 또는 후원 실행권, 지갑 이전·회수, 의도 위임장, 실행·환불·정산, 서명 오퍼 피드, 집계 보고, 회로 차단 |
| `ad_coin/receipts.py` | 노출·보상·실행권·이전·실행·환불·정산·회수·오퍼 수신·위임장 영수증(Ed25519) |
| `ad_coin/api.py` | `/api/ad-coin/v1/*`와 숨김 화면 `/ad-coin`. 초대 토큰·관리자 토큰 검사, `no-store` |
| `ad_coin/upgrade.py` | 일반 답변 뒤 별도 요청으로 유료 업그레이드가 있는지 판단. 답변이 이미 낸 에이전트를 그 순서대로만 읽고, 카탈로그의 가격·품질 등급·상태만 본다. 후원·입찰·지갑은 보지 않는다 |
| `ad_coin/page.py` | 영어 공개 문구 화면(`/ad-coin`). 고정 내용은 바로 보이고, 영역마다 누를 때 불러온다. 답변의 에이전트 ID를 넣으면 업그레이드 확인 → 후원 견적으로 이어진다 |
| `ad_coin/admin_page.py` | 한국어 운영 화면(`/ad-coin/admin`, 관리자 토큰). 상태·재원(두 요청 병렬), 회로 열기·닫기, 배분율, 시험 캠페인 생성·충전·중지·환불·보고서, 실행 완료·가상 정산·휴면 회수. 팝업·전체 화면 로딩 없음 |

## 지키는 규칙(시험으로 확인)

- **선택–재원 분리**
  - `agent_market` 안에서 `ad_coin`을 import할 수 있는 곳은 front.py의 라우터 연결뿐이다.
  - `ad_coin`은 추천(selection·engine·ranking) 모듈을 import하지 않는다.
- **동일 품질:** 제공자에게 가는 요청(`provider_request`)에는 실행 ID·제공자·작업만 들어간다. 후원 여부는 들어가지 않는다.
- **동의와 노출**
  - 동의 없이 노출 보상은 없다.
  - 포그라운드 15초 미만이면 보상하지 않는다.
  - P2는 확인 문항 답이 필요하지만, 정답 여부와 관계없이 보상한다. 일치 여부는 영수증에만 남긴다.
- **빈도 상한:** 같은 사람·같은 캠페인은 하루 3회까지다.
- **지갑**
  - 지갑 간 이전으로 새 가치가 생기지 않는다.
  - 다른 사람에게 5,000원 상당 이상을 보내면 본인 재확인이 필요하다.
  - 메모에 지시문이나 안전 주장이 있으면 보류한다.
- **회수:** 14일 동안 쓰지 않은 에이전트 지갑이나 위임을 철회한 에이전트 지갑의 잔액은 사용자 지갑으로 돌아간다.
- **의도 위임장**
  - 최대 30일까지 만들 수 있다.
  - 정해진 제공자·건당 한도·총액 안에서만 에이전트가 쓸 수 있다. 벗어나면 사람에게 확인을 요청한다.
- **회로 차단:** 재원 불변식이 깨지면 회로가 열린다. 열리는 동안 새 후원 제안은 나가지 않고, 불변식이 다시 맞아야만 닫을 수 있다.
- **배분 기본값:** 사용자 50·운영자 10·직접비 15·플랫폼 25. 관리자 설정으로 바꿀 수 있다.
  - 사용자 몫은 40% 아래로 내릴 수 없다.
  - 운영자+직접비는 40%를 넘을 수 없다(작업 후원 몫 보장).
- **서명 오퍼 피드(B1)**
  - Web Bot Auth로 서명한 에이전트만 받는다.
  - `context_use`는 `presentation_only`, 공개 사본 URL을 함께 준다.
  - 수신 영수증은 토큰당 한 번만 운영자 보상이 된다. 사용자 코인은 생기지 않는다.

## 업그레이드 확인 규칙

- 1위가 무료면, 답변 안의 다음 후보 중 코인을 받을 수 있는 유료 에이전트를 고른다. 1위가 유료이고 자격이 있으면 1위를 고른다.
- 코인 수납 자격: 가격이 있음, 등급 A·B, 상태 healthy·reachable, 활성.
- 가격 환산: x402 `price_usdc`(USDC 기본 단위) × 1,380원, 10원 단위 올림.
- 후원 가능 범위: 500원(50코인)~50,000원. 이보다 싸면 코인 결제나 무료 결과만 안내한다. 100만 원을 넘으면 견적을 만들지 않는다.
- Chat·Explore 응답 경로는 바꾸지 않았다. 답변을 보여준 뒤 `POST /api/ad-coin/v1/upgrade-check`를 따로 부르므로 응답 시간 정책(Explore 3초, Chat 5초)에 영향이 없다.

## 작업 묶음 견적

- 일반 계획이 이미 정한 단계(카탈로그 에이전트 + 호출 수) 묶음을 한 번의 후원 단위로 계산한다.
  - 요청: `POST /api/ad-coin/v1/upgrade-check {"bundle": [{"resource_id": 109457, "calls": 1}, ...]}`
  - 최대 20단계, 단계당 1~1,000회.
- 가격 계산
  - 줄마다 정확한 원 가격(USDC × 1,380 × 호출 수)을 더한 뒤 **한 번만** 10원 단위로 올린다.
  - 그 합계를 가장 큰 나머지 순서로 줄에 나눠, 줄 금액의 합이 총액과 정확히 같게 한다.
  - 호출마다 올림하면 13.8원 호출이 20원이 되어 45% 비싸지기 때문이다.
- 자격
  - 유료 단계는 모두 코인 수납 자격(등급 A·B, 작동 중)이 있어야 한다. 하나라도 없으면 `bundle_has_ineligible_step`과 해당 ID를 돌려준다.
  - 무료 단계는 0원 줄로 남는다.
  - 범주는 가장 비싼 단계의 범주를 쓴다.
- 실행
  - 제공자 요청에는 줄별 제공자·호출 수만 들어가고, 후원 여부는 들어가지 않는다.
- 완료·정산
  - `line_results`로 줄마다 성공 여부를 받는다.
  - 성공한 줄은 각 제공자에게 지급 예정으로 넣는다.
  - 실패한 줄의 돈은 낸 쪽으로 돌려준다. 코인이면 지갑으로, 후원이면 광고주 에스크로로 간다. 전부 실패하면 후원 실행권을 되살린다.
  - 결과는 `succeeded`·`partial`·`refunded` 중 하나다.
- 위임장으로 묶음을 결제하려면 묶음 안의 모든 유료 제공자가 위임장에 있어야 한다.
- 후원이 붙지 않은 이유를 견적에 적는다.
  - `no_matching_sponsor`: 관련 후원자가 없거나 입찰가가 최저가보다 낮음
  - `task_below_minimum`
  - `circuit_open`

## 공개 워크플로 → 묶음 견적

- 요청: `POST /api/ad-coin/v1/upgrade-check {"workflow": {"template_id": 57, "runs": 5}}`
  - 공개 정의(`published_detail`)만 읽는다. 실행 횟수는 1~100회다.
- 단계 계산
  - 에이전트 노드를 카탈로그 에이전트별로 합치고, 실행 1회당 1호출로 센다.
  - 실행 횟수를 곱해 묶음을 만든다.
  - 꺼진 노드는 빼고, 트리거·라우터·변환 노드는 0원이다.
- 라우터가 있으면 모든 가지를 센 **상한 견적**이다(`upper_bound: true`). 실행되지 않은 가지는 실행 뒤 줄별 결과로 환불한다.
- 카탈로그 ID가 없는 에이전트 단계(`resource_ref`만 있는 단계)는 값을 매길 수 없다. 이름을 `unpriced_steps`에 보여 준다.
- 견적의 선택 확인 코드에는 워크플로 ID·정의 해시·실행 횟수가 들어간다. 작업 이름은 `workflow-<id>-<해시 앞 12자>-x<횟수>`다.
- 화면(`/ad-coin`)에서는 `w57x5`처럼 입력한다.

## 숨김 시험 상품

공개 워크플로가 모두 무료라서, 실제 카탈로그 에이전트로 만든 숨김 워크플로 상품을 AI AD Coin 안에 둔다(`ad_coin/test_products.py`).

- **만들기:** 관리자만 만든다(`POST /api/ad-coin/v1/admin/test-products`, 화면 `/ad-coin/admin`의 "시험 상품").
  - 단계: 카탈로그 ID × 실행당 호출 수(1~100), 최대 12단계. 같은 에이전트는 한 번만 넣는다.
  - 이름·설명은 광고 소재와 같은 결정론 심사를 거친다.
- **거부 조건**
  - 카탈로그에 없거나 비활성인 에이전트
  - 종류가 x402·MCP·A2A가 아닌 에이전트
  - 코인을 받을 수 없는 유료 에이전트(등급 B 미만·작동 안 함)
  - 유료 단계가 하나도 없는 상품
  - 이름·주소에 send·transfer·withdraw·swap·deposit·order·buy·sell·delete·update·create·post·sign·approve 같은 말이 들어간 에이전트. 돈을 옮기거나 상태를 바꾸는 것으로 보고 거부한다(읽기 전용 원칙).
- **노출과 실행**
  - 공개 워크플로 목록에는 나가지 않는다.
  - 초대된 사람은 `GET /api/ad-coin/v1/test-products`로 목록을 본다.
  - 견적은 `upgrade-check {"test_product": {"id": "tp_…", "runs": 5}}`로 받는다.
  - 실행은 시뮬레이션이다. 결제가 닫혀 있어 제공자를 실제로 부르지 않는다.
- **보관:** 보관한 상품은 견적에서 `unknown_test_product`가 된다.

## 고객의 비공개 워크플로 견적

- 요청: `upgrade-check {"private_workflow": {"workspace_id": "ws_…", "flow_id": "wtf_…", "runs": 5}}`
  - 화면에서는 `ws_…/wtf_… x5`처럼 입력한다.
- 권한: 고객 워크스페이스의 기존 경계를 그대로 쓴다(`ad_coin/private_workflows.py`).
  - 같은 출처의 고객 세션 쿠키(`customer_actor`)
  - 워크스페이스 구성원 확인(`core.actor`)
  - typed flow 상세 읽기(`core.typed.detail`)
  - ID를 알고 있다는 것만으로는 읽을 수 없다.
  - 로그인하지 않으면 401, 남의 워크스페이스·없는 흐름·비활성 흐름은 403이다.
  - 고객 워크스페이스가 닫힌 서버에서는 503이다.
- 가격 계산에 필요한 것만 꺼낸다: 노드의 카탈로그 ID와 꺼짐 여부.
  - 흐름 이름·입력·바인딩·출력은 응답에 들어가지 않는다.
  - 이름은 "Your saved workflow"로 바꾼다.
- 조건부(`when`) 단계가 있으면 상한 견적이다. 실행되지 않은 단계는 실행 뒤 줄별로 환불한다.
- 견적 작업 이름은 `private-<flow id>-<해시>-x<횟수>`다.
- 한계: AI AD Coin의 사람 식별은 아직 초대 visitor token이다. 고객 세션은 흐름을 읽는 권한 확인에만 쓴다. 둘을 하나로 묶는 일(초대를 고객 로그인과 연결)은 남은 일이다.

## 실제 실행 기록으로 정산

워크플로를 위한 실행권·코인 결제는 실제 실행 기록으로 정산한다(`ad_coin/run_results.py`).

- 요청
  - 본인: `POST /api/ad-coin/v1/executions/settle-from-runs {"execution_id", "run_ids", "workspace_id"?}`
  - 운영자: `/admin/executions/settle-from-runs`. 공개 워크플로만 정산할 수 있다.
  - 운영 화면 "실행·정산"에서도 할 수 있다.
- 대상은 실행의 작업 이름으로 정한다.
  - `workflow-<id>-…-x<횟수>`: 공개 워크플로
  - `private-<flow id>-…-x<횟수>`: 고객 비공개 흐름. 본인 로그인 세션에서만 정산한다.
  - `product-…`: 시험 상품. 실행이 시뮬레이션이라 기록 정산 대상이 아니다.
- 기록 확인
  - 실행 기록 수는 견적의 실행 횟수와 같아야 하고, 서로 달라야 한다.
  - 각 기록은 그 워크플로의 것이어야 하고, 결제(실행권 사용·코인 결제) 뒤에 시작돼야 한다.
  - 실행 중인 기록이 있으면 `waiting`으로 답하고 정산하지 않는다.
  - 기록 하나는 한 번만 정산에 쓰인다(`run_claims`).
- 지급
  - 줄마다 성공한 호출 수를 센다. 노드의 카탈로그 ID 기준, 모든 실행 합계, 줄의 호출 수가 상한이다.
  - 그 비율만큼(`won × 성공 ÷ 호출`) 제공자에게 지급한다.
  - 나머지는 낸 쪽으로 돌려준다. 코인이면 지갑, 후원이면 광고주 에스크로다.
  - 분기로 실행되지 않은 단계(`skipped`)와 실패한 단계는 성공으로 세지 않는다.
- 읽는 것은 실행 상태와 단계 상태뿐이다. 입력·출력은 읽지 않는다.
  - 공개 실행은 운영 PG에 이미 등록된 SQL을 그대로 쓴다. `SELECT * FROM workflow_runs WHERE id=?`, `SELECT node_id,status,started,finished FROM workflow_node_runs WHERE run_id=? ORDER BY node_id LIMIT 50`. 등록 여부를 시험으로 확인한다.
  - 비공개 실행은 고객 경계의 `core.typed.get`을 쓴다.
- 결과 해시는 실행 ID와 단계 상태로 만든다. 실행 영수증에 단계별 성공 호출 수를 남긴다.

## 월간 후원 감사

후원을 켜도 일반 추천이 바뀌지 않는다는 약속을 운영에서 확인한다(기획 v3 10절 즉시 중지 조건 4). 판정은 `ad_coin/audit.py`, 실행은 `scripts/ad_coin_sponsorship_audit.py`가 한다.

- 실행
  ```
  AD_COIN_ADMIN_TOKEN=… nice -n 10 .venv/bin/python -m scripts.ad_coin_sponsorship_audit --base http://127.0.0.1:8400
  ```
  - 기본은 Explore로, 질문 20개 각각의 상위 3개를 본다.
  - `--surface chat`으로 Chat을 볼 수 있다. LLM 비용이 든다.
  - `--queries 파일`로 질문을 바꿀 수 있다.
- 질문마다 순서
  1. 후원 끔(회로 열림) 상태에서 읽는다.
  2. 후원 켬(회로 닫힘) 상태에서, 그 질문 결과로 실제 후원 견적을 만들어 예산을 잠근 뒤 다시 읽는다.
  3. 다시 끄고 읽는다.
- 판정
  - **같음:** 세 번 모두 같다.
  - **바뀜:** 두 번의 "끔"이 서로 같은데 "켬"만 다르다.
  - **흔들림:** 두 번의 "끔"끼리 다르다. 판정에서 뺀다.
  - **오류:** 읽기에 실패했다.
  - 바뀜이 하나라도 있으면 실패다. 같음이 0이면 판정 불가다.
- 끝나면
  - 감사 중 만든 후원 예약은 모두 풀어 준다.
  - 보고서는 `gateway-data/ad_coin_audits/`에 저장한다(git 제외). 서버에도 기록한다(`POST /admin/audits`, 운영 화면 "후원 감사").
  - 실패하면 서버가 회로를 `audit_mismatch:<개수>`로 연다. 통과하거나 판정 불가면 회로를 감사 전 상태로 되돌린다.
- 부하: 질문당 읽기 3번과 후원 호출 2번이다. 읽기는 1초 간격이고 연결은 재사용한다.

## 누가 쓰는가: 초대받은 로그인 고객과 그 사람의 에이전트 키

- 신원 판별 순서(`ad_coin/people.py`, `api.py`의 `person`)
  1. **에이전트 키**(`X-Ad-Coin-Agent-Key: ack_…`)
     - 고객이 만든 키다. 한 에이전트 이름에 묶이며, `X-Agent-Name`으로 다른 이름을 사칭할 수 없다.
     - 키는 해시로만 저장하고, 원문은 만들 때 한 번만 보여 준다.
  2. **로그인한 고객**: 같은 출처의 고객 세션 쿠키. 쓰기 요청에는 세션의 CSRF 값(`X-Customer-CSRF`)이 있어야 한다.
  3. 관리자 토큰
  4. 예전 visitor token 초대(시험 호환용)
- **초대**
  - 관리자가 고객 계정 ID로 초대한다(`/admin/invites`, 운영 화면 "초대").
  - 사용자는 화면의 "Check my account"(`GET /account`)에서 자기 계정 ID와 초대 여부를 본다.
  - 초대를 거두면 그 사람의 에이전트 키도 모두 멈춘다.
- **사람 식별값:** `c_` + sha256(`customer:` + 계정 ID) 앞 24자다. 사람의 지갑과 그 사람 에이전트 키의 지갑이 같은 식별값으로 묶인다.
- **에이전트 키 관리**
  - 키 발급·목록(`/agent-keys`)은 본인 로그인 세션에서만 할 수 있다. 에이전트 키로는 할 수 없다.
  - 한 사람당 최대 10개다. 같은 에이전트 이름으로 다시 만들면 이전 키가 멈춘다.
  - 에이전트 철회(`/agents/revoke`)는 키를 멈추고, 위임장을 철회하고, 그 에이전트 지갑의 코인을 사용자 지갑으로 옮긴다.
- 고객 워크스페이스가 닫힌 서버에서는 로그인 경로가 없다. 이때는 관리자와 예전 초대 토큰만 쓸 수 있다.

## 남은 일

- 운영 PostgreSQL 이전
  - 지금은 전용 SQLite 파일이다.
  - 운영 PG로 옮기려면 SQL을 `application_store_sql.json`에 등록해야 한다.
- 초대 계정 연결: 지금은 visitor token 해시 목록이다. 고객 로그인 세션과 연결하는 일이 남았다.
- Chat 화면에서 답변이 끝난 뒤 업그레이드 확인을 자동으로 부르는 일. Chat 화면 파일은 다른 세션이 고치는 중이라 이번에는 건드리지 않았다. 지금은 `/ad-coin` 화면과 API로 쓴다.
- 공개용 유료 워크플로 상품: 숨김 시험 상품으로 흐름은 검증했다. 공개하려면 결제(그랜드 오픈)와 제공자 계약이 먼저다.
- 로그인 고객 흐름의 화면 확인(계정 확인, 에이전트 키 발급, 비공개 워크플로 견적): 로컬에 고객 로그인 세션이 없어 통합 시험으로만 확인했다. 운영(고객 워크스페이스 열림)에서 플래그를 켠 시험 계정으로 확인해야 한다.
- 기존 관리자 화면(`/admin/ui`)에서 `/ad-coin/admin`으로 가는 링크.
- 월간 감사를 정기 실행으로 등록하기(launchd 등): 지금은 수동 실행이다. 운영에서 플래그를 켠 뒤에 등록한다.
- 실행 완료 연결: 지금은 관리자 API로 시뮬레이션한다. 실제 제공자 실행 결과와 연결해야 한다.
- 그랜드 오픈 전 검토 목록: 법률·기관 검토, 판매 주체 구조, 약관상 명칭, 신탁 계좌 잔액 대사.
