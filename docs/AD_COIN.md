# AI AD Coin 개발 현황 (시험 모드)

- **화면·성능 구현(2026-11-09):** `/ad-coin/v2`에 영어 사용자 보상/선택과 광고주 캠페인/보고 화면을 추가했다. `include_workspace=True`를 명시한 격리 앱에서 검증하며 기본 등록은 꺼져 있다. 초기 화면은 API/DB 없이 표시하고 계정 정보는 사용자가 열 때만 조회한다. PostgreSQL schema 4의 여섯 인덱스로 원장 미완료 검사와 권한별 목록을 보강했다. 승인 도중 화면 이동·중지·권한 철회·늦은 응답을 검증하며, 실제 IdP 연결·운영 활성화·실가치 결제는 별도 미완료다. 최신 시험·측정의 범위와 한계는 [화면·성능 증거](../reports/ad-coin-v6.2-ui-performance-2026-11-09/README.md)를 따른다.
- **v6.2 구현 재검수(2026-11-08):** PostgreSQL 전용 model schema 3·38개 표·고정 계약 29개 API의 모델 처리 코드를 추가했다. 개선 코드에서 시간 조작·정지 누락·재시도·보고서·이전 DB 제약 문제를 재현하고 수정했으며, 원본 증거의 독립 재검증과 보고 근거 manifest를 보강했다. 상세 결과·실패/수정 증거는 [개발 기록](../reports/ad-coin-v6.2-development-2026-11-08/PROGRESS.md)과 [재검수 기록](../reports/ad-coin-v6.2-development-2026-11-08/wp04-review/README.md)을 따른다. 화면·실제 IdP/mTLS·운영 권한/복구/성능 인수는 미완료이며 운영 앱·실가치·체인을 활성화하지 않았다.
- **개발 설계 갱신(2026-11-07):** v6.1 정책을 [플랫폼 아키텍처 v6.2](AD_COIN_PLATFORM_ARCHITECTURE.md), [데이터·API 계약](AD_COIN_PLATFORM_DATA_API.md), [개발 작업·인수 기준](AD_COIN_PLATFORM_IMPLEMENTATION_PLAN.md)으로 구체화했다. [최신 조사 기반 보강](AD_COIN_PLATFORM_DESIGN_UPGRADE.md)과 [현재 P1 OpenAPI](ad_coin_platform_p1_v6_2.openapi.json)를 함께 적용한다. 모형 시험 범위의 예정 계약이며 제품 API가 이미 생겼다는 뜻이 아니다. v6.1 기계 계약은 역사본으로 보존한다.
- **최종 사업 방향 갱신(2026-11-07):** [광고주 중심 글로벌 에이전트 광고 플랫폼 정책 v6.1](AD_COIN_PLATFORM_POLICY.md)와 [실행 기획·성장 지표·추가 검수](AD_COIN_PLATFORM_ROADMAP.md)를 적용한다. 전략·매체 거래·광고 유통·성과·시장 분석·재집행까지 확장할 정책이며, 아래 현재 시험 기능의 구현 상태를 바꾸는 선언은 아니다. v5는 자산·준비금·보상·상환의 기반으로 유지한다.
- **앞으로의 정책·설계:** [발행·유통·광고 정책 v5](AD_COIN_POLICY.md), [블록체인·외부 결제 기술 설계](AD_COIN_ARCHITECTURE.md), [구현 순서와 검수](AD_COIN_V5_IMPLEMENTATION_PLAN.md)를 수립했다. 초기 공급 0·광고주 실제 입금 기반 USDC 담보 토큰은 추가 개발 대상이다. 아래 내용은 현재 원화 기준 시험 구현이며 v5가 구현·배포됐다는 뜻이 아니다.
- 소스 확인·문서 갱신: **2026-11-06(한국 시간)**. 최신 요약은 [개발 현황 v4](../reports/AI-AD-Coin-implementation-v4-2026-11-06.md), 사업 배경과 사용자 결정 이력은 [기획 v3](../reports/AI-AD-Coin-business-plan-v3-2026-11-04.md)의 0.3절이다.
- 최상위 목표: **완벽 보안 → 품질 100% → 글로벌 최고 처리 속도**. 보안·권한·정합성을 속도나 수익과 맞바꾸지 않는다. 이는 목표이며 현재 달성 선언이 아니다. 승인 기준과 증거의 한계는 [AD_COIN_TARGETS.md](AD_COIN_TARGETS.md)를 따른다.
- 소스 상태: 기능 플래그 뒤의 닫힌 시험이다. 기본값은 꺼짐이다. 이번 최신화에서 운영 플래그·활성 릴리스·운영 DB를 조회하거나 변경하지 않았다. 아래의 배포·운영 측정은 해당 날짜의 기록이다.
  - 예산·코인은 가상 값이다.
  - 결제·실제 광고주 집행·외부 체인 출고는 그랜드 오픈 전까지 닫혀 있다.
  - 법률·기관 검토는 그랜드 오픈 전에 한다.

아래 환경 변수·화면·SQLite 설명은 기존 v1 시험 구현의 기록이다. **신규 v6.2는 PostgreSQL 전용**이며 기존 v1 설정으로 v2를 켜거나 v1 잔액을 가져오지 않는다. v2 캠페인/P1 화면은 격리 모델 시험 앱에서 연결·검증하며 운영 앱에는 아직 연결하지 않았다.

## 현재 상품과 사업 기획의 차이

- 구현된 상품은 `PRODUCTS = ('S1', 'P2', 'B1')`이다. S1은 노출 뒤 후원 실행권, P2는 노출과 확인 답변 뒤 지갑 코인, B1은 서명 오퍼 수신에 대한 운영자 보상이다.
- 사용자 요구인 **승인된 노출 자체의 독립 코인 보상**은 사업 목표로 유지한다. 현재 P2는 빈 답변을 거부하므로, 추가 답변 없이 순수 노출만으로 지갑 코인을 지급하는 상품까지 완료됐다고 표현하지 않는다. 답의 정답 여부는 지급 조건이 아니다.
- 클릭·재생 시간별 추가 보상·가입·구독·구매 전환 상품, 방문 에이전트의 자율적인 외부 사용자 설명·전달 연동은 전체 구현·검증 완료 근거가 없다. 현재 견적 패킷의 설명과 별도로 구분한다.
- 지갑 이전은 내부 원장의 사용자·에이전트 계정 사이 이전이다. 외부 블록체인 지갑 출고·현금 출금은 구현된 내부 이전과 다르며 열려 있지 않다.

## 지키는 규칙(시험으로 확인)

- **선택–재원 분리**
  - `agent_market` 안에서 `ad_coin`을 import할 수 있는 곳은 front.py의 라우터 연결뿐이다.
  - `ad_coin`은 추천(selection·engine·ranking) 모듈을 import하지 않는다.
- **동일 품질:** 제공자에게 가는 요청(`provider_request`)에는 실행 ID·제공자·작업만 들어간다. 후원 여부는 들어가지 않는다.
- **동의와 노출**
  - 동의 없이 노출 보상은 없다.
  - 포그라운드 15초 미만이면 보상하지 않는다.
  - P2는 확인 문항 답이 필요하지만, 정답 여부와 관계없이 보상한다. 일치 여부는 영수증에만 남긴다.
- **빈도 상한:** 같은 사람·같은 캠페인은 하루 3회까지다.
- **지갑**
  - 지갑 간 이전으로 새 가치가 생기지 않는다.
  - 다른 사람에게 5,000원 상당 이상을 보내면 본인 재확인이 필요하다.
  - 메모에 지시문이나 안전 주장이 있으면 보류한다.
- **회수:** 14일 동안 쓰지 않은 에이전트 지갑이나 위임을 철회한 에이전트 지갑의 잔액은 사용자 지갑으로 돌아간다.
- **의도 위임장**
  - 최대 30일까지 만들 수 있다.
  - 정해진 제공자·건당 한도·총액 안에서만 에이전트가 쓸 수 있다. 벗어나면 사람에게 확인을 요청한다.
- **회로 차단:** 재원 불변식이 깨지면 회로가 열린다. 열리는 동안 새 후원 제안은 나가지 않고, 불변식이 다시 맞아야만 닫을 수 있다.
- **배분 기본값:** 사용자 50·운영자 10·직접비 15·플랫폼 25. 관리자 설정으로 바꿀 수 있다.
  - 사용자 몫은 40% 아래로 내릴 수 없다.
  - 운영자+직접비는 40%를 넘을 수 없다(작업 후원 몫 보장).
- **서명 오퍼 피드(B1)**
  - Web Bot Auth로 서명한 에이전트만 받는다.
  - `context_use`는 `presentation_only`, 공개 사본 URL을 함께 준다.
  - 수신 영수증은 토큰당 한 번만 운영자 보상이 된다. 사용자 코인은 생기지 않는다.

## 업그레이드 확인 규칙

- 1위가 무료면, 답변 안의 다음 후보 중 코인을 받을 수 있는 유료 에이전트를 고른다. 1위가 유료이고 자격이 있으면 1위를 고른다.
- 코인 수납 자격: 가격이 있음, 등급 A·B, 상태 healthy·reachable, 활성.
- 가격 환산: x402 `price_usdc`(USDC 기본 단위) × 1,380원, 10원 단위 올림.
- 후원 가능 범위: 500원(50코인)~50,000원. 이보다 싸면 코인 결제나 무료 결과만 안내한다. 100만 원을 넘으면 견적을 만들지 않는다.
- Chat·Explore 응답 경로는 바꾸지 않았다. 답변을 보여준 뒤 `POST /api/ad-coin/v1/upgrade-check`를 따로 부르므로 응답 시간 정책(Explore 3초, Chat 5초)에 영향이 없다.

## 작업 묶음 견적

- 일반 계획이 이미 정한 단계(카탈로그 에이전트 + 호출 수) 묶음을 한 번의 후원 단위로 계산한다.
  - 요청: `POST /api/ad-coin/v1/upgrade-check {"bundle": [{"resource_id": 109457, "calls": 1}, ...]}`
  - 최대 20단계, 단계당 1~1,000회.
- 가격 계산
  - 줄마다 정확한 원 가격(USDC × 1,380 × 호출 수)을 더한 뒤 **한 번만** 10원 단위로 올린다.
  - 그 합계를 가장 큰 나머지 순서로 줄에 나눠, 줄 금액의 합이 총액과 정확히 같게 한다.
  - 호출마다 올림하면 13.8원 호출이 20원이 되어 45% 비싸지기 때문이다.
- 자격
  - 유료 단계는 모두 코인 수납 자격(등급 A·B, 작동 중)이 있어야 한다. 하나라도 없으면 `bundle_has_ineligible_step`과 해당 ID를 돌려준다.
  - 무료 단계는 0원 줄로 남는다.
  - 범주는 가장 비싼 단계의 범주를 쓴다.
- 실행
  - 제공자 요청에는 줄별 제공자·호출 수만 들어가고, 후원 여부는 들어가지 않는다.
- 완료·정산
  - `line_results`로 줄마다 성공 여부를 받는다.
  - 성공한 줄은 각 제공자에게 지급 예정으로 넣는다.
  - 실패한 줄의 돈은 낸 쪽으로 돌려준다. 코인이면 지갑으로, 후원이면 광고주 에스크로로 간다. 전부 실패하면 후원 실행권을 되살린다.
  - 결과는 `succeeded`·`partial`·`refunded` 중 하나다.
- 위임장으로 묶음을 결제하려면 묶음 안의 모든 유료 제공자가 위임장에 있어야 한다.
- 후원이 붙지 않은 이유를 견적에 적는다.
  - `no_matching_sponsor`: 관련 후원자가 없거나 입찰가가 최저가보다 낮음
  - `task_below_minimum`
  - `circuit_open`

## 공개 워크플로 → 묶음 견적

- 요청: `POST /api/ad-coin/v1/upgrade-check {"workflow": {"template_id": 57, "runs": 5}}`
  - 공개 정의(`published_detail`)만 읽는다. 실행 횟수는 1~100회다.
- 단계 계산
  - 에이전트 노드를 카탈로그 에이전트별로 합치고, 실행 1회당 1호출로 센다.
  - 실행 횟수를 곱해 묶음을 만든다.
  - 꺼진 노드는 빼고, 트리거·라우터·변환 노드는 0원이다.
- 라우터가 있으면 모든 가지를 센 **상한 견적**이다(`upper_bound: true`). 실행되지 않은 가지는 실행 뒤 줄별 결과로 환불한다.
- 카탈로그 ID가 없는 에이전트 단계(`resource_ref`만 있는 단계)는 값을 매길 수 없다. 이름을 `unpriced_steps`에 보여 준다.
- 견적의 선택 확인 코드에는 워크플로 ID·정의 해시·실행 횟수가 들어간다. 작업 이름은 `workflow-<id>-<해시 앞 12자>-x<횟수>`다.
- 화면(`/ad-coin`)에서는 `w57x5`처럼 입력한다.

## 숨김 시험 상품

공개 워크플로가 모두 무료라서, 실제 카탈로그 에이전트로 만든 숨김 워크플로 상품을 AI AD Coin 안에 둔다(`ad_coin/test_products.py`).

- **만들기:** 관리자만 만든다(`POST /api/ad-coin/v1/admin/test-products`, 화면 `/ad-coin/admin`의 "시험 상품").
  - 단계: 카탈로그 ID × 실행당 호출 수(1~100), 최대 12단계. 같은 에이전트는 한 번만 넣는다.
  - 이름·설명은 광고 소재와 같은 결정론 심사를 거친다.
- **거부 조건**
  - 카탈로그에 없거나 비활성인 에이전트
  - 종류가 x402·MCP·A2A가 아닌 에이전트
  - 코인을 받을 수 없는 유료 에이전트(등급 B 미만·작동 안 함)
  - 유료 단계가 하나도 없는 상품
  - 이름·주소에 send·transfer·withdraw·swap·deposit·order·buy·sell·delete·update·create·post·sign·approve 같은 말이 들어간 에이전트. 돈을 옮기거나 상태를 바꾸는 것으로 보고 거부한다(읽기 전용 원칙).
- **노출과 실행**
  - 공개 워크플로 목록에는 나가지 않는다.
  - 초대된 사람은 `GET /api/ad-coin/v1/test-products`로 목록을 본다.
  - 견적은 `upgrade-check {"test_product": {"id": "tp_…", "runs": 5}}`로 받는다.
  - 실행은 시뮬레이션이다. 결제가 닫혀 있어 제공자를 실제로 부르지 않는다.
- **보관:** 보관한 상품은 견적에서 `unknown_test_product`가 된다.

## 고객의 비공개 워크플로 견적

- 요청: `upgrade-check {"private_workflow": {"workspace_id": "ws_…", "flow_id": "wtf_…", "runs": 5}}`
  - 화면에서는 `ws_…/wtf_… x5`처럼 입력한다.
- 권한: 고객 워크스페이스의 기존 경계를 그대로 쓴다(`ad_coin/private_workflows.py`).
  - 같은 출처의 고객 세션 쿠키(`customer_actor`)
  - 워크스페이스 구성원 확인(`core.actor`)
  - typed flow 상세 읽기(`core.typed.detail`)
  - ID를 알고 있다는 것만으로는 읽을 수 없다.
  - 로그인하지 않으면 401, 남의 워크스페이스·없는 흐름·비활성 흐름은 403이다.
  - 고객 워크스페이스가 닫힌 서버에서는 503이다.
- 가격 계산에 필요한 것만 꺼낸다: 노드의 카탈로그 ID와 꺼짐 여부.
  - 흐름 이름·입력·바인딩·출력은 응답에 들어가지 않는다.
  - 이름은 "Your saved workflow"로 바꾼다.
- 조건부(`when`) 단계가 있으면 상한 견적이다. 실행되지 않은 단계는 실행 뒤 줄별로 환불한다.
- 견적 작업 이름은 `private-<flow id>-<해시>-x<횟수>`다.
- 고객 로그인 초대와 에이전트 키의 동일 사용자 결속은 `people.py`와 `api.py:person()`에 구현되어 있다. visitor token은 시험 호환 경로다. 실제 로그인·키 발급·비공개 견적의 운영 브라우저 검증은 별도로 남아 있다.

## 실제 실행 기록으로 정산

워크플로를 위한 실행권·코인 결제는 실제 실행 기록으로 정산한다(`ad_coin/run_results.py`).

- 요청
  - 본인: `POST /api/ad-coin/v1/executions/settle-from-runs {"execution_id", "run_ids", "workspace_id"?}`
  - 운영자: `/admin/executions/settle-from-runs`. 공개 워크플로만 정산할 수 있다.
  - 운영 화면 "실행·정산"에서도 할 수 있다.
- 대상은 실행의 작업 이름으로 정한다.
  - `workflow-<id>-…-x<횟수>`: 공개 워크플로
  - `private-<flow id>-…-x<횟수>`: 고객 비공개 흐름. 본인 로그인 세션에서만 정산한다.
  - `product-…`: 시험 상품. 실행이 시뮬레이션이라 기록 정산 대상이 아니다.
- 기록 확인
  - 실행 기록 수는 견적의 실행 횟수와 같아야 하고, 서로 달라야 한다.
  - 각 기록은 그 워크플로의 것이어야 하고, 결제(실행권 사용·코인 결제) 뒤에 시작돼야 한다.
  - 실행 중인 기록이 있으면 `waiting`으로 답하고 정산하지 않는다.
  - 기록 하나는 한 번만 정산에 쓰인다(`run_claims`).
- 지급
  - 줄마다 성공한 호출 수를 센다. 노드의 카탈로그 ID 기준, 모든 실행 합계, 줄의 호출 수가 상한이다.
  - 그 비율만큼(`won × 성공 ÷ 호출`) 제공자에게 지급한다.
  - 나머지는 낸 쪽으로 돌려준다. 코인이면 지갑, 후원이면 광고주 에스크로다.
  - 분기로 실행되지 않은 단계(`skipped`)와 실패한 단계는 성공으로 세지 않는다.
- 읽는 것은 실행 상태와 단계 상태뿐이다. 입력·출력은 읽지 않는다.
  - 공개 실행은 운영 PG에 이미 등록된 SQL을 그대로 쓴다. `SELECT * FROM workflow_runs WHERE id=?`, `SELECT node_id,status,started,finished FROM workflow_node_runs WHERE run_id=? ORDER BY node_id LIMIT 50`. 등록 여부를 시험으로 확인한다.
  - 비공개 실행은 고객 경계의 `core.typed.get`을 쓴다.
- 결과 해시는 실행 ID와 단계 상태로 만든다. 실행 영수증에 단계별 성공 호출 수를 남긴다.

## 운영 PostgreSQL로 옮기기

`AD_COIN_STORE=application`이면 AD Coin 표(`ad_coin_*`, 33개, 스키마 3)를 애플리케이션 PostgreSQL 데이터베이스에 둔다. 방식은 `workspace_admin_events`의 덧붙이기 이전과 같다.

- **연결(11-05 운영 리허설로 바꿈):** AD Coin 전용 세션 풀(`PooledPostgresDatabase`)을 쓴다.
  - 크기는 프로세스당 최대 `AD_COIN_POOL_MAXIMUM`(기본 6, 0이면 저장소 연결 공유)이다. 한번 연 세션은 열어 둔다.
  - 이유: 저장소는 프로세스당 연결 1개와 파이썬 잠금 1개를 쓴다. 공유하면 AD Coin 요청이 Explore·Chat 뒤에 줄을 선다(리허설 실측).
  - 연결 예산: 운영은 앱 연결 약 20개, 상한 48이다. 켜면 frontend 프로세스마다 최대 6개가 늘어난다.
  - 세션을 2초 안에 못 얻으면 503 `busy`로 거부한다. 무한 대기는 없다.
- **동시성 규칙(전역 직렬화 대신 행 단위):**
  - 잔액: `INSERT … ON CONFLICT … RETURNING`으로 원자적으로 증감한다. 계정 순서로 정렬해 교착을 막는다. 음수가 되면 그 분개만 savepoint로 되돌린다.
  - 사람: 쓰기 요청마다 `lock_key('who:…')`를 잡는다. 빈도 상한, 위임장, 동의, 지갑이 여기서 보호된다.
  - 캠페인: 예약·해제·충전·환불 전에 캠페인 행을 `FOR UPDATE`로 잠근다. 잠금 순서는 항상 사람 → 캠페인(id 순) → 계정(이름 순)이다. 일 예산이 여기서 보호된다.
  - 합계: 실행 합계(`ad_coin_totals`)는 버킷마다 16줄로 나눠, 한 행에 쓰기가 몰리지 않게 한다.
  - 멱등 키: 같은 멱등 키를 동시에 쓰면 고유 제약이 막는다. 늦은 쪽은 `Duplicate`로 돌려받는다.
  - 교착·잠금 시간 초과: 요청 전체를 되돌리고 최대 3번 다시 실행한다.
  - 관리 작업 차단: 모든 쓰기는 공유 advisory lock을 잡는다. 전체 합계 재작성은 배타 모드로 다른 쓰기를 멈춘다.
- **견적 2단계:** 후보 경매는 잠금 밖에서 읽는다. 전용 풀이면 S1·P2를 두 세션으로 나란히 읽는다. 그 뒤 잠금을 잡고 예약할 캠페인만 같은 규칙으로 다시 검증해 예약한다. 그 사이에 자격을 잃은 캠페인은 예약하지 않는다(시험).
- **게재 후보 조회:**
  - 관련도 등급(정확 1.0, 상위 분류 0.6)별로 입찰가 순으로 읽고, 자격 있는 캠페인을 필요한 수만큼 찾으면 멈춘다. 경매 결과는 전체를 읽은 것과 같다(무작위 시험).
  - 예산 소진, 검토 미통과, 잔액 부족은 SQL에서 먼저 거른다.
  - 일 예산 사용액은 같은 트랜잭션에서 갱신되는 `ad_coin_campaign_daily`로 판정한다. 전체 점검(`full_check`)이 예약 기록과 어긋나는지(`daily_spend_drift`) 확인한다.
- **배경 작업:** 만료 정리(5초 주기)와 전체 재계산(500회 이동마다)은 별도 스레드에서 짧은 트랜잭션으로 돈다. 요청 경로는 예약·실행권의 만료를 각자 직접 검사한다.
- **서버 구간 시간:** 응답마다 `Server-Timing`을 붙인다(`adc-queue`, `adc-work`, `adc-cpu`, `adc-db`, `adc-sql`, `adc-pool`, `adc-lock`, `adc-hold`).
- **카탈로그 무변경:** `application_store_sql.json`(등록 SQL 목록)과 카탈로그 스키마 프로필을 바꾸지 않는다. 목록을 다시 만들 필요가 없다(r14 사고 방지).
- **표·인덱스 이름:** 다른 기능과 섞이지 않게 모두 `ad_coin_` 접두사를 붙였다.
- **SQL 변환:** AD Coin이 쓰는 SQLite 표기 몇 가지만 바꾼다(`?`→`%s`, `INSERT OR IGNORE`→`ON CONFLICT DO NOTHING`). 값은 항상 매개변수로 넘긴다.
- **트랜잭션 규칙:** 전용 풀에서는 중첩 쓰기가 savepoint라서, 실패한 부분만 되돌리고 계속할 수 있다. 저장소 연결을 공유하는 방식(`AD_COIN_POOL_MAXIMUM=0`)에서는 원장이 쓰기 전에 사전 확인으로 거부한다.
- **이전 전 안전장치:** 이전하지 않은 저장소로 켜면 AD Coin만 꺼진다. `/status`가 503과 이유를 알리고, 프론트 전체는 정상으로 뜬다.
- **운영자 명령**(`scripts/ad_coin_migrate_postgres.py`): 서버를 시작·재시작하지 않고, 연결은 하나만 쓴다.
  - `status`: 표가 있는지와 표별 행 수
  - `migrate`: 표·인덱스 생성과 ad_coin 표 통계(ANALYZE). 덧붙이기 전용이고 여러 번 실행해도 안전하다. 통계가 없으면 후보 조회 계획이 10배 느렸다(리허설).
  - `copy --sqlite <파일>`: 기존 SQLite 장부를 빈 PG 표로 복사한다. 대상에 행이 있으면 거부한다.
  ```
  .venv/bin/python -m scripts.ad_coin_migrate_postgres status  --dsn-file <DSN 파일> --key-file <워크플로 키 파일>
  .venv/bin/python -m scripts.ad_coin_migrate_postgres migrate --dsn-file <DSN 파일> --key-file <워크플로 키 파일>
  ```

## 월간 후원 감사

후원을 켜도 일반 추천이 바뀌지 않는다는 약속을 운영에서 확인한다(기획 v3 10절 즉시 중지 조건 4). 판정은 `ad_coin/audit.py`, 실행은 `scripts/ad_coin_sponsorship_audit.py`가 한다.

- 실행
  ```
  AD_COIN_ADMIN_TOKEN=… nice -n 10 .venv/bin/python -m scripts.ad_coin_sponsorship_audit --base http://127.0.0.1:8400
  ```
  - 기본은 Explore로, 질문 20개 각각의 상위 3개를 본다.
  - `--surface chat`으로 Chat을 볼 수 있다. LLM 비용이 든다.
  - `--queries 파일`로 질문을 바꿀 수 있다.
- 질문마다 순서
  1. 후원 끔(회로 열림) 상태에서 읽는다.
  2. 후원 켬(회로 닫힘) 상태에서, 그 질문 결과로 실제 후원 견적을 만들어 예산을 잠근 뒤 다시 읽는다.
  3. 다시 끄고 읽는다.
- 판정
  - **같음:** 세 번 모두 같다.
  - **바뀜:** 두 번의 "끔"이 서로 같은데 "켬"만 다르다.
  - **흔들림:** 두 번의 "끔"끼리 다르다. 판정에서 뺀다.
  - **오류:** 읽기에 실패했다.
  - 바뀜이 하나라도 있으면 실패다. 같음이 0이면 판정 불가다.
- 끝나면
  - 감사 중 만든 후원 예약은 모두 풀어 준다.
  - 보고서는 `gateway-data/ad_coin_audits/`에 저장한다(git 제외). 서버에도 기록한다(`POST /admin/audits`, 운영 화면 "후원 감사").
  - 실패하면 서버가 회로를 `audit_mismatch:<개수>`로 연다. 통과하거나 판정 불가면 회로를 감사 전 상태로 되돌린다.
- 부하: 질문당 읽기 3번과 후원 호출 2번이다. 읽기는 1초 간격이고 연결은 재사용한다.

## 누가 쓰는가: 초대받은 로그인 고객과 그 사람의 에이전트 키

- 신원 판별 순서(`ad_coin/people.py`, `api.py`의 `person`)
  1. **에이전트 키**(`X-Ad-Coin-Agent-Key: ack_…`)
     - 고객이 만든 키다. 한 에이전트 이름에 묶이며, `X-Agent-Name`으로 다른 이름을 사칭할 수 없다.
     - 키는 해시로만 저장하고, 원문은 만들 때 한 번만 보여 준다.
  2. **로그인한 고객**: 같은 출처의 고객 세션 쿠키. 쓰기 요청에는 세션의 CSRF 값(`X-Customer-CSRF`)이 있어야 한다.
  3. 관리자 토큰
  4. 예전 visitor token 초대(시험 호환용)
- **초대**
  - 관리자가 고객 계정 ID로 초대한다(`/admin/invites`, 운영 화면 "초대").
  - 사용자는 화면의 "Check my account"(`GET /account`)에서 자기 계정 ID와 초대 여부를 본다.
  - 초대를 거두면 그 사람의 에이전트 키도 모두 멈춘다.
- **사람 식별값:** `c_` + sha256(`customer:` + 계정 ID) 앞 24자다. 사람의 지갑과 그 사람 에이전트 키의 지갑이 같은 식별값으로 묶인다.
- **에이전트 키 관리**
  - 키 발급·목록(`/agent-keys`)은 본인 로그인 세션에서만 할 수 있다. 에이전트 키로는 할 수 없다.
  - 한 사람당 최대 10개다. 같은 에이전트 이름으로 다시 만들면 이전 키가 멈춘다.
  - 에이전트 철회(`/agents/revoke`)는 키를 멈추고, 위임장을 철회하고, 그 에이전트 지갑의 코인을 사용자 지갑으로 옮긴다.
- 고객 워크스페이스가 닫힌 서버에서는 로그인 경로가 없다. 이때는 관리자와 예전 초대 토큰만 쓸 수 있다.

## 등록된 SQL만 실행 (11-05, 에이전트콘시어지 규칙 적용)

- 앱 저장소처럼 AI AD Coin도 등록된 SQL만 실행한다. 등록 목록은 `agent_market/ad_coin/sql_registry.json`(2026-11-06 확인: 174개 문장 모양)이다.
- 검사는 모든 어댑터(전용 풀, 앱 저장소 공유, SQLite)에서 DB로 보내기 전에 한다. 목록에 없으면 `UnregisteredSql`로 거부한다.
- 정규화 방식: 공백을 접고, `IN (?, ?, …)`와 여러 행 `VALUES`는 길이와 상관없이 한 모양으로 접는다. 열 이름을 끼워 넣던 수정 SQL은 고정 문장(`META_UPDATES`)으로 바꿨다.
- 다시 만드는 법: `.venv-tests/bin/python -m scripts.ad_coin_sql_registry --write`
  - 제품 코드가 시험과 리허설 연기 단계에서 실행한 문장을 기록한다.
  - 소스의 상수 SQL도 정적으로 추가한다. 시험이 직접 넣는 SQL은 등록하지 않는다.
- 시험이 지키는 것:
  - 소스의 상수 SQL이 모두 등록돼 있다.
  - 등록 안 된 문장은 PostgreSQL에 닿지 않는다.
  - 제품 코드는 검사를 건너뛰는 `unchecked()`를 쓰지 않는다. 이 범위는 시험의 확인 조회와 운영자 이전 명령(`status`, `copy`)만 쓴다.

## 2026-11-06 재검증과 보안상 출시 차단 항목

- 현재 소스의 관련 시험은 최초 80건 통과·9건 건너뜀(격리 PostgreSQL 시작 제한)이었다. 별도 허용된 임시 PostgreSQL에서 해당 파일 10건을 통과했고, 중복 시험 1건을 제외한 최신 결과는 **89건 통과·실패 0·미확인 건너뜀 0**이다. 전체 프로젝트 시험 결과는 아니다.
- 기존 실제 HTTP 동적 보안 스크립트를 격리 PostgreSQL·시험 로그인 대역으로 재실행해 **219/219 통과**했다. [원자료](../reports/ad-coin-doc-refresh-2026-11-06/security/dynamic-security.json). 새로운 공격 범위까지 완전 검증했다는 뜻은 아니다.
- **사람 승인과 에이전트 인증의 경계:** `/consents`, `/exposures`, `/transfers`, `/mandates` 등의 `person` 권한은 에이전트 키도 허용한다. `/spends`는 본문의 `mandate_id` 유무로 `actor`를 정한다. 에이전트 키만으로 사람 전용 행위나 위임 없는 결제가 가능하지 않은지 별도 부정 시험과 권한 보강이 필요하다. 현재 문서에서 모든 행위에 사람 승인·위임이 강제된다고 보증하지 않는다.
- **사람 노출 증거:** `displayed_ms`, `foreground`는 요청 본문의 값이다. 현 검사는 값·동의·중복·예약 상태를 검증하지만 실제 사람이 15초간 보았음을 독립적으로 증명하지 않는다. 서명 영수증도 원장에 기록된 사실의 무결성 증명이다.
- **재인증:** 다른 사람에게 5,000원 상당 이상 이전하면 `step_up_required`로 보류한다. 공개 이전 API는 `step_up=False`로 고정되어 있어 실제 재인증 뒤 해제하는 흐름이 완성된 것은 아니다.
- **상용 보안:** 실제 로그인·Web Bot Auth·운영 경계 속도 제한, 백업 복구·키 수명주기·비상 회수, 실제 예치금 대사와 외부 지급은 현재 219개 시험으로 인증되지 않았다. 보안 목표를 달성했다고 선언하거나 실제 가치 유통을 여는 근거로 쓰지 않는다.
- 정적 Bandit 결과와 부하·화면 속도는 11-05 원자료를 참조한다. 이번에는 이를 다시 실행하지 않았다. 소스 변경 시 증거를 갱신해야 한다.
